# @lpmc/tui — интерактивный диалог с Линой

Терминальный интерфейс полного цикла: отправка обращения, ожидание уточняющих
вопросов и ответы на них, получение результата, приёмка. Всё в одном окне.

Это **ещё один канальный фронтенд контура LINA**, а не отдельная система: он
пользуется тем же `ChannelAdapter` и тем же каналом `cli`, что и командная
строка, поэтому ответы возвращаются уже работающим путём
(`outbound.cli.v1` → `lina deliveryd` → таблица `deliveries`). TUI лишь
показывает этот путь целиком.

Границу контура TUI не переступает: он подключается к схеме LINA (пользователь
`lpmc-lina`) и **не видит реестра задач PACT** — как и положено недоверенному
контуру. Всё, что показано как «ответ системы», уже прошло egress-проверку PACT
и легло в `deliveries`. Поэтому «ожидание» — честное отражение границы, а не
заглушка.

## Запуск

После развёртывания роль ставит обёртку:

```bash
lpmc-tui                       # запускает TUI под пользователем lpmc-lina
```

Напрямую (тот же эффект):

```bash
sudo -u lpmc-lina /usr/bin/node \
  /usr/local/lib/lpmc/packages/tui/dist/src/main.js
```

TUI работает под `lpmc-lina`, потому что подключается к схеме LINA по
peer-аутентификации (unix-сокет PostgreSQL, без пароля).

### Переменные окружения

| Переменная | По умолчанию | Значение |
|---|---|---|
| `LPMC_TUI_CONVERSATION` | свежий `tui-<hex>` | идентификатор диалога; один и тот же id продолжает прежний разговор |
| `LPMC_TUI_ACTOR` | `operator` | отправитель; по нему PACT определяет владельца (таблица привязок) |

```bash
# свежий именованный диалог от отправителя operator
sudo -u lpmc-lina env LPMC_TUI_CONVERSATION=demo LPMC_TUI_ACTOR=operator \
  /usr/bin/node /usr/local/lib/lpmc/packages/tui/dist/src/main.js
```

## Команды

| Ввод | Действие |
|---|---|
| любой текст | отправить обращение / ответить на уточняющий вопрос |
| `/status` | состояние черновика (цель, владелец, критерии) и чего ждём |
| `/accept` | принять результат работы |
| `/reject <причина>` | не принять результат и назвать причину |
| `/quit` | выход |

## Как выглядит полный цикл

Обращение вида «сходи на публичную страницу и собери данные» (первый сценарий,
владелец `internal`, исполнитель MITA):

```
› Открой https://example.com, сделай снимок экрана и собери короткий отчёт
  принято; не хватает поля «owner» — жду уточняющий вопрос системы…
  🤖 К какому владельцу относится обращение: клиент, проект или внутренний контур?
› внутренний
  принято; не хватает поля «dod» — жду уточняющий вопрос системы…
  🤖 По какому признаку считать работу выполненной? Перечислите критерии приёмки.
› снимок сделан; отчёт собран
  принято; обращение полное, задача передана (…). Жду результат…
  🤖 Нужна проверка человеком: … прочитано страниц: 1; заголовки: Example Domain
› /accept
  решение передано: принято
  🤖 Результат принят, задача закрыта.
```

Уточняющие вопросы задаёт Лина (правила решают, ЧТО спрашивать; модель — лишь
формулировку). Результат приходит после того, как MITA реально сходил браузером
через egress-proxy и PACT проверил вывод перед раскрытием.

## Сборка

Пакет собирается общей сборкой репозитория (`npm run build` в корне) вместе с
контурами. Отдельно:

```bash
npm run build -w @lpmc/tui
```
