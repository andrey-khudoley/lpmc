# deploy/ — развёртывание узла LPMC

Здесь живёт то, что превращает **собранный** код в **работающий** узел: роль
`lpmc_system` и playbook, который её применяет. До сборки единого репозитория это
находилось в отдельном репозитории инфраструктуры (см. README монорепо и ROADMAP,
пункт `P1-CHK-04`, где роль `lpmc_system` названа местом проверки узловых
критериев `Н-7`, `Н-8`, `Н-9`, `Н-16`).

## Статус

**Каркас, а не готовая роль.** На момент сборки единого репозитория работающей роли
`lpmc_system` в исходных каталогах не существовало — только ссылки на неё в ROADMAP.
Поэтому `roles/lpmc_system/` и `playbooks/deploy.yml` — заготовки с пустыми задачами.
Их наполняет отдельная работа (волна W1, пункты `P1-CHK-02`, `P1-CHK-03`).

Общие серверные роли (nginx, nftables, apache, base_system, security_hardening,
admin_panel) **сюда намеренно не переносились**: они общие с проектом админ-панели и
не принадлежат LPMC. Если узел LPMC разворачивается на том же хосте, эти роли
подключаются из инфра-репозитория (`requirements.yml` / сабмодуль), а не копируются.

## Что делает роль (когда будет наполнена)

- отдельные системные пользователи на компонент: канальный адаптер (LINA),
  control-plane (PACT), исполнитель (MITA), egress proxy (`P1-CHK-02`);
- сетевые правила: исполнителю запрещён исходящий трафик мимо прокси (`Н-7`);
- JetStream и PostgreSQL с учётными записями и ролями **на компонент**;
- раскладка каталогов узла по `NODE-LAYOUT.md` (`P1-CHK-03`): `config/`, `runs/`,
  `artifacts/`, три корня владельцев, `services/`, `playbooks/`.

## Чего здесь НЕТ и не будет

Секретов, `storage_state`, паролей, allowlist с учётными данными. Они живут **вне
репозитория и вне его резервных копий** (ROADMAP; ADR-0011, ADR-0012 контура MITA).
«Клонировал → готовая система» означает *собираемую и разворачиваемую* систему;
секреты подаются на узел отдельным каналом при применении playbook.
