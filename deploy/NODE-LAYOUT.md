# Целевая раскладка контура MITA — каталоги и файлы

**Тип документа:** spec-as-source. Описывает **желаемое** состояние. Фактическая раскладка сегодняшней системы
описана в `docs/overview.md` §2, `docs/data-model.md`, `docs/secrets.md`, `docs/runtime/local-state.md`
и здесь не воспроизводится.

**Статус:** черновик, редакция 1. Дата: 2026-08-11. Выведен из `docs/spec/spec.md` (редакция 2); каждый узел
дерева сопровождается ссылкой на раздел спецификации, из которого он следует. Узел без такой ссылки —
техническое решение этого документа, а не требование спецификации.

**Границы применимости.** Раскладка — **внутреннее устройство MITA**, а не контракт с соседями
(`spec.md` §12.6.1, п. 2). Ни один контур не адресуется к путям этого дерева: PACT получает непрозрачные
идентификаторы (`task_id`, `run_id`, `artifact_ref`), а не пути. Изменение раскладки не является изменением
контракта и не требует согласования с PACT — до тех пор, пока интерфейсы §5, §12.6 и §17 остаются прежними.
Признак нарушения проверяем: если для работы соседнего контура нужно знать имя каталога — граница нарушена.

## 1. Принципы, из которых выведено дерево

| № | Принцип | Раздел | Следствие для раскладки |
|---|---|---|---|
| 1 | MITA хранит только то, чем владеет | §12.1, §12.2 | Реестра задач, состояний, лизингов и вердиктов в дереве нет |
| 2 | Рабочая тетрадь и хранилище артефактов — разные поверхности | §12.6.1 | Два независимых корня: `runs/` и `artifacts/` |
| 3 | Артефакт адресуется непрозрачной ссылкой | §12.6.2, M-16 | Путь артефакта не выводится из `artifact_ref` и наоборот |
| 4 | Доказательства переживают очистку рабочих каталогов | §12.4, п. 4 | `artifacts/` не находится внутри `var/` и не вытесняется вместе с ним |
| 5 | Значений секретов на диске исполнителя нет | §9.1, M-3 | Каталога `.secrets/` в целевом дереве не существует |
| 6 | Реестр владельцев — проекция только для чтения | §14.2 | Каталоги владельцев и их `INDEX.md` генерируются событием PACT и не правятся руками |
| 7 | Категория владельца видна структурно, а не значением поля | ADR-0010 | Три корня владельцев сохраняются: `clients/`, `projects/`, `internal/` |
| 8 | Источник правды о браузерных инстансах — состояние узла | §10.4, пп. 2–3 | Файла с привязкой «владелец → инстанс» в репозитории нет |
| 9 | Единица исполнения — запуск, а не задача | §2.3, §12.2 | Рабочие материалы адресуются `run_id`, а не карточкой задачи |
| 10 | Соответствие имён событий задаётся конфигурацией | §4.2 | `config/events.yml`, а не константы в коде |
| 11 | Знание расщепляется по модальности | §13.1 | В карточке сервиса у MITA только браузерный раздел |
| 12 | Один источник — N вендорных проекций | ADR-0013 | `.agents/` остаётся каноном, `.claude/`/`.codex/` — генерируемые |
| 13 | Семантика безопасности не зависит от метаданных клиента | §20.5 | Ни один узел дерева не является механизмом принуждения |

## 2. Верхний уровень

```
mita/
├── README.md                  # обзор для людей; собирается из канона, руками не правится
├── docs/                      # spec-as-source (spec.md, layout.md), adr/, docs-as-state
├── config/                    # конфигурация контура (§6 этого документа)
├── clients/                   # ПОСТОЯННЫЕ клиенты — корень владельцев (ADR-0010)
├── projects/                  # разовая и проектная работа — корень владельцев (ADR-0010)
├── internal/                  # собственные контуры исполнителя — корень владельцев (ADR-0010)
│                              #   все три — проекция реестра PACT: generated, read-only (§14.2)
├── services/                  # общие сервисы: только браузерная модальность (§13.1)
├── playbooks/                 # общие процедуры ручных сценариев (§13.3)
├── runs/                      # рабочие тетради запусков (§12.2); состав — §4 ниже
├── artifacts/                 # хранилище доказательств, вне git (§12.6); состав — §5 ниже
├── notes/                     # системные и кросс-владельческие наблюдения (§13.4)
├── llm/                       # сырые журналы сессий исполнителя, append-only (§12.1)
├── templates/                 # шаблоны сущностей MITA
├── infra/                     # документация исполнительного стека (не конфигурация узла)
├── var/                       # вне git: производное состояние инструментов
├── .agents/                   # канон ролей, скиллов, политики (ADR-0013)
├── scripts/agents.mjs         # сборщик канона в вендорные проекции
├── .githooks/pre-commit       # локальный механический контроль (ADR-0015)
└── .claude/, .codex/, .mcp.json   # generated-проекции канона
```

Три корня владельцев (`clients/`, `projects/`, `internal/`) **сохраняются** в целевом состоянии, как их
зафиксировал ADR-0010. Спецификация этому не препятствует: §14.1, п. 2 запрещает делать категорию частью
**идентификатора** — слаг остаётся глобально уникальным и не содержит корня (§14.1, п. 1), — но раскладку
каталогов не предписывает. Разбор совместимости — §11 этого документа.

## 3. Владелец

```
<root>/                            # один из: clients/ | projects/ | internal/ (ADR-0010)
├── INDEX.md                       # generated из проекции: список владельцев этого корня
└── <owner-slug>/
    ├── projection.yml             # generated (§14.2): слаг, категория, признак наличия инстанса
    ├── operations.md              # операционные особенности исполнения — часть MITA (§13.2)
    ├── services/
    │   └── <service-slug>/
    │       └── web.md             # «что и где делается» в браузере, грабли интерфейса (§13.1)
    ├── playbooks/
    │   └── <slug>.md              # локальные процедуры, приоритетнее общих (§13.3, п. 7)
    ├── notes/
    │   ├── INDEX.md
    │   └── YYYY-MM/<YYYY-MM-DD>-<topic>.md
    └── llm/
        └── YYYY-MM/<YYYY-MM-DD-HHMM>-<role>-<topic>.md
```

Требования к узлам:

1. `projection.yml` — **только для чтения**: заводится, переименовывается и удаляется событием PACT (обмен С-8,
   §2.2). Ручная правка — дефект, а не операция; отсутствующий владелец приводит к отказу исполнения
   (§4.4, п. 5), а не к созданию каталога на месте.
2. Корень (`clients/` / `projects/` / `internal/`) определяется полем `category` проекции, а не решением
   исполнителя. Смена категории у PACT приводит к перемещению каталога при следующем обновлении проекции;
   **слаг при этом не меняется** (§14.1, п. 3), поэтому ни один идентификатор задачи, запуска или артефакта
   от перемещения не страдает.
3. `INDEX.md` каждого корня — generated из проекции, а не ведётся руками. Это снимает риск рассинхрона индексов
   с фактическим составом каталогов, зафиксированный ADR-0010 как отрицательное последствие трёх корней.
4. `operations.md` содержит **только** часть MITA из расщепления §13.2. Запреты, лимиты и пороги в него
   не попадают: они у PACT и не являются enforcement, будучи записанными здесь (§13.2, п. 1).
5. `services/<service-slug>/web.md` не содержит имён секретов, правил выдачи и классификации необратимости —
   это разделы PACT (§13.1). Раздел «через опубликованный контракт» отсутствует: он у CITA.
6. Каталог владельца **не содержит** `tasks/`: задачи и их состояния — реестр PACT (§12.2).
7. `instructions.md` в прежнем виде отсутствует: документ расщеплён на три части по §13.2, и в MITA остаётся
   только `operations.md`.

## 4. Рабочая тетрадь запуска

```
runs/
└── <owner-slug>/
    └── <task_id>/
        └── <run_id>/
            ├── plan.md          # план выполнения, выведенный из objective и DoD (§12.1)
            ├── journal.md       # append-only журнал хода работы (§12.3)
            ├── result.json      # копия опубликованного внутреннего результата запуска (§5.2)
            ├── reply.md         # текст предложения ответа (§5.4, §16)
            ├── evidence.json    # карта: пункт DoD / изменение → artifact_ref (M-16)
            └── drafts/          # черновики и промежуточные заметки; артефактами не являются
```

1. Адресация — по `run_id`; `task_id` служит только группировкой (§12.2). Возобновляющий запуск получает
   собственный каталог рядом, а не переписывает прежний (§5.6.3, п. 5).
2. Владелец в пути `runs/` обозначается **слагом без корня**, в отличие от каталогов владельцев (§3): слаг
   глобально уникален (§14.1, п. 1), а смена категории владельца не должна двигать уже созданные рабочие
   материалы и обесценивать пути в журналах. Категория читается из проекции (§3), а не из пути запуска.
3. `journal.md` — append-only (§12.3, п. 1), с маскированием значений до записи (§17.4, п. 1) и без ссылки
   аварийного вывода сессии (M-11).
4. `result.json` — **копия опубликованного**, а не источник истины: расхождение с реестром PACT разрешается
   в пользу реестра (§12.2). Поля состояния задачи, лизинга и вердиктов в нём не воспроизводятся.
5. `evidence.json` содержит ссылки, а не байты: сами файлы живут в `artifacts/` (§12.6.1, п. 1).
6. `drafts/` вытесняем: его удаление не должно ронять ни одно доказательство (§12.4, п. 4).
7. Удаление или архивирование каталога запуска не влияет на состояние задачи (§12.2).

## 5. Хранилище артефактов

```
artifacts/                       # вне git; отдельный том, переживающий очистку var/
├── objects/<xx>/<artifact_ref>          # байты; неизменяемо (§12.6.2)
├── meta/<xx>/<artifact_ref>.json        # тип, размер, момент создания, task_id, run_id,
│                                        #   отметка о пройденном маскировании (§17.4)
└── index.db                             # соответствие artifact_ref → путь, срок хранения (§12.6.3)
```

1. `<xx>` — первые символы `artifact_ref`, служебное разветвление каталогов. Из `artifact_ref` **не выводится**
   владелец, сервис, задача и назначение артефакта (§12.6.2): смысл живёт в `meta/`, доступной только MITA
   и отдающейся вместе с байтами через интерфейс разыменования.
2. Запись в `objects/` — сознательная публикация (§12.6.1, п. 3). Всё, что не должно покидать MITA, остаётся
   в `runs/*/drafts/` или в `var/`.
3. Артефакт неизменяем: обновление порождает новый `artifact_ref` (§12.6.2).
4. Срок хранения — 90 суток по умолчанию и не меньше срока жизни записи реестра для доказательств DoD
   и необратимых изменений (§12.6.3, пп. 1–2). Вычистка — по `index.db`, а не по времени файла.
5. Интерфейс разыменования (§12.6.2) обслуживает **только** этот корень. Каталоги `runs/`, `llm/`, `notes/`,
   `var/` из-под него недостижимы — это техническая граница, а не соглашение.

## 6. Конфигурация контура

```
config/
├── executor.yml    # идентификатор исполнителя из закрытого перечня PACT (§19.1)
├── events.yml      # соответствие «смысл события → имя топика и event_type» (§4.2, O-1)
├── limits.yml      # пределы удержания (§5.6.5), срок хранения артефактов (§12.6.3)
└── reasons.yml     # generated: закрытый перечень типизированных причин (§5.7)
```

1. `events.yml` существует именно потому, что конвенция имён не принята: до решения O-1 MITA обязана
   поддерживать оба варианта конфигурацией и не считать ни один каноническим (§4.2).
2. `executor.yml` хранит **значение**, а не правило проверки: закрытый перечень ведёт PACT (§19.1, п. 1).
   Совпадение проверяется посимвольно, без нормализации (§19.1, п. 4).
3. `limits.yml` — узловая конфигурация, а не константы в коде (§5.6.5). Значения действуют до принятия
   системного решения по O-6 и O-7.
4. `reasons.yml` генерируется из §5.7 сборщиком и участвует в проверке схемы событий; ручная правка запрещена —
   перечень расширяется изменением спецификации, а не файла (§5.7).

## 7. Узлы, которых в дереве намеренно нет

Отрицательная часть раскладки так же обязательна, как положительная: перечисленное ниже отсутствует не потому,
что «пока не сделано», а потому, что принадлежит другому контуру или другому носителю.

| Чего нет | Где это в целевом состоянии | Раздел |
|---|---|---|
| `.secrets/` — значения, TOTP-семена, снимки сессий | custody PACT; выдача на `run_id` с TTL | §9.1, §9.2, M-3 |
| `tasks/` — карточки, статусы, `inbox/`, `archive/` | реестр задач PACT | §12.2, §1.3, п. 3 |
| Файл привязки «владелец → инстанс», инвентарь портов | состояние узла + конфигурация Ansible-роли | §10.4, пп. 2–3 |
| Allowlist доменов, допустимые методы | политика PACT, принуждение — egress proxy | §8.4 |
| Таблица классификации необратимости | PACT | §7.1 |
| Канонический реестр владельцев | PACT; в MITA только проекция | §14.1 |
| Каналы, адаптеры, шаблоны сообщений, история диалога | LINA | §1.3, п. 12 |
| Интеграции по опубликованным контрактам, схемы API | CITA | §1.3, п. 10; §18.5 |
| `deploy/` — временный каталог переноса legacy | не переносится в целевое состояние | — |

## 8. Что сегодня где и куда уходит

Левая колонка — фактические узлы существующей автоматизации по `docs/overview.md` §2 и
`docs/data-model.md`. **Назначение таблицы после решения D-013 — миграционное:** она показывает, куда
переносится содержимое существующих узлов, а не порядок, в котором целевая раскладка возникает. Целевая
раскладка создаётся сразу целиком (§1–§7); правила переноса данных — `ROADMAP.md` раздел 14.

Правая колонка называет **свойство** §22, из-за которого узел меняет форму или исчезает. Идентификаторы
`Ц-n` порядкового смысла не несут (§22.1).

| Сегодня | В целевом состоянии | Свойство §22 |
|---|---|---|
| `clients/`, `projects/`, `internal/` как три корня | сохраняются; но становятся проекцией реестра PACT: содержимое генерируется, а не ведётся руками | Ц-2 |
| `clients/INDEX.md`, `projects/INDEX.md`, `internal/INDEX.md` — ведутся руками | generated из проекции | Ц-2 |
| `<root>/<owner>/overview.md` | расщепляется: контекст владельца — PACT/LINA; операционные особенности — `<root>/<owner>/operations.md` | Ц-2, Ц-6 |
| `<root>/<owner>/instructions.md` | расщепляется на три части (§13.2); в MITA остаётся `operations.md` | Ц-2, Ц-6 |
| `<root>/<owner>/tasks/inbox/` | исчезает: постановки принимает LINA | Ц-6 |
| `<root>/<owner>/tasks/{active,archive}/` | исчезает: реестр — у PACT; рабочие материалы — в `runs/` | Ц-2 |

## 9. Соответствие узлов свойствам §22

Таблица отвечает на вопрос «наличием какого свойства обусловлен этот узел», а **не** «в каком порядке узлы
появляются»: в целевой сборке Ц-0…Ц-6 выполняются одновременно, поэтому и обусловленные ими узлы создаются
вместе. Колонка «что исчезает» относится к миграции из существующей автоматизации (§8), а не к этапу жизни
целевого контура. Отдельно стоит только Ц-7: пока свойство отложено, долгоживущие профили браузера как
носитель сессий между задачами сохраняются, и это единственная строка, читаемая во времени.

| Свойство §22 | Чем обусловлены узлы | Что при миграции исчезает |
|---|---|---|
| **Ц-0** | — | — (раскладка не меняется; меняется сеть узла) |
| **Ц-1** | — | `.secrets/**`; раздел «Доступ» в карточках сервисов |
| **Ц-2** | `config/`, `runs/`, `artifacts/`, `<root>/<owner>/projection.yml`, `services/<slug>/web.md` | `tasks/{active,archive}/`, `deploy/`, `templates/task.md`; ручное ведение каталогов владельцев и их `INDEX.md` |
| **Ц-3** | точки останова в текстах плейбуков (§13.3) | — |
| **Ц-4** | — | — |
| **Ц-5** | интерфейс разыменования `artifact_ref`; `runs/**/reply.md` как публикуемое предложение | раздел «Отчёт» как конечный текст в карточке |
| **Ц-6** | — | `tasks/inbox/`, `templates/inbox-item.md`, `infra/webapp/`, части `instructions.md`, ушедшие в LINA |
| **Ц-7** | — | долгоживущие профили браузера как носитель сессий между задачами |

Правило §21.3 действует и здесь: узел считается исчезнувшим, когда прежний путь **закрыт технически**,
а не когда каталог опустел. Пустой `tasks/`, в который по-прежнему можно писать, закрытием не считается —
и в целевой сборке такого узла не создаётся вовсе.

## 10. Что эта раскладка не определяет

1. **Границу «в git / вне git» для `runs/`.** Текстовые рабочие тетради версионируются естественно, но объём
   и частота записи при штатной работе неизвестны; решение принимается по факту, а не заранее.
2. **Формат `result.json` и `evidence.json`** как файлов: состав полей задан §5.2 и §15.4, сериализация —
   вопрос реализации.
3. **Схему `artifact_ref`.** Требование одно — непрозрачность (§12.6.2); конкретный генератор не предписывается.
4. **Раскладку внутри `var/`** — она производная и вытесняемая по определению.
5. **Физическое размещение `artifacts/`** (том, файловая система, репликация): требование — переживать очистку
   рабочих каталогов и сроки §12.6.3, а не конкретный носитель.
6. **Имена файлов конфигурации** как контракт: `config/*.yml` — внутреннее устройство, соседи о нём не знают
   (§12.6.1, п. 2).

## 11. Совместимость трёх корней с целевым состоянием

ADR-0010 («Владельцы физически разделены на clients / projects / internal», статус **Принято**) сохраняется
в целевом состоянии без изменений. Раздел разбирает, что при этом меняется, а что нет, — чтобы решение
не оказалось формально сохранённым, но фактически подорванным переносом реестра к PACT.

**Что сохраняется дословно:**

1. Три непересекающихся корня одинаковой внутренней структуры и их `INDEX.md`.
2. Глобальная уникальность слага среди всех трёх корней: идентификатор задачи и пути рабочих материалов
   не содержат корня и не меняются при переносе владельца между корнями (§14.1, пп. 1 и 3).
3. Главное свойство, ради которого решение принималось: категория видна **структурно**, а не значением поля,
   и ошибка классификации даёт расхождение места, а не тихо искажённый срез.

**Что меняется и почему это усиливает, а не ослабляет ADR-0010:**

1. Каталоги владельцев становятся **проекцией** канонического реестра PACT только для чтения (§14.2).
   Корень перестаёт быть решением исполнителя: он вычисляется из поля `category` проекции.
2. Тем самым закрывается отрицательное последствие, зафиксированное самим ADR-0010, — рассинхрон `INDEX.md`
   с фактическим составом каталогов: индексы генерируются из проекции, а не поддерживаются вручную.
3. Второе отрицательное последствие — «перенос между корнями требует `git mv` вместо правки поля» — перестаёт
   быть операцией человека: перенос выполняется пересборкой проекции по событию PACT (обмен С-8, §2.2).
4. Аргумент ADR-0010 про маршрутизацию сессии в браузерный инстанс остаётся верным, но перестаёт быть
   единственной защитой: несоответствие «владелец задачи ↔ инстанс подключения» даёт отказ исполнения
   (M-5, §10.4, п. 4), а не тихую ошибку маршрута.

**Что при этом нельзя делать** (иначе решение сохранится только на бумаге):

1. Заводить владельца созданием каталога на месте. Владельца заводит PACT; отсутствующий в проекции владелец —
   отказ исполнения (§4.4, п. 5).
2. Определять категорию по каталогу при расхождении с проекцией: источник правды — проекция, каталог —
   её представление. Расхождение фиксируется как дефект (§17.3), а не разрешается на месте.
3. Переносить владельца между корнями вручную, минуя событие PACT.

**Ограничение области действия.** ADR-0010 определяет раскладку **каталогов владельцев**. Пути рабочих
материалов запуска (§4) корень не содержат: `runs/<owner-slug>/…` адресуется слагом, потому что смена категории
не должна двигать уже созданные тетради и обесценивать ссылки в журналах. Это не отступление от ADR-0010,
а следствие его же правила о глобальной уникальности слага.
