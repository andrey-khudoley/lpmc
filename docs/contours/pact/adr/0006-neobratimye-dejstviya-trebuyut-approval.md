# Необратимые действия MITA требуют approval по таблице PACT

- **Статус:** Принято
- **Дата:** не установлена как отдельная дата решения; в источниках зафиксированы только даты документов — CONTOURS.md 2026-08-08 (откуда взяты §7.2 и инвариант 10 §10), DECISIONS.md 2026-08-09 (запись D-006 внесена в этой ревизии со статусом «принято»)
- **Контур:** pact

## Контекст

MITA — исполнитель, работающий через интерфейсы, спроектированные для человека, а не через опубликованный контракт. Из этого положения в архитектуре следует асимметрия риска, зафиксированная дословно (CONTOURS.md §7.2): «Контуры соседние по положению и несопоставимые по риску. MITA читает недоверенные веб-страницы и действует по прочитанному, работает в живых сессиях внешних систем, а его действия часто необратимы. При модели доставки at-least-once повторная отправка формы — это второе выполнение действия, а не повторное чтение.»

Три факта складываются в одну проблему:

1. **Недоверенный вход.** MITA действует по содержимому страниц, которые не контролирует ни MITA, ни PACT; это тот же класс недоверенности, что оправдывает статус LINA как недоверенного контура на входе, только здесь он материализуется не в тексте, а в действии.
2. **Живая сессия.** Действие выполняется от имени владельца в состоянии, которое MITA не может откатить — своей учётной записью в чужой системе, без API-транзакции и без гарантии компенсирующей операции.
3. **At-least-once и неидемпотентность.** Событийная модель доставки задач (§15.1) требует, чтобы каждый потребитель был идемпотентен, но веб-форма идемпотентной не является: повторная доставка одного и того же запроса на исполнение оборачивается вторым нажатием кнопки «Отправить», то есть вторым платежом, вторым письмом, вторым удалением.

Сегодня в MITA этой защиты нет вовсе: подтверждения для необратимых действий не существует, и то, что операция рискованна, распознаёт (или не распознаёт) сам исполнитель по ходу выполнения задачи — то есть тот же агент, который прочитал недоверенную страницу и может быть ею введён в заблуждение. Формулировка задачи прямо называет источник проблемы: «Отнесение операции к необратимым определяется таблицей PACT по хосту и типу операции, а не решением агента.» Без внешнего классификатора у MITA нет механизма отличить чтение статуса заказа от его отмены раньше, чем действие уже совершено.

Это тот же принцип, что уже закреплён для выдачи полномочий вообще (§6.2, ADR 0003): «LLM выбирает маршрут. LLM не выбирает полномочия. Авторизация — сама проверка. Если проверку выполняет модель, проверять больше нечем.» Источник формулирует связь явно: правило об approval для необратимых действий — «то же правило 6.2, применённое на уровне отдельного запроса».

## Решение

1. **Необратимость действия классифицирует таблица PACT, ключ — хост и тип операции**, а не суждение исполнителя MITA в моменте выполнения задачи. Таблица — часть enforcement PACT: детерминированные данные, а не решение диспетчера-LLM.
2. **Действие, классифицированное как необратимое, по умолчанию требует approval.** Действие, не попавшее в таблицу как необратимое (в том числе не классифицированное вовсе), правило по умолчанию не описывает явно — источники этого не уточняют; см. «Открытые вопросы».
3. Диспетчер PACT (LLM) вправе предложить капабилити и маршрут исполнения, но не вправе снять требование approval для операции, которую таблица относит к необратимым: это тот же водораздел «маршрут предлагает LLM — полномочия проверяет детерминированный код», что и в ADR 0003, только на уровне не задачи целиком, а отдельного запроса на исполнение внутри неё.
4. Для контура это означает обязанность **вести и версионировать таблицу необратимости** как часть таблиц правил PACT: добавление хоста, изменение классификации операции — фиксируемое, воспроизводимое, диффуемое изменение данных, а не факт из журнала.

## Последствия

**Положительные.** Решение «требуется ли подтверждение человека перед необратимым действием» перестаёт зависеть от того, распознал ли в моменте риск тот же агент, который уже мог быть введён в заблуждение прочитанной страницей: at-least-once повторная доставка задачи может привести MITA к повторной попытке исполнения, но не к повторному совершению уже подтверждённого необратимого действия без нового подтверждения. Появляется предмет для регрессии вида «операция X на хосте Y никогда не исполняется без approval» и объяснение постфактум, почему конкретное действие было пропущено или остановлено — то же следствие детерминированности enforcement (§6.2, следствия 2–3), что и для выдачи капабилити вообще.

**Отрицательные.** Каждое действие, классифицированное как необратимое, добавляет шаг ожидания подтверждения на happy path MITA — задержку и точку отказа там, где раньше исполнение шло без остановки. Прерванное на этом шаге необратимое действие может оставить внешнюю систему в промежуточном состоянии; источники прямо фиксируют этот риск как открытый и не закрытый данным решением (REVIEW-FINDINGS.md §4.5: «отзыв lease, прекращение процесса, судьба уже совершённых через Tool Gateway побочных эффектов, применимые таймауты» — механика не описана).

**Что становится дороже.** PACT обязан не только принять решение о необратимости на уровне правила, но и содержать саму таблицу: по каждому хосту и типу операции, с которыми MITA сталкивается — платёж, отправка сообщения вовне, удаление, необратимая смена состояния заказа и т. п., — таблица должна содержать классификацию заранее, до того как MITA впервые столкнётся с этой операцией на этом хосте, иначе решение по умолчанию для незнакомой комбинации не определено (см. «Открытые вопросы»). Расширение состава сервисов и владельцев MITA требует не только выдачи капабилити, но и отдельного, явного пополнения этой таблицы.

**Открытые вопросы, не закрытые этим решением.** Источники фиксируют, но не решают: (а) поведение по умолчанию для операции, отсутствующей в таблице — консервативный отказ/approval или пропуск, не определено; (б) канал получения самого approval — «по архитектуре ответ владельца приходит обычным сообщением через канальный адаптер и интерпретируется квалификатором, то есть языковой моделью, обработавшей недоверенный контекст того же диалога», а значит содержимое, попавшее в диалог извне, потенциально влияет на решение о выдаче полномочий; требуется отдельный доверенный путь подтверждения, не проходящий через LINA (аутентифицированная сессия веб-интерфейса или подписанные callback-кнопки с непрозрачным идентификатором и одноразовым значением) — решается при дальнейшей проработке контура PACT; (в) отмена и таймауты для уже начатого, но не подтверждённого необратимого действия (§13, §4.5) — механика не описана.

## Рассмотренные альтернативы

В переданных источниках альтернативные схемы явно не описаны как рассмотренные и отклонённые. Зафиксировано только текущее, действующее до этого решения положение дел в MITA — полное отсутствие механизма approval («необратимые действия не требуют подтверждения»), которое источники называют признанным и незакрытым риском, а не сознательно выбранной альтернативой. Единственная граница, о которую разбивается техническая изоляция и которая явно упомянута как обоснование самого механизма approval, а не его альтернатива: «Системы, работающие только с человеческой сессией» (MFA, капча, привязка к устройству) — «техническая изоляция достигает потолка; остаётся подтверждение каждого необратимого действия».
