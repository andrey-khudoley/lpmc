# Декомпозиция на четыре контура

- **Статус:** Принято
- **Дата:** не установлена как отдельная дата решения; в источниках зафиксированы только даты документов — CONTOURS.md 2026-08-08, DECISIONS.md 2026-08-09 (запись D-001 внесена в этой ревизии со статусом «принято»)
- **Контур:** pact

## Контекст

Это общесистемное решение, принятое на уровне всей Second System, а не только контура PACT. Оно продублировано здесь как определяющее положение самого PACT: без него у PACT нет собственного предмета — PACT существует ровно постольку, поскольку система разделена на контуры и один из них должен встать границей между ними.

Система строится как событийная: сообщение из внешнего канала → квалификация → адресованная задача → исполнение → ответ в исходный канал. Требовалось решить, как эта последовательность делится на независимо развиваемые части. Критерий разреза — своя, не пересекающаяся с другими ось изменения у каждой части (CONTOURS.md §3.1): диалоговый контур должен меняться при смене API мессенджера или стиля диалога и не должен меняться при появлении новой интеграции; контур правил должен меняться при изменении политик и не должен меняться при переверстке внешнего сайта; и так далее для исполнителей по веб-интерфейсам и исполнителей по API.

Одновременно с функциональным разрезом требовалось провести границу доверия: часть системы обрабатывает недоверенный внешний ввод и не должна иметь полномочий действовать, другая часть обладает полномочиями и доступом к внешним системам и не должна принимать решений о том, что и когда делать.

## Решение

Система делится на четыре контура:

- **LINA** (Linguistic Interface Agent) — диалог с человеком, сбор и обогащение запроса до полноты, возврат одобренного результата в разговор.
- **PACT** (Policy, Authorization & Control Tier) — маршрутизация, авторизация, реестр и состояния задач, проверка исходящего результата перед раскрытием.
- **MITA** (Manual Interaction Task Agent) — исполнение задач через веб-интерфейсы там, где API отсутствует.
- **CITA** (Contract Integration Task Agent) — исполнение задач через подготовленные API-интеграции.

Контуров доверия при этом два, а не четыре: недоверенный (LINA) и привилегированный (MITA, CITA). Граница между ними проходит по PACT — PACT является единственным арбитром на этой границе, причём в обе стороны:

```
недоверенный          арбитр            привилегированные
    LINA        →      PACT        →      MITA / CITA
    LINA        ←      PACT        ←      MITA / CITA
```

Не существует пути от внешнего сообщения к привилегированному исполнителю и обратно, минующего PACT. Прямой путь — проверка допустимости исполнения. Обратный путь — проверка допустимости раскрытия результата, и он не менее важен: результат исполнения содержит фрагменты страниц, ответы API, тексты ошибок и содержимое файлов, часть которых не предназначена внешнему каналу.

Основание разреза на четыре части (не только PACT/не-PACT) — четыре независимые оси изменения: у LINA меняется API мессенджера и стратегия уточнений; у PACT — правила, типы capabilities, состояния задач; у MITA — целевой веб-интерфейс; у CITA — версия внешнего API. Ни одно из этих изменений не требует правки остальных трёх контуров.

## Последствия

**Положительные.** Функциональные изменения в одном контуре (переверстка сайта у MITA, смена стиля диалога у LINA, новая интеграция у CITA) не требуют правок в остальных. Существует ровно одна точка, где проверяются полномочия на исполнение и допустимость раскрытия результата, — это делает возможным единый аудит, единую таблицу правил и единственный компонент, который нужно защищать от промпт-инъекции с особой тщательностью.

**Отрицательные.** Каждое действие проходит через дополнительный узел (PACT) на пути туда и обратно — задержка и точка отказа, которых не было бы в монолитной системе. Появляется необходимость в контракте событий между контурами (раз PACT не читает хранилища MITA/CITA напрямую) и в дисциплине его соблюдения. Разработка требует согласованно вести четыре независимых воркспейса вместо одного.

**Что становится дороже.** Любое изменение, которое затрагивает сразу несколько контуров (например, добавление нового типа задачи, требующего одновременно новой capability в PACT и нового сценария в MITA), требует координации между воркспейсами, а не правки одного файла. Диагностика сквозного сбоя усложняется — путь запроса теперь пересекает границы процессов/хранилищ, а не остаётся в рамках одного процесса.
