# Вариант реализации: гибрид на готовом шлюзе (OpenClaw)

- **Статус:** Предложено
- **Дата:** не установлена как дата принятия — статус решения «предложено», акта принятия нет; в источниках зафиксированы только даты документов: `IMPLEMENTATION-OPTION-OPENCLAW.md` (Draft 0.1) — 2026-08-06, `DECISIONS.md` (запись D-008 внесена в этой ревизии) — 2026-08-09
- **Контур:** pact

## Контекст

Second System (LINA/PACT/MITA/CITA) как работающая система не существует. Реально существует только независимая MITA (репозиторий `cloud-tech-tasks`), без PACT-проверки поверх и без связи с LINA. Всё, что описано ниже, — вариант проектируемой архитектуры, а не текущее состояние PACT.

Базовая спецификация Second System допускает несколько вариантов реализации периферийного (канального) и исполнительского слоя: (1) полностью самостоятельная реализация всех канальных адаптеров и Workers, (2) единственный экземпляр OpenClaw без внешнего брокера, (3) гибрид — OpenClaw на границах системы плюс собственное событийное ядро. Данный ADR фиксирует третий вариант.

Обоснование выбора этого варианта для сравнения: периферия каналов (webhook lifecycle, переподключения, rate limiting, медиа, chunking, треды/reply, delivery receipts, протокол веб-чата) сама по себе не создаёт ценности продукта и оценивается в 4–8 недель самостоятельной разработки; ценность сосредоточена в квалификации, политике и контрактах, которые в любом из трёх вариантов остаются собственной разработкой.

Проверенные на 2026-08-09 факты об OpenClaw (сторонний agent gateway с channel-адаптерами, Plugin SDK, Gateway RPC и runtime для Codex/Claude Code): Telegram — bundled-плагин, WebChat в ядре, всего 31 канал; Plugin SDK — 28 хуков, включая `message_received` и `before_agent_run` с возможностью блокировки до подачи промпта модели; Channel Outbound API даёт `sendDurableMessageBatch` с `MessageReceipt`, согласованием неоднозначной отправки и подавлением эха; из CLI-бэкендов `claude-cli` поставляется в комплекте, бандл `codex-cli` уже удалён (Codex работает через app-server harness, продакшн-путь — ACP Agents); Max в актуальном перечне каналов отсутствует.

Ключевой подтверждённый риск: версии OpenClaw «датовые», релизы выходят по несколько в неделю, несовместимые изменения затрагивают в том числе plugin API и миграции хранилища — удаление бандла `codex-cli` уже произошло, а не является гипотетическим сценарием.

Сравнительная оценка трудоёмкости (порядок величины, один опытный TypeScript/backend-разработчик, без учёта бизнес-правил квалификатора и полного UI, требует уточнения после PoC): технический MVP — 6–10 недель гибрид против 4–7 месяцев полностью самостоятельно; production hardening — ещё 4–8 недель против ещё 3–6 месяцев.

## Решение

Общесистемное решение (охватывает все четыре контура; здесь фиксируется применительно к PACT): использовать OpenClaw в двух изолированных точках на границе внешних коммуникаций и исполнения.

- **OpenClaw Intake Gateway** — шлюз Telegram/Max/Web, работает с внешними недоверенными отправителями. «Мощных» инструментов не имеет: exec/filesystem write/browser/external MCP — всё `deny`, `sandbox: all`.
- **OpenClaw Execution Gateway** — runtime для Codex и Claude Code, работает с персональными credentials и workspaces, но не принимает внешние сообщения напрямую (loopback only, без channel credentials).

Собственной разработкой Second System остаются: внешний брокер событий, Qualifier, Domain Event Router, Task Ingress, событийные схемы/версии, **Business Policy Gate**, approval-оркестрация на уровне задачи, **Task Registry**, Execution Task Runner, transactional outbox, DLQ, end-to-end аудит.

Для контура PACT это ключевая формулировка решения буквально: Business Policy Gate, Task Registry, approval-оркестрация и аудит **не заменяются** готовым шлюзом ни при каком из трёх вариантов реализации — они остаются собственной реализацией PACT независимо от исхода данного решения. OpenClaw в этой архитектуре покрывает только периферию (channel adapters и execution runtime), не арбитраж.

Решение принимается лишь частично уже на уровне соседнего решения D-009 (статус тоже «предложено»): на первом этапе Execution Gateway откладывается, исполнение реализуется собственным тонким runner'ом, потому что зависимость от стороннего гейтвея ложится именно в тот контур, где хранятся персональные учётные данные, — наиболее чувствительное место. Де-факто первый практический шаг гибрида — это только Intake Gateway.

Двойная система состояния задачи фиксируется явно как принятый и поименованный риск, а не как случайный побочный эффект: OpenClaw ведёт собственный task ledger, PACT — Task Registry; Task Registry объявлен **бизнесовым** source of truth (не единственным технически существующим состоянием) — расхождение между двумя ledger'ами возможно и смягчается reconciliation, а не устраняется архитектурно.

Статус решения — «предложено», не «принято»: семипунктный критерий принятия (документ §18) не проверялся, PoC (четыре этапа: intake, обратная доставка, execution, Max) не запускался. OpenClaw физически не установлен, каталог `vds-kz-pact` пуст, ни один компонент этого решения не является частью текущего состояния PACT.

## Последствия

**Положительные.** Экономия трудоёмкости на порядок величины на периферии каналов (недели вместо месяцев). Plugin SDK даёт технический механизм блокировки исполнения до подачи промпта модели (`before_agent_run`) на границе Intake — дополнительный технический барьер снаружи PACT, не заменяющий его enforcement. Channel Outbound API снимает с PACT необходимость самостоятельно решать доставку, дедупликацию и подавление эха на уровне транспорта.

**Отрицательные.** Зависимость от темпа релизов стороннего продукта: датовые версии, несколько релизов в неделю, несовместимые изменения plugin API и миграций хранилища — с уже случившимся прецедентом (удаление `codex-cli`). Двойная система состояния задачи (OpenClaw task ledger против Task Registry PACT) — расхождение возможно, устранить архитектурно нельзя, только процессно смягчить reconciliation. Max отсутствует в перечне каналов OpenClaw — на этом канале гибрид не даёт экономии (отдельно зафиксировано в соседнем решении D-010). Дефолт `sandbox.mode: off` у OpenClaw — известная ловушка: без явной настройки шлюз подключается к внешнему каналу без изоляции.

**Что становится дороже.** PACT обязан сопровождать pin точной версии OpenClaw, contract tests на Plugin SDK и Gateway RPC, канал extended-stable и процесс контролируемого обновления — это постоянная эксплуатационная нагрузка, а не разовая интеграция. Reconciliation между двумя системами состояния задачи — новый процесс, которого не было бы при полностью самостоятельной реализации. PACT вынужден поддерживать два физических представления политики вместо одного: бизнесовый Policy Gate (Second System) и технический уровень политики внутри OpenClaw Execution Gateway (sandbox/tool allow-deny/approvals) — документ прямо называет второй не заменяющим первый.

## Рассмотренные альтернативы

1. **Полностью самостоятельная реализация** всех канальных адаптеров и Workers. Даёт полный контроль над каждым байтом channel pipeline и низкую vendor-зависимость, но отклонена как основной вариант из-за трудоёмкости (4–7 месяцев MVP против 6–10 недель у гибрида). Остаётся вариантом отката при срабатывании условий пересмотра.
2. **Единственный экземпляр OpenClaw без внешнего брокера.** Упомянут источниками как один из трёх рассматриваемых вариантов, но не детализирован отдельно; отклонён в пользу гибрида — видимо, потому что не даёт PACT сохранить собственный Task Registry и Business Policy Gate как отделённый источник истины, а гибрид это условие соблюдает.
3. **Частичный откат — OpenClaw только как execution runtime.** Не отдельная альтернатива, а явно предусмотренный исход самого критерия принятия: если хотя бы один из первых пяти пунктов критерия §18 не подтвердится, происходит либо возврат к самостоятельным адаптерам, либо использование OpenClaw только на исполнении.
4. **Execution Gateway сразу, без отсрочки.** Рассмотрен и отклонён отдельным соседним решением D-009 в пользу собственного тонкого runner'а на первом этапе — экономия на исполнении наименьшая (одноразовый запуск CLI в изолированной рабочей области — сотни строк кода), а зависимость от стороннего гейтвея легла бы в контур с персональными учётными данными.

## Условия пересмотра

Явно зафиксированные rollback-триггеры (дословный смысл D-008) — возврат к самостоятельной реализации, если:

(а) интеграция потребует недокументированных внутренних API OpenClaw;
(б) Intake Gateway не удастся надёжно лишить возможности исполнения;
(в) стоимость сопровождения обновлений превысит экономию на каналах.

Формальное условие повышения статуса с «предложено» до «принято»: одновременное подтверждение семи пунктов критерия принятия (документ §18) по итогам PoC — документированность точек расширения Broker Bridge, гарантированное отсутствие исполнения у Intake Gateway, требуемая изоляция Codex/Claude в Execution Gateway, приемлемая стоимость поддержки Max plugin, сохранение идемпотентности сквозной доставки, проверяемость обновлений закреплённой версии contract tests'ами, устойчивое превышение экономии гибрида над полной самостоятельной реализацией. Если хотя бы один из первых пяти не подтверждён — откат к альтернативе 3 выше.

Отдельно, для включения Execution Gateway (соседнее частичное решение D-009, здесь не пересматривается, но обуславливает объём фактически принятой части D-008): появление потребности в интерактивных возобновляемых сессиях, фоновых задачах и готовой sandbox-модели.
