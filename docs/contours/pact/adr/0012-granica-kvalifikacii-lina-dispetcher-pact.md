# Граница классификации между LINA и диспетчером PACT

- **Статус:** Предложено
- **Дата:** не установлена
- **Контур:** pact

## Контекст

В существующей MITA роль `qualifier` (`.agents/agents/qualifier.md`, скилл `intake`)
совмещает в одном шаге две разные по природе функции: разбирает сырую постановку
менеджера в карточку задачи, то есть одновременно «добирает» недостающую информацию
до полноты, достаточной для передачи дальше, и решает, к какому классу относится
задача и какой набор возможностей ей может понадобиться. В целевой архитектуре эти
две функции физически разъезжаются по разным контурам: LINA — недоверенный диалоговый
контур, не владеющий задачей и полномочиями; PACT — арбитр, которому единственному
принадлежит решение о выдаче полномочий, причём выдаёт их детерминированный
enforcement по таблицам, а не сам диспетчер. Граница между ними не проведена явно ни в
одном источнике: CONTOURS.md §13 прямо перечисляет «где проходит граница между
подчинёнными агентами LINA и диспетчером PACT при классификации» как открытый вопрос
проектирования, ещё не закрытый ни одним из решений D-001…D-011.

Есть и содержательный аргумент, почему `qualifier` не может быть просто перенесён в
LINA целиком: общая политика MITA явно запрещает делегированной роли обращаться к
пользователю напрямую — только вернуть результат вызывающему контексту, а решение о
`blocked` принимает вызывающий. LINA же по определению обязана быть единственной, кто
говорит с человеком. Значит `qualifier`, как он есть сегодня, не может исполнять роль
LINA целиком: диалоговую часть (переспросить, уточнить) сегодня фактически ведёт
главный контекст команды `/new-task`/`/task`, а не сама роль `qualifier`.
Спецификация (SPECIFICATION.md §7.7, Request Qualifier) описывает компонент, который
на выходе даёт один из типов результата — кандидат в задачу, требование уточнения,
информационное сообщение, требование эскалации, отклонённое/неподдерживаемое
обращение, отмена/обновление — и который «может предложить необходимые возможности,
но не назначает фактически разрешённые инструменты». Это формулировка о разделении
полномочий, но не формулировка о том, кому — LINA или диспетчеру PACT — принадлежит
сам компонент; сегодняшние источники такого разделения не проводят.

## Решение

Разрезать функцию `qualifier`/Request Qualifier по вопросу, на который отвечает шаг,
а не по тому, кто физически его сегодня исполняет:

- **«Достаточно ли информации, чтобы вообще передать запрос дальше»** — решает **LINA**.
  Это единственное решение LINA о переходе (SPECIFICATION.md §23, CONTOURS.md §5.2): она
  либо задаёт уточняющий вопрос обратно в канал, либо считает запрос полным и передаёт
  его как кандидата в задачу.
- **«К какому классу относится задача, какие capabilities ей могут понадобиться, кто
  предполагаемый исполнитель (MITA или CITA)»** — решает **диспетчер PACT**: LLM-
  компонент, чьё предложение затем проверяется детерминированным enforcement по
  таблицам правил и capabilities, а не принимается как окончательное само по себе.
  Диспетчер вправе только предлагать (инвариант устройства PACT: enforcement не
  использует LLM для самого решения о выдаче полномочий); фактическая выдача —
  за детерминированной частью PACT.

Это решение помечается явно как **предложение**, а не закрытие открытого вопроса:
CONTOURS.md §13 называет эту границу открытой прямым текстом, и молчаливо закрыть её
одним ADR без явной пометки — значит скрыть решение, которое ещё предстоит подтвердить
при появлении рабочего PACT и рабочей LINA.

## Последствия

**Положительные.** У функции `qualifier`/Request Qualifier появляется недвусмысленный
критерий, по какую сторону границы LINA/PACT находится каждый конкретный вопрос:
«не хватает данных» — это LINA и её раунды уточнения; «не хватает решения о классе и
полномочиях» — это диспетчер PACT и последующий enforcement. Это снимает
неоднозначность, из-за которой сегодня `qualifier` в MITA одновременно похож и на
LINA, и на диспетчер PACT, и явно не совпадает ни с тем, ни с другим.

**Отрицательные.** Между LINA и диспетчером PACT появляется дополнительный шаг
передачи «кандидата в задачу», на котором нужно детерминированно решить, что LINA уже
сочла «достаточным», а PACT ещё может счесть недостаточным для классификации
(например, данных хватает для понятной формулировки, но не хватает для однозначного
выбора capabilities) — событийный контракт этого случая (кто в таком случае возвращает
запрос на дополнительное уточнение и через какой канал) источниками не описан и
остаётся открытым.

**Что становится дороже.** Реализация `qualifier`-подобной функции перестаёт быть одной
ролью в одном репозитории: часть логики (сбор полноты) должна жить в недоверенном
контуре LINA без доступа к таблицам правил и capabilities, часть (классификация) — в
PACT с доступом к ним, но без права разговаривать с пользователем. Перенос из MITA
одной роли `qualifier` в архитектуру два раза сложнее прямого переноса «роль → контур»,
которым можно было бы обойтись для однозначных случаев (`task-executor` → MITA,
`librarian` → вне контурной модели).

## Рассмотренные альтернативы

- **Весь `qualifier` целиком передать LINA** (LINA одновременно добирает полноту и
  классифицирует). Отклонено: LINA по определению не владеет задачей и полномочиями,
  а классификация — это в первую очередь решение про capabilities и исполнителя, то
  есть про полномочия; отдавать его недоверенному контуру нарушает границу «PACT —
  единственная точка между недоверенным и привилегированным контурами».
- **Весь `qualifier` целиком передать диспетчеру PACT** (PACT сам ведёт цикл
  уточняющих вопросов к пользователю). Отклонено по двум причинам: PACT не отвечает за
  диалог с человеком и формулировку ответа — это зона LINA; и общая политика MITA уже
  сегодня явно запрещает делегированной роли обращаться к пользователю напрямую,
  что подсказывает то же самое разделение, только на уровне существующей системы, а не
  проектируемой.
- **Оставить границу открытой без рабочей версии до появления работающих LINA и PACT.**
  Отклонено: CONTOURS.md §13 уже фиксирует вопрос как открытый, и повторение этого
  факта без предложенного разреза не продвигает проектирование; источники прямо требуют
  дать рабочую границу, даже предварительную, вместо того чтобы просто ссылаться на
  открытый список.

## Условия пересмотра

Статус остаётся «предложено» до появления работающих LINA и диспетчера PACT и должен
быть подтверждён или пересмотрен явно, когда:
- появится реальная реализация LINA и придётся столкнуться с пограничным случаем
  «данных достаточно для формулировки, но недостаточно для классификации»;
- будет закрыт открытый вопрос CONTOURS.md §13 в целом (граница LINA/диспетчер PACT
  при классификации) — на момент написания этого ADR он остаётся открытым, и данное
  решение — лишь предлагаемый, не финально принятый разрез;
- будет решён связанный открытый вопрос SPECIFICATION.md §22 «правила, по которым
  квалификатор может автоматически задавать вопросы», от которого зависит, где именно
  проходит практическая граница «достаточно ли информации».
