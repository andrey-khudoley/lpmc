# Capability не содержит указания на модальность

- **Статус:** Принято
- **Дата:** не установлена как отдельная дата решения; в источниках зафиксированы только даты документов — CONTOURS.md 2026-08-08, DECISIONS.md 2026-08-09 (запись D-007 внесена в этой ревизии со статусом «принято»)
- **Контур:** pact

## Контекст

Граница между MITA и CITA проведена не по предметной области, а по наличию у целевой системы пригодного API (CONTOURS.md §7.1): «Граница проходит по наличию пригодного API у целевой системы, а не по предметной области.» Эта граница подвижна: у сервиса, сегодня доступного только через веб-интерфейс, завтра может появиться опубликованный API, и та же по смыслу возможность должна переехать из MITA в CITA без изменения того, что о ней знают правила PACT.

Если бы имя capability содержало указание на способ исполнения (например, `invoice.submit.via-web`), то переезд возможности между контурами потребовал бы переписывания всех мест, где это имя используется: таблиц правил, capabilities, записей approval, журнала вердиктов. Модальность в имени намертво привязывает политику к исполнителю, который сегодня умеет её выполнять, хотя вопрос «можно ли» (сфера PACT) не должен зависеть от вопроса «как именно» (сфера MITA/CITA) — это и есть основной нож, которым проведена граница внутри PACT между «можно ли» и «как именно».

## Решение

Capability именуется по смыслу действия, а не по способу его исполнения: `invoice.submit`, а не `invoice.submit.via-web`. Задачу не адресует исполнителю заказчик — заказчик формулирует, что нужно сделать; кому именно это поручить (MITA через веб-интерфейс или CITA через контракт) решает диспетчер PACT в момент маршрутизации, а не постановка задачи и не имя capability.

Отсюда — инвариант 9 (CONTOURS.md §10): «Исполнителя выбирает PACT; capability не содержит указания на модальность.»

## Последствия

**Положительные.** Появление или исчезновение API у внешнего сервиса становится решением маршрутизации, а не изменением схемы политик: меняется, какой исполнитель обслуживает capability, а не сама capability, таблицы правил и накопленный по ней журнал вердиктов. Правила PACT, однажды написанные для capability, переживают смену исполнителя без ревизии. Асимметрия риска между MITA и CITA (см. §7.2: MITA действует по недоверенному прочитанному контенту, живёт в живых сессиях, действия часто необратимы) обрабатывается отдельно — таблицей необратимости по хосту и типу операции (D-006/инвариант 10), а не именем capability, то есть два независимых основания для решения не смешиваются в одном идентификаторе.

**Отрицательные.** Имя capability само по себе не говорит, каким риском обладает конкретное исполнение (веб-сессия и недоверенный контент против структурированного вызова API с типизированными ошибками) — это знание нужно доставать из таблицы маршрутизации/необратимости отдельно, что усложняет как ручной аудит правил, так и объяснение постфактум («почему это конкретное исполнение потребовало approval»).

**Что становится дороже.** PACT обязан держать явную таблицу маршрутизации capability → исполнитель (и её историю), поскольку эта информация больше не восстановима из самого имени capability. Любое расширение состава исполнителей или появление у сервиса нового способа доступа требует явного решения диспетчера о перемаршрутизации, а не переименования правила.

## Рассмотренные альтернативы

В переданных источниках явно рассмотренная и отклонённая альтернатива — именование capability с указанием модальности (`invoice.submit.via-web`); она названа несостоятельной именно потому, что «появление API потребует переписывания политик вместо изменения маршрута» (arch-vision.md §1.4). Других вариантов именования (например, версионирование capability по модальности с явной таблицей соответствия) источники не описывают как рассмотренные и отклонённые.
