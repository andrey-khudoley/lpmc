# Открытые вопросы и пробелы

Это `docs/`-файл, то есть фиксация текущего состояния (docs-as-state): что сегодня
**не определено** и **где именно это зафиксировано** в источниках. Ни один пункт этого
файла не закрывается здесь — ни выбором варианта, ни предположением, ни ссылкой на
`docs/spec/spec.md` за недостающими данными. Если по вопросу уже заведён ADR контура
CITA, ссылка на него приведена как на точку, где решение об **отсутствии выбора**
формально зафиксировано с датой и статусом, — сам ADR тоже не закрывает вопрос, а
документирует факт, что он открыт.

Общее для всех пяти пунктов ниже: они происходят из проектных документов
`second-system/` (статус «проектирование, реализация не начата»), а не из фактов,
которые можно было бы отнести к работающей CITA — работающей CITA не существует.

## 1. Перечень исходных интеграций CITA

**Источник вопроса.** `second-system/CONTOURS.md` §13 «Открытые вопросы» — дословно,
седьмым пунктом закрытого списка из семи: «перечень исходных интеграций CITA и
целевых систем MITA». Список сопровождён формулировкой «не решается в этом документе,
подлежит решению при проработке контуров».

**Что об этом известно, без попытки закрыть.** Ни один из решений `DECISIONS.md`
(D-001…D-012) не называет конкретный сервис или интеграцию как первую для CITA.
Материал-кандидат перечислен в `allocation.md` §2.6 и подробно разобран в
`docs/adr/0012-perechen-pervyh-integraciy-otlozhen.md` этого воркспейса:
`services/gc-chatium-gateway/` (собственный gateway автора, GetCourse API старый и
новый — раздел «Доступ» не заполнен, TODO), интеграции `services/chatium/`
(GetCourse SDK, AmoCRM OAuth2, Notion, Toggl Track v9, Bizon365 API v2.0 — исполняются
в облаке Chatium, не нашей системой), Bizon365 API v2.0 как отдельный внешний сервис
(хост `start.bizon365.ru` физически недостижим с узла — SNI-фильтрация, не связано с
пригодностью контракта), Notion API (ключ доступа не сохранён нигде, операции не
наблюдались). Ни один из них ADR 0012 не назначает первой интеграцией — таблица
кандидатов приведена без ранжирования и без выбора.

**Кто вправе закрыть.** Пользователь или главный архитектор работы (см. ADR 0012,
раздел «Решение»); ни один агент, наполняющий воркспейс `vds-kz-cita`, таким
полномочием не наделён.

## 2. Формат подписи авторизации PACT для egress proxy

**Источник вопроса.** `second-system/CONTOURS.md` §13, пятым пунктом того же
семипунктного списка: «формат подписи авторизации PACT, проверяемой egress proxy».

**Что об этом известно, без попытки закрыть.** Существование самой проверки
зафиксировано (`CONTOURS.md` §8.3, шаг внедрения №2 из четырёх: «proxy проверяет
подпись PACT на каждом запросе» → «закрывает: действие без авторизации»,
воспроизведено в `docs/adr/0005-egress-proxy-i-podstanovka-zagolovka.md` этого
воркспейса). Но ни формат самой подписи (алгоритм, что именно подписывается — тело
запроса, заголовки, идентификатор задачи и лизинга; где хранится и как проверяется
публичный/симметричный материал; срок действия подписи в привязке к лизингу
исполнителя), ни протокол её передачи от PACT к proxy и от proxy к исполнителю нигде
в прочитанных документах `second-system/` (`CONTOURS.md`, `SPECIFICATION.md`,
`DECISIONS.md`, `REVIEW-FINDINGS.md`, `STAGE-0.md`) не определены. Слово «подпись»
употреблено ровно один раз в источниках вне этого перечня открытых вопросов — в
таблице шагов внедрения `CONTOURS.md` §8.3 — и там же, без раскрытия механизма.

**Почему это касается именно CITA, а не только PACT.** Для контрактной модальности
`docs/adr/0005` этого воркспейса уже конкретизирует, что proxy подставляет заголовок
авторизации в запрос к целевому API (`Authorization`, `X-Api-Key` — конкретное имя по
контракту сервиса). Формат подписи PACT, проверяемой на входе в proxy (шаг 2), —
это отдельный, более ранний рубеж проверки, предшествующий самой подстановке; без
его определения шаг 2 таблицы `CONTOURS.md` §8.3 не может быть реализован ни для
CITA, ни для MITA.

## 3. Выбор брокера событий — **закрыт 2026-08-11**; формат схем остаётся открытым

**Источник вопроса.** `second-system/CONTOURS.md` §13, третьим пунктом: «выбор
брокера и формата схем событий» — единая формулировка, объединяющая два вопроса.
Отдельно закреплено как решение `second-system/DECISIONS.md` D-012 «Брокер событий».
Дублируется в `SPECIFICATION.md` §22 «Открытые решения» первым пунктом: «брокер:
Kafka, NATS JetStream, RabbitMQ или другой».

**Текущий факт.** 2026-08-11 D-012 переведён в статус **«принято»**: транспорт
событий — **NATS JetStream**, состояние — **PostgreSQL** (`SPECIFICATION.md` §16).
Определяющим при выборе названо требование авторизации на уровне subject; Kafka
отклонена как избыточная для профиля нагрузки, собственный транспорт поверх
PostgreSQL — как помещающий собственный код в точку принуждения границы, внешний
брокер — как выносящий события наружу мимо egress-проверки, файловая система — как
не дающая офсетов, durable consumers и атомарной публикации. Перенос решения в
контур — `docs/adr/0015-broker-nats-jetstream-i-sostoyanie-v-postgresql.md`;
`docs/adr/0014` в части продукта закрыт, в части конвенции имён действует.

**Что осталось открытым в этом же пункте CONTOURS §13.** Формат схем событий:
`SPECIFICATION.md` §22 перечисляет отдельно JSON Schema, Avro или Protobuf и
механизм Schema Registry — ни то, ни другое не выбрано. Выбор продукта брокера
этого не предрешает.

## 4. Конвенция имён топиков

**Источник вопроса.** `second-system/REVIEW-FINDINGS.md` §4.1 «Рассогласование имён
событий и топиков», статус **«открыто»** (находка ревью, не отдельное решение
`DECISIONS.md`). Дублирующая формулировка — `allocation.md` §3.2 «Оговорка о
номенклатуре»: «Имена топиков в SPECIFICATION.md §8 и имена `event_type` в §10
расходятся… Конвенция не выбрана».

**Что об этом известно, без попытки закрыть.** Топология §8 и контракты §10
`SPECIFICATION.md` используют разные имена для одних и тех же событий — минимум шесть
расхождающихся пар, включая `requests.task-candidate.v1` (§8) против
`request.task-candidate.v1` (§10) и `runs.completed.v1` против
`agent.run.completed.v1`; полная таблица шести пар — в
`docs/adr/0014-broker-sobytiy-i-konvenciya-imen-topikov.md` этого воркспейса и в
`REVIEW-FINDINGS.md` §4.1 напрямую. Диагноз ревью дословно: «Смешаны два разных
понятия: subject или топик брокера и `event_type`. По документу нельзя написать схемы,
не приняв решение за автора». Полный список топиков логической топологии §8
(`arch-vision.md` §9.5) насчитывает 33 имени, включая пять очередей `*.dlq.v1`
(`qualification`, `routing`, `task-ingress`, `execution`, `delivery`); расхождение с
`event_type` §10 не устранено ни для одной из приведённых пар по состоянию источников
на 2026-08-09.

**Прямое следствие для CITA.** Реестр интеграций и схемы операций CITA сегодня не
существуют; вопрос не решён, а следствие для CITA, когда реестр появится, описано в
`docs/adr/0014`: реестр и схемы обязаны будут ссылаться на конкретное имя
топика/`event_type` события «внутренний результат запуска» (продюсер — исполнитель,
консьюмер — egress-проверка PACT, `allocation.md` §3.2) и события «авторизованная
задача» (продюсер — enforcement PACT, консьюмер — исполнитель). До разрешения этого
пункта ADR 0014 предписывает CITA приводить оба варианта номенклатуры с пометкой о
нерешённости, а не выбирать один самостоятельно.

## 5. Различение MITA и CITA в гибридном варианте на OpenClaw

**Источник вопроса.** `openclaw-option.md`, раздел «Чего я не нашёл /
неоднозначности», пункт 2, дословно: «Не найдено, как в этой архитектуре различаются
MITA и CITA. D-007 фиксирует, что capability не должна знать о модальности исполнения
(MITA vs CITA выбирается диспетчером PACT), но вариант OpenClaw описывает единый
Execution Gateway для Codex/Claude Code — неясно, предполагается ли внутри Execution
Gateway/Task Runner различение «браузерных» (MITA-подобных) и «контрактных»
(CITA-подобных) задач, или же весь этот документ фактически описывает только один из
двух контуров (ближе к CITA/coding-agent сценарию), а MITA (браузерная автоматизация
недоверенных веб-интерфейсов) в архитектуру OpenClaw вообще не заложена». Тот же отчёт
уточняет источник наблюдения: «В тексте про браузер сказано только применительно к
Intake Gateway tool-policy (`browser: deny`) — про браузерный инструмент на стороне
Execution Gateway ничего не сказано» — и это наблюдение прошло верификацию отчёта без
замечаний (раздел «Верификация», п. «Отдельно отмечено»).

**Смежный, не менее прямой пробел.** Тот же раздел «Чего я не нашёл», пункт 1
(дословно): «Прямого маппинга «компонент документа → LINA/PACT/MITA/CITA» в
исходниках нет. Единственная явная таблица соответствия — в `STAGE-0.md` §2, и она
относится только к минимальному этапу 0, а не к полной гибридной архитектуре».
Отображение на этапе 0 (`STAGE-0.md` §2, воспроизведено в `arch-vision.md` §8.2)
называет MITA «отсутствует», а CITA — «встроенными инструментами runtime», то есть на
этапе 0 CITA формально представлена, а MITA — нет; но это утверждение об одном
минимальном этапе, не о целевой гибридной архитектуре, где вопрос остаётся открытым.

**Что об этом известно, без попытки закрыть.** Единый вариант реализации на OpenClaw
(`IMPLEMENTATION-OPTION-OPENCLAW.md`, статус документа «вариант для обсуждения», сам
вариант — решение D-008, статус **«предложено»**, не «принято») описывает один
Execution Gateway / Task Runner для Codex- и Claude-воркеров, не разводя внутри него
браузерную и контрактную модальность исполнения явным образом. Разобрано в
`docs/adr/0013-gibrid-na-openclaw-i-mesto-cita-na-etape-0.md` этого воркспейса. Здесь
дополнительно: сам факт отсутствия различения в источнике не разрешён этим ADR и не
может быть разрешён на уровне CITA — вариант на OpenClaw в целом не подтверждён
(«предложено»), и любое предположение о том, как в нём проведена граница MITA/CITA,
было бы инженерной реконструкцией сверх источника, а не фактом.
