# Инвентаризация контрактного материала в репозитории MITA

Этот документ описывает **текущее состояние** одного конкретного репозитория —
`/home/agent/workspaces/cloud-tech-tasks` (MITA, единственный реально существующий и
работающий контур на 2026-08-09). Задача — пройти по всему материалу в нём, который
может быть отнесён к контрактной (API) модальности, и вынести по каждой позиции
вердикт: **зачаток CITA** (материал по существу контрактный, годится как основание
для первой интеграции CITA после переезда), **остаётся у MITA** (материал описывает
браузерную автоматизацию или сервис, у которого нет пригодного опубликованного
контракта), **вне контуров** (материал не относится ни к MITA, ни к CITA — исполняется
третьей стороной или является каналом другого контура).

Снимок сделан прямым чтением исходников `cloud-tech-tasks` на 2026-08-09. Значения
секретов (пароли, токены, TOTP-семена, куки) в документе не воспроизводятся — только
имена ключей, пути и структура.

## 3. Шаблон `templates/service.md` и распределение `type`

Шаблон карточки сервиса задаёт frontmatter:

```
type: web               # web | api | db | server | other
```

Значение `api` в шаблоне допустимо и явно перечислено, но **не встречается ни в одной
из 18 карточек** (4 общих + 14 клиентских), проверенных выше. Раздел «Доступ» шаблона
рассчитан на веб-модальность буквально по тексту:

```
- URL входа: <...>
- Учётные данные: секреты `<client>/<service>/username`, `<client>/<service>/password`
- 2FA: нет | TOTP (секрет `<client>/<service>/totp`)
- Playwright storage-state: `.secrets/storage-state/<client>/<service>.json`
```

Формат «Возможности и типовые операции» — свободный текст, различий между веб- и
API-модальностью операций шаблон не проводит.

Вердикт: шаблон формально нейтрален к модальности (значение `api` допустимо), но
фактическое использование целиком веб-центрично, и структура раздела «Доступ»
(storage-state, TOTP-вход через форму) не подходит без переработки для описания
контрактного доступа (ключ API, OAuth2 client credentials и т. п.). Расщепление
карточки сервиса между MITA и CITA по разделам, а не по карточке целиком — предложенное
решение уровня CITA, не пересказывается здесь (см. `docs/adr/0009`,
`docs/adr/0010`).

## 5. `services/chatium/` — интеграции, исполняемые не нашей системой

Карточка (`type: web`, `completeness: partial`) описывает low-code платформу Chatium:
код (TypeScript/Vue) пишется в аккаунте платформы и **исполняется в облаке Chatium**,
без отдельного хостинга. Автор — официально аккредитованный интегратор Chatium,
использует платформу как инструмент разработки для клиентских проектов.

Раздел «Возможности и типовые операции» перечисляет модули платформы, включая блок
«Внешние интеграции (E01–E06)»: GetCourse SDK, AmoCRM (OAuth2), Notion, Toggl Track
v9, Bizon365 API v2.0.

Вердикт: **вне контуров.** Эти пять интеграций — часть кода приложений, которые
исполняются платформой Chatium в её собственном облаке, а не кодом, который
запускает наша система (MITA/CITA). Автор пишет и деплоит этот код в чужую среду
исполнения; ни MITA, ни CITA не являются рантаймом для него и не выполняют вызовы к
GetCourse/AmoCRM/Notion/Toggl/Bizon365 от имени этих Chatium-приложений напрямую.
Карточка `chatium` описывает платформу как **инструмент разработки**, а не как цель
интеграции CITA. Раздел «Доступ» тем же TODO, что и у `gc-chatium-gateway`
(доступы намеренно не перенесены), к вердикту не относится.

## 6. Наблюдения внутренних (неопубликованных) эндпоинтов

Два случая зафиксированы в клиентских/общих карточках как побочный результат
наблюдения сетевого трафика браузерной сессии, не как цель отдельной задачи:

- **Kinescope**: в карточке `services/kinescope/overview.md` и в скриптах
  `var/kinescope/net.mjs`, `var/kinescope/project.mjs`, `var/kinescope/folders.mjs`,
  `var/kinescope/getid.mjs` зафиксирован эндпоинт `app.kinescope.io/api/entities` и
  GraphQL-операции `createEvent`/`updateEvent`/`event` (интроспекция схемы отключена —
  структуру операций пришлось восстанавливать по перехваченным запросам/ответам, а не
  по опубликованной схеме).
- **Bizon365**: в карточке `clients/neso/services/bizon365/overview.md` описан способ
  создания вебинарной комнаты через `POST` с телом
  `{"id": "...", "title": "...", "group": "199542"}`, где CSRF-токен предварительно
  получается через `GET /my/<project>/api/init?perm=1` → поле `_csrf` (не из meta-тега).

Вердикт: **вне статуса «контракт»**, но и не совсем «остаётся у MITA» в чистом виде —
это пограничный материал. Оба эндпоинта не опубликованы поставщиком как API
(отсутствует документация, отключена интроспекция GraphQL-схемы у Kinescope), извлечены
наблюдением изнутри браузерной сессии, а не по спецификации. Признание такого
наблюдения основанием для перевода возможности в CITA — открытый, не решённый вопрос
(см. `docs/adr/0007`, там же зафиксирован его статус «серая зона»). До решения этого
вопроса оба эндпоинта фактически используются только браузерными скриптами MITA (см.
§7) и с эксплуатационной точки зрения остаются у MITA.

Отдельный факт, ограничивающий проверяемость: с узла недоступен `start.bizon365.ru`
(обрыв TLS после ClientHello, фильтрация по SNI на стороне нашей сети, зафиксировано
2026-08-08) — Bizon365 нельзя сегодня проверить ни в браузерной, ни в гипотетической
контрактной модальности.

## 7. Скрипты `var/kinescope/*.mjs` и `var/login-checks/*.mjs`

### `var/kinescope/` — 27 файлов `.mjs`

`bill.mjs`, `bill2.mjs`, `bz.mjs`, `check.mjs`, `folders.mjs`, `gcl.mjs`, `gcl2.mjs`,
`gc-neso.mjs`, `gc-neso2.mjs`…`gc-neso6.mjs`, `getid.mjs`, `larina-folders.mjs`,
`lib.mjs`, `login.mjs`, `net.mjs`, `otp.mjs`, `probe.mjs`, `project.mjs`, `save.mjs`,
`showbz.mjs`, `tilda.mjs`, `tilda2.mjs`, `ws.mjs`, `ws2.mjs` (плюс скриншоты `*.png` —
не код). Общий модуль `lib.mjs` открывает соединение:

```js
const browser = await chromium.connectOverCDP(`http://127.0.0.1:${port}`)
```

и читает секреты напрямую: `readFileSync('.secrets/env', 'utf8')`. Каждый из 27
скриптов либо вызывает `connectOverCDP` напрямую (как, например, `net.mjs`), либо
через `open()`/`secret()`/`totpFrom()` из `lib.mjs` — прямого исключения (файла без
привязки к CDP-подключению или чтению `.secrets/env`) в каталоге нет.

### `var/login-checks/` — 4 файла `.mjs`

`larina-getcourse.mjs`, `neso-getcourse.mjs`, `shared-kinescope.mjs`, `lib.mjs`. Тот
же паттерн: `lib.mjs` определяет `secret()`/`totp()`/`connect()`, читает
`/home/agent/workspaces/cloud-tech-tasks/.secrets/env` через `readFileSync` и
подключается через `chromium.connectOverCDP(...)`.

Вердикт по обеим директориям целиком: **остаются у MITA.** Все 31 скрипт (27 + 4) —
это CDP-браузерная автоматизация поверх веб-интерфейсов сервисов (Kinescope,
Bizon365, GetCourse, Tilda), не работа по контракту/API. Названия файлов (`gc-neso*`,
`larina-getcourse`, `neso-getcourse`) могут ввести в заблуждение — упоминание
GetCourse в имени не означает работу через GetCourse API: подключение везде идёт
через `connectOverCDP` к тому же браузерному инстансу, что и остальная MITA-автоматизация,
т.е. это тоже управление веб-интерфейсом ЛК GetCourse, а не вызовы его API.
По архитектуре разграничение MITA/CITA проходит по наличию у целевой системы
пригодного опубликованного контракта, а не по имени файла или названию сервиса в
нём (см. `allocation.md` §3.3, реплика MITA↔CITA).

## 8. MCP-реестр `.agents/mcp/registry.json`

Реестр содержит ровно два сервера:

| id | transport | назначение |
|---|---|---|
| `playwright` | stdio, `npx -y @playwright/mcp@latest --cdp-endpoint http://127.0.0.1:${KIOSK_CDP_PORT:-9222} ...` | браузерная автоматизация поверх веб-интерфейсов, тот же CDP-контур, что и скрипты `var/` |
| `knowledge-search` | stdio, `obsidian-hybrid-search-mcp` | локальный гибридный поиск по самой базе знаний репозитория (BM25 + семантика + RRF), наружу ничего не уходит |

Ни один из двух серверов не является контрактной интеграцией с внешней системой в
смысле CITA (типизированный API стороннего сервиса с версионированным контрактом):
`playwright` — универсальный браузерный протокол (CDP), не контракт конкретного
сервиса; `knowledge-search` работает по собственному репозиторию, а не по внешней
системе.

Вердикт: **вне контуров сегодня, потенциальная будущая точка регистрации для CITA.**
Реестр `.agents/mcp/registry.json` архитектурно нейтрален к тому, кто им пользуется
(структура — логический id + команда запуска + переменные окружения, без указания на
модальность исполнителя), и это делает его правдоподобным кандидатом на место
регистрации будущих контрактных MCP-серверов CITA — но сегодня в нём нет ни одного.
Это предположение о будущем использовании существующего механизма, не факт текущего
состояния; решение по этому вопросу — `docs/adr/0011` (статус «Предложено»), здесь не
пересказывается.

`docs/adr/`, полностью — в `docs/spec/spec.md`):

  MITA и CITA не закрыты окончательно (`docs/adr/0009`, `docs/adr/0010`).

  `.agents/mcp/registry.json` — предположение, не решение (`docs/adr/0011`).
