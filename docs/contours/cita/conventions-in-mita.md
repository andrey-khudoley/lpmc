# Конвенции MITA, относящиеся к контрактной модальности

Этот файл — docs-as-state: текущее состояние, а не желаемое. Он не описывает CITA как
систему (её не существует, см. `docs/current-state.md`) — он описывает пять конвенций,
которые сегодня действуют в репозитории MITA (`/home/agent/workspaces/cloud-tech-tasks`)
и которые пригодны как заготовка для CITA при переезде возможности из браузерной
модальности в контрактную.

**Обязательная оговорка, которую нельзя терять нигде в этом файле.** Слово `CITA` не
встречается ни разу ни в одном исходнике MITA — ни в `AGENTS.md`, ни в
`.agents/policy/`, ни в 34 журналах `llm/`, ни в шаблонах `templates/`. MITA сегодня не
знает о существовании CITA и не проектировалась с оглядкой на неё. Всё, что ниже
помечено как «связь с CITA», — инженерная реконструкция автора этого документа, а не
факт, вычитанный из источника. Раздел 6 собирает все такие реконструкции в одном месте
и явно их так называет.

## 1. Шаблон карточки сервиса и допустимый тип `api`

Источник: `cloud-tech-tasks/templates/service.md`, используется во всех 18 карточках
сервисов репозитория (`services/<slug>/overview.md` — 4 общих; `<root>/<owner>/services/<slug>/overview.md` — 14 клиентских/внутренних).

Frontmatter шаблона:

```
name: <название сервиса>
client: <slug владельца | shared>
type: web | api | db | server | other
url: <адрес входа>
owner: <ответственный на стороне клиента>
updated: <дата>
```

Тело шаблона — четыре раздела: «Что это и зачем» → «Доступ» → «Возможности и типовые
операции» → «Грабли и особенности».

**Раздел «Доступ» рассчитан буквально на веб-модальность.** В шаблоне это:

```
- URL входа: <...>
- Учётные данные: секреты `<client>/<service>/username`, `<client>/<service>/password`
- 2FA: нет | TOTP (секрет `<client>/<service>/totp`)
- Playwright storage-state: `.secrets/storage-state/<client>/<service>.json`
```

Значение `type: api` в шаблоне синтаксически допустимо и явно перечислено в
комментарии frontmatter — но **не встречается ни в одной из 18 существующих карточек**:
11 клиентских `web`, 3 клиентских `other` (`neso/payments`, `neso/salebot`,
`neso/telegram`, все три `completeness: stub`), 4 общих `web`
(`bizon365`, `chatium`, `gc-chatium-gateway`, `kinescope`). Полный разбор по каждой
карточке — в `docs/contract-material-inventory.md` этого воркспейса, здесь не
повторяется.

Практический вывод для CITA-реконструкции: формат карточки сервиса нейтрален к
модальности на уровне frontmatter (`type` уже различает `web` и `api`), но раздел
«Доступ» в теле карточки — нет. Расщепление карточки сервиса между MITA и CITA по
разделам, а не по карточке целиком, — предложенное решение уровня CITA
(`docs/adr/0009-reestr-integraciy-nasleduet-strukturu-kartochki-servisa.md`,
`docs/adr/0010-rasscheplenie-kartochki-servisa-mezhdu-konturami.md`), не факт из MITA.

## 2. Схема имён секретов `<client>/<service>/<field>` и слаг `shared`

Источник: `cloud-tech-tasks/.secrets/README.md` (единственный файл каталога `.secrets/`,
который коммитится в git), подтверждено `.agents/policy/common/04-secrets.md`.

**Модель хранения.** Единственный чувствительный каталог — `.secrets/` в корне
репозитория, вне git целиком, кроме `README.md`:

```
.secrets/
├── README.md                              # коммитится
├── env                                    # KEY=VALUE, один файл, chmod 600
├── storage-state/
│   ├── _TEMPLATE.json                     # образец формата, не рабочая сессия
│   └── <owner>/<service>.json             # снимки Playwright, chmod 600, каталог chmod 700
└── totp/<owner>/<service>                 # TOTP-секрет (base32), chmod 600
```

**Каноническое имя секрета** — `<owner>/<service>/<field>` (например
`neso/getcourse/password`). В файле `.secrets/env` оно кодируется механической
подстановкой: `/` → `__`, буквы → верхний регистр, `-` → `_`
(`NESO__GETCOURSE__PASSWORD`). Это правило нейминга README называет уже
спроектированным под перенос: «этот же нейминг сохранится при переезде в менеджер
секретов (этап 2)» — то есть схема имён рассчитана пережить смену хранилища, сама
миграция не реализована и не начата.

**Логин — тоже значение секрета.** Политика `04-secrets.md` прямо запрещает выписывать
логин/email открытым текстом в карточках и заметках: секрет — вся пара
логин+пароль, а не только пароль.

**Слаг `shared`** занимает позицию `<owner>` в имени, когда одна физическая учётная
запись обслуживает нескольких владельцев одновременно. Текущий факт (не воспроизвожу
значений, только структуру): `shared/bizon365` — один аккаунт на проекты трёх
владельцев (`neso`, `larina`, `akh-tech`); `shared/kinescope` — личный аккаунт автора,
внутри которого клиенты живут как отдельные проекты. Мотив введения — ротация: три
копии одного пароля под разными владельцами молча расходятся при смене, а расхождение
вскрывается только отказом входа. Слаг используется одинаково в позиции владельца
во всех трёх хранилищах: `env` (`SHARED__<SERVICE>__*`), `totp/shared/<service>`,
`storage-state/shared/<service>.json`. Правило введено сознательно и явно
зафиксировано дважды (Bizon365 и Kinescope, 2026-08-08): «общий секрет ≠ общая
сессия» — учётные данные можно делить, рантайм (профиль браузера) — нельзя.

**Формат `env` — не shell-файл.** Значение хранится «как есть», без кавычек и
экранирования. Документирован реальный инцидент (2026-08-08): пароль со спецсимволами
при `source .secrets/env` либо падает с ошибкой синтаксиса, либо (пароль вида
`abc&touch PWNED`) тихо исполняет хвост как команду и обрезает значение. Единственный
безопасный способ прочитать значение — построчный парсинг по первому `=`
(`.split('=', 1)[1]` — так и сделано в `var/login-checks/lib.mjs`, функция `secret()`).
Поиск по содержимому — только `grep -F`.

**Кто и как читает секреты сегодня.** `var/login-checks/lib.mjs` (33 строки, три
экспорта: `secret()`, `totp()`, `connect()`) делает прямой `readFileSync('.secrets/env')`
без какого-либо посредника — исполнитель (процесс, управляющий браузером) имеет
файловый доступ к значению напрямую. Никакого брокера, выдачи по авторизованному
запросу или логирования доступа нет; единственный «аудит» — человекочитаемый журнал
`llm/` (см. раздел 4), который пишет тот же процесс, что и читает секрет.

Связь с CITA (реконструкция): схема имён `<client>/<service>/<field>` и слаг `shared`
названы в исследовании (`allocation.md` §5) как наследуемые CITA почти без изменений —
именно потому, что README уже проектирует их как переживающие смену хранилища
(«этап 2»). Кому будет принадлежать custody самих значений (сегодня — никому,
файл читается напрямую) — вопрос PACT, не CITA; в этом файле не пересказывается.

## 3. Дисциплина Definition of Done (DoD)

Источник: `cloud-tech-tasks/.agents/policy/common/06-definition-of-done.md` (в виде
собранного `AGENTS.md`), шаблон `templates/task.md`.

Каждая карточка задачи (`<root>/<owner>/tasks/{active,archive/YYYY}/<id>/task.md`)
обязана содержать раздел **Definition of Done** — чек-лист. Требования к нему,
действующие сегодня как норма (проверено на реальных архивных карточках):

- Формулировка пункта — **фактически проверяемый критерий**, не намерение. Пример
  правильной формулировки из политики: «в сервисе X на странице Y отображается Z», а не
  «настроить интеграцию».
- Пункт DoD **нельзя отметить выполненным без фактической проверки** — обычно через
  Playwright (запрос защищённой страницы, снятие скриншота). «Должно работать по
  логике» результатом не считается — правило сформулировано явно как запрет.
- Верификация успеха отдельно оговорена методологически: судить о результате «по URL»
  или другому косвенному признаку запрещено там, где сервис может вернуть неоднозначную
  страницу (задокументированный случай — GetCourse после ввода 2FA-кода иногда
  показывает страницу логина «в варианте для уже вошедших», что выглядит как отказ).
  Верифицировать нужно запросом факта (доступна ли защищённая страница/ресурс), а не
  по внешнему признаку перехода.
- DoD заполняется на этапе нормализации постановки (скилл `intake`) и проверяется
  на этапе исполнения (скилл `execute-task`) — то есть это не разовая формальность, а
  двухшаговая процедура: сформулировать проверяемо → фактически проверить перед
  закрытием.

Связь с CITA (реконструкция): исследование `allocation.md` §5 называет «дисциплину DoD
как фактически проверяемого критерия» одной из вещей, которые CITA наследует
дословно. Смысл переноса: у CITA верификация результата контрактными средствами
(ответ API, идемпотентный статус операции) заменяет Playwright-скриншот как способ
фактической проверки, но сама норма «без факта — не готово» не меняется. Это
предположение о будущем устройстве CITA, не факт из MITA — в MITA формулировка DoD
не различает модальность проверки, потому что другой модальности, кроме браузерной,
там сегодня нет.

## 4. Конвенция журналов `llm/`

Источник: `cloud-tech-tasks/.agents/policy/common/08-llm-logs.md` (собранный
`AGENTS.md`), `templates/llm-log.md`, `llm/README.md`.

**Назначение.** `llm/` — «append-only архив того, что агенты реально делали»: сырец
сессии целиком (запрос, шаги, ошибки, решения, итог), в противоположность `notes/`
(дистиллированные наблюдения) и разделу «Журнал» карточки задачи (только ключевые шаги
для читателя карточки). Три уровня детализации одного процесса: `task.md`/«Журнал» →
`notes/` → `llm/` (полный технический сырец).

**Путь и имя файла.**

- По владельцу: `<root>/<owner>/llm/YYYY-MM/YYYY-MM-DD-HHMM-<agent>-<topic>.md`.
- Системная/кросс-владельческая работа (включая уборку `compact-notes`, даже если она
  правила клиентские каталоги): корневой `llm/YYYY-MM/YYYY-MM-DD-HHMM-<agent>-<topic>.md`.
- Сегмент `<agent>` обязателен всегда: `main` либо имя роли из `.agents/agents/`
  (`librarian`, `qualifier`, `service-scout`, `task-executor`).

**Frontmatter** (`templates/llm-log.md`): `date`, `agent`, `client` (пусто для
системной работы), `task` (глобальная ссылка `<owner>/<task-id>`, если работа шла по
задаче), `skill`, `trigger` (что запустило сессию).

**Тело:** «Запрос» → «Ход работы» (сырой пошаговый лог: команды и результаты, открытые
страницы, принятые решения и их причины, ошибки/тупики и как обойдены) → «Итог».

**Правила, действующие как норма, а не как рекомендация:**

- **Append-only.** Задним числом не редактируется, компакции/архивированию/промоушену
  в знания не подлежит — в отличие от `notes/`, это сырец навсегда. Даже структурные
  переименования (например, `clients/akh-tech/` → `internal/akh-tech/` 2026-08-08) не
  меняют пути в уже написанных старых журналах — это признаётся нормальным
  историческим следом, а не дефектом.
- **Обязателен для каждой изменяющей сессии.** Каждая сессия агента или делегированной
  роли, которая что-то реально сделала (выполнила/создала/изменила), обязана
  завершиться журналом. Обязателен и при исходе `blocked` (не только при успехе).
- **Пишется до коммита**, чтобы попасть в него вместе с изменением.
- **Чисто читающие процедуры журнал не пишут** — пример: скилл `status`, единственная
  из шести процедур `.agents/skills/`, не пишущая в `llm/`, потому что логировать
  чтение — шум.
- **Значения секретов маскируются.** Это единственный содержательный аудит-лог
  изменений секретов, который есть в системе сегодня — отдельного структурированного
  журнала доступа/ротации не существует. Задокументированный пример маскирования при
  сверке значений: сравнение через `[ "$v" = "..." ]` без печати целиком, показ длины
  несовпадения через `sed 's/[a-z0-9]/x/g'`.

Практический пример, который можно использовать как образец формата (не значения,
только структуру): `clients/neso/llm/2026-08/2026-08-08-1545-main-rename-getcourse-chatium.md` —
`agent: main`, `trigger` — прямая цитата вопроса пользователя, «Ход работы» — grep по
репозиторию, чтение аудита миграции, переименование карточки сервиса.

Связь с CITA (реконструкция): `allocation.md` §5 называет конвенцию журналов `llm/`
(append-only, маскирование секретов) одной из вещей, наследуемых CITA дословно — как
операционный лог исполнителя, а не как реестр PACT (реестр вердиктов/аудит доступа к
секретам — отдельная, не существующая сегодня функция PACT, см. `secrets-model.md`
§10 п.6 из материалов исследования; здесь не пересказывается).

## 5. Принцип «один канонический источник — N вендорных проекций» (`.agents/ARCHITECTURE.md`)

Источник: `cloud-tech-tasks/.agents/ARCHITECTURE.md`, статус `DECIDED`, версия 1.0,
дата 2026-08-03.

Дословная формулировка принципа:

> У каждой смысловой сущности существует ровно одна редактируемая каноническая версия.
> Всё, что нужно конкретному клиенту, либо ссылается на неё, либо детерминированно из
> неё строится и никогда не редактируется вручную.

**Как это устроено физически в MITA сегодня.** Единственный редактируемый источник —
каталог `.agents/` (`skills/`, `agents/`, `commands/`, `policy/`, `mcp/registry.json`).
Всё остальное — вендорные проекции для конкретного AI-клиента:

- `.claude/` — каталог симлинков на `.agents/`;
- `.codex/agents/*.toml`, `.codex/mcp-servers.toml` — детерминированно генерируемые
  артефакты;
- `AGENTS.md`, `AGENTS.override.md`, `CLAUDE.md` — сборка из фрагментов
  `.agents/policy/common/*.md` (14 файлов на сегодня) + `.agents/policy/runtime/<client>.md`,
  выполняемая инструментом `node scripts/agents.mjs build`.

Generated-артефакты несут шапку `<!-- GENERATED — не редактировать вручную. -->` и
хеш в `scripts/generated.lock.json`. Правка вносится только в `.agents/`, после чего
`build` пересобирает проекции; `check` сверяет проекции с планом побайтово и падает при
расхождении. Enforcement — единственный барьер, `.githooks/pre-commit`
(`lint && check`), сознательно одноуровневый (обоснование и условие пересмотра — в
`.agents/ARCHITECTURE.md` §8.1, не пересказывается здесь подробно).

**Инвариант 7 архитектуры** — методологически важнейшая часть принципа для темы этого
файла, дословно: «Семантика безопасности не может зависеть от метаданных, которые
клиент игнорирует». Пример, которым это подтверждено экспериментально: поле `tools` в
определении роли реально ограничивает набор инструментов под Claude Code, но Codex CLI
это поле не применяет вовсе — то есть одна и та же декларация безопасности работает
как enforcement под одним клиентом и как ничего не значащая рекомендация под другим,
если полагаться только на неё.

Связь с CITA (реконструкция): `allocation.md` §5 называет этот принцип одной из вещей,
которые CITA наследует у MITA — «подход "один канонический источник — N вендорных
проекций"». Перенос по смыслу для CITA: реестр интеграций/описание контракта могло бы
играть роль канонического источника, а конкретные MCP-клиенты/адаптеры под них — роль
вендорных проекций, генерируемых из него, а не редактируемых вручную. Это проекция
принципа на предметную область CITA, а не факт — в самом `.agents/ARCHITECTURE.md` нет
ни слова про CITA или про реестр интеграций внешних сервисов; документ описывает
исключительно доставку собственного агентского тулинга MITA под разных AI-клиентов.
Отдельно: тот же инвариант 7 в другом отчёте исследования назван «методологическим
предком» правила PACT «enforcement не использует LLM» (`allocation.md` §5, наследование
PACT) — то есть один и тот же исходный принцип по смыслу проецируется сразу на два
разных будущих контура (PACT и CITA) по-разному; это не противоречие, а следствие того,
что принцип сформулирован на уровне инженерной методологии, а не привязан к контуру.

## 6. Сводка: что здесь реконструкция, а что факт

| Утверждение | Статус |
|---|---|
| Шаблон `templates/service.md` допускает `type: api`, ни одна из 18 карточек его не использует | Факт (прямая проверка) |
| Схема имён секретов `<client>/<service>/<field>` и слаг `shared` — описаны и используются | Факт (`.secrets/README.md`, реальные ключи `env`) |
| DoD обязателен, формулировки только фактически проверяемые, без факта — не готово | Факт (`06-definition-of-done.md`, реальные карточки) |
| Журналы `llm/` append-only, обязательны, маскируют секреты | Факт (`08-llm-logs.md`, 34 реальных журнала) |
| Принцип «один источник — N проекций» и инвариант 7 | Факт (`.agents/ARCHITECTURE.md`, статус `DECIDED`) |
| Любая формулировка вида «CITA наследует X» | Реконструкция — слова `CITA` нет в источниках MITA |
