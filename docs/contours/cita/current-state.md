# Текущее состояние контура

Этот файл — фиксация факта «как есть сейчас» (docs-as-state). Он не описывает желаемое
устройство CITA — оно в `docs/spec/spec.md` — и не пересказывает его. Единственная
отсылка к спецификации в этом файле — расшифровка имени контура и его место в
четырёхконтурной схеме (принципиально неизменная вещь, допустимое исключение из правила
«не ссылаться на спецификацию за данными»): CITA (Contract Integration Task Agent) —
один из четырёх контуров системы (LINA, PACT, MITA, CITA), исполнитель задач через
опубликованные контракты внешних систем (`second-system/CONTOURS.md` §2, §2.1). Всё
остальное ниже — наблюдаемые факты, а не проект.

## 1. Итог одной фразой

**Контур CITA как работающая система не существует.** Ни одна задача в системе сегодня
не выполняется через опубликованный контракт внешнего сервиса. Вся автоматизация,
которая реально работает, — браузерная (Playwright/CDP поверх веб-интерфейсов) и живёт
в другом репозитории, `/home/agent/workspaces/cloud-tech-tasks` (MITA).

## 2. Что физически лежит в этом воркспейсе

Каталог: `/home/agent/workspaces/vds-kz-cita`.

```
vds-kz-cita/
└── docs/
    ├── README.md                         — индекс участка (статус контура, перечень файлов)
    ├── current-state.md                  — этот файл
    ├── contract-material-inventory.md    — инвентаризация материала MITA по вердикту
    ├── conventions-in-mita.md            — конвенции MITA, пригодные для CITA
    ├── observed-endpoints.md             — наблюдённые внутренние эндпоинты
    ├── open-questions.md                 — открытые вопросы контура
    ├── sources.md                        — карта источников
    ├── adr/                               — 14 файлов, 0001…0014, архитектурные решения
    └── spec/
        └── spec.md                        — желаемое состояние контура (spec-as-source)
```

Кода нет. Реестра интеграций (в любом виде — файл, каталог, формат) нет. MCP-конфигурации
с контрактными инструментами нет. Исполняемых артефактов (скриптов, клиентов API,
CI-проверок идемпотентности, схем ошибок) нет. Тестов нет. Кроме перечисленных выше
файлов `docs/` — README.md, шести файлов docs-as-state (включая этот), `docs/adr/` и
`docs/spec/spec.md` — в воркспейсе ничего не создано.

Три категории документов в этом воркспейсе — `docs/*.md` (docs-as-state, текущее
состояние, шесть файлов и README), `docs/adr/` (архитектурные решения) и
`docs/spec/spec.md` (спецификация) — сами по себе не являются механизмом: они фиксируют
факты, решения и желаемое устройство, но не создают ни одной работающей возможности.
Раздел «Что это меняет» здесь не пишется намеренно — по правилам документооборота
содержимое ADR и `spec.md` не пересказывается в `docs/`-файлах текущего состояния;
полный перечень и статус каждого решения — в `docs/README.md` этого воркспейса.

## 4. Состояние сетевой границы

**Egress-контроля на узле нет.** Роль `nftables` в `/var/lib/infra/src` (проверяемый
исходник — `filter.nft.j2`) определяет цепочку **input** с `policy drop` и правилами
фильтрации: `table inet main { chain input { type filter hook input priority filter;
policy drop; ... } }`. Роль также объявляет `chain output` и `chain forward`
(`type filter hook output/forward priority filter; policy accept;`, строки 250–258
`filter.nft.j2`) — обе цепочки существуют и активны, но не содержат ни одного правила
фильтрации, поэтому исходящий трафик не проверяется. Файл `nat.nft.j2` создаёт только
`table ip nat` с цепочкой `postrouting` для NAT VPN-подсети, к фильтрации исходящего
трафика узла отношения не имеющей.

Это подтверждено не только чтением шаблонов, но и прямой диагностикой на самом узле
08.08.2026, при разборе блокировки `start.bizon365.ru` (TLS обрывается после ClientHello
— фильтрация по SNI где-то на сетевом пути провайдера, не на этом узле): в ходе проверки
собственной стороны явно зафиксировано «nftables, цепочка `output` — пуста, policy
`accept` — узел исходящее не фильтрует» и «iptables OUTPUT — пусто»
(`cloud-tech-tasks/notes/2026-08/2026-08-08-bizon365-sni-blocked.md`). Тот же факт,
дословно — в тексте обращения к хостеру: «Firewall сервера: в nftables цепочка output
пуста, policy accept; iptables OUTPUT пуст».

Практическое следствие: **исполнитель (сегодня — MITA, единственный работающий
исполнитель) имеет прямой исходящий сетевой доступ**, без какого-либо посредника,
проверяющего домен, метод или наличие авторизации на конкретный запрос. Из-за этого же
устройства сети — фильтрации по SNI на стороне провайдера, а не на узле — с узла
недоступен `start.bizon365.ru`: это отдельный, не связанный с egress-контролем факт,
упомянутый здесь только потому, что он обнаружен той же диагностикой и ограничивает
проверяемость Bizon365 (ни в браузерной, ни в возможной будущей контрактной модальности
проверить его с этого узла нельзя).

Egress proxy как механизм принуждения границы «исполнитель не имеет прямого исходящего
доступа» — это проектное решение (`second-system/DECISIONS.md`, D-005, статус
«принято»), а не работающий механизм: он не установлен, узел его не запускает, ни один
исполнитель через него не ходит. За описанием целевого устройства — `docs/spec/spec.md`
этого воркспейса; здесь он не пересказывается.
