# Внутренние эндпоинты веб-интерфейсов не переводят возможность в CITA
- **Статус:** Предложено
- **Дата:** не установлена
- **Контур:** cita

## Контекст

ADR 0003 фиксирует критерий разреза MITA/CITA — наличие у целевой системы
пригодного опубликованного контракта, а не предметная область — и уже отмечает
как «серую зону» внутренние, ненамеренно наблюдённые изнутри браузерной сессии
эндпоинты, оставляя вопрос об их пригодности как контракта открытым. Этот ADR
закрывает часть той серой зоны для конкретных, фактически наблюдённых случаев.

`allocation.md` §2.6 в таблице «Данные CITA» называет наблюдение эндпоинта
`app.kinescope.io/api/entities` признаком «сервис пригоден к переезду в CITA»
одной строкой, без разбора условий и без отсылки к остальным наблюдённым
эндпоинтам того же рода. Формулировка допускает прочтение «сам факт наблюдения
эндпоинта — достаточное основание для переезда», что противоречит критерию
«пригодный опубликованный контракт» из ADR 0003 (CONTOURS.md §7.1) и правилу
«не выдумывать критерий пригодности», которого источники прямо не дают
(CONTOURS.md §13: «перечень исходных интеграций CITA» — открытый вопрос).
Настоящий ADR фиксирует расхождение явно и разрешает его в пользу более
строгого прочтения.

Фактический материал, наблюдённый изнутри MITA (карточки
`cloud-tech-tasks/services/kinescope/overview.md`,
`cloud-tech-tasks/clients/neso/services/kinescope/overview.md`,
`cloud-tech-tasks/clients/neso/services/bizon365/overview.md`):

- **Kinescope.** `GET https://app.kinescope.io/api/entities` — эндпоинт не
  задокументирован вендором, обнаружен перехватом сетевых запросов из открытого
  в браузере интерфейса («Как снять id нового владельца: открыть
  `.../live`… и `.../video`, перехватив ответы `api/entities`»). GraphQL-операции
  `createEvent`/`updateEvent`/`event`, которыми фактически создаётся трансляция,
  используются при явно отключённой интроспекции схемы («Интроспекция
  GraphQL-схемы в этом окружении отключена» — фраза повторена в обеих карточках).
  Без интроспекции нет способа получить схему типов, обязательность полей и
  версию операции иначе как эмпирически, пробами из браузера. Доступ выдаётся
  той же сессией (`storage-state` конкретного профиля `kiosk_browser`), что и
  доступ в веб-интерфейс — отдельного механизма аутентификации для API нет.
- **Bizon365.** `GET /my/<project>/api/init?perm=1` используется исключительно
  как источник CSRF-токена (поле `_csrf`) для последующего
  `POST .../createRoom` и `POST .../saveRoomSettings`. Токен для второго
  эндпоинта берётся не из ответа `api/init`, а из значения `__bizon._csrf` в
  DOM уже открытой страницы настроек — то есть даже внутри одного «эндпоинта»
  процедура получения токена не единообразна и завязана на конкретную страницу
  веб-интерфейса, а не на стабильный контракт. Формат тела запроса
  (`data[...]`, form-encoded) задокументирован только эмпирически, в комментарии
  карточки, а не вендором.

Общий признак обоих случаев: эндпоинт не опубликован вендором ни в каком виде
(нет страницы документации, нет OpenAPI/GraphQL-schema-файла, нет объявленной
версии), доступ к нему неотделим от браузерной сессии, из которой он
наблюдался, а не выдан как отдельная учётная запись API (ключ, OAuth-клиент,
сервисный токен). Это не единичный факт про один сервис, а системная
характеристика всех наблюдений, добытых MITA к 2026-08-09: других
источников API-материала в системе не существует (ADR 0003; вывод
`allocation.md` §2.6: «API-материал существует только как наблюдения изнутри
браузерного контура и как карточки собственных продуктов автора»).

## Решение

Факт наблюдения внутреннего эндпоинта веб-интерфейса изнутри браузерной сессии
сам по себе **не является основанием** для переезда возможности из MITA в
CITA. Он признаётся только **признаком кандидата** — сигналом, что у целевой
системы, возможно, существует API, достаточный для дальнейшей проверки, — но
не заменяет проверку критерия «пригодный опубликованный контракт» из ADR 0003.

Для перевода возможности в CITA по такому эндпоинту недостаточно факта, что
эндпоинт отвечает; требуется как минимум (перечень открыт, критерий
«пригодности» в целом остаётся нерешённым вопросом CONTOURS.md §13):

- эндпоинт официально задокументирован вендором либо контракт получен иным
  санкционированным способом (например, соглашением о доступе к внутреннему
  API), а не только перехватом трафика браузера;
- у эндпоинта есть версия или иная явная гарантия обратной совместимости —
  для GraphQL это, в частности, означает доступную интроспекцию схемы, а не
  операции, состав полей которых установлен пробами вслепую при отключённой
  интроспекции;
- доступ к эндпоинту выдаётся как самостоятельная учётная сущность API
  (ключ, токен, OAuth-клиент), не совпадающая с сессией браузерного профиля;
  использование значения, добытого исключительно как побочный продукт
  веб-сессии (CSRF-токен под конкретную страницу, cookie storage-state), не
  считается выданным доступом к контракту.

Ни `app.kinescope.io/api/entities`, ни GraphQL-операции Kinescope при
отключённой интроспекции, ни `GET /my/<project>/api/init` Bizon365 этому
не удовлетворяют ни по одному из трёх пунктов на 2026-08-09. Соответствующие
возможности остаются в MITA. `allocation.md` §2.6 в части формулировки «признак
«сервис пригоден к переезду в CITA»» этим ADR уточняется: наблюдение эндпоинта —
признак кандидата, а не признак пригодности; пригодность устанавливается
отдельно и по другим основаниям.

## Последствия

**Положительные**

- Критерий ADR 0003 («пригодный опубликованный контракт») не размывается
  первым же практическим случаем: без этого уточнения любой перехваченный
  сетевой запрос браузера формально попадал бы под «наблюдение эндпоинта» и
  открывал бы дорогу в CITA, обесценивая профиль CITA (структурированные
  ошибки, достижимая идемпотентность, ADR 0003) — ничего из этого не следует
  из факта, что запрос отвечает 200.
- Формулировка `allocation.md` §2.6 приведена в соответствие с критерием
  ADR 0003 вместо того, чтобы существовать как более слабая альтернативная
  версия того же решения в другом документе.
- Даёт проверяемый (хоть и не исчерпывающий) чек-лист из трёх пунктов вместо
  бинарного «есть эндпоинт / нет эндпоинта» для будущих кандидатов, снижая
  число случаев ручного спора о пригодности.

**Отрицательные / что становится дороже**

- Единственный практический материал CITA к 2026-08-09 (Kinescope, Bizon365)
  окончательно не годится в качестве стартовой интеграции; ближайшим реальным
  кандидатом остаётся `services/gc-chatium-gateway/` (ADR 0003), у которого при
  этом не заполнен раздел «Доступ» — то есть у CITA после этого ADR не
  остаётся вообще ни одного кандидата, готового по документации к переезду.
  Открытый вопрос CONTOURS.md §13 «перечень исходных интеграций CITA»
  этим не закрывается, а лишь сужается на два конкретных случая.
- Полный критерий «пригодности» контракта по-прежнему не определён — этот ADR
  формулирует необходимые условия (три пункта), но не достаточные; решение,
  закрывающее CONTOURS.md §13 целиком, остаётся отдельной задачей.
- Если у Kinescope или Bizon365 в будущем появится официально опубликованный
  API, применимость этого ADR к ним придётся пересматривать заново — сейчас он
  фиксирует состояние источников на 2026-08-09, а не общее правило вида
  «Kinescope и Bizon365 никогда не будут в CITA».

## Рассмотренные альтернативы

- **Принять `allocation.md` §2.6 буквально**: сам факт наблюдения эндпоинта —
  достаточное основание для переезда. Отклонена: противоречит критерию
  ADR 0003 и профилю CITA (структурированные ошибки, достижимая
  идемпотентность), ни один из наблюдённых случаев эти свойства фактически не
  даёт (у Kinescope интроспекция отключена, у Bizon365 CSRF-процедура
  завязана на конкретную HTML-страницу).
- **Полный запрет использовать любые внутренние эндпоинты в принципе, даже как
  сигнал.** Отклонена как избыточная: сам факт существования отвечающего
  эндпоинта — полезная информация для планирования (например, для приоритета,
  какой сервис проверять на публичный API в первую очередь), терять её не
  нужно; отклоняется только использование этого факта как основания для
  переезда.
- **Отложить решение целиком до появления общего критерия пригодности
  (CONTOURS.md §13).** Отклонена: расхождение с `allocation.md` §2.6 уже
  существует в документах контура и должно быть зафиксировано явно, а не
  оставлено как немое противоречие между ADR 0003 и таблицей allocation.md;
  общий критерий пригодности при этом остаётся открытым вопросом и решением
  этого ADR не подменяется.

## Условия пересмотра

- Появление общего решения по критерию «пригодности» контракта, закрывающего
  CONTOURS.md §13 «перечень исходных интеграций CITA» — после него этот ADR
  дополняется ссылкой на общий критерий, а не переписывается.
- Публикация вендором Kinescope или Bizon365 официальной документации API,
  версии контракта или выдача отдельной API-учётной записи — пересмотр статуса
  конкретно этих двух случаев по трём пунктам решения выше.
- Уточнение или изменение формулировки `allocation.md` §2.6 главным архитектором
  работы — при расхождении с этим ADR приоритет имеет более поздний документ;
  расхождение подлежит явному снятию, а не молчаливому сосуществованию.

Решение не перенесено из принятого источника — в `second-system/DECISIONS.md`
нет пункта D-00N, посвящённого статусу внутренних эндпоинтов как контракта, а
CONTOURS.md §13 прямо называет «перечень исходных интеграций CITA» открытым
вопросом. ADR сформулирован как предложение, разрешающее расхождение между
ADR 0003 (`second-system/CONTOURS.md` §7.1, D-007, «принято») и формулировкой
`/tmp/vds-kz-pipeline/research/allocation.md` §2.6 («признак «сервис пригоден к
переезду в CITA»»), на основании фактического материала карточек
`cloud-tech-tasks/services/kinescope/overview.md`,
`cloud-tech-tasks/clients/neso/services/kinescope/overview.md` и
`cloud-tech-tasks/clients/neso/services/bizon365/overview.md`. Статус — «предложено»,
не повышен, поскольку ни в переписке, ни в `second-system/DECISIONS.md`
это решение как принятое не зафиксировано.
