# Результат CITA раскрывается только после egress-проверки PACT
- **Статус:** Принято
- **Дата:** 2026-08-09 (в этот день создан `second-system/DECISIONS.md` и результаты
  ревью сведены в отдельные документы — хронология DECISIONS.md §2; тем же днём
  датирована строка «Правки внесены» в таблице CONTOURS.md §11, фиксирующей перенос
  находки REVIEW-FINDINGS §3.1 в CONTOURS.md и SPECIFICATION.md. Отдельно дата именно
  обсуждения D-004, в отличие от даты его письменной фиксации, в источниках не
  выделена)
- **Контур:** cita

## Контекст

CITA исполняет задачи через опубликованные контракты внешних систем: ответы
типизированы, ошибки предсказуемы, идемпотентность, как правило, достижима
(CONTOURS.md §7.1, таблица разреза MITA/CITA). Это свойство контрактной модальности
касается формы ответа, а не его доверенности: тело ответа API — текстовые поля,
названия объектов, сообщения об ошибках, идентификаторы — приходит из внешней
системы и может содержать данные, не предназначенные для показа пользователю
(секреты, содержимое чужого проекта, инструкции, вписанные третьей стороной
в поле, которое затем всплывает в отчёте). Типизированность не отменяет
границы доверия.

Исходная редакция SPECIFICATION.md (до ревью) отдавала право публикации внешнего
сообщения самому Worker: он же публиковал `outbound`-событие и сам проставлял
`visibility: external` (§6/§12.1/§17 исходной редакции). Находка ревью
REVIEW-FINDINGS.md §3.1 «У контроля исходящего трафика не было владельца» (статус
«закрыто») сформулировала проблему дословно: «Worker исполняет вывод модели,
работавшей с недоверенным контекстом. Право самостоятельно объявлять сообщение
разрешённым к отправке — граница, которой нельзя доверять исполнителю». Для CITA
недоверенным контекстом является в том числе ответ контрактного API — он получен
снаружи привилегированного контура так же, как HTML-страница для MITA.

Общесистемное решение — **D-004, «PACT является двусторонней точкой сужения»**
(`second-system/DECISIONS.md`, статус «принято»): «Результат исполнения попадает
в LINA только после egress-проверки PACT... Исходная схема проверяла только прямой
путь». CONTOURS.md §3.3 называет это свойство прямо: «не существует пути от
внешнего сообщения к привилегированному исполнителю и обратно, минующего PACT»,
и отдельно подчёркивает, что обратный путь (допустимость раскрытия результата)
«не менее важен» прямого (допустимость исполнения), поскольку результат содержит
«фрагменты страниц, ответы API, тексты ошибок и содержимое файлов».

Решение внесено в SPECIFICATION.md в нескольких местах:

- §5.7 «Внешний ответ публикуется единственным доверенным компонентом»: «Компоненты,
  формирующие содержимое, публикуют предложение ответа. Единственным продюсером
  событий внешней доставки является `Egress Guard` (§7.16)».
- §7.14 «Codex Worker и Claude Worker»: Worker «публикует внутренний результат
  и **предложение** внешнего ответа. Публикацию события внешней доставки
  выполняет `Egress Guard` (§7.16)».
- §7.16 «Egress Guard»: единственный компонент, публикующий события внешней
  доставки; принимает предложения ответа от Workers и квалификатора, применяет
  политику раскрытия, проверяет содержимое на секреты/учётные
  данные/внутренние логи/трассировки, проверяет соответствие маршрута исходной
  задаче, публикует `outbound.message.requested.v1`, направляет на ручной review
  то, что политика не разрешает публиковать автоматически.
- §14 «Политики исполнения»: «результат исполнения проверяется перед раскрытием
  во внешний канал наравне с проверкой перед исполнением».
- §23, инварианты 6 («внутренний результат запуска и внешний ответ являются
  разными событиями»), 12 («единственным продюсером событий внешней доставки
  является Egress Guard») и 13 («результат исполнения проверяется перед
  раскрытием так же, как задача проверяется перед исполнением»).

CITA — Worker в терминологии §7.14 наравне с MITA (Workers «разделяются по
модальности исполнения»); правило о раскрытии сформулировано для Worker вообще,
без исключения по модальности исполнения, и применяется к CITA напрямую, а не
по аналогии.

## Решение

CITA публикует про завершение задачи ровно два события, оба — не окончательные
с точки зрения раскрытия:

1. **Внутренний результат запуска** (`agent.run.completed`-подобное,
   SPECIFICATION §10.4, «не предназначено для прямой отправки во внешний чат») —
   полный контекст исполнения: сырые тела ответов контрактного API, коды и схемы
   ошибок, идентификаторы объектов, диагностика. Единственный консьюмер этого
   события — egress-проверка PACT (allocation.md §3.2, граница «MITA/CITA → PACT»).
2. **Предложение внешнего ответа** (`reply.proposed.v1`) — черновик текста для
   пользователя. Это предложение, а не решение о публикации.

CITA не публикует событие внешней доставки (`outbound.message.requested.v1`) ни
при каких условиях и не проставляет `visibility: external` — это исключительное
право единственного продюсера, Egress Guard, части enforcement PACT (§7.16, §23
п.12). Любое содержимое ответа внешней системы, попавшее в предложение ответа
CITA (текст, названия, сообщения об ошибке, ID), после публикации CITA
по-прежнему считается недоверенным содержимым: доверенным оно становится только
после того, как Egress Guard применит проверку на секреты и внутренние данные,
проверит соответствие `reply_route` исходной задаче и примет решение о допустимости
автоматической публикации — и сам опубликует `outbound.message.requested.v1`
(allocation.md §3.2, граница «PACT → LINA»: продюсер — «egress PACT, единственный
продюсер внешних сообщений»).

Инженерное следствие для реестра интеграций CITA: клиент каждой контрактной
системы обязан различать «сырой ответ API» (целиком идёт во внутренний результат)
и «предложенный текст ответа» (кандидат для показа, вычленяемый Worker'ом) — но
даже второе CITA не имеет права трактовать как готовое к отправке.

## Последствия

**Положительные**

- Единая точка раскрытия для обоих привилегированных исполнителей (MITA и CITA):
  проверка на секреты, внутренние данные и соответствие маршрута реализуется один
  раз, в Egress Guard, а не дублируется в каждом контрактном клиенте CITA.
- Типизированность контрактных ответов не создаёт исключения из общей проверки —
  не появляется соблазна счесть Worker с предсказуемыми, схемными ответами более
  доверенным источником публикации, чем Worker, читающий произвольные веб-страницы.
  Ответ контрактного API, в котором через пользовательское поле оказался
  посторонний текст, проходит ту же проверку, что и результат MITA.
- Компетенция CITA (реестр интеграций, критерий пригодности сервиса к контрактной
  модальности — назначение контура) остаётся ограничена содержанием результата и
  предложением ответа; политика раскрытия не становится ещё одной вещью, которую
  CITA обязана поддерживать при добавлении каждой новой интеграции.

**Отрицательные / что становится дороже**

- Между завершением задачи CITA и фактической доставкой ответа пользователю
  появляется дополнительный шаг и задержка: раскрытие не мгновенно, зависит от
  доступности и очереди Egress Guard.
- `reply.proposed.v1` обязан быть структурой, которую Egress Guard может проверить
  программно (маршрут, отсутствие секретов), а не произвольным текстом — это
  дополнительная дисциплина при разработке каждого контрактного клиента CITA.
- Модель деградации при недоступности Egress Guard/PACT для CITA этим решением не
  определяется (см. «Условия пересмотра») — до её появления неясно поведение CITA,
  если задача формально исполнена, а раскрытие не происходит.
- Тестирование CITA end-to-end (включая доставку) не может обойтись без окружения
  PACT/Egress Guard: контур либо мокает egress-проверку, либо проверяет только
  формирование предложения ответа, не факт доставки.

## Рассмотренные альтернативы

Единственная альтернатива, зафиксированная в источниках, — та, что была в
исходной редакции спецификации и отвергнута находкой REVIEW-FINDINGS §3.1: Worker
сам публикует внешнее сообщение и сам проставляет `visibility: external`.
Отклонена по причине, названной дословно: Worker исполняет вывод модели,
обработавшей недоверенный контекст, и не может быть источником решения о том,
что можно показать наружу. Для CITA это означало бы, что ответ, полученный от
контрактного API, определял бы факт своей же публикации.

Альтернатива «упростить проверку для CITA, поскольку его ответы типизированы» в
источниках отдельно не рассматривалась и не отвергалась явно — она просто не
предусмотрена: §7.16 описывает единую проверку для Workers, разделённых по
модальности исполнения (§7.14), без исключений по контуру.

## Условия пересмотра

- Модель деградации при недоступности Egress Guard или PACT в целом не
  определена (открытый вопрос, зафиксированный при исследовании allocation.md —
  «Отсутствует модель деградации»). Её появление может уточнить поведение CITA
  при недоступности проверки (например, буферизация результата вместо блокировки
  задачи), но не отменяет сам принцип «раскрытие — не решение исполнителя»; это
  предмет отдельного решения PACT, не пересмотр данного ADR.
- Способ, которым владелец подтверждает решение (approval), сам по себе идёт
  «по недоверенному пути» — открытая находка ревью (REVIEW-FINDINGS §3.2). Её
  закрытие может изменить, как Egress Guard получает разрешение на автоматическую
  публикацию, но не то, что публикует только он.
- Если для конкретной контрактной интеграции CITA когда-либо будет предложена
  отдельная категория «источник, не требующий проверки» — такое исключение из
  общего правила §7.16/§23 п.12/13 требует отдельного архитектурного решения
  (правило SPECIFICATION §23: «не должны меняться без отдельного архитектурного
  решения»), а не локального изменения клиента интеграции внутри CITA.
