# Идемпотентность операции как обязательное свойство интеграции CITA
- **Статус:** Предложено
- **Дата:** не установлена (само требование к реестру CITA как отдельный пункт
  не датировано ни в одном источнике; общий принцип, на который оно опирается —
  `SPECIFICATION.md` §15.1 — зафиксирован 2026-08-06, таблица сравнения
  MITA/CITA — `CONTOURS.md` §7.1–7.2 — 2026-08-08)
- **Контур:** cita

## Контекст

Базовая модель доставки во всей системе — `at-least-once`: «Базовая модель —
`at-least-once`. Каждый consumer обязан быть идемпотентным» (SPECIFICATION.md
§15.1). Дедупликация на уровне брокера (§15.2) покрывает входящие сообщения (по
каналу/account ID/внешнему ID), задачи (по `idempotency_key` адресованного
события, §10.3), запуски (по `run_id` и lease generation) и исходящие сообщения
(по `message_id`/`idempotency_key`, §10.5) — но это дедупликация *событий*,
адресованных consumer'у, а не гарантия того, что побочный эффект во внешней
системе, вызванный операцией CITA, не произойдёт дважды. Классический разрыв
at-least-once: запрос физически ушёл во внешний API и выполнился, ответ потерян
(сеть, таймаут, падение Worker), run считается незавершённым и перезапускается —
внутренняя дедупликация по `run_id` здесь не защищает, потому что новый запуск
получает новый `run_id` и обращается к тому же внешнему API повторно.

Таблица разреза MITA/CITA (CONTOURS.md §7.1) фиксирует идемпотентность как
различающее свойство: «Идемпотентность | как правило отсутствует (MITA) | как
правило достижима (CITA)». Формулировка «как правило» — не гарантия и не
проверяемый факт, а общее ожидание от контрактной модальности. §7.2 разворачивает
следствие этого свойства для MITA явно и подробно («его действия часто
необратимы... повторная отправка формы — это второе выполнение действия») и
из этого выводит D-006 (approval для необратимых действий MITA) — но
симметричного разбора для CITA в источниках нет: оптимистичная сторона таблицы
осталась тезисом, не превращённым в требование. SPECIFICATION §7.14 подтверждает
асимметрию тем же способом — от противного: Worker веб-модальности «совершает
преимущественно неидемпотентные действия», из чего по контрасту следует
негласное ожидание, что Worker контрактной модальности (CITA) идемпотентен
преимущественно — но это ожидание, а не декларация конкретной операции
конкретной интеграции.

Инженерный факт на стороне реестра: формат описания сервиса, используемый
сейчас (`templates/service.md` в MITA, поле `type: api` в нём предусмотрено, но
ни одна из 18 карточек его не использует), не содержит поля идемпотентности
вообще — ни на уровне сервиса, ни тем более на уровне отдельной операции.
Реестра интеграций CITA не существует; перечень исходных интеграций CITA прямо
назван открытым вопросом (CONTOURS.md §13). Решение принимается заранее, до
появления хотя бы одного прецедента.

## Решение

1. Описание каждой интеграции CITA обязано для каждой операции содержать явный
   признак идемпотентности (`idempotent: true` / `false`), а не наследовать
   общий тезис CONTOURS §7.1 «как правило достижима». Презумпция для операции
   без явного, обоснованного признака — `false`: операция считается
   неидемпотентной, пока идемпотентность не подтверждена и не задокументирована
   (документацией внешнего API, естественной идемпотентностью метода — например
   PUT-замена состояния, а не POST-создание — или тестом повторного вызова).

2. Для операций с `idempotent: true` CITA обязан формировать ключ
   идемпотентности, детерминированно производный от `task_id` адресованной
   задачи (`task.requested.v1`, §10.3 SPECIFICATION.md), так что повторный
   запуск того же `task_id` (например, после истечения lease, §15.2) порождает
   тот же ключ. Этот ключ передаётся во внешний API, если тот поддерживает
   собственный механизм идемпотентности (заголовок/параметр типа
   `Idempotency-Key`), либо используется для проверки «уже выполнено» перед
   вызовом, если внешний API такого механизма не предоставляет. Ключ,
   привязанный к `task_id`, — самостоятельная линия обороны, отдельная от
   дедупликации событий брокера по `run_id`: она защищает именно от повторного
   реального вызова внешней системы, для которого сценарий «ответ потерян после
   фактического выполнения» — штатный случай at-least-once, а не редкое
   исключение.

3. Операции с `idempotent: false` реестр обязан явно маркировать; такая
   операция не ретраится автоматически при повторной доставке/повторном
   запуске. Решение о том, что делать с попыткой повторного выполнения
   неидемпотентной операции CITA (запретить, потребовать approval, обработать
   вручную) — не относится к компетенции CITA (классификация необратимости и
   выдача полномочий — PACT, ровно как для MITA и D-006) и этим ADR не
   принимается; ADR фиксирует только обязанность CITA заявить свойство и
   передать его дальше по цепочке, а не решить, что с ним делать.

## Последствия

**Положительные**

- Закрывает разрыв между оптимистичной формулировкой CONTOURS §7.1 («как
  правило достижима») и проверяемым инженерным фактом: каждая интеграция
  декларирует свойство конкретной операции, а не наследует общее допущение
  контура.
- Симметризует надёжность: CITA получает те же гарантии at-least-once, что
  и остальные consumers брокера (§15.1), не полагаясь молчаливо на то, что
  «контрактность» сама по себе означает безопасность повтора.
- Разделение `idempotent`/`non-idempotent` по операциям даёт PACT материал для
  политики повторов и approval, не заставляя CITA самостоятельно решать вопрос
  допустимости повтора — граница ответственности (CITA описывает,
  PACT распоряжается) не нарушается.
- Ключ идемпотентности, привязанный к `task_id`, даёт трассируемость: по логам
  внешнего API и `task_id` можно установить, что повторный вызов — тот же
  самый task, а не новый.

**Отрицательные / что становится дороже**

- Каждая новая интеграция должна на этапе описания провести или задокументировать
  анализ идемпотентности своих операций у конкретного внешнего API — это
  дополнительная работа перед тем, как интеграция считается готовой к реестру;
  для API без документации или тестовой среды такой анализ может быть
  невозможен без риска пробного повторного вызова в проде.
- Презумпция «неидемпотентна, пока не доказано обратное» по умолчанию снижает
  автоматизм retry для новых интеграций до момента завершения анализа — система
  становится по умолчанию менее отзывчивой на временные сбои, а не более.
- Для внешних API без встроенного механизма идемпотентности необходим
  дополнительный код проверки «уже выполнено» перед вызовом в каждом клиенте
  (лишний запрос на чтение состояния, окно гонки между проверкой и вызовом).
- Формат реестра CITA приобретает обязательное поле раньше, чем появится первая
  интеграция: `templates/service.md` (шаблон MITA, единственный существующий
  прецедент формата карточки сервиса) такого поля не содержит, и ни одна из
  18 карточек не размечена как `type: api` — решение проверяется не на живом
  материале, а заранее.

## Рассмотренные альтернативы

- **Полагаться на общее правило §15.1 без операционной конкретизации.**
  Отклонено: правило сформулировано на уровне брокерных consumers (Worker в
  целом), а не отдельной операции внешнего API. Таблица CONTOURS §7.1 сама
  квалифицирует идемпотентность CITA как достижимую «как правило» — то есть
  не универсально; без явного признака по операции это «как правило» никогда
  не проверяется и не документируется, оставаясь тезисом, а не фактом.

- **Симметрично распространить на CITA правило D-006** (необратимые действия
  требуют approval по умолчанию) без разделения на idempotent/non-idempotent
  и без промежуточного признака в реестре. Отклонено для целей этого ADR:
  D-006 — решение о политике approval, принятое для MITA и принадлежащее
  PACT/Policy Gate, а не CITA. Этот ADR сознательно ограничивается тем, что
  относится к компетенции CITA (описание интеграции, реестр, признак
  свойства операции), и передаёт дальнейшее распоряжение признаком на арбитраж
  PACT, не подменяя его решение.

- **Не вводить отдельный операционный ключ идемпотентности, полагаться только
  на дедупликацию событий брокера** по `run_id`/lease generation (§15.2).
  Отклонено: дедупликация событий защищает от повторной доставки одного и того
  же события одному и тому же запуску, но не защищает от случая «запрос ушёл
  во внешнюю систему и выполнился, ответ потерян, run признан упавшим и
  перезапущен с новым `run_id`» — это и есть содержательный риск at-least-once
  для операции с реальным побочным эффектом за пределами брокера, и именно от
  него ключ, привязанный к `task_id`, защищает.

## Условия пересмотра

- Перечень исходных интеграций CITA — открытый вопрос (CONTOURS.md §13);
  решение сформулировано до появления хотя бы одной конкретной интеграции.
  При появлении первой (вероятный кандидат по текущему материалу MITA —
  `services/gc-chatium-gateway/`, собственный gateway на GetCourse API) формат
  признака идемпотентности и способ передачи ключа может потребовать уточнения
  под конкретный контракт API.
- Модель деградации при недоступности брокера/PACT не определена в источниках
  (см. также ADR-0006, «Условия пересмотра») — как обрабатывать попытку
  повтора операции, помеченной `non-idempotent`, при недоступности PACT для
  арбитража, этим решением не определяется.
- Формат Schema Registry и схем событий не выбран (SPECIFICATION.md §22,
  «Открытые решения») — конкретное место поля признака идемпотентности в схеме
  события или реестра может измениться вместе с выбором формата; сам принцип
  (обязательность признака и ключа, привязанного к `task_id`) это не отменяет.
- Если для отдельной интеграции внешний API предоставит собственный надёжный
  механизм идемпотентности, покрывающий весь класс её операций, точечное
  решение о способе передачи ключа для этой интеграции может быть пересмотрено
  без изменения общего принципа — это локальная настройка клиента, а не
  пересмотр ADR.
