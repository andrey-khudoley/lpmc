# Декомпозиция на четыре контура: последствия для CITA
- **Статус:** Принято
- **Дата:** 2026-08-08 (фиксация декомпозиции на четыре контура и создание CONTOURS.md; см. second-system/DECISIONS.md, хронология §2)
- **Контур:** cita

## Контекст

Система делится на четыре независимых контура: LINA (диалог с человеком), PACT
(арбитр — правила, полномочия, реестр задач, egress-проверка), MITA (исполнение через
веб-интерфейсы) и CITA (исполнение через опубликованные API-контракты). Решение о самой
декомпозиции принято на уровне всей системы — D-001 в
`second-system/DECISIONS.md` («Система делится на LINA, PACT, MITA и CITA»,
статус «принято»). Здесь фиксируются только следствия этого решения для контура CITA,
без переоткрытия самого решения.

Разрез контуров проведён по двум независимым основаниям (CONTOURS.md §3, §7.1):

1. **Ось изменения.** Разрез верен, если у каждого контура своя причина меняться и эти
   причины не пересекаются (CONTOURS.md §3.1). Для CITA: «новая интеграция, изменилась
   версия внешнего API»; CITA не меняется, когда «изменилась логика диалога». Соседняя
   ось MITA — «целевой веб-интерфейс переделали, добавили новый сайт»; MITA не меняется,
   когда «у вендора появилось API» (arch-vision.md §2, CONTOURS.md §3.1).
2. **Контур доверия.** Функциональных контуров четыре, контуров доверия — два, граница
   между ними проходит по PACT. LINA — недоверенный контур (обрабатывает внешний ввод,
   не имеет полномочий). MITA и CITA — привилегированный контур: обладают доступом к
   внешним системам и не принимают решений о том, что и когда выполнять (CONTOURS.md §3.2,
   §3.3; README.md). Не существует пути от внешнего сообщения к CITA и обратно, минующего
   PACT — это верно как для запуска задачи, так и для раскрытия результата
   (двусторонняя точка сужения, D-004).

Граница между MITA и CITA проведена не по предметной области, а по наличию у целевой
системы пригодного API (CONTOURS.md §7.1): «Граница проходит по наличию пригодного API у
целевой системы, а не по предметной области.» CITA — задачи, для которых у внешней
системы есть подготовленная API-интеграция; MITA — задачи через веб-интерфейс, спроектированный
для человека.

## Решение

CITA — исполнитель задач через опубликованные контракты/API внешних систем. CITA
**не принимает решений о том, что и когда выполнять** — этот выбор делает диспетчер PACT
(LLM-часть PACT предлагает исполнителя и capabilities, enforcement-часть проверяет и
выдаёт полномочия; правило D-003 «LLM выбирает маршрут, но не выбирает полномочия»).
Задача поступает в CITA уже авторизованной: с набором capabilities, лизингом и
привязкой к reply_route, а не как прямая команда от LINA или от человека.

Capability не содержит указания на модальность (D-007, CONTOURS.md §7.3): capability
именуется, например, `invoice.submit`, а не `invoice.submit.via-api`. Следствие —
граница MITA/CITA подвижна: при появлении у внешнего сервиса API та же возможность
может переехать из MITA в CITA без переименования capability и без изменения политик
PACT, только за счёт смены исполнителя, которого выбирает диспетчер.

CITA относится к тем же инвариантам границы, что и MITA, как исполнитель привилегированного
контура: у исполнителя нет прямого исходящего сетевого доступа (инв. 7, механизм —
egress proxy, D-005), учётные данные внешних систем не находятся в исполнителе (инв. 8),
исполнителя выбирает PACT, а не заказчик задачи (инв. 9) (allocation.md §3.1).

## Последствия

**Положительные**

- Собственная, не пересекающаяся с MITA и PACT ось развития: CITA растёт добавлением
  новых интеграций и обновлением версий уже подключённых API, а не изменениями в
  диалоге, в правилах или в вёрстке чужих сайтов. Работа над CITA не требует
  координации с изменениями в LINA.
- По сравнению с MITA — структурно более дешёвая эксплуатация: интеграция делается
  один раз и переиспользуется (а не сценарий под каждую цель), ошибки структурированы
  (коды и схемы, а не неструктурированный текст страницы), идемпотентность, как
  правило, достижима (CONTOURS.md §7.1, таблица). Это снижает стоимость retry и
  устраняет для CITA то основание, по которому в MITA действия по умолчанию
  необратимы (D-006 обосновано именно моделью MITA at-least-once + неидемпотентность;
  для CITA идемпотентность — по умолчанию достижимая цель, а не исключение).
- Задачи CITA не блокируются занятостью общего браузерного инстанса и не зависят от
  живой сессии человека в целевой системе — в отличие от MITA, где браузерная сессия
  ограниченно доступна и общая для владельца.
- Подвижность границы (D-007) означает, что появление API у сервиса, который сегодня
  обслуживается через MITA, — это операционный переезд, а не архитектурная переработка:
  меняется исполнитель в решении PACT, а не контракт capability.

**Отрицательные / что становится дороже**

- CITA не имеет собственного канала к человеку и не может уточнить постановку задачи —
  любая недостаточность входных данных не устраняется диалогом, а возвращается как отказ
  через PACT в LINA. Это дороже, чем для MITA/LINA в сумме, поскольку у CITA нет даже
  доступа к «прочитанному со страницы» контексту, на который может опереться MITA.
- CITA полностью зависит от PACT в вопросе «можно ли»: без действующей авторизации и
  лизинга запрос наружу не проходит (allocation.md §3.3). Пока PACT не существует как
  работающая система, CITA не может выполнить ни одной задачи, даже если интеграция
  готова технически.
- Пока не описан явно критерий пригодности сервиса к контрактной модальности и порядок
  переезда возможности из MITA в CITA, каждый такой переезд требует отдельного разбора
  вручную — это прямо названо открытым вопросом в CONTOURS.md §13 («перечень исходных
  интеграций CITA»), к нему добавляется невыясненный порядок обратного вывода
  capability из MITA в CITA без переписывания политик PACT.
- Сходство имён MITA/CITA (различаются одним символом, D-002) — цена родственности:
  риск опечатки в таблицах правил PACT, переносящей полномочие с исполнителя API на
  исполнителя, управляющего чужим веб-интерфейсом (то есть в сторону большего риска).
  Компенсируется только на стороне PACT (проверка идентификатора исполнителя по
  закрытому перечню, инвариант 11) — CITA как контур не может закрыть этот риск
  самостоятельно.

## Рассмотренные альтернативы

Альтернативы декомпозиции как таковой (объединение исполнителей в один контур,
разрез по предметной области вместо модальности исполнения, разрез по контуру доверия
без арбитра) относятся к системному решению D-001 и рассмотрены в
`second-system/CONTOURS.md`, а не в этом ADR — здесь их не переоткрывать
(см. правило пользователя: спор о самой декомпозиции — не предмет карточки CITA).

Специфичная для CITA альтернатива, отклонённая на уровне системы: **именовать
capability с указанием модальности** (`invoice.submit.via-api` вместо `invoice.submit`).
Отклонена решением D-007, поскольку жёстко привязывает политики PACT к конкретному
исполнителю и требует переписывания правил при каждом переезде возможности между MITA
и CITA, вместо того чтобы менять только маршрут в решении диспетчера.

## Условия пересмотра

- Появление первой реально работающей интеграции CITA и опыт эксплуатации PACT как
  системы — источник данных для закрытия открытого вопроса CONTOURS.md §13 (перечень
  исходных интеграций CITA) и для формулировки критерия пригодности сервиса к
  контрактной модальности, которого сегодня не существует ни в одном источнике.
- Если для конкретного вендора окажется, что «наличие API» недостаточно для отнесения
  задачи к CITA (например, API официально не поддерживается, требует ручной выдачи
  ключа человеком на каждый случай или не покрывает нужную операцию) — потребуется
  уточнение разреза §7.1, а не отказ от него.
- Решение о брокере событий (D-012) влияет на то, как именно CITA получает
  авторизованную задачу от PACT и возвращает результат; когда оно будет принято, этот
  ADR может потребовать дополнения (не пересмотра решения о декомпозиции).
  **Обновление 2026-08-11:** D-012 принят (NATS JetStream как транспорт, PostgreSQL
  как состояние) — см. `docs/adr/0015`. Решение о декомпозиции не пересматривается;
  следствия для границ контура зафиксированы в новом ADR.
