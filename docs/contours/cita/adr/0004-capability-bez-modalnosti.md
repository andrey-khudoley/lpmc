# Capability не содержит указания на модальность, исполнителя выбирает PACT
- **Статус:** Принято
- **Дата:** не установлена (решение зафиксировано в `second-system/DECISIONS.md`,
  D-007, документ с датой правки 2026-08-09; раздел §7.3 CONTOURS.md, откуда решение
  переизложено, датирован 2026-08-08; более точная дата принятия конкретно D-007 в
  источниках не выделена)
- **Контур:** cita

## Контекст

Граница между MITA и CITA проходит не по предметной области задачи, а по наличию у
целевой системы пригодного API (CONTOURS.md §7.1, дословно: «Граница проходит по
наличию пригодного API у целевой системы, а не по предметной области»). Это разрез,
который со временем сдвигается: у внешнего сервиса может появиться API там, где его
не было, и тогда одна и та же возможность (например, «отправить счёт») переезжает из
браузерной модальности в контрактную (CONTOURS.md §7.3).

Если бы имя capability содержало указание на модальность (например,
`invoice.submit.via-web`), такой переезд требовал бы переписывания всех мест, где
это имя используется: политик PACT, правил approval, таблиц классификации
необратимости, журналов и ссылок на capability в реестре задач. Расходится модальность
исполнения с идентичностью возможности как таковой — с точки зрения заказчика задачи
(LINA, собравшая запрос от человека) и с точки зрения PACT, выдающего полномочия,
«отправить счёт» — одна и та же операция независимо от того, кто и как её физически
выполнит.

Это частный случай общесистемного правила «LLM выбирает маршрут, но не выбирает
полномочия» (README.md, инвариант 4 CONTOURS.md §10; обоснование — D-003): выбор
конкретного исполнителя для авторизованной задачи — тоже часть маршрута, а не часть
полномочия, и делает его LLM-диспетчер PACT, а не тот, кто формулирует задачу.

## Решение

Capability именуется по сути возможности, а не по способу её исполнения:
`invoice.submit`, а не `invoice.submit.via-web` или `invoice.submit.via-api`. Задача
не адресуется исполнителю заказчиком (LINA/человеком) — исполнителя для авторизованной
задачи выбирает диспетчер PACT (CONTOURS.md §7.3; SPECIFICATION.md §23, инварианты 11
и 15; CONTOURS.md §10, инвариант 9).

Прямое следствие для CITA как контура: **CITA не вправе опираться на имя capability
при определении своей применимости к задаче**. Если для `invoice.submit` подготовлена
контрактная интеграция, применимость CITA к этой задаче определяется наличием у CITA
рабочей интеграции с целевой системой (реестром интеграций CITA) и решением PACT о
маршрутизации — а не тем, что имя capability «выглядит» как контрактное или содержит
какой-либо суффикс модальности. Симметрично: CITA не вправе интерпретировать
отсутствие суффикса как разрешение или запрет на исполнение.

## Последствия

**Положительные**

- Переезд возможности между MITA и CITA — при появлении API у ранее браузерного
  сервиса или, наоборот, при недоступности API — становится изменением маршрута
  (какой исполнитель назначен на capability в PACT), а не изменением политики
  (какие полномочия и approval требует эта capability). Правила approval,
  классификация необратимости и записи в реестре задач, привязанные к имени
  capability, продолжают действовать без правки при смене модальности исполнения.
- Единая точка перечисления интеграций и их пригодности к контрактной модальности
  (реестр интеграций CITA) не дублируется в именах capability и не может разойтись
  с фактическим состоянием контура.

**Отрицательные / что становится дороже**

- CITA не может по одному только identifier'у задачи локально решить, относится ли
  она к его компетенции — требуется либо явное поле маршрутизации в авторизованной
  задаче от PACT, либо сверка с собственным реестром интеграций. Отсутствие такого
  поля в текущей спецификации (CONTOURS.md §13 прямо называет перечень исходных
  интеграций CITA и связанные с ним детали открытым вопросом) — не решается этим ADR
  и остаётся открытым для CITA.
- Наличие contract-ready интеграции у CITA само по себе не гарантирует, что задача с
  подходящим capability будет направлена именно в CITA: решение остаётся за PACT.
  Это делает критерий «пригодности сервиса к контрактной модальности» (в
  компетенции CITA — см. назначение контура) необходимым, но не достаточным условием
  фактического переезда возможности; достаточное условие — решение диспетчера PACT.
- Тестирование и код-ревью реестра интеграций CITA не могут полагаться на
  соглашение об именовании capability (например, поиск по суффиксу `.via-api`) —
  сопоставление «capability → доступна ли контрактная интеграция» обязано быть
  явной структурой данных, а не выводиться из строки идентификатора.

## Рассмотренные альтернативы

Явно поименованных альтернатив для этого конкретного решения в источниках не
зафиксировано отдельным перечнем (в отличие, например, от D-002 с явным списком
отклонённых имён контуров). Из формулировки D-007 и CONTOURS.md §7.3 восстанавливается
одна альтернатива, которая отвергается самим текстом решения: включать модальность в
имя capability (`invoice.submit.via-web` / `invoice.submit.via-api`). Названная причина
отказа — переезд возможности между контурами при появлении/исчезновении API потребовал
бы переписывания политик, ссылающихся на capability по имени, вместо изменения одной
записи маршрутизации в PACT.

## Условия пересмотра

- Если перечень исходных интеграций и критерий их отбора для CITA (открытый вопрос
  CONTOURS.md §13) будет закрыт, и это потребует явного поля модальности в задаче —
  предмет пересмотра не имя capability, а формат авторизованной задачи, выдаваемой
  PACT; имя capability остаётся без модальности.
- Если на практике окажется, что PACT не может надёжно определить пригодного
  исполнителя без подсказки от заказчика задачи (например, для capability, пригодных
  сразу и MITA, и CITA, с разной стоимостью и разным риском исполнения) — предмет
  пересмотра здесь же: нужен ли отдельный, явно поименованный канал предпочтения
  модальности, не совпадающий с идентификатором самой capability.
- Появление у CITA нескольких контрактных интеграций для одной и той же capability
  (например, старое и новое API GetCourse) потребует отдельного решения о выборе
  между ними — это решение о версионировании внутри контрактной модальности, не
  предмет данного ADR и не основание пересматривать отсутствие модальности в имени.
