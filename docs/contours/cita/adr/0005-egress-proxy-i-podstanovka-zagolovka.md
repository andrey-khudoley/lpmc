# Egress proxy как механизм принуждения границы; для CITA — подстановка заголовка авторизации
- **Статус:** Принято
- **Дата:** не установлена (решение зафиксировано в `second-system/DECISIONS.md`, D-005,
  документ датирован 2026-08-09; раздел CONTOURS.md §8, откуда решение переизложено,
  относится к документу, зафиксированному 2026-08-08; более точная дата принятия
  конкретно D-005 в источниках не выделена)
- **Контур:** cita

## Контекст

Постановка задачи (CONTOURS.md §8.1, DECISIONS.md D-005): PACT является арбитром
(гейтом) только в том случае, если исполнитель — в данном случае CITA — физически не
способен действовать без его решения. При постоянных, долгоживущих учётных данных на
стороне исполнителя PACT защищает лишь корректный путь исполнения: дефект в
интеграции или инъекция через данные контракта обходят арбитра целиком, потому что
исполнителю для похода наружу не требуется никакого нового разрешения. Внешние
сервисы в большинстве своём не выдают короткоживущих, привязанных к конкретной задаче
учётных данных — значит, свойство «исполнитель не может действовать без решения
арбитра» обязано обеспечиваться механизмом, находящимся под контролем системы, а не
протоколом целевого сервиса.

Это общесистемное решение (D-005, «Egress proxy как механизм принуждения границы»,
статус «принято»): MITA и CITA не имеют прямого исходящего сетевого доступа; учётные
данные хранятся в egress proxy и подставляются им; на каждый запрос proxy проверяет
действующую авторизацию PACT для задачи, допустимость домена назначения и
допустимость HTTP-метода (CONTOURS.md §8.2). Настоящий ADR не переоткрывает
общесистемное решение — он фиксирует его конкретизацию и границы применительно к
контрактной модальности, которой ведает CITA.

Честный факт о текущем состоянии, без которого контекст был бы искажён: CITA как
работающая система сегодня не существует — воркспейс пуст, реестра интеграций и
исполняемых артефактов нет, ни одна задача по опубликованному контракту не
выполняется. Egress proxy для CITA сегодня тоже не существует. Более того, на узле,
где физически размещался бы такой proxy, egress-контроля нет вовсе: правила
`nftables` (`/var/lib/infra/src`) фильтруют только input, цепочка OUTPUT — policy
accept; это подтверждено 2026-08-08 при диагностике недоступности `start.bizon365.ru`
(обрыв TLS после ClientHello, фильтрация по SNI, а не результат применения политики
egress). Инвариант 7 («исполнитель не имеет прямого исходящего сетевого доступа»)
нарушается по факту для существующей MITA и был бы нарушен для CITA, начни она
работать сегодня без proxy. Владение политикой egress (домены, методы, авторизация) —
у PACT; физическое принуждение — механизм под управлением PACT, размещённый на узле
(`allocation.md` §4.5); CITA не отвечает ни за то, ни за другое, но обязана
проектировать свои интеграции в предположении, что этот механизм существует и
принудителен.

## Решение

Для контрактной модальности механизм egress proxy (D-005) конкретизируется так
(CONTOURS.md §8.2–§8.3):

- CITA не имеет и не будет иметь прямого исходящего сетевого доступа к целевым
  системам, с которыми она интегрируется по контракту; весь исходящий HTTP-трафик
  CITA идёт через egress proxy.
- В отличие от MITA (где proxy работает как MITM с собственным CA и подставляет
  `Cookie` в запросы браузера, так что «браузер сессию не видит»), для CITA proxy
  **подставляет заголовок авторизации** (например, `Authorization`, `X-Api-Key` —
  конкретное имя заголовка определяется контрактом целевого сервиса) в запросы к
  разрешённым хостам. CITA формирует запрос к внешнему API без значения учётных
  данных; значение подставляет proxy на пути запроса наружу. CITA не хранит, не
  читает и не видит значение секрета ни на одном этапе исполнения задачи —
  custody остаётся у PACT (хранение) и egress proxy (подстановка), это не меняется
  этим ADR и не входит в зону ответственности CITA.
- На каждый запрос proxy проверяет три вещи: действующую авторизацию PACT для этой
  задачи (капабилити и лизинг не истёк), допустимость домена назначения по allowlist
  и допустимость HTTP-метода для этой капабилити.
- Внедрение поэтапное, шаги общесистемны, разделяемы и полезны по отдельности
  (CONTOURS.md §8.3):

  | Шаг | Содержание | Что закрывает |
  |---|---|---|
  | 0 | нет прямого egress у исполнителей, proxy с allowlist доменов, учётные данные пока на месте | эксфильтрацию данных |
  | 1 | учётные данные переносятся в proxy | извлечение секрета из исполнителя |
  | 2 | proxy проверяет подпись PACT на каждом запросе | действие без авторизации |
  | 3 | эфемерное окружение на задачу, отзыв лизинга по завершении | переиспользование доступа между задачами |

  Шаг 0 наиболее дёшев и снимает наиболее вероятный риск — он же первый шаг, который
  необходимо будет пройти и для CITA, когда контур перестанет быть пустым
  воркспейсом.

## Последствия

**Положительные**

- Учётные данные внешних API не находятся в памяти или на диске исполнителя CITA —
  их нельзя извлечь через компрометацию задачи, дефект интеграции или содержимое,
  пришедшее в ответе контрактного вызова.
- Контроль применяется к каждому запросу, а не к сессии или к задаче целиком:
  истечение лизинга обрывает следующий запрос независимо от того, сколько шагов
  контрактного взаимодействия уже выполнено.
- Allowlist домена на транспортном уровне закрывает попытку обратиться к постороннему
  хосту в рамках той же задачи — для контрактной модальности это дешёво проверяемое
  свойство: набор хостов по контракту известен заранее и конечен, в отличие от
  произвольной навигации браузера в MITA.
- Единый журнал внешних вызовов на proxy — материал одновременно и для фактической
  верификации результата (обязанность CITA по назначению контура), и для
  расследования инцидентов вне зависимости от того, что сообщил сам исполнитель.
- Подстановка заголовка инженерно проще, чем MITM с собственным CA: для типового
  REST- или GraphQL-контракта перехватывается один известный заголовок, а не
  пересобирается TLS-сессия браузера с произвольным множеством cookie на нескольких
  доменах (ср. `docs/adr` MITA, где storage-state одного профиля покрывает 4+
  домена). Стоимость принуждения границы для контрактной модальности ниже, чем для
  браузерной, — это довод в пользу переезда возможности из MITA в CITA при появлении
  API, а не только довод в пользу самого механизма.

**Отрицательные / что становится дороже**

- Механизм в виде «подстановка одного заголовка» не покрывает схемы аутентификации,
  где секрет не сводится к статичному значению в заголовке: HMAC-подпись тела
  запроса, подпись в query-параметре, mTLS с клиентским сертификатом, cookie-based
  API без отдельного токена. Контракт с такой схемой не переезжает в CITA без
  отдельного расширения proxy — это не решается настоящим ADR.
- Каждый новый внешний хост требует явного добавления в allowlist PACT до первого
  обращения к нему — реестр интеграций CITA обязан заранее декларировать полный
  список хостов контракта, иначе первый же вызов будет отклонён на транспортном
  уровне независимо от корректности авторизации и метода.
- Egress proxy становится единой точкой отказа и единой точкой обзора для всех
  контрактных задач CITA одновременно: его недоступность останавливает исполнение
  любой интеграции, а не только одной задачи.
- Механизм не закрывает два класса ситуаций (CONTOURS.md §8.4), оба напрямую касаются
  CITA:
  - **легитимный по домену, методу и авторизации запрос, отправленный не по
    назначению** — например, капабилити разрешает создание записи, а исполнитель
    создал не ту запись; proxy это пропустит, поскольку с точки зрения транспорта
    всё корректно. Снижается только сужением капабилити до конкретной операции и
    approval на необратимое действие (D-006), а не механизмом egress;
  - **системы, работающие только с человеческой сессией** (многофакторная
    аутентификация, капча, привязка к устройству) — для CITA это, по существу, часть
    критерия непригодности сервиса к контрактной модальности: если у целевой системы
    нет пути авторизации, сводимого к статичному заголовку или ключу, подстановка
    заголовка невозможна в принципе, и такая возможность остаётся за MITA либо
    требует расширения механизма отдельным решением.
- Пока это решение не реализовано (сегодня — ни один из шагов 0–3, egress-контроля
  на узле нет вовсе, CITA как система отсутствует), описание в этом ADR — целевое
  устройство, а не наблюдаемое поведение. Практически проверить «заголовок
  подставляется, домен и метод проверяются» невозможно за отсутствием и CITA, и
  proxy; это не повод понижать статус решения (оно принято на уровне архитектуры), но
  обязательный факт для `docs/` CITA, чтобы документация не выдавала желаемое за
  действительное.

## Рассмотренные альтернативы

Общесистемная развилка, явно зафиксированная источниками (`allocation.md` §4.5), —
не про существование самого egress proxy, а про то, кому принадлежит правило:
политика egress (какие домены, какие методы, какая авторизация) закреплена за PACT,
а физическое принуждение — за механизмом под управлением PACT, размещённым на узле
(`cloud-vds-admin`, вне обоих репозиториев исполнителей). Это разграничение
ответственности внутри решения, а не альтернатива egress proxy как таковому.

Альтернатива «оставить учётные данные внешних API в самой CITA, полагаясь только на
allowlist домена и код-ревью интеграций» источниками не рассматривается как
самостоятельный вариант — она отклоняется самим основанием D-005 (CONTOURS.md §8.1):
без выноса учётных данных из исполнителя PACT защищает лишь корректный путь
исполнения, а дефект или инъекция внутри самой интеграции обходят его целиком.
Специфичной для контрактной модальности альтернативы подстановке заголовка (например,
выдача исполнителю короткоживущего токена напрямую от целевого сервиса) источники не
называют — по факту, отмеченному в §8.1, большинство внешних сервисов такой механизм
и не предоставляет.

## Условия пересмотра

- Появление у CITA контракта, чья аутентификация не сводится к одному подставляемому
  заголовку (HMAC-подпись, mTLS, query-signature) — потребует либо расширить механизм
  proxy отдельным решением, либо явно признать такую интеграцию непригодной к
  контрактной модальности и оставить её за MITA.
- Фактическая реализация шага 0 на узле (появление действующего egress proxy) —
  тогда честный факт «egress-контроля нет вовсе» (`allocation.md` §4.5, инцидент
  08.08.2026 с недоступностью Bizon365) устаревает и подлежит замене в `docs/` CITA
  на описание фактического состояния, без изменения этого ADR.
- Пересмотр общесистемного D-005 (изменение самого механизма принуждения границы)
  автоматически требует пересмотра настоящего ADR как производного от него.
