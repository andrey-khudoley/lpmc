# Гибридный вариант реализации и место CITA на этапе 0
- **Статус:** Предложено — **частично отменён 2026-08-11**
- **Дата:** не установлена
- **Контур:** cita
- **Частичная отмена:** часть о **месте CITA на этапе 0** («встроенные инструменты runtime»)
  отменена вместе с решением D-011, отклонённым в пользу D-013; действующее решение —
  `docs/adr/0016`. Часть о **статусе гибридного варианта реализации** (D-008 — «предложено»,
  продукт не установлен и не используется, описывать его как часть текущего состояния запрещено)
  остаётся в силе полностью.

## Контекст

`second-system/DECISIONS.md` содержит два решения, напрямую определяющих, чем
CITA будет в ближайшей реализации:

- **D-008** («Вариант реализации: гибрид на готовом шлюзе», статус
  «предложено») — использовать сторонний agent gateway OpenClaw на границе
  внешних коммуникаций, сохранив брокер, событийные контракты, PACT и реестр
  задач собственными. D-009 (тоже «предложено») уточняет, что на первом этапе
  гибрида исполнение (Execution) реализуется собственным тонким runner-ом, а
  не готовым Execution Gateway — то есть даже сам гибрид принимается лишь
  частично: граница (Intake) сейчас, исполнение — не сейчас.
- **D-011** («Этап 0: минимальный контур», статус «предложено») — начать с
  одного экземпляра OpenClaw, настроенного конфигурацией, без брокера и без
  собственного кода. Подробности раскрыты в `STAGE-0.md`, на который D-011
  прямо ссылается.

Ни одно из двух решений не имеет статуса «принято»: шкала DECISIONS.md
различает «принято» (зафиксировано и внесено в документы), «предложено»
(выработано в обсуждении, явного подтверждения не было) и «открыто» (решения
нет). D-008 и D-011 — во второй категории. Критерий принятия D-008
(документ §18 варианта, `openclaw-option.md` §14) требует одновременного
подтверждения семи пунктов через PoC (Broker Bridge только через
документированные extension points, гарантия неисполнения на Intake Gateway,
изоляция Codex/Claude на Execution Gateway, приемлемая стоимость Max-плагина,
идемпотентная сквозная доставка, автоматические contract tests на обновление
версии, оценка гибрида существенно ниже самостоятельной реализации) — ни в
`IMPLEMENTATION-OPTION-OPENCLAW.md`, ни в `DECISIONS.md` нет указания, что
PoC запускался и что хотя бы один из критериев проверен.

`STAGE-0.md` §2 и `CONTOURS.md` §12 содержат по существу одну и ту же таблицу
соответствия этапа 0 четырём контурам, но не дословно совпадающую —
единственное место во всех источниках, где такое соответствие зафиксировано
письменно (а не выведено интерпретацией), приведено ниже раздельно по
источнику:

`STAGE-0.md` §2:

| Контур | Чем представлен на этапе 0 |
|---|---|
| LINA | канальный слой шлюза: Telegram, при необходимости веб-чат |
| PACT | allowlist отправителей, профиль sandbox, политика инструментов |
| MITA | отсутствует |
| CITA | встроенные инструменты runtime |

`CONTOURS.md` §12:

| Контур | Этап 0 |
|---|---|
| LINA | канальный слой: Telegram и WebChat |
| PACT | allowlist отправителей, sandbox-профиль, права инструментов |
| MITA | отсутствует |
| CITA | встроенные инструменты runtime |

Различия построчные: LINA и PACT описаны разными словами в двух документах
(строка CITA и MITA — единственные, совпадающие дословно). Оговорка после
таблицы тоже не идентична: `STAGE-0.md` §2 — «Границы существуют в
конфигурации, но не в развёртывании»; `CONTOURS.md` §12 — «Границы существуют
в коде и конфигурации, но не в развёртывании» (с добавлением «в коде»). Смысл
общий: на этапе 0 LINA, PACT и CITA физически размещены в одном процессе
OpenClaw, разделены только настройками, а не отдельными сервисами или сетями.
MITA на этом этапе не представлена ничем — она не «встроена в том же
процессе», а именно отсутствует как класс задач.

Ни в `IMPLEMENTATION-OPTION-OPENCLAW.md`, ни в `STAGE-0.md`, ни в
`CONTOURS.md` нет описания того, как внутри «встроенных инструментов
runtime» отличить задачу CITA (исполнение по опубликованному контракту) от
задачи MITA (исполнение через веб-интерфейс), если бы MITA на этапе 0 была
включена. Документ-вариант описывает Execution Gateway унифицированно, как
runtime для запуска Codex/Claude Code, без разбиения на исполнителей «через
браузер» и «через API». Единственное упоминание браузера в документе —
tool-policy Intake Gateway (`browser: deny`); про браузерный инструмент на
стороне исполнения не сказано ничего ни в одну, ни в другую сторону. D-007
(«Capability не содержит указания на модальность», статус «принято»)
фиксирует, что выбор MITA или CITA для конкретной задачи делает диспетчер
PACT, а не сама capability, — но это решение о том, кто выбирает модальность,
а не о том, как рантайм-слой, представляющий CITA на этапе 0, отличает свои
задачи от задач, которые в перспективе достанутся MITA. Это прямо
зафиксированный пробел в источниках, а не техническая деталь, которую можно
достроить логически: без ответа на этот вопрос переход от этапа 0 (MITA
отсутствует) к этапу 1, на котором MITA появляется, не имеет описанного пути
— непонятно, что физически меняется во «встроенных инструментах runtime»,
когда в них добавляется различение.

## Решение

Настоящий ADR фиксирует три факта, ничего не решая по существу:

1. **Статус D-008 и D-011 переносится в документацию CITA как есть —
   «предложено», не «принято».** Ни `spec.md`, ни другие ADR контура cita не
   имеют права описывать гибрид на OpenClaw или минимальный контур этапа 0
   как решённую архитектуру. Формулировки должны быть в сослагательном
   наклонении («в рассматриваемом варианте», «если этап 0 будет принят»), а
   не в изъявительном.
2. **На этапе 0 (если он будет принят) CITA представлена «встроенными
   инструментами runtime»** OpenClaw Execution/Task Runner слоя, MITA на этом
   же этапе отсутствует полностью. Граница между контурами в этот момент
   существует только в конфигурации (allowlist, sandbox-профиль, tool
   allow/deny), а не в развёртывании — CITA не является отдельным процессом,
   сетью или сервисом ни на этапе 0, ни в первой части гибрида (D-008+D-009:
   Intake через OpenClaw, Execution — собственным тонким runner-ом).
3. **Отсутствие описания различения MITA/CITA внутри исполнительского слоя
   фиксируется как открытый пробел источников**, а не закрывается
   интерпретацией или домыслом. Ни одна карточка `services/` в MITA, ни один
   раздел `IMPLEMENTATION-OPTION-OPENCLAW.md`/`STAGE-0.md`/`CONTOURS.md` не
   отвечает на вопрос, что физически отличает вызов инструмента CITA от
   вызова инструмента MITA внутри единого рантайма — до появления такого
   ответа документация CITA обязана говорить «не определено», а не
   реконструировать разделение задним числом.

## Последствия

**Положительные**

- Документация CITA не выдаёт вариант для обсуждения за принятую
  архитектуру — снижает риск, что кто-то (включая последующего исполнителя
  этой же работы) начнёт проектировать реестр интеграций или схемы операций
  CITA в предположении, что раннер, изоляция и промежуточный брокер уже
  определены.
- Пробел «как различаются MITA и CITA на этапе 0» явно назван, а не спрятан
  — следующий шаг проектирования (переход к этапу 1, где MITA появляется)
  имеет конкретный вопрос, который нужно закрыть, а не абстрактную задачу
  «спроектировать оба контура».

**Отрицательные / что становится дороже**

- CITA не может опереться на этап 0 или гибрид как на готовую точку
  интеграции — раздел о механизме исполнения в `spec.md` контура вынужден
  оставаться на уровне «целевое устройство описано в second-system/, ни
  одна деталь не подтверждена PoC и не принята», что снижает конкретность
  документа.
- Если этап 0 всё же будет запущен до того, как пробел о различении
  MITA/CITA закрыт, есть риск, что первая реализация «встроенных
  инструментов runtime» будет спроектирована как недифференцированный слой
  и её придётся переделывать при появлении MITA на этапе 1, а не расширять
  — что противоречит собственному основанию D-011 («рост идёт добавлением
  компонентов, а не переписыванием»).
- Условия пересмотра D-008 и D-011 (PoC, критерии §18 варианта) требуют
  ресурсов вне контура CITA (собственно запуск и оценка OpenClaw) — CITA
  сама не может закрыть свой открытый вопрос, пока PoC не проведён на
  уровне всей Second System.

## Рассмотренные альтернативы

- **Принять статус D-008/D-011 как «фактически принятые», раз это
  единственный проработанный вариант реализации в источниках.** Отклонена:
  правила документооборота (docs-as-state, п. 2–3) запрещают документации
  контура выдавать желаемое или обсуждаемое за текущее состояние; ни один
  источник не подтверждает переход этих решений из «предложено» в
  «принято», а критерий принятия (семь пунктов PoC) явно не пройден.
- **Достроить своей интерпретацией, как «встроенные инструменты runtime»
  должны различать MITA и CITA**, опираясь на D-007 (диспетчер PACT выбирает
  модальность) и общий разрез MITA/CITA по наличию контракта (ADR 0003
  контура cita). Отклонена: D-007 описывает, кто выбирает модальность на
  уровне PACT, а не как это выражено физически внутри единого
  исполнительского процесса OpenClaw на этапе 0 — перенос принципа с одного
  уровня абстракции на другой без источника был бы нарушением правила «не
  выдумывай факты» (общее правило документооборота, п. 6/7 в терминах
  запроса на этот ADR).
- **Не заводить отдельный ADR, ограничившись упоминанием статуса «предложено»
  в spec.md.** Отклонена: статус двух решений, прямо определяющих
  единственное известное место CITA в ближайшей реализации, и явный пробел
  в источниках о разграничении с MITA — это архитектурно значимый факт с
  последствиями для порядка проектирования, а не деталь для сноски; по
  правилу «одно решение — один файл» ему полагается отдельный ADR.

## Условия пересмотра

- D-008 или D-011 переходят в статус «принято» в `second-system/DECISIONS.md`
  (по итогам PoC, критерии §18 варианта реализации) — тогда этот ADR
  переиздаётся с новым статусом и датой принятия, взятой из источника.
  Молчаливо повышать статус в переносе — как раз то, что этот ADR запрещает.
- В `IMPLEMENTATION-OPTION-OPENCLAW.md`, `STAGE-0.md` или отдельном документе
  появляется описание, как Execution Gateway/Task Runner отличает задачи CITA
  от задач MITA (например, отдельный набор capabilities, отдельный
  sandbox-профиль или отдельная конфигурация tool allow/deny) — снимает
  пробел, зафиксированный в этом ADR, и позволяет заменить раздел
  «Последствия» конкретным механизмом.
- Проектные документы `second-system/` явно распространяют этап 0 на MITA
  (снимают формулировку «отсутствует») — меняет таблицу соответствия и,
  соответственно, содержание раздела «Решение» этого ADR.
