# MCP-реестр как точка регистрации контрактных инструментов CITA
- **Статус:** Предложено
- **Дата:** не установлена
- **Контур:** cita

## Контекст

Действующий реестр `.agents/mcp/registry.json` в репозитории MITA
(`cloud-tech-tasks`) сегодня содержит ровно два сервера и описан в файле явным
нейтральным комментарием: «Нейтральный реестр MCP-серверов. Только логические id,
команды запуска и имена переменных окружения — никаких значений секретов»:

- `playwright` — браузерная автоматизация: `command: npx -y @playwright/mcp@latest
  --cdp-endpoint http://127.0.0.1:${KIOSK_CDP_PORT:-9222} --output-dir
  var/playwright-mcp --output-max-size 52428800`; привязан к ролям `task-executor`,
  `service-scout` через шаблон `mcp__playwright__*` в поле `tools`;
- `knowledge-search` — гибридный локальный поиск по базе знаний репозитория
  (`command: obsidian-hybrid-search-mcp`, `env: OBSIDIAN_VAULT_PATH=.`,
  `OBSIDIAN_IGNORE_PATTERNS` явно исключает `.secrets/**` и `deploy/**`); не
  привязан к конкретной роли.

Ни одного контрактного инструмента (клиента опубликованного API) в реестре нет —
он и не мог там появиться: в системе не выполняется ни одной задачи по
опубликованному контракту, а `services/gc-chatium-gateway/` — единственный
названный источниками реальный кандидат в CITA — до сих пор имеет раздел
«Доступ» как `TODO`.

Спецификация этого воркспейса (`docs/spec/spec.md` §17.1) уже фиксирует связанное
решение как предложенное: C-141 называет реестр MCP-серверов «точкой регистрации
инструментов — конвенцией, унаследованной от MITA»; C-142 отделяет регистрацию
инструмента от выдачи полномочия («реестр инструментов и таблица правил PACT —
разные сущности с разными владельцами»); C-143 требует, чтобы весь трафик
инструментов шёл через egress proxy, независимо от удобства. Настоящий ADR не
вводит новых требований поверх этих пунктов — он фиксирует и обосновывает решение
как архитектурный документ, на который C-140–C-149 могут ссылаться.

Решение нельзя принимать, не оговорив фактические ограничения доставки —
`agent-infra.md` (§2.3, §2.5, §5.3) и `.agents/ARCHITECTURE.md` (§2, инвариант 7;
§3.1) фиксируют их как проверенные запуском, а не как документированные:

- на машине установлено и проверено запуском ровно два клиента — Claude Code и
  Codex CLI 0.146.0; Gemini CLI и Kimi Code не установлены и в канон не заносятся
  («непроверяемое утверждение в канон не попадает»);
- у Claude Code проектный `.mcp.json` реально читается, а заполненное поле
  `tools` роли фактически отсекает MCP-инструменты, не перечисленные в нём
  (allowlist работает);
- у Codex CLI проектный `.codex/config.toml` **не читается** — проверено дважды,
  включая `trust_level=trusted`. Сгенерированный `.codex/mcp-servers.toml` — это
  честно задокументированный «фрагмент для оператора»: файл клиентом не читается,
  перенос в `~/.codex/config.toml` делает человек руками; на момент исследования
  там MCP не настроен вообще;
- у Codex CLI такого механизма allowlist по полю `tools` нет в принципе —
  инвариант 7 ARCHITECTURE.md прямо запрещает опираться на метаданные, которые
  клиент игнорирует: «поле `tools` роли не является защитой»;
- подстановка `${KIOSK_CDP_PORT:-9222}` в аргументах команды проверена фактически
  только для Claude Code; для Codex не проверялась — риск, что при ручном
  переносе плейсхолдер уедет в конфиг Codex буквальным текстом, а не значением.

CITA как исполнитель ещё не существует физически, и вопрос, через какого клиента
(и клиентов) он будет запускаться, источниками не решён. Значит, ADR обязан
закладывать решение так, чтобы оно не подразумевало гарантии доставки, которых
сегодня нет ни для одного второго клиента, кроме Claude Code.

## Решение

Использовать тот же механизм и ту же дисциплину описания, что действует в
`.agents/mcp/registry.json` MITA, как точку регистрации контрактных инструментов
CITA — при этом:

1. **Формат записи не меняется.** Логический id сервера, `description`,
   `transport`, команда запуска, аргументы, `env` — только **имена** переменных
   окружения, без значений секретов. Тот же нейтральный запрет, что действует в
   исходном файле, действует и для CITA буквально, не по аналогии.
2. **Реестр CITA — не тот же файл, а собственная копия того же формата.**
   `.agents/mcp/registry.json` физически принадлежит репозиторию MITA; по
   принципу «ни один контур не пишет в хранилище другого» (`allocation.md` §1,
   принцип 3; `CONTOURS.md` §9) CITA не получает право редактировать этот файл и
   не пытается зарегистрировать в нём свои серверы. CITA ведёт собственный реестр
   той же формы в своей части инфраструктуры — тот же паттерн «один канонический
   источник — N проекций», что ADR 0009 этого воркспейса уже применил к шаблону
   карточки сервиса.
3. **Регистрация инструмента не заменяет и не создаёт полномочие.** Наличие
   сервера в реестре делает вызов технически возможным для клиента, но не
   разрешённым: разрешает вызов только capability, выданная PACT на конкретный
   запуск (C-80, C-142). Реестр CITA и таблица правил PACT остаются раздельными
   сущностями с разными владельцами — записывать в описание инструмента что-либо
   похожее на разрешение запрещено.
4. **Весь трафик инструмента идёт через egress proxy.** Инструмент, технически
   способный открыть соединение мимо proxy (например, самостоятельно резолвящий
   и держащий TCP/TLS-сессию до внешнего API в обход прокси), не допускается
   к регистрации независимо от того, насколько он удобнее (C-143). Ограничение
   состава допустимых операций обеспечивают capability и egress proxy, а не
   факт присутствия записи в реестре.
5. **Реестр не единственная линия защиты и не может ею быть.** Поле `tools`
   роли и присутствие сервера в реестре — это фильтр, работающий только там, где
   клиент фактически его применяет (сегодня доказано — только у Claude Code).
   Для любого клиента, у которого такого фильтра нет или он не проверен
   (сегодня — Codex CLI), безопасность обеспечивается исключительно
   capability + egress proxy, а не тем, что сервер «не значится» в реестре
   клиента. Формулировка описания сервера обязана избегать слов, из которых
   читатель может заключить, что регистрация сама по себе ограничивает доступ.
6. **Оговорка о доставке фиксируется в самом реестре CITA, а не подразумевается.**
   Каждая запись, аналогично `$comment-cdp-endpoint` в исходном файле MITA,
   сопровождается явным указанием: для каких клиентов доставка проверена запуском,
   для каких — нет, и какой путь переноса используется там, где нативной доставки
   нет (по образцу того, как MITA документирует перенос `.codex/mcp-servers.toml`
   оператором вручную).
7. Состав первых записей реестра этот ADR не определяет — перечень исходных
   интеграций CITA остаётся открытым вопросом (`CONTOURS.md` §13, O-1 в §21
   `spec.md`). Решение фиксирует только форму и дисциплину точки регистрации.

## Последствия

**Положительные**

- Не создаётся отдельный, никем не проверенный формат регистрации инструментов:
  переиспользуется схема, уже опробованная на двух реально работающих серверах в
  MITA (`playwright`, `knowledge-search`), и её нейтральный запрет на значения
  секретов — готовое, проверенное решение вместо решения с нуля.
- Явное разделение «регистрация ≠ полномочие» (C-142) переносит уже проверенную
  на реестре интеграций CITA дисциплину (C-80: «наличие записи в реестре не
  является полномочием») на уровень ниже — на инструменты, а не только на
  описания интеграций. Одна и та же дисциплина в двух местах снижает риск, что
  кто-то ошибочно понадеется на реестр как источник прав именно потому, что
  «в реестре интеграций так уже принято».
- Оговорка о доставке предотвращает конкретный, уже дважды подтверждённый
  экспериментально класс ошибки — принятие поля `tools`/факта регистрации за
  защиту там, где клиент (Codex CLI) её не применяет.

**Отрицательные / что становится дороже**

- CITA не может просто дописать себя в `cloud-tech-tasks/.agents/mcp/registry.json`
  — нужен отдельный носитель того же формата в инфраструктуре самого CITA,
  которая на сегодня физически не существует; носитель этого реестра ADR не
  называет (ADR 0009 столкнулся с той же проблемой для реестра интеграций —
  открытый вопрос O-13 по факту распространяется и на реестр инструментов, хотя
  формально назван только применительно к реестру интеграций).
- Формат MITA спроектирован под stdio-серверы, оборачивающие браузер или
  локальный индекс; контрактный API-клиент, оформленный как MCP-сервер, требует
  дополнительной инженерной работы по упаковке (сервер, транслирующий вызовы
  операций описания интеграции в HTTP-запросы через egress proxy) — сама MITA
  такого прецедента не содержит, готового образца для копирования нет.
- Гарантии доставки, зафиксированные в решении, слабее, чем может показаться на
  первый взгляд: под вторым проверенным клиентом (Codex CLI) сегодня нет ни
  чтения проектного MCP-конфига, ни allowlist по `tools` — то есть при появлении
  у CITA более чем одного клиента потребуется либо ручной перенос конфигурации
  оператором на каждый релиз (тот же процесс, что уже задокументирован как узкое
  место в MITA), либо отдельный модуль доставки, которого сегодня не существует.
- Каждая запись реестра CITA обязана нести оговорку о проверенности доставки —
  дополнительная дисциплина сопровождения, которую нужно обновлять при каждом
  новом факте проверки (например, когда для Codex CLI фактически подтвердят или
  опровергнут доставку `.mcp.json`-аналога).

## Рассмотренные альтернативы

- **Спроектировать для CITA отдельный, не связанный с MCP реестр контрактных
  инструментов** (собственный формат, специфичный только для контрактных
  вызовов). Отклонена: в системе уже есть проверенная запуском конвенция
  (`.agents/mcp/registry.json` MITA, два реально работающих сервера), и
  альтернативный формат без опоры на этот фактический материал не даёт ничего
  взамен, кроме дополнительной инженерной работы; MITA уже показала, что
  нейтральная схема (только id/команда/имена переменных) работает на практике.
- **Опираться на поле `tools` роли и факт присутствия сервера в реестре как на
  единственный механизм ограничения доступа к контрактным инструментам, без
  отдельной проверки через egress proxy.** Отклонена: экспериментально
  подтверждено (`ARCHITECTURE.md` §3.1, `agent-infra.md` §2.3), что фильтрация по
  `tools` работает только под Claude Code; под Codex CLI такого механизма нет
  вовсе. Инвариант 7 прямо запрещает опирать семантику безопасности на
  метаданные, которые какой-либо клиент игнорирует.
- **Физически хранить единый `registry.json` на MITA и CITA вместе**, чтобы не
  дублировать формат. Отклонена: нарушает принцип «ни один контур не пишет в
  хранилище другого» (`allocation.md` §1, принцип 3; `CONTOURS.md` §9) — тот же
  аргумент, что уже применён в ADR 0009 этого воркспейса к шаблону карточки
  сервиса.
- **Отложить выбор точки регистрации инструментов до момента, когда появится
  хотя бы одна реальная контрактная интеграция CITA.** Отклонена: `spec.md` уже
  фиксирует связанные пункты (C-140–C-149) как предложенные независимо от того,
  какая интеграция станет первой; форма точки регистрации не зависит от
  конкретного сервиса-кандидата, а откладывание без необходимости оставляет
  открытым вопрос, который можно закрыть уже сейчас.

## Условия пересмотра

- Фактически проверится (прогоном, а не документацией) доставка MCP-конфигурации
  для Codex CLI или появится третий подключённый и проверенный запуском клиент
  (`ARCHITECTURE.md` §2, инвариант 10) — оговорка о доставке в п. 5–6 решения
  требует правки на основании нового факта, а не предположения.
- `CONTOURS.md` §13 / O-1 получит решение по перечню исходных интеграций CITA —
  первая реальная запись реестра инструментов может вскрыть требования к формату
  описания сервера (например, работу с webhook-каналом или клиентским
  TLS-сертификатом), не предусмотренные сегодняшним нейтральным форматом MITA.
- Определится физическое место хранения реестра интеграций CITA (открытый вопрос
  O-13) — вместе с ним нужно будет закрыть и место хранения реестра инструментов
  CITA, который этот ADR оставляет неназванным.
- Custody секретов фактически переедет в PACT/egress proxy (`allocation.md`
  §2.1) — потребуется сверить, что ни одна запись реестра инструментов CITA не
  начала принимать значение секрета параметром вызова (C-148 `spec.md`).

## Источник

Решение не перенесено из принятого источника — в `second-system/DECISIONS.md`
нет пункта D-00N, посвящённого точке регистрации инструментов CITA; ни `D-001`
—`D-012`, ни `CONTOURS.md`, ни `SPECIFICATION.md` реестр MCP не упоминают вовсе.
Это решение вводится настоящим ADR впервые — источника уровня системы, из
которого оно было бы перенесено, не существует. `docs/spec/spec.md` этого
воркспейса §17.1 (C-140–C-149) и §21 (O-1, O-13) не являются основанием этого
ADR: они формулируют то же решение как **следствие** этого ADR, а не его
источник, и сами помечены [П] («предложено этой спецификацией»), то есть не
имеют более высокого статуса, на который можно было бы опереться. Фактический
материал, на котором реально основано решение, — `agent-infra.md` (§2.3 «что
реально проверено экспериментально», §2.5 «матрица доставки», §5 «MCP-серверы
и права», §5.3 «доставка по клиентам»), `cloud-tech-tasks/.agents/ARCHITECTURE.md`
(§2 «несущие инварианты», инвариант 7; §3.1 «что установлено экспериментом, а
не документацией») и фактическое содержимое
`cloud-tech-tasks/.agents/mcp/registry.json`. Опирается на решения этого же
воркспейса: ADR 0001 (декомпозиция на четыре контура — граница CITA/MITA как
отдельных хранилищ) и ADR 0009 (тот же паттерн «один канонический источник — N
проекций», уже применённый к шаблону карточки сервиса, — здесь применён к
реестру инструментов). Статус — «предложено», не повышен: ни в переписке, ни в
`second-system/DECISIONS.md` использование MCP-реестра как точки регистрации
контрактных инструментов CITA как принятое решение не зафиксировано.
