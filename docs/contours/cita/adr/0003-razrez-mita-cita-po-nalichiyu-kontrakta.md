# Граница MITA/CITA проходит по наличию пригодного контракта, а не по предметной области
- **Статус:** Принято
- **Дата:** 2026-08-08 (формулировка зафиксирована в CONTOURS.md §7.1 в дату
  создания документа; см. хронологию `second-system/DECISIONS.md` §2. Точная дата
  принятия именно этого пункта отдельно от даты создания CONTOURS.md в источниках
  не выделена)
- **Контур:** cita

## Контекст

ADR 0001 фиксирует последствия для CITA от общесистемной декомпозиции на четыре
контура и уже называет критерий разреза MITA/CITA мимоходом, как часть более
широкого решения. Здесь этот критерий — единственный предмет: чем именно определяется,
относится ли конкретная задача к MITA или к CITA, и почему это основание, а не
какое-либо другое.

Наивная альтернатива — резать по предметной области: например, «всё про GetCourse —
в CITA, потому что у автора есть свой gateway (`services/gc-chatium-gateway/`)»,
«всё про Kinescope — в MITA, потому что известны только внутренние эндпоинты
браузера». Источники прямо отклоняют это основание. CONTOURS.md §7.1, дословно:
«Граница проходит по наличию пригодного API у целевой системы, а не по предметной
области.» Формулировка повторена без изменений в arch-vision.md §1.4 и §11 и в
allocation.md §3.3 («граница между нами подвижна и проходит по наличию пригодного
API у целевой системы, а не по предметной области; переезд возможности из одного
контура в другой не меняет имя capability»).

Следствие этого основания — раздел «Что каждый контур обязан сказать про соседей»
(allocation.md §3.3): MITA и CITA обязаны говорить друг о друге буквально этими
словами, а не пересказывать это через предметную область.

Профиль различий MITA/CITA при разрезе по модальности исполнения (CONTOURS.md §7.1,
дословная таблица):

| | MITA | CITA |
|---|---|---|
| Способ | веб-интерфейс, браузер | подготовленная API-интеграция |
| Стоимость | сценарий под каждую цель | интеграция один раз, переиспользуется |
| Хрупкость | ломается при редизайне | ломается при смене версии API |
| Ошибки | неструктурированные | коды и схемы |
| Идемпотентность | как правило отсутствует | как правило достижима |

Разрез по предметной области эту таблицу разрушил бы: одна и та же предметная
область (например, GetCourse) распадается на задачи с разным профилем — то, что
проходит через `gc-chatium-gateway` (подготовленный API), не имеет ничего общего по
стоимости, хрупкости и идемпотентности с тем, что делается через веб-кабинет
GetCourse руками MITA, хотя предметная область одна и та же.

Текущее состояние подтверждает, что разрез по предметной области и без того не
проведён нигде: ни одна из 18 карточек `services/` в MITA не имеет
`type: api`, хотя `templates/service.md` такой тип допускает; единственный
API-материал, добытый самой системой, — ненамеренно наблюдённые изнутри браузера
эндпоинты (`app.kinescope.io/api/entities`, GraphQL-операции Kinescope,
`GET /my/<project>/api/init?perm=1` у Bizon365), а не спроектированная интеграция.
CITA как работающая система сейчас не выполняет ни одной задачи.

## Решение

Критерий отнесения задачи к MITA или к CITA — один: наличие у целевой системы
пригодного опубликованного контракта (API), а не то, к какой предметной области
относится задача.

- Если у целевой системы есть пригодный опубликованный контракт — задача
  адресуется CITA.
- Если пригодного контракта нет и остаётся только веб-интерфейс, спроектированный
  для человека, — задача адресуется MITA.
- «Пригодность» контракта, наблюдённого изнутри браузерной сессии (внутренний,
  не опубликованный эндпоинт), сама по себе не переводит задачу в CITA: раздел
  «Доступ» и порядок использования такого эндпоинта как контракта не описаны
  (открытый вопрос, см. ниже).

Граница подвижна: при появлении у внешнего сервиса опубликованного API та же
возможность переезжает из MITA в CITA без переоткрытия задачи заново — меняется
только выбор исполнителя, который делает диспетчер PACT (CONTOURS.md §7.3,
D-007), а не имя capability и не её постановка. Обратное движение (CITA → MITA
при отзыве или поломке API) в источниках отдельно не рассмотрено, но из того же
основания следует симметрично: критерий тот же, направление переезда не
фиксировано заранее.

Из подвижности границы следует запрет, обязательный к соблюдению обоими
контурами: capability не может кодировать в своём имени способ исполнения
(`invoice.submit`, а не `invoice.submit.via-web` или `invoice.submit.via-api`,
CONTOURS.md §7.3). Иначе переезд возможности между MITA и CITA требовал бы
переписывания политик PACT вместо смены исполнителя в маршруте.

## Последствия

**Положительные**

- Критерий проверяем и не зависит от вкуса или от истории: не «что нам удобнее
  сегодня отнести к CITA», а объективный факт — есть ли у целевой системы
  пригодный опубликованный контракт. Это снимает спор о принадлежности задачи на
  входе.
- Профиль стоимости, хрупкости, вида ошибок и идемпотентности (таблица §7.1)
  становится предсказуемым по одному факту — наличию контракта, — а не требует
  отдельной оценки для каждой предметной области.
- Появление нового API у уже используемого через MITA сервиса не требует
  архитектурной переработки: это операционный переезд capability между
  исполнителями, а не пересмотр разреза контуров.

**Отрицательные / что становится дороже**

- Критерий требует явной, воспроизводимой оценки «пригодности» контракта, а такой
  оценки в источниках нет — CONTOURS.md §13 прямо называет «перечень исходных
  интеграций CITA» открытым вопросом. Без критерия пригодности решение о переезде
  задачи каждый раз принимается вручную, а не по правилу.
- Возникает серая зона: внутренний, не опубликованный, но наблюдаемый эндпоинт
  (Kinescope `app.kinescope.io/api/entities`, Bizon365
  `/my/<project>/api/init?perm=1`) формально не «пригодный опубликованный API» —
  использование его как контракта CITA не санкционировано и не описано (нет схемы
  ошибок, нет гарантии стабильности версии, объект может поменяться без
  предупреждения вендора). Пока это не решено, такие эндпоинты остаются
  наблюдениями MITA, а не материалом для интеграции CITA, что дороже: приходится
  каждый раз заново решать, на какой стороне границы находится конкретный случай.
- Разрез по контракту, а не по предметной области, означает, что одна и та же
  предметная область (например, GetCourse: `services/chatium/` и
  `services/gc-chatium-gateway/`) может одновременно обслуживаться и MITA, и CITA
  по разным задачам — это требует от диспетчера PACT (а не от исполнителя)
  различать задачи внутри одной предметной области по признаку контракта, а не
  маршрутизировать по одному только имени сервиса.
- Раздел «Доступ» в карточках `services/gc-chatium-gateway/` и `services/chatium/`
  не заполнен (TODO), инженерная документация не перенесена из исходного
  Obsidian-vault — до её переноса даже ближайший реальный кандидат в CITA
  формально не проходит проверку «пригодный контракт» по полноте описания.

## Рассмотренные альтернативы

- **Разрез по предметной области** (например, «всё GetCourse — CITA, всё
  Kinescope/Bizon365 — MITA»). Отклонён: разрушает однородность профиля стоимости
  и идемпотентности внутри контура (одна предметная область может иметь и API, и
  веб-интерфейс, эксплуатируемые разными задачами), а профиль (таблица §7.1) —
  единственное, что делает разрез CONTOURS.md §7.1 полезным для планирования
  исполнения.
- **Кодирование модальности в имени capability** (`invoice.submit.via-web` /
  `.via-api`). Отклонена в CONTOURS.md §7.3 (D-007): при подвижной границе это
  привязывает политики PACT к текущей модальности и требует их переписывания при
  каждом переезде возможности между MITA и CITA, вместо изменения одного поля
  «исполнитель» в маршруте.
- **Разрез по формальному признаку «есть ли эндпоинт вообще», включая
  ненамеренно наблюдённые внутренние эндпоинты браузера.** Источники этого не
  утверждают напрямую («пригодный» — не «любой обнаруженный»), и допущение такой
  альтернативы без решения обесценило бы разницу профилей MITA/CITA (наблюдённый
  внутренний эндпоинт не даёт структурированных ошибок и гарантии стабильности,
  которые таблица §7.1 приписывает CITA). Не принята и не отклонена явно —
  оставлена открытым вопросом ниже.

## Условия пересмотра

- Появление явного критерия «пригодности» контракта (документация, стабильность
  версии, наличие схемы ошибок, публичность vs. наблюдённый внутренний эндпоинт) —
  предмет отдельного решения, закрывающего пункт CONTOURS.md §13 «перечень
  исходных интеграций CITA»; после его появления этот ADR должен быть дополнен
  ссылкой, а не переписан.
- Если для интеграции с наблюдённым внутренним эндпоинтом (Kinescope, Bizon365)
  будет принято отдельное решение о его использовании как контракта CITA —
  требуется зафиксировать, при каких условиях внутренний эндпоинт признаётся
  «пригодным», иначе граница из этого ADR становится непроверяемой на практике.
- Если на опыте эксплуатации выяснится, что различие профилей (таблица §7.1)
  не подтверждается для какого-то класса задач (например, идемпотентность API
  оказывается недостижима на практике) — это основание пересмотреть не сам
  критерий разреза, а таблицу профиля, на которую критерий опирается.
