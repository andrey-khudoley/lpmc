# Как сегодня человек ставит задачи и получает результат

Статус документа: docs-as-state, фиксация факта на дату 2026-08-09. Здесь описан
только фактический путь постановки задачи и получения результата, как он
существует сегодня. Это не проекция на то, как должно быть по архитектуре —
целевое устройство диалогового пути (маршрут ответа, egress-проверка,
разделение канал/диалог/исполнение) раскрыто в `docs/spec/spec.md`; здесь оно
не пересказывается.

Источники: `/home/agent/workspaces/cloud-tech-tasks/.agents/commands/new-task.md`,
`.agents/commands/task.md`, `.agents/agents/qualifier.md`,
`.agents/agents/task-executor.md`, `.agents/skills/intake/SKILL.md`,
`.agents/skills/execute-task/SKILL.md`, `templates/inbox-item.md`,
`ROADMAP.md` (этап 1) — все внутри репозитория MITA
`/home/agent/workspaces/cloud-tech-tasks`.

---

## 0. Главный факт: посредника нет

Пользователь и исполнитель — один и тот же сеанс. Постановка задачи,
уточняющие вопросы, выполнение, проверка результата и показ ответа происходят
в одной непрерывной интерактивной сессии Claude Code или Codex CLI внутри
репозитория `/home/agent/workspaces/cloud-tech-tasks` (репозиторий MITA —
Manual Interaction Task Agent). Отдельного диалогового контура (LINA),
арбитра полномочий (PACT) и egress-проверки результата перед показом
пользователю не существует. Всё, что описано ниже, — собственность MITA, а не
LINA: в исходниках MITA слова `LINA`, `PACT`, `CITA` не встречаются ни разу,
сопоставление с контурами — инженерная реконструкция, а не факт из кода.

Это соответствует этапу 1 («ручной прототип», текущий) дорожной карты MITA
(`ROADMAP.md`): «Задачи передаются вручную: пользователь вставляет текст
постановки агенту. Агент запускается вручную командами вида «разбери inbox»,
«возьми задачу X»».

## 1. Постановка задачи: команда `/new-task`

Точка входа — файл `.agents/commands/new-task.md`. Frontmatter:

```yaml
description: Принять постановку от менеджера и завести карточку задачи у клиента
argument-hint: '<client>: текст постановки (или путь к файлу из tasks/inbox/)'
disable-model-invocation: true
```

`disable-model-invocation: true` означает: команда исполняется только тогда,
когда её произнёс пользователь явным текстом вида `/new-task <аргументы>` —
сам агент не может вызвать её по собственному решению как часть более
широкого плана. Для клиента Codex CLI это правило продублировано отдельно
(override-профиль `AGENTS.override.md`, раздел «Команды репозитория»): любой
текст, начинающийся с `/`, но не найденный в таблице команд, — обычное
сообщение, не команда; таблица команд там же перечисляет `/new-task` и
`/task` как единственные две.

Тело команды (без пересказа политики, дословный алгоритм):

1. Пользователь передаёт текст постановки как `$ARGUMENTS`.
2. Главный агент делегирует разбор роли `qualifier` (файл
   `.agents/agents/qualifier.md`), передавая исходный текст постановки без
   пересказа и без домысливания; если клиент указан явно — передаёт и его.
3. Роль `qualifier` работает по процедуре `.agents/skills/intake/SKILL.md`:
   определяет владельца по `clients/INDEX.md` / `projects/INDEX.md` /
   `internal/INDEX.md` (при неоднозначности — не гадает, а возвращает список
   кандидатов и вопрос), создаёт карточку
   `<root>/<owner>/tasks/active/<YYYY-MM-DD-slug>/task.md`, сохраняет исходный
   текст менеджера дословно в разделе карточки «Исходное сообщение»,
   формулирует Definition of Done, проверяет карточки упомянутых сервисов;
   при нехватке информации выставляет `status: blocked` и формулирует вопросы
   так, чтобы их можно было переслать менеджеру как есть.
4. Получив ответ роли, главный агент показывает пользователю результат:
   - если карточка создана — путь, клиента, DoD и открытые вопросы;
   - если клиент не определился — кандидатов и сам задаёт пользователю
     вопрос (делегированная роль `qualifier` этого сделать не может — общая
     политика MITA прямо запрещает делегированной роли обращаться к
     пользователю напрямую: всё неясное она обязана вернуть в своём ответе как
     вопрос);
   - если карточка создана со `status: blocked` — чего не хватает, готовым к
     пересылке менеджеру текстом.

Роль `qualifier` (`.agents/agents/qualifier.md`): `profile: fast`, набор
инструментов — `Read, Grep, Glob, Write, Edit, Bash`, инструментов Playwright
у неё нет — задачу она только заводит, не выполняет.

Постановка может попасть в систему и не через команду напрямую в чат, а
файлом в `tasks/inbox/YYYY-MM-DD-HHMM-<source>.md` по шаблону
`templates/inbox-item.md` (frontmatter `received`, `source`
(`manual | telegram | api`), `chat`, `manager`); тогда `intake` разбирает
именно этот файл. На практике сегодня (этап 1) пользователь почти всегда
передаёт текст агенту сразу в диалоге, и `intake` создаёт карточку задачи,
минуя `tasks/inbox/` вовсе. Значение `source: telegram` в шаблоне
присутствует, но канал Telegram не подключён и этим значением фактически
никогда не пользуются; поле `chat` (будущий маршрут ответа) сегодня нигде не
используется — ответ агент формирует и показывает в той же интерактивной
сессии, а не доставляет по внешнему адресу.

## 2. Выполнение задачи: команда `/task`

Точка входа — `.agents/commands/task.md`. Frontmatter:

```yaml
description: Выполнить задачу по её карточке — от плана до верификации DoD и отчёта
argument-hint: '<client>/<YYYY-MM-DD-slug> [уточнения]'
disable-model-invocation: true
```

Тело команды дословно:

1. Первый токен аргументов — глобальная ссылка на задачу вида
   `<client>/<YYYY-MM-DD-slug>`; остальное — уточнения пользователя.
2. Главный агент находит карточку:
   `<root>/<owner>/tasks/active/<YYYY-MM-DD-slug>/task.md` (`<root>` —
   `clients/`, `projects/` или `internal/`); если её там нет — проверяет
   `archive/` и `inbox/` того же владельца и сообщает пользователю, что
   нашёл, вместо того чтобы угадывать.
3. Делегирует выполнение роли `task-executor` (`.agents/agents/task-executor.md`),
   передавая путь к карточке и уточнения пользователя дословно.
4. Показывает пользователю: итоговый статус, результат проверки по каждому
   пункту DoD и готовый текст отчёта для менеджера; если роль вернула
   `blocked` — вопросы в виде, пригодном для пересылки менеджеру как есть.

В самой команде явно зафиксировано: «Эта команда меняет содержимое
репозитория и коммитит — она запускается только по явной просьбе
пользователя», то есть выполнение задачи никогда не стартует само по
инициативе модели.

## 3. Кто формирует отчёт и кто его проверяет — никто, кроме самой MITA

Роль `task-executor` (`.agents/agents/task-executor.md`): инструменты `Read,
Write, Edit, Grep, Glob, Bash, ToolSearch, mcp__playwright__*`, `profile:
deep`. Работает по процедуре `.agents/skills/execute-task/SKILL.md`:

1. Читает карточку задачи целиком, собирает контекст (`instructions.md`
   владельца, карточки затронутых сервисов, релевантные плейбуки, свежие
   заметки).
2. Записывает план в раздел карточки «План».
3. Выполняет задачу — доступ к веб-сервисам через Playwright со
   storage-state, секреты берёт из `.secrets/` по именам, указанным в
   карточке сервиса; ключевые шаги фиксирует в разделе карточки «Журнал».
4. **Верификация**: проходит каждый пункт Definition of Done и проверяет его
   фактически (обычно скриншотом через Playwright) — пункт без фактической
   проверки не отмечается выполненным.
5. **Отчёт**: заполняет раздел карточки «Отчёт» — готовый ответ менеджеру
   (что сделано, где посмотреть, что важно знать, без внутренней кухни и
   путей к файлам).
6. Переводит `status: done`, переносит каталог задачи в
   `<root>/<owner>/tasks/archive/<год>/`, коммитит.

Формат ответа роли пользователю (по `task-executor.md`): статус задачи, что
сделано, результат верификации по каждому пункту DoD, готовый текст отчёта
для менеджера (или вопросы, если `blocked`).

Ключевой факт: **тот же исполнитель, что выполнял задачу, сам верифицирует
DoD и сам формулирует отчёт**. Никакой независимой проверки результата между
формированием отчёта и его показом пользователю нет — ни автоматической, ни
через отдельный компонент. Раздел «Отчёт» карточки — это конечный текст,
который команда `/task` показывает пользователю без промежуточной инстанции.
Маскировка значений секретов в журналах и отчётах — тоже гигиена самой MITA
(правило политики), а не проверка внешним контролёром.

## 4. Что отсутствует — прямо, без обиняков

- **Посредника между постановкой и исполнением нет.** Команды `/new-task` и
  `/task` вызывает тот же пользователь в той же сессии, где потом получает
  результат; отдельного диалогового контура (LINA), который бы принимал
  запрос, доводил его до полноты и только затем передавал дальше, не
  существует.
- **Egress-проверки результата не существует.** Отчёт, сформированный
  `task-executor`, идёт пользователю напрямую; никакой отдельный компонент не
  проверяет его перед показом (в том числе на утечку значений секретов —
  единственная защита сегодня это дисциплина самой MITA: «запрещено выводить
  значения секретов в логи, отчёты, заметки, журналы, коммиты», без
  независимого контролёра).
- **Отдельного канала доставки нет.** Ответ появляется как текст в той же
  интерактивной сессии Claude Code / Codex CLI, а не в мессенджере или
  веб-чате; поле `chat` в `templates/inbox-item.md` для маршрута ответа
  заведено, но не используется — присвоить ответу внешний адрес доставки
  сегодня нечем.
- **Реестра задач и полномочий отдельно от самой MITA нет.** Роль
  `qualifier` определяет владельца и заводит карточку сама, без подтверждения
  чьей-либо политикой снаружи; кто разрешил задачу и на каких основаниях — не
  фиксируется отдельно от факта существования карточки в `tasks/active/`.
- **Эталонного файла-шаблона карточки задачи `templates/task.md` в этом
  документе не рассматривается** — исследовательский черновик этого участка
  ошибочно утверждал, что такого файла нет в `templates/`. Это неверно: файл
  `/home/agent/workspaces/cloud-tech-tasks/templates/task.md` физически
  существует; проверка и разбор — `docs/qualifier-and-intake.md` §4. Карточка
  задачи фактически создаётся `intake` по полям, перечисленным в этом
  документе и в других файлах канона.

Все перечисленные механизмы, включая их отсутствие, целиком относятся к
устройству MITA. Как это должно быть устроено в целевой архитектуре —
маршрут ответа, разделение диалога и исполнения, egress-проверка результата
перед показом человеку, реестр задач и полномочий вне MITA — раскрыто в
`docs/spec/spec.md`; здесь этот вопрос намеренно не пересказывается.
