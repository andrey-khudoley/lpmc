# Действующие конвенции постановки и отчёта (принадлежат MITA)

Статус документа: docs-as-state, фиксация факта на дату 2026-08-09. Здесь описаны
только те конвенции MITA, что относятся к разговору с человеком: как выглядит сырая
постановка, какие правила действуют при её приёме и как оформляется отчёт. Все они
сегодня закреплены в репозитории `/home/agent/workspaces/cloud-tech-tasks`, действуют
только внутри него и **принадлежат MITA**, а не LINA. LINA как работающая система не
существует; ничего из описанного ниже физически ей не принадлежит. Эти конвенции
действуют в MITA сегодня; разбор их наследования между контурами — `allocation.md`
§5 (см. §7 этого документа), целевое разграничение того, что из этого станет функцией
LINA, а что — диспетчера PACT, — `docs/spec/spec.md` §22, здесь оно не пересказывается.

## 1. Поля сырой постановки

Постановка задачи от менеджера/пользователя кладётся (или на этапе 1 — просто
передаётся текстом в диалоге) как файл `<root>/<owner>/tasks/inbox/YYYY-MM-DD-HHMM-<source>.md`
по шаблону `templates/inbox-item.md`. Frontmatter:

```yaml
received: YYYY-MM-DDTHH:MM
source: manual        # manual | telegram | api
chat: ""              # идентификатор чата, если известен
manager: ""
```

Тело файла — дословный текст постановки, без обработки. Поле `source` фиксирует канал,
которым постановка попала в систему; на сегодня фактически используется только
`manual` — пользователь передаёт текст агенту напрямую в интерактивной сессии Claude
Code/Codex CLI, зачастую минуя сам файл `inbox/` (карточка задачи заводится сразу).
Значение `source: telegram` объявлено в формате шаблона как задел на будущее (этап 2
ROADMAP), но ни разу не создавалось — Telegram-бот не развёрнут. Поле `chat` — тем же
образом задел на маршрут доставки ответа во внешний канал, сегодня без потребителя.

После обработки скиллом `intake` файл `inbox/` удаляется, а его текст переносится
дословно в раздел «Исходное сообщение» карточки задачи (`templates/task.md`).

## 2. «Задач без владельца не бывает»

Задача не может существовать без владельца — это жёсткое правило. Владелец
определяется скиллом `intake` по контексту постановки (упомянутые сервисы, имя
менеджера, канал/чат), сверкой с `clients/INDEX.md`, `projects/INDEX.md`,
`internal/INDEX.md`. Карточка задачи всегда создаётся внутри каталога владельца
(`<root>/<owner>/tasks/active/...`) — «задачи в никуда» конвенция не допускает.

## 3. «При неоднозначности — спросить, а не угадать»

Если владелец постановки не определяется однозначно, это вопрос к пользователю, а не
повод создать задачу или молча выбрать вариант. То же правило действует и при заведении
нового владельца (скилл `add-owner`): постоянное сотрудничество → `clients/`, разовая
работа → `projects/`; при неоднозначности — спросить, потому что перенос владельца
между корнями дешёвый, а неверная классификация тихо искажает все последующие срезы «по
клиентам».

Важная деталь механизма: **задавать вопрос пользователю может только главный агент
сессии**, не делегированная роль. Общая политика MITA (`.agents/policy/common/13-agent-toolkit.md`)
прямо запрещает делегированной роли обращаться к пользователю напрямую — всё неясное
она обязана вернуть в своём ответе как вопросы, а карточку пометить `status: blocked`.
Роль `qualifier` этому правилу подчиняется: команда `.agents/commands/new-task.md`
явно перекладывает финальный вопрос пользователю на вызвавшего её агента. Подробнее
этот механизм разобран в `docs/qualifier-and-intake.md`.

## 4. Клиент ≠ проект ≠ внутренний контур; глобально уникальные слаги

Вся работа организована вокруг понятия **владелец** — сущности, для которой ведётся
отдельный набор задач/сервисов/знаний. Владельцы делятся на три непересекающихся корня:

| Корень | Смысл | Кто там сейчас |
|---|---|---|
| `clients/` | постоянное сотрудничество (ретейнер) — таких ровно двое | `neso`, `larina` |
| `projects/` | разовая/проектная работа: сделка, пилот, лид, законченный запуск | 18 каталогов |
| `internal/` | собственный аккаунт исполнителя, не заказчик, технически устроен как «клиент» | `internal` |

Разграничение словаря пользователя жёсткое: «мои клиенты» / «все клиенты» — это ровно
`neso` и `larina`, а не обход всех 20+ владельцев. Обход всех трёх корней делается
только по явному «везде»/«по всей системе» или для системных задач. Ошибочное чтение
«клиенты» как «все владельцы» прямо названо в политике типовой ошибкой агента.

Слаг владельца **уникален глобально** среди всех трёх корней (`neso`, `sevinch`,
`internal` и т.п. не могут совпасть между корнями) — поэтому глобальная ссылка на
задачу пишется как `<slug>/YYYY-MM-DD-<slug задачи>` без указания корня. Во frontmatter
карточек поле по историческим причинам всё ещё называется `client:` и хранит слаг
владельца независимо от того, в каком корне он на самом деле лежит — переименовывать
поле во всех существующих карточках задним числом не стали.

## 5. Отчёт должен быть готов к пересылке менеджеру без правки

Требование к результату сквозное и повторяется на нескольких уровнях:

- Карточка задачи (`templates/task.md`) содержит отдельный раздел «Отчёт»,
  заполняемый по завершении **в формате готового ответа менеджеру** — не служебной
  записи для внутреннего чтения.
- Формат ответа роли `qualifier` (файл `.agents/agents/qualifier.md`) зафиксирован
  дословно: «id созданной карточки и путь к ней (или причина, почему не создана),
  клиент, краткая постановка, DoD, открытые вопросы — сформулированные так, чтобы их
  можно было переслать менеджеру как есть».
- Definition of Done в карточке задачи требует только фактически проверяемых
  критериев («в сервисе X на странице Y отображается Z», не «настроить интеграцию»);
  пункт без фактической проверки (обычно — через Playwright) не отмечается
  выполненным. Это прямое следствие того же требования: отчёт, отправляемый
  менеджеру, не может содержать формулировок «должно работать по логике».

Это требование сегодня выполняет сама MITA целиком — она же формулирует отчёт, она же
его проверяет; независимой проверки результата «снаружи» (egress-проверки) не
существует.

## 6. Язык: содержимое русское, слаги — английский kebab-case

Содержимое файлов (текст постановки, карточек, отчётов, заметок, журналов) — русский
язык. Имена файлов, каталогов и слаги (владельцев, сервисов, задач, плейбуков) —
английские, kebab-case, без пробелов: `neso`, `larina`, `internal`,
`gc-chatium-gateway`, `dmitry-bernadskiy`. Даты — `YYYY-MM-DD`, время — `HHMM`. Текущую
дату и время положено брать из системы (команда `date`), а не из памяти модели.

## 7. Принадлежность и статус наследования

Все конвенции этого документа сегодня действуют **только внутри репозитория MITA**
(`/home/agent/workspaces/cloud-tech-tasks`) и принадлежат ей. Они не являются частью
LINA — контура, который сегодня не существует как работающая система. Разбор
наследования этих конвенций между контурами — `allocation.md` §5; целевое
разграничение, в том числе какие поля `templates/inbox-item.md` и `templates/task.md`
использует напрямую LINA, а какие достаются PACT (в частности решение о легитимности
владельца и egress-проверка отчёта перед доставкой в диалог), — вопрос спецификации
(`docs/spec/spec.md` §22), не этого документа.
