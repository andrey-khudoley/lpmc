# Роль qualifier и скилл intake: что это и почему это не LINA

Статус документа: docs-as-state, фиксация факта на дату 2026-08-09. Здесь описано
только то, что сегодня физически существует в репозитории MITA
(`/home/agent/workspaces/cloud-tech-tasks`) и связано с приёмом сырой постановки
задачи. LINA как работающая система не существует; ничего из описанного ниже ей
не принадлежит — это собственность MITA, разобранная здесь ровно настолько,
насколько нужно, чтобы объяснить, почему она не годится в прообраз контура целиком.
Целевое разграничение решений между LINA и диспетчером PACT раскрыто в
`docs/spec/spec.md` (см. также `docs/adr/0008-granica-s-dispetcherom-pact-i-sudba-qualifier.md`,
статус «Предложено») — здесь оно не пересказывается.

Источники: `.agents/agents/qualifier.md`, `.agents/skills/intake/SKILL.md`,
`templates/inbox-item.md`, `templates/task.md`, `.agents/policy/common/13-agent-toolkit.md`,
`.agents/commands/new-task.md`, `ROADMAP.md` — все внутри
`/home/agent/workspaces/cloud-tech-tasks`; исследовательские отчёты
`tasks-agent-rules.md`, `tasks-operating-model.md` и разбор
`/tmp/vds-kz-pipeline/research/allocation.md` §4.2 и §7 п.1.

## 1. Роль `qualifier`: что это фактически

Файл `.agents/agents/qualifier.md`. Frontmatter:

```yaml
name: qualifier
description: Квалификатор постановок. Используй для разбора сырой постановки
  менеджера или файлов из {clients,projects,internal}/*/tasks/inbox/ —
  превращает текст в карточку задачи, не занимая контекст главного агента.
  На этапе 2 будет вызываться автоматически для постановок из Telegram.
  Не выполняет задачи — только квалифицирует.
tools: Read, Grep, Glob, Write, Edit, Bash
profile: fast
```

Набор `tools` не включает Playwright (браузер) и `ToolSearch` — роль работает
только с текстом и файловой системой репозитория, никаких действий во внешних
системах не совершает. `profile: fast` — облегчённый профиль запуска (в
противовес `profile: deep` у `task-executor`, которая реально выполняет задачи).

Тело роли (дословно, без пересказа политики — политику делегированная роль
получает целиком отдельно, см. §3): «Ты — квалификатор постановок в системе
cloud-tech-tasks: превращаешь сырую постановку в карточку задачи, не выполняя
её. Работай по `.agents/skills/intake/SKILL.md`». То есть роль `qualifier` —
это делегируемая обёртка вокруг процедуры `intake`, а не самостоятельный
алгоритм: вся содержательная логика описана в скилле (§2), роль лишь даёт этой
процедуре тулинг и формат ответа.

**Формат ответа**, зафиксированный в самом файле роли: «id созданной карточки
и путь к ней (или причина, почему не создана), клиент, краткая постановка,
DoD, открытые вопросы — сформулированные так, чтобы их можно было переслать
менеджеру как есть». Это прямое требование к результату — текст, готовый к
пересылке во внешний чат без редактирования, включая формулировку вопросов.

## 2. Скилл `intake`: процедура нормализации

Файл `.agents/skills/intake/SKILL.md`. Используется в двух случаях: когда
разбор ведёт делегированная роль `qualifier`, и когда постановку заводит сам
главный агент (без делегирования) — это одна и та же процедура, вызываемая
по-разному (`.agents/policy/common/13-agent-toolkit.md`: «скилл — когда
работаешь сам, роль — когда делегируешь»).

Шаги процедуры (дословно по файлу):

1. **Определить владельца** по контексту (упомянутые сервисы, имя менеджера,
   чат), сверяясь с `clients/INDEX.md`, `projects/INDEX.md`, `internal/INDEX.md`.
   Если не определяется однозначно — спросить пользователя, не гадать. Если
   владельца в системе ещё нет — скилл `add-owner`.
2. **Создать карточку** `<root>/<owner>/tasks/active/<id>/task.md` по
   `templates/task.md`, id = `YYYY-MM-DD-<slug>`. Исходный текст менеджера —
   дословно в раздел «Исходное сообщение»; нормализованная формулировка — в
   «Постановку».
3. **Сформулировать Definition of Done** в карточке.
4. **Проверить сервисы**: каждый упомянутый сервис должен иметь карточку в
   `<root>/<owner>/services/` или `services/`; незнакомый сервис — создать
   заготовку по `templates/service.md` с пометкой `TODO: заполнить`.
5. **Открытые вопросы**: не хватает критичной информации — `status: blocked`,
   вопросы в карточке и в ответе пользователю в виде, пригодном для пересылки
   менеджеру как есть; иначе `status: active`.
6. **Журнал**: запись журнала сессии (`skill: intake`).
7. **Коммит**: `tasks: accept <client>/<id>`.
8. **Ответ пользователю**: id задачи, клиент, краткая постановка, DoD, вопросы
   (если есть).

Если постановка пришла файлом из `<root>/<owner>/tasks/inbox/` — после
создания карточки файл удаляется (содержимое уже сохранено в карточке). Если
в одном сообщении несколько задач — отдельная карточка на каждую.

## 3. Шаблон `templates/inbox-item.md`

Файл присутствует в репозитории, поля frontmatter:

```yaml
received: YYYY-MM-DDTHH:MM
source: manual        # manual | telegram | api
chat: ""              # идентификатор чата, если известен
manager: ""
```

Тело файла — текст постановки дословно, без обработки. Комментарий в самом
шаблоне поясняет конвенцию: файл кладётся в `<root>/<owner>/tasks/inbox/` с
именем `YYYY-MM-DD-HHMM-<source>.md`; на этапе 1 пользователь чаще передаёт
текст агенту напрямую в диалоге — тогда `intake` создаёт карточку сразу,
минуя `inbox/`; после обработки скиллом `intake` inbox-файл удаляется.

Поле `chat` — задел на будущий маршрут ответа (адрес доставки во внешнем
канале). Поле `source: telegram` — задел на подключение Telegram. Оба поля
сегодня существуют только как объявленная возможность формата, без
реализованного потребителя (см. §5).

## 4. Уточнение по `templates/task.md`

Исследовательские материалы, на которых основан этот участок работы
(`tasks-agent-rules.md`, `tasks-operating-model.md`, `allocation.md` §7 п.1),
единогласно утверждают, что файла `templates/task.md` в каталоге `templates/`
не существует, хотя на него ссылаются `CLAUDE.md`,
`.agents/policy/common/01-repository-layout.md` и сам `.agents/skills/intake/SKILL.md` —
и характеризуют это как битую ссылку самого канона MITA. Тот же вывод
воспроизведён и в другом файле этого участка, `docs/dialog-today.md` (раздел 4).

При подготовке этого документа файл был прочитан напрямую: **`templates/task.md`
физически присутствует** в `/home/agent/workspaces/cloud-tech-tasks/templates/task.md`,
закоммичен в git с 2026-07-30 (`403a46c`) и содержит полный набор полей карточки
задачи (`id`, `title`, `client`, `status`, `priority`, `source`, `manager`,
`created`, `updated`, `services`) и секции «Постановка», «Исходное сообщение»,
«Definition of Done», «Открытые вопросы», «План», «Журнал», «Отчёт» — то есть
именно те поля и разделы, которые перечисляет процедура `intake` в §2. Ссылка
`intake` на `templates/task.md` рабочая, а не битая.

Это расхождение с исследовательскими материалами зафиксировано здесь как факт
прямой проверки на дату этого документа; `docs/dialog-today.md` §4 исправлен
той же правкой и ссылается сюда.

## 5. Почему `qualifier`/`intake` — не прообраз контура LINA

Три конкретных факта, каждый — самостоятельное основание:

1. **Общая политика MITA запрещает делегированной роли обращаться к
   пользователю напрямую.** Дословно, `.agents/policy/common/13-agent-toolkit.md`:
   «Делегированная роль не обращается к пользователю напрямую. Всё неясное она
   возвращает в своём ответе как вопросы, а незавершённые карточки помечает
   `status: blocked`». Роль `qualifier` — делегированная роль, значит на неё
   это правило распространяется прямо. LINA же по определению обязана быть
   единственной, кто ведёт диалог с человеком — правило прямо противоположно
   тому, что требуется от контура LINA.

2. **Вопрос пользователю задаёт главный агент, а не `qualifier`.** Команда
   `.agents/commands/new-task.md`, которой пользователь фактически ставит
   задачу, явно перекладывает эту обязанность: «если клиент не определился —
   покажи кандидатов и задай пользователю вопрос сам: делегированная роль
   этого сделать не может». То есть даже единственный канал уточнения,
   которым обладает эта функциональность, физически не принадлежит
   `qualifier` — он принадлежит главному агенту сессии (самой MITA), которая
   в целевой архитектуре не совпадает ни с LINA, ни с диспетчером PACT.

3. **Значение `source: telegram` фактически не используется.** Поле
   объявлено в шаблоне `templates/inbox-item.md` (§3) и упомянуто в
   `description` роли `qualifier` как план этапа 2 («На этапе 2 будет
   вызываться автоматически для постановок из Telegram», то же в `ROADMAP.md`,
   раздел «Этап 2 — агент-квалификатор + Telegram»). Telegram-бот не
   развёрнут, канала приёма постановок из мессенджера нет, и постановка с
   `source: telegram` сегодня в системе ни разу фактически не создавалась —
   единственный работающий путь: пользователь передаёт текст агенту прямо в
   интерактивной сессии Claude Code / Codex CLI, минуя `tasks/inbox/` вовсе.

Дополнительно, по функции (не факт, а характер задачи): `qualifier`/`intake`
одновременно решает и «хватает ли информации, чтобы вообще пойти дальше», и
«к какому классу относится задача, кто её исполнитель» — то есть смешивает
то, что в целевой архитектуре разнесено по разным контурам доверия (LINA и
диспетчер PACT). Это отдельный открытый вопрос архитектуры, а не факт о
сегодняшнем состоянии; он разобран в `docs/adr/0008-granica-s-dispetcherom-pact-i-sudba-qualifier.md`
(статус «Предложено») и здесь не пересказывается.

## 6. Вывод

`qualifier` и `intake` — сегодня одна связная функция внутри MITA: превратить
сырой текст постановки в карточку задачи с DoD и (если нужно) вопросами,
пригодными к пересылке менеджеру без правки. Это ближайший существующий
аналог одной из функций LINA — «довести запрос до полноты» — но не прообраз
контура целиком: политика MITA прямо запрещает делегированной роли говорить с
пользователем, фактически этим занимается главный агент сессии, а
задел на Telegram (`source: telegram`) объявлен в формате, но не реализован и
не задействован ни разу. Каким образом эта функциональность в итоге разойдётся
между LINA и диспетчером PACT — вопрос спецификации, не этого документа.
