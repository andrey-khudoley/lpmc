## Контекст

`SPECIFICATION.md` §5.1 определяет брокер как центральную интеграционную шину,
используемую в обе стороны: «от внешнего канала к квалификатору и агенту» и «от
квалификатора или агента обратно к внешнему каналу». Для каждого внешнего канала
(Telegram, Max, веб-интерфейс) нужен компонент, который граничит с этим каналом с обеих
сторон — и на приёме, и на отправке.

`SPECIFICATION.md` §5.2, «Канальные адаптеры двунаправленные» (дословно): «Для каждого
внешнего канала существует логически единый адаптер, который: принимает входящие
сообщения; публикует сырые события; читает адресованные его каналу исходящие события;
отправляет сообщения через API канала; публикует результат доставки. Отдельный общий
`Outbound Router` не предусматривается.»

Термин `Outbound Router` в документе больше нигде не определяется и не всплывает как
рассмотренный и отклонённый компонент с отдельным обоснованием — фраза «не
предусматривается» в §5.2 является единственным местом, где эта возможность вообще
упомянута. Альтернативная архитектура (общий сервис, который читает все исходящие
события системы и рассылает их по каналам) в источнике не описана и не сопоставлена с
принятым вариантом; решение сформулировано как констатация, а не как результат
сравнения.

Конкретизация того же решения — §7.1–7.3, контракты трёх адаптеров:

- **Telegram Adapter** (§7.1): принимать и проверять webhook/update; устранять дубликаты
  по идентификатору update/message; создавать или разрешать `reply_route`; сохранять
  большие вложения; публиковать `message.raw.telegram.v1`; читать `outbound.telegram.v1`;
  отправлять сообщение; публиковать `message.delivery.succeeded.v1` или
  `message.delivery.failed.v1`.
- **Max Adapter** (§7.2): «Имеет тот же контракт, что Telegram Adapter, но реализует API
  и особенности Max. Публикует `message.raw.max.v1` и читает `outbound.max.v1`.»
- **Web Adapter** (§7.3): аутентифицировать пользователя веб-интерфейса; принимать
  сообщения и вложения; публиковать `message.raw.web.v1`; читать `outbound.web.v1`;
  доставлять ответы через WebSocket, SSE или периодический опрос; публиковать состояние
  доставки, когда оно определимо.

Все три контракта повторяют одну и ту же форму: приём + публикация сырого события на
входе, чтение своего исходящего топика + отправка + публикация результата доставки на
выходе. Ни один из трёх не читает чужой исходящий топик и не публикует в чужой.

Усиление того же решения — §11, «Адресация и reply route», инварианты 4 и 5 (дословно):
«4. Канальный адаптер читает только топик собственного канала. 5. Адаптер дополнительно
проверяет свой `adapter_id` перед доставкой.» Это те же границы, что и в §5.2, но
сформулированные как проверка на этапе доставки, а не только как разделение обязанностей
на этапе проектирования: адаптеру запрещено доставлять чужое сообщение, даже если оно
почему-то оказалось в доступном ему потоке.

Решение закреплено как системный инвариант в `SPECIFICATION.md` §23 (пункты 2–3 из
16, входят в исходную десятку, не в добавленные из `CONTOURS.md`): «2. Канальный адаптер
двунаправленный и сам доставляет адресованные его каналу события. 3. Отдельного общего
Outbound Router нет.»

Физическая декомпозиция (§20) продолжает ту же линию на уровне развёртывания: внутри
каждого канального адаптера рекомендуется два независимо масштабируемых обработчика
(`inbound webhook/session handler` и `outbound event consumer`), «остающихся частями
одного логического адаптера» с общим хранилищем `endpoint mapping` и `delivery ledger`.
То есть даже разделение на два процесса ради масштабирования не создаёт отдельного
общесистемного маршрутизатора — оба обработчика принадлежат одному адаптеру одного
канала.

Сегодня решение не реализовано ни в каком виде: ни один канальный адаптер не развёрнут,
Telegram-бот не создан, веб-чат отсутствует, Max не используется, брокера событий нет.
Диалог с человеком сейчас ведёт напрямую MITA в интерактивной сессии Claude Code / Codex
CLI, минуя и адаптеры, и брокер (`allocation.md` §2.5).

## Решение

LINA реализует канальный слой как набор независимых двунаправленных адаптеров, по одному
на канал (Telegram, Max, веб-интерфейс, при появлении — другие). Каждый адаптер
самостоятельно закрывает полный цикл своего канала:

1. принимает входящее сообщение через специфичный для канала протокол (webhook, сессия,
   long polling);
2. публикует сырое событие в топик, специфичный для канала (`message.raw.<channel>.v1`);
3. читает исходящие события только из топика своего канала (`outbound.<channel>.v1`) и
   не подписывается на исходящие топики других каналов;
4. проверяет собственный `adapter_id` перед доставкой (§11, инв. 5) — вне зависимости от
   того, что событие уже пришло из «правильного» топика;
5. отправляет сообщение через API канала;
6. публикует результат доставки (`message.delivery.succeeded.v1` /
   `message.delivery.failed.v1`).

Общего компонента, который читал бы все исходящие события системы и распределял их по
каналам («Outbound Router»), не существует и не проектируется. Маршрутизация «какой
канал доставляет это сообщение» решается не диспетчеризацией внутри общего сервиса, а
топологией брокера: каждый канал имеет собственный исходящий топик, и только адаптер
этого канала на него подписан.

## Последствия

**Положительные.**
- Изоляция отказа по каналу: сбой, перегрузка или деградация Telegram Adapter не
  затрагивают доставку в Max или веб-интерфейс — нет общего компонента, падение которого
  останавливает исходящий трафик сразу всех каналов.
- Меньше привилегированных компонентов: не появляется сервис с доступом на чтение ко
  всем исходящим топикам системы сразу — это уменьшает поверхность, которую нужно
  защищать и проверять при egress-аудите PACT.
- Симметрия входа и выхода одного канала: команда, добавляющая новый канал, реализует
  один контракт целиком (приём + отправка), а не согласовывает изменения в двух разных
  местах — своём адаптере на входе и общем роутере на выходе.
- Соответствует рекомендованной физической декомпозиции (§20): масштабирование входящего
  и исходящего обработчика канала независимо друг от друга не требует выделения
  дополнительного сетевого компонента с собственной моделью надёжности.

**Отрицательные / что становится дороже.**
- Сквозная исходящая политика (глобальный rate limit, единый DLQ для всех недоставленных
  сообщений, общая логика ретраев) не может быть реализована один раз в одном месте —
  её придётся либо дублировать в каждом адаптере, либо выносить в разделяемую библиотеку,
  за поведенческой идентичностью которой между Telegram/Max/Web придётся следить отдельно.
- Согласованность имён исходящих топиков становится частью контракта, на который нет
  подстраховки в виде маршрутизирующего слоя: расхождение имён между топологией §8 и
  контрактами §10 (`REVIEW-FINDINGS.md` §4.1, статус «открыто») в отсутствие общего
  роутера будет молча приводить к тому, что адаптер не находит свой топик, а не
  диагностироваться в одном месте.
- Модель деградации при недоступности брокера не определена (`REVIEW-FINDINGS.md` §5.2,
  статус «открыто») и должна решаться на уровне каждого адаптера отдельно: пример из
  источника — при недоступности брокера адаптер Telegram либо не подтверждает webhook
  (риск дублей от платформы), либо подтверждает и теряет сообщение.
- Добавление нового канала требует реализовать полный двусторонний контракт (приём,
  сырое событие, чтение своего исходящего топика, отправка, публикация результата
  доставки) целиком, а не подключиться к уже существующему общему механизму раздачи
  исходящих сообщений.

## Рассмотренные альтернативы

В источнике зафиксирован только сам отказ («Отдельный общий `Outbound Router` не
предусматривается», §5.2), без описания рассмотренной альтернативы и без сравнения
вариантов — фраза не сопровождается обоснованием, почему общий роутер был бы хуже.
Единственная альтернатива, которую можно реконструировать по обратному прочтению
решения: общий сервис, подписанный на все исходящие события системы, определяющий по
полю канала в событии, какому внешнему API доставить сообщение, и делегирующий
собственно отправку внешнему API либо самому адаптеру. Такой вариант в явном виде не
разбирается ни в `SPECIFICATION.md`, ни в `REVIEW-FINDINGS.md`, ни в `DECISIONS.md`.
Выдумывать за источник аргументы против него не следует — честная фиксация в том, что
источник даёт решение без сопоставления с отклонённым вариантом.

## Условия пересмотра

Пункты 2 и 3 инвариантов `SPECIFICATION.md` §23 отнесены документом к «базовым» —
изменение требует отдельного архитектурного решения. Прямо связанные открытые находки,
которые не отменяют это решение, но должны быть закрыты до реализации:

- `REVIEW-FINDINGS.md` §4.1 (открыто) — рассогласование имён топиков между §8 и §10:
  нужна единая конвенция именования, иначе адаптеры физически не смогут договориться,
  какой топик каждый из них читает;
- `REVIEW-FINDINGS.md` §5.2 (открыто) — отсутствует модель деградации при недоступности
  брокера, недоступности API канала и переполнении DLQ; для двунаправленного адаптера без
  общего роутера это поведение определяется отдельно для каждого канала.
