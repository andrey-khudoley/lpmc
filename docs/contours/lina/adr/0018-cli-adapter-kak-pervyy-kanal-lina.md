# CLI-адаптер как первый экземпляр канального слоя

- **Статус:** Принято
- **Дата:** 2026-08-11
- **Контур:** lina
- **Основание:** D-014 «Минимально жизнеспособный контур: каркас с минимальным наполнением».

## Контекст

D-013 запретил промежуточные формы, но оставил открытым вопрос, чем измеряется минимальность внутри
контура. Для LINA он стоит острее, чем для соседей: канальный слой — это её предмет, и «минимальная
LINA» легко читается как «LINA без канала», то есть как приём постановок каким-нибудь другим способом.
Такой способ немедленно становится вторым путём приёма, который затем сносится вместе с привычками —
ровно то, что D-013 запрещает.

Отдельно: состав каналов первой версии в источниках противоречив (`O-8`) — `SPEC §21` называет
Telegram + Max + Web, `D-010` откладывает Max. Ни одно из этих утверждений не обязывает начинать
именно с мессенджера.

## Решение

**Первым экземпляром канального слоя служит CLI-адаптер.** Он реализует полный контракт §13: публикует
сырое входящее (`inbound.raw.cli.v1`), кандидата в задачу, требование уточнения и результат доставки;
принимает только одобренный результат от egress-части PACT; имеет собственную учётную запись на брокере
с правами ровно под этот перечень.

Из этого следует:

1. **Это не обход канального слоя, а его первый экземпляр.** Telegram-адаптер и веб-чат (волна W3) —
   новые экземпляры того же контракта, а не переделка. Граница LINA ↔ PACT при их появлении не меняется.
2. **`reply_route` создаётся доверенным компонентом и для CLI**: выводится из идентификатора сессии
   и оператора. Инварианты `L-5` и `L-10` действуют с первого дня, хотя маршрут ровно один.
3. **Критерий полноты, цикл уточнений с потолками и состояние диалога — в целевом виде на W1.**
   Это механизмы, а не наполнение: добавить их позже нельзя, не переучив способ приёма.
4. **Минимальность выражается наполнением:** один канал, один оператор, один владелец, один диалоговый
   сценарий. Оформление ответа под ограничения канала (W3) и разрешение получателя при нескольких
   владельцах (W3) — данные и правила поверх готового механизма.

## Последствия

**Положительные**

- Первый пользователь системы — оператор — с самого начала работает с той LINA, которая останется:
  через полноту запроса, уточнения и маршрут ответа, а не «пока напрямую».
- Подключение мессенджера перестаёт быть архитектурным событием и становится конфигурационным.
- Инварианты контура проверяемы с первой волны: негативные тесты §5.3 не требуют наличия Telegram.

**Отрицательные / что становится дороже**

- CLI-канал не даёт материала по недоверенному вводу: оператор — доверенный отправитель, и модель угроз
  §19 на W1 проверяется только искусственными сообщениями.
- Часть решений о канальном слое (оформление под канал, allowlist отправителей, восстановление после
  недоступности API канала) откладывается до появления мессенджера и потому не получает практической
  проверки на первых двух волнах.

## Рассмотренные альтернативы

- **Начать с Telegram.** Отклонена по объёму, а не по принципу: бот, allowlist отправителей, вебхук
  и восстановление после недоступности API — работа, не приближающая сквозной путь, ради которого
  существует первая волна.
- **Начать без канала, принимая постановки напрямую в PACT.** Отклонена: это второй путь приёма мимо
  LINA, то есть нарушение инварианта 2 списка `CONTOURS §10` и прямая промежуточная форма.

## Условия пересмотра

- Отмена или изменение D-014.
- Решение о составе каналов первой версии (`O-8`), если оно потребует иного первого экземпляра.
