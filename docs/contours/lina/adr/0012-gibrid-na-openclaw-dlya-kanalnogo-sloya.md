# Гибрид на готовом шлюзе (OpenClaw) для канального слоя

- **Статус:** Предложено
- **Дата:** не установлена как дата отдельного архитектурного решения. `DECISIONS.md`
  (Draft 0.1) фиксирует D-008 с пометкой «проверенные факты по состоянию на 2026-08-09» —
  это дата верификации фактов об OpenClaw, а не дата принятия решения; отдельной даты
  принятия у D-008 в источнике нет. Сам вариант описан в
  `IMPLEMENTATION-OPTION-OPENCLAW.md` (Draft 0.1, дата 2026-08-06, статус на титуле
  «вариант для обсуждения»).
- **Контур:** lina

## Контекст

Второй базовый вариант реализации канальной периферии LINA — полностью самостоятельная
разработка адаптеров Telegram/Max/Web, событийных мостов и runtime для исполнителей.
`IMPLEMENTATION-OPTION-OPENCLAW.md` (вариант для обсуждения, не принятая архитектура)
разбирает вместо этого гибрид: сторонний «agent gateway» OpenClaw берёт на себя
периферию каналов на двух изолированных границах — Intake Gateway (Telegram/Max/Web,
недоверенные отправители, `exec: deny`, `filesystem write: deny`, `browser: deny`,
`external MCP: deny`, `sandbox: all`, fail-closed по дизайну) и отдельный Execution
Gateway (не относится к LINA, см. D-009 — интеграция исполнения отложена отдельным
решением). Остальное — брокер событий, квалификатор, маршрутизация, бизнесовая
политика, реестр задач — в любом варианте остаётся собственной разработкой Second
System и не передаётся OpenClaw ни при каком раскладе.

Явного маппинга «компонент документа → LINA/PACT/MITA/CITA» в источниках нет
(`openclaw-option.md` §16 прямо это оговаривает); единственное дословное соответствие —
таблица `STAGE-0.md` §2 для минимального этапа 0 (отдельное решение D-011, не входит в
этот ADR). Для полной гибридной архитектуры соответствие — интерпретация, извлечённая
из смыслового пересечения с `CONTOURS.md`: **LINA ≈ OpenClaw Intake Gateway + Intake
Broker Bridge** — канальный/диалоговый слой (Telegram/Max/Web, нормализация,
thread/reply semantics, доставка, receipts), без квалификации и без исполнения. Это
согласуется с уже принятыми инвариантами LINA (ADR-0007: LINA не владеет состоянием
задачи и полномочиями) и с явной формулировкой источника: Intake Gateway «не
квалифицирует обращения и не выполняет персональные задачи» (§3).

Периферия каналов — webhook lifecycle, переподключения, rate limiting, медиа,
chunking длинных сообщений, треды/reply, delivery receipts, протокол веб-чата — по
основанию D-008 «не создаёт ценности» и оценивается в 4–8 недель самостоятельной
разработки; ценность системы сосредоточена в квалификации, политике и контрактах,
которые в любом варианте остаются собственными и в LINA не входят (граница уже
закреплена ADR-0008 этого репозитория).

Ключевой факт, из-за которого решение остаётся предложением, а не принятой
архитектурой: OpenClaw сегодня **не установлен и не используется**. MITA
(`cloud-tech-tasks`) — единственная реально существующая система — про OpenClaw не
знает, слово в её исходниках не встречается. Любая формулировка, описывающая OpenClaw
как часть текущего состояния LINA, была бы браком документации.

## Решение

Для канального слоя LINA **предлагается** (не принято) взять готовым продуктом OpenClaw
Intake Gateway, а не разрабатывать адаптеры Telegram/WebChat самостоятельно, оставив
LINA только логику, которую OpenClaw принципиально не делает: квалификацию (граница с
PACT — предмет отдельного ADR-0008) и передачу канальных фактов дальше по конвейеру.

Что берётся готовым (`openclaw-option.md` §3, §8): Telegram channel (bundled), встроенный
WebChat + Gateway API, channel sessions/routing, pairing и allowlists, DM/group policies,
threading/reply-to, обработка медиа, chunking/форматирование, outbound delivery +
receipts, hooks + Plugin SDK, включая хуки `message_received` и `before_agent_run` с
возможностью блокировки до подачи промпта модели — именно этим механизмом Intake
Gateway лишается возможности самостоятельно исполнить обращение. Точное число хуков
(28) в `IMPLEMENTATION-OPTION-OPENCLAW.md` не встречается ни в одном разделе — оно
зафиксировано только в решении D-008 (`second-system/DECISIONS.md`), без указания там
источника/метода проверки (`openclaw-option.md` §9, §15, помечено «уточнено при
верификации» и как открытая неоднозначность отчёта).

Что LINA обязана реализовать сама поверх готового шлюза (§4, §8): Intake Broker
Bridge — in-process plugin (слушает `message_received`, пишет canonical event в
локальный outbox, блокирует стандартный agent run) + внешний bridge worker (выгружает
outbox в брокер событий, получает publish ack, обрабатывает исходящие события,
вызывает Gateway RPC на отправку, ведёт delivery ledger). Fire-and-forget публикация
прямо из hook признана источником недостаточной для продакшна — нужна транзакционная
запись и подтверждение после ack брокера.

Max откладывается как канал независимо от этого решения (отдельная запись D-010): он
отсутствует в официальном перечне каналов OpenClaw, поэтому одинаково дорог что в
гибридном, что в полностью самостоятельном варианте — гибрид здесь экономии не даёт.

Оценка трудоёмкости именно канальной части (`openclaw-option.md` §3, §10): OpenClaw +
Telegram + WebChat — 2–5 дней MVP / 1–2 недели hardening; правильная схема Broker
Bridge (plugin + outbox + внешний worker) — 2–4 недели MVP / 4–7 недель hardening.
Для сравнения, полностью самостоятельная реализация всех адаптеров — 4–8 недель MVP /
3–6 месяцев hardening.

## Последствия

**Положительные.**
- Резко меньше объём собственного кода на границе с недоверенным вводом: webhook
  lifecycle, rate limiting, медиа, chunking, треды и receipts закрываются готовым
  продуктом, а не собственной реализацией.
- Готовый tool-профиль Intake Gateway (`exec/filesystem write/browser/external MCP:
  deny`, `sandbox: all`) даёт fail-closed изоляцию «по умолчанию» на самой опасной
  границе системы — там, где обращение ещё не квалифицировано.
- Оценка по срокам (2–5 дней MVP канальной части) на порядок меньше самостоятельной
  разработки (4–8 недель) — при равной изначальной ценности этого слоя.

**Отрицательные.**
- Зависимость от стороннего продукта с высокой скоростью изменений: версии OpenClaw
  датовые, релизы выходят по несколько в неделю, несовместимые изменения затрагивают
  plugin API и миграции хранилища. Уже произошедший пример подвижности — удаление
  бандла `codex-cli` из комплекта поставки (факт зафиксирован в D-008, относится к
  Execution-стороне продукта, но демонстрирует темп изменений того же продукта, на
  который опирается и Intake-сторона).
- Дороже становится не сам факт использования OpenClaw, а его сопровождение: pin
  точной версии, contract tests на используемую часть Plugin SDK/Gateway RPC, канал
  extended-stable, контролируемые обновления — постоянная статья затрат, которой нет
  у полностью собственного адаптера.
- Intake Broker Bridge — не бесплатная надстройка, а отдельный, не тривиальный по
  надёжности компонент (2–4 недели MVP, 4–7 недель hardening): наивная реализация
  (in-process, без outbox) явно помечена источником как «hardening не рекомендуется»,
  то есть тупиковая для продакшна.
- Vendor dependency на границе, через которую проходит весь входящий недоверенный
  трафик LINA, — при отказе или несовместимом изменении OpenClaw деградирует именно
  канальный слой, то есть единственный способ связи с человеком.
- Max остаётся вне выигрыша от гибрида в любом случае (см. D-010) — экономия
  распространяется не на весь канальный слой LINA, а только на Telegram и WebChat.

## Рассмотренные альтернативы

- **Полностью самостоятельная реализация всех канальных адаптеров.** Отклонено (пока)
  из-за трудоёмкости: 4–8 недель MVP / 3–6 месяцев hardening против 2–5 дней / 1–2
  недели у гибрида для Telegram+WebChat, при том что периферия канала не создаёт
  собственной ценности системы. Даёт полный контроль и низкую vendor dependency —
  остаётся кандидатом, если условия пересмотра ниже сработают.
- **Один экземпляр OpenClaw без внешнего брокера** (второй вариант из трёх,
  `openclaw-option.md` §1, п. 2). В `openclaw-option.md` не детализирован отдельно от
  гибрида; ближайший его аналог — этап 0 (`STAGE-0.md`, D-011), где границы LINA/PACT/
  CITA существуют только в конфигурации одного процесса, без раздельного
  развёртывания. Это отдельное решение (D-011), не входит в состав данного ADR;
  здесь зафиксировано только полное гибридное разделение на Intake и Execution Gateway.

## Условия пересмотра

Дословно из D-008 — возврат к самостоятельной реализации канальных адаптеров, если:

- интеграция потребует недокументированных внутренних API OpenClaw (то есть выход за
  пределы официального Plugin SDK и Gateway RPC);
- шлюз приёма (Intake Gateway) не удастся надёжно лишить возможности исполнения —
  то есть если гарантия «raw message не запускает execution-agent» перестанет
  выполняться технически;
- стоимость сопровождения обновлений (закрепление версий, contract tests, реакция на
  breaking changes plugin API) превысит экономию, полученную на канальном слое.

Дополнительно для LINA: пересмотр требуется, если PoC (`openclaw-option.md` §12, §14)
не подтвердит хотя бы один из первых пяти критериев принятия — в первую очередь
пункт 2 («Intake Gateway гарантированно не исполняет внешние сообщения») — либо если
решение D-008 будет формально принято или формально отклонено на уровне
`DECISIONS.md`: тогда этот ADR нужно будет привести в соответствие новому статусу, а
не оставлять как отдельное предложение.
