## 2. Кто сегодня фактически ведёт диалог с человеком

Функцию, которую по архитектуре должна выполнять LINA, сегодня целиком
выполняют **пользователь напрямую и репозиторий MITA**
(`/home/agent/workspaces/cloud-tech-tasks`) в интерактивной сессии Claude Code
или Codex CLI. Никакого отдельного диалогового контура между человеком и
исполнителем нет — человек разговаривает с тем же агентом, который потом
выполняет задачу и сам решает, что показать в ответ.

Схема сегодняшнего цикла (`/home/agent/workspaces/cloud-tech-tasks/ROADMAP.md`,
этап 1 «ручной прототип», текущий):

1. Пользователь вставляет текст постановки прямо в диалог с агентом внутри
   репозитория `cloud-tech-tasks`.
2. Агент (или делегированная роль `qualifier`) нормализует постановку в карточку
   задачи и, если чего-то не хватает, сам задаёт уточняющие вопросы пользователю
   в этой же сессии.
3. Агент выполняет задачу, сам верифицирует Definition of Done и сам решает,
   какой текст показать пользователю как результат — никакой независимой
   проверки результата перед показом нет.

Никакого разделения на «канал → диалоговый слой → передача задачи →
исполнение → проверка результата → доставка в канал» сегодня не существует:
все шаги происходят в одном непрерывном сеансе одного и того же агента.

## 3. Где физически лежат ближайшие артефакты диалога — внутри MITA

Все перечисленные ниже артефакты принадлежат репозиторию
`/home/agent/workspaces/cloud-tech-tasks` и являются собственностью MITA, а не
LINA. Слова `LINA`, `PACT`, `CITA` в исходниках MITA не встречаются ни разу —
сопоставление ниже является инженерной реконструкцией, а не фактом,
зафиксированным в самих файлах.

- **`.agents/commands/new-task.md`** — команда `/new-task`
  (`disable-model-invocation: true`, то есть вызывается только явным
  обращением пользователя, а не решением модели). Принимает постановку от
  менеджера, делегирует разбор роли `qualifier` и, если клиент не определился,
  сама задаёт вопрос пользователю — потому что делегированная роль отвечать
  напрямую пользователю не может.
- **`.agents/commands/task.md`** — команда `/task`
  (`disable-model-invocation: true`). Принимает ссылку на уже заведённую задачу
  вида `<client>/<YYYY-MM-DD-slug>`, делегирует выполнение роли `task-executor`
  и показывает пользователю итоговый статус, результат проверки DoD и готовый
  текст отчёта.
- **`.agents/agents/qualifier.md`** — делегированная роль (`profile: fast`,
  инструменты `Read, Grep, Glob, Write, Edit, Bash`, без Playwright/браузера).
  Разбирает сырую постановку в карточку задачи по процедуре
  `.agents/skills/intake/SKILL.md`. Общая политика MITA прямо запрещает
  делегированной роли обращаться к пользователю напрямую: всё неясное `qualifier`
  возвращает как кандидатов и вопросы в своём ответе, а вопрос пользователю
  задаёт уже главный агент через `/new-task`.
- **`.agents/skills/intake/SKILL.md`** — процедура приёма задачи: определить
  владельца по `clients/INDEX.md` / `projects/INDEX.md` / `internal/INDEX.md`
  (при неоднозначности — спросить, не гадать), создать карточку
  `<root>/<owner>/tasks/active/<id>/task.md`, сохранить исходный текст менеджера
  дословно в разделе «Исходное сообщение», сформулировать Definition of Done,
  проверить карточки упомянутых сервисов, при нехватке информации выставить
  `status: blocked` и сформулировать вопросы «готовыми к пересылке менеджеру».
- **`templates/inbox-item.md`** — шаблон сырой постановки с полями `received`,
  `source` (`manual | telegram | api`), `chat`, `manager`. Значение `source:
  telegram` в шаблоне присутствует, но канал Telegram сегодня не подключён и
  фактически никогда этим значением не пользуется — на этапе 1 пользователь
  почти всегда передаёт текст агенту напрямую в диалоге, и тогда `intake`
  создаёт карточку задачи сразу, минуя файл `tasks/inbox/` вовсе. Поле `chat`
  (идентификатор чата, будущий маршрут ответа) сегодня нигде не используется:
  ответ агент формирует и показывает в той же интерактивной сессии, а не
  доставляет по внешнему адресу.

Ни одна из этих сущностей не является прообразом контура LINA целиком:
`qualifier` — прообраз одной функции («достаточно ли информации для передачи
дальше»), а не диалогового контура; команды `/new-task` и `/task` явно
перекладывают разговор с пользователем на главного агента, а не на отдельный
компонент.

## 4. Каналов связи не существует

- **Telegram** — не подключён. Единственный след — неиспользуемое значение
  `telegram` в поле `source` шаблона `templates/inbox-item.md` и упоминание в
  `ROADMAP.md` MITA (этап 2, «не начат по интеграции») как одного из планов
  самого репозитория MITA, а не контура LINA.
  `ROADMAP.md` MITA описывает подключение Telegram напрямую в `tasks/inbox/`
  собственными средствами MITA — это план другого репозитория, направленный
  мимо LINA, и он не реализован ни в каком виде.
- **Веб-чат** — не существует ни в каком виде, ни черновика, ни макета.
- **Max** — не используется.
- **OpenClaw** — не установлен на узле, никаких его артефактов (демона, конфигурации,
  портов) в системе нет.
- **Брокер событий** — отсутствует.
