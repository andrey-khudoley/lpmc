> docs-as-state: этот документ описывает то, что есть сейчас, по исходникам
> репозитория `cloud-tech-tasks`. Про целевое устройство и перенос обязанностей на

## 0. Имя: чего в исходниках нет и что там есть на самом деле

Прежде чем читать дальше, важно снять путаницу в именовании, потому что она реальна
и её нельзя сгладить.

- Репозиторий называет себя **`cloud-tech-tasks`** — так называется каталог, так
  подписан `README.md`, так фигурирует во всех git-коммитах и путях. Слова «MITA»
  как имени системы в файлах политики (`AGENTS.md`, `.agents/policy/`), в скиллах, в
  ролях и в 34 журналах `llm/` (сырых) **не встречается ни разу**.
- Действующее лицо, от которого ведётся исполнение и записываются журналы, называет
  себя **«main agent»**. Это термин из самих исходников, не наша интерпретация.
- Имя **MITA** появилось в этом репозитории только **2026-08-09**, и означает оно не
  переименование системы, а переименование **агентской учётной записи во внешних
  сервисах**: отображаемое имя логина сменилось с **ESTA** на **MITA / MITA Agent** у
  GetCourse NeSo, Bizon365, Kinescope (при этом пароли не менялись, у GetCourse NeSo
  сменился TOTP-секрет). Факт зафиксирован в
  `notes/2026-08/2026-08-09-agent-account-rename.md` и в журнале
  `llm/2026-08/2026-08-09-1050-main-agent-account-rename.md`. До этого момента в
  текстах репозитория логин
  агента фигурировал как ESTA; в git этого логина как строки нет — было только
  отображаемое имя учётки на стороне сервисов.
- **Слова LINA, PACT, CITA в исходниках `cloud-tech-tasks` не встречаются ни разу** —
  ни в `.agents/`, ни в политике, ни в журналах, ни в карточках сервисов. Всё
  сопоставление «сущность репозитория ↔ контур четырёхконтурной архитектуры»
  (например, «репозиторий целиком = MITA», «роль `qualifier` тяготеет к LINA») — это
  **инженерная реконструкция**, сделанная снаружи, при разметке этого воркспейса, а
  не факт, зафиксированный в самих исходниках `cloud-tech-tasks`. Обоснование этого
  сопоставления и его тонкости (в частности, почему `qualifier` и команды
  `/new-task`/`/task` не тождественны LINA, а лишь ближе всего к её функции) —
  `docs/adr/0016-priyom-postanovok-iz-telegram-peresmatrivaetsya.md`.

Ниже по тексту имя «MITA» используется как имя контура (в терминах воркспейса), а
не как факт из исходников репозитория — там, где важно различие, это отмечено явно.

## 1. Назначение репозитория `cloud-tech-tasks`

`cloud-tech-tasks` — инфраструктура для передачи задач от менеджеров клиентов
агентам-исполнителям (Claude Code, а также Codex CLI) и их автономного выполнения на
реальных сервисах через Playwright.

Модель работы одной фразой: постановка из чата → агент нормализует её в карточку
задачи с проверяемым Definition of Done (DoD) → выполняет по внутренним инструкциям и
знаниям о сервисах клиента через веб-интерфейсы (браузер) → верифицирует результат
**фактически**, а не «по логике» → отдаёт текст отчёта, готовый для пересылки
менеджеру человеком-оператором.

Файлы + git — единственный источник истины, внешних баз данных нет. История git
одновременно служит аудит-логом системы: каждая осмысленная операция (принята задача,
завершена задача, обновлено знание) — отдельный коммит вида `<область>: <что
сделано>`.

Точка входа для агентов — `CLAUDE.md` в корне репозитория. Он не редактируется
вручную: **генерируется** командой `node scripts/agents.mjs build` из канонических
файлов в `.agents/`. Так же генерируются `AGENTS.md`, `AGENTS.override.md` и раздел
«что умеет система» в `README.md`. План развития — `ROADMAP.md`.

Сегодня репозиторий полностью самостоятелен: секреты хранятся в открытом виде на
узле, проверки поверх (то, что в целевой архитектуре делает PACT) нет, диалогового
слоя перед исполнителем (то, что делает LINA) нет — пользователь отдаёт команды
напрямую в сессии Claude Code / Codex CLI.

## 2. Состав верхнего уровня

```
cloud-tech-tasks/
├── README.md            # обзор для людей; раздел «что умеет система» собирается
│                         #   сборщиком из frontmatter канона — руками не правится
├── ROADMAP.md            # три этапа развития
├── CLAUDE.md, AGENTS.md, AGENTS.override.md   # generated-представления канона .agents/
├── clients/               # ПОСТОЯННЫЕ клиенты (ретейнер) — их ровно двое:
│                          #   NeSo Академия (neso) и ИП Ларина (larina)
├── projects/               # разовая/проектная работа: сделки, пилоты, лиды
├── internal/                # собственные контуры исполнителя: internal
├── services/                 # общие сервисы, не привязанные к одному владельцу:
│                            #   bizon365, chatium, gc-chatium-gateway, kinescope
├── playbooks/                 # общие процедуры выполнения типовых классов задач
│                             #   (сегодня один плейбук — captcha-escalation)
├── notes/                    # ТОЛЬКО системные и кросс-владельческие заметки
├── llm/                      # сырые системные журналы работы агентов (append-only)
├── templates/                # шаблоны сущностей (frontmatter-схемы)
├── infra/                    # документация исполнительного стека: playwright/,
│                            #   web-browser/, webapp/ (не реализовано), knowledge-search/
├── .secrets/                  # ВНЕ git (кроме README.md): значения секретов, сессии
├── deploy/                    # ВНЕ git; появляется только на время migrate-legacy
├── var/                       # ВНЕ git: производное состояние инструментов
│                            #   (индекс knowledge-search, снимки браузера)
├── .agents/                   # канон агентской инфраструктуры: скиллы, роли, команды,
│                            #   политика — единственный редактируемый источник
├── scripts/agents.mjs         # сборщик канона в вендорные проекции
├── .githooks/pre-commit        # механический enforcement (сборка, знания, индекс)
├── .claude/, .codex/            # generated/симлинки — конфиги под конкретный AI-клиент
└── .mcp.json                    # generated из .agents/mcp/registry.json
```

Три корня владельцев (`clients/`, `projects/`, `internal/`) имеют одинаковую
внутреннюю структуру:

```
<root>/<owner-slug>/
├── overview.md          # кто это, контакты, контекст
├── instructions.md      # локальные правила; ПРИОРИТЕТНЕЕ общих политик
├── tasks/{inbox,active,archive}/
├── services/INDEX.md + <service-slug>/overview.md
├── playbooks/            # локальные процедуры; приоритетнее общих playbooks/
├── notes/INDEX.md + YYYY-MM/ + archive/
└── llm/YYYY-MM/           # сырые журналы работы агентов по этому владельцу
```

У каждого из трёх корней есть свой `INDEX.md` со списком владельцев. Слаг владельца
уникален глобально (не может совпасть между `clients/`, `projects/`, `internal/`),
поэтому глобальная ссылка на задачу — `<owner-slug>/<YYYY-MM-DD-slug>` без указания
корня.

На сегодня: 21 владелец в трёх корнях — 2 в `clients/` (NeSo Академия, ИП Ларина), 18
в `projects/`, 1 в `internal/` (internal).

Каталоги `deploy/`, `var/`, `.secrets/storage-state/`, `.secrets/totp/` в чистом
репозитории отсутствуют — создаются по мере надобности, их отсутствие не считается
дефектом.

## 3. Что система фактически делает

### 3.1. Жизненный цикл задачи

Статусы: `inbox → active → (blocked|review) → done | cancelled`. Грубое состояние
задаёт каталог (`tasks/inbox/`, `tasks/active/`, `tasks/archive/`), точное — поле
`status` во frontmatter карточки. Действует правило «место следует за состоянием»:
переход статуса — это в том числе перемещение файла между каталогами.

1. **Постановка попадает в систему.** Сегодня — вручную, текстом в диалоге с
   пользователем (Telegram/API как источник `inbox/` — не реализовано, это шаг
   этапа 2 по `ROADMAP.md`).
2. **`intake`** (скилл) / роль `qualifier`: нормализация сырой постановки в карточку
   `<root>/<owner>/tasks/active/YYYY-MM-DD-<slug>/task.md` с проверяемым DoD.
   Задачам без определённого владельца не бывает: если владелец не ясен однозначно —
   это вопрос к пользователю, а не задача «в никуда»; делегированная роль не имеет
   права спросить пользователя сама, она возвращает вопрос в своём ответе.
3. **`execute-task`** (скилл) / роль `task-executor`: план → выполнение через
   Playwright по веб-интерфейсам сервисов клиента → верификация каждого пункта DoD
   фактически (обычно скриншотом, а не «по логике») → текст отчёта для менеджера.
4. Карточка со `status: done` переносится в `<root>/<owner>/tasks/archive/<год>/`.

DoD обязателен в каждой карточке задачи. Формулировки — только фактически проверяемые
критерии («в сервисе X на странице Y отображается Z»), а не намерения («настроить
интеграцию»). Пункт без фактической проверки не считается выполненным.

### 3.2. Исполнение — браузер, не API

Единственный операционный канал исполнения — Playwright поверх веб-интерфейсов
сервисов клиентов, не опубликованные контракты/API. MCP-сервер `playwright`
подключается по CDP к уже запущенному headed-браузеру (не запускает его сам); у
каждого владельца — свой инстанс браузера со своим профилем и портом CDP
(`default`=0, `larina`=1, `neso`=2, `internal`=3, порт = 9222+index), инстансы
перечислены в `config/ansible-vars.yml` роли `kiosk_browser` в `/var/lib/infra/src` —
это единственная точка ручной правки, всё остальное на узле идёт через ту же роль.
Есть аварийный контур просмотра сессии человеком — nginx на порту 22325, одноразовый
путь, TTL 30 минут.

Помимо основного исполнителя (`task-executor`) есть разведывательная роль
`service-scout` (то же самое исполнение через браузер, но только чтение — ограничение
инструкцией, не правами) и служебная `librarian` (компакция заметок, актуализация
индексов, поиск зависших задач — уборка самой системы, не исполнение клиентских
задач).

### 3.3. Секреты — без посредника

Секреты хранятся вне git, в открытом виде на узле: `.secrets/env` (`KEY=VALUE`, права
600), `.secrets/storage-state/<owner>/<service>.json` (снимки сессий Playwright —
основной механизм авторизации, без ввода пароля на каждый запуск),
`.secrets/totp/<owner>/<service>` (base32-семена TOTP). В самом репозитории (в git) —
только **имена** секретов вида `<client>/<service>/<field>`, никогда значения.
Исполнитель читает эти файлы с диска напрямую, никакого посредника (аналога PACT для
custody секретов) нет. Значения секретов в этом документе и во всех остальных файлах
репозитория не воспроизводятся принципиально.

### 3.4. Знания и заметки

Заметка — наблюдение, не знание: `<root>/<owner>/notes/` — про владельца, корневой
`notes/` — про саму систему или кросс-владельческое. Устойчивые знания живут в
`overview.md`/`instructions.md` владельца, карточках `services/`, `playbooks/`.
Перенос заметок в базу знаний делает скилл `compact-notes` (раз в две недели или по
просьбе). Поиск по базе знаний — гибридный локальный `obsidian-hybrid-search`, индекс
`var/knowledge-search/index.db` (+ симлинк `.obsidian-hybrid-search.db` в корне —
путь к нему жёстко вычисляется инструментом снаружи, переопределить нечем),
переиндексация запускается внутри `.githooks/pre-commit`.

Каталоги `llm/` (сырые журналы сессий, обязательны для каждой осмысленной сессии
агента или делегированной роли, append-only, не подлежат компакции) — отдельная
сущность от заметок; путь — `<root>/<owner>/llm/YYYY-MM/` для работы по владельцу,
корневой `llm/YYYY-MM/` для системной работы.

### 3.5. Канон агентской инфраструктуры

`.agents/` — единственный редактируемый источник: скиллы (`add-owner`,
`compact-notes`, `execute-task`, `intake`, `migrate-legacy`, `status`), роли
(`task-executor`, `service-scout`, `qualifier`, `librarian`), команды (`/new-task`,
`/task`, обе с `disable-model-invocation: true` — их может вызвать только человек, не
модель) и общая политика. Сборщик `scripts/agents.mjs` (подкоманды `build`/`check`/
`lint`) генерирует из канона `.claude/` (симлинки) и `.codex/` (генерируемые файлы)
для двух поддерживаемых AI-клиентов — Claude Code и Codex CLI — а также корневые
`CLAUDE.md`/`AGENTS.md`/`AGENTS.override.md`. `.githooks/pre-commit` механически
проверяет, что сборка, знания и индекс актуальны на момент коммита.

## 4. Чего сегодня нет

- **webapp** (этап 3 по `ROADMAP.md`) — не реализован; каталог `infra/webapp/`
  содержит только документацию, о том, каким он должен быть — `docs/spec/spec.md`.
- **Брокер событий, интеграция с Telegram** — не реализованы; постановка задач сегодня
  идёт только текстом в диалоге напрямую пользователю.
- **Проверка поверх исполнения (аналог PACT)** — не существует: реестра задач с
  полномочиями, лизингов, egress-проверки результата в репозитории нет; MITA сама
  решает о легитимности и владельце задачи.
- **Диалоговый слой перед исполнителем (аналог LINA)** — не существует: команды
  `/new-task` и `/task` и роль `qualifier` — единственное, что структурно ближе всего
  к этой функции, но работают внутри того же security-контекста, что и исполнение, а
  не как отдельный недоверенный контур.
- **Исполнение по опубликованным контрактам (аналог CITA)** — не существует: вся
  автоматизация сегодня браузерная; ближайшие кандидаты (собственный gateway
  `gc-chatium-gateway` на GetCourse API, платформа `chatium` с интеграциями GetCourse
  SDK/AmoCRM/Notion/Toggl/Bizon365) остаются карточками сервисов внутри MITA.

Целевое устройство всего перечисленного — предмет `docs/spec/spec.md` и
`docs/adr/0001-chetyre-kontura-i-mesto-mita.md`,
`docs/adr/0002-imya-i-granicy-kontura-mita.md`; здесь эти вопросы не пересказываются.
