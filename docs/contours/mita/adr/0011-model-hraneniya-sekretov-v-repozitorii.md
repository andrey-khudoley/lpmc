# Секреты хранятся плоскими файлами в .secrets и никогда не проходят через shell

- **Статус:** Принято
- **Дата:** не установлена как единый момент — модель сложилась поэтапно: базовая
  структура `.secrets/` (каталог, `README.md`, `env`) заведена 2026-07-30 вместе с
  базовой структурой системы задач и знаний; формат `storage-state` и явное
  определение сессионного файла как секрета, равного паролю, добавлены 2026-08-03
  13:19; запрет `source .secrets/env` закреплён 2026-08-08 12:46 разбором на реальном
  пароле с спецсимволами (см. «Источник»)
- **Контур:** mita

## Контекст

MITA — исполнитель, работающий через интерфейсы для человека (браузер, веб-панели),
и ему для каждого сервиса нужны логин, пароль, иногда TOTP-секрет и Playwright
`storage-state`. Система изначально строилась одним оператором с прямыми коммитами в
`main`, без второго участника с правом коммита и без внешнего gate (см. также ADR
про единственный барьер enforcement — `.githooks/pre-commit`, зафиксирован в
`.agents/ARCHITECTURE.md` §8.1).

При заведении секретов 2026-08-08 обнаружился конкретный инцидент: пароль
`shared/kinescope/password` содержал спецсимволы. `source .secrets/env` на значении
с `)` падал с синтаксической ошибкой — терпимый случай. Но на значении вида
`abc&touch PWNED` `source` **не падал**: тихо исполнял хвост как команду оболочки и
клал в переменную только `abc`. То есть файл секретов, прочитанный через `source`,
превращается в исполняемый код всякий раз, когда пароль содержит `& ; \` $(…)` и
похожее — а какие символы окажутся в очередном пароле, заранее не известно и не
контролируется MITA (пароли задаёт внешний сервис или пользователь).

Отдельно обнаружилось, что `storage-state` — не «сессия одного сервиса», а слепок
всего профиля браузера (cookies и localStorage всех доменов, в которые заходили в
этом инстансе), то есть по факту самый широкий по охвату секрет из трёх категорий:
он даёт доступ без пароля и в обход 2FA.

Нужна была модель хранения, которая: не требует внешнего секрет-менеджера (которого
нет и не планировался как задача этого этапа), безопасна для чтения произвольным
кодом на Node/shell без риска инъекции, и совместима с будущим переездом в менеджер
секретов, если он появится («этап 2», упомянут в `.secrets/README.md`).

## Решение

Секреты хранятся плоскими файлами вне git, в каталоге `.secrets/` на узле-исполнителе:

```
.secrets/
├── README.md                              # единственное, что коммитится
├── env                                    # KEY=VALUE, один файл, chmod 600
├── storage-state/
│   ├── _TEMPLATE.json                     # образец формата, не рабочая сессия
│   └── <client>/<service>.json            # сессии Playwright, chmod 600, каталог 700
└── totp/<client>/<service>                # TOTP-секрет (base32), chmod 600
```

- **`env` — не shell-файл.** Значение хранится «как есть», от первого `=` до конца
  строки, без кавычек и экранирования. Единственные допустимые способы прочитать
  значение — построчный парсинг по первому `=` (`sed -n 's/^KEY=//p'`,
  `line.split('=', 1)[1]`) или `grep -F` для поиска по содержимому. `source
  .secrets/env` запрещён безусловно. В коде правило соблюдено: `var/login-checks/lib.mjs`
  читает файл построчно через `indexOf('=')`, не через оболочку.
- **TOTP-секреты (base32) хранятся отдельными файлами**, а не строками в `env`:
  значение, начинающееся с `#`, или иначе «неудобное» для построчного формата,
  выносится отдельным файлом по тому же принципу.
- **Схема имён — `<client>/<service>/<field>`**, в `env` кодируется как
  `CLIENT__SERVICE__FIELD` (`/` → `__`, верхний регистр, `-` → `_`). Логин
  считается частью секрета наравне с паролем и по этой же схеме не выносится в
  открытый текст карточек и заметок. Позиция `<client>` допускает слаг `shared` для
  учётной записи, физически общей для нескольких клиентов (см. отдельный ADR-0009).
- **Права выставляются вручную**: `env` — `600`, подкаталоги `totp/`/`storage-state/`
  — `700`, файлы внутри — `600`. `README.md` — `644`, он единственный коммитится в
  git. Playwright сам права не выставляет (задокументирован реальный инцидент с
  `644` из-за гонки `umask` между вызовами оболочки) — `chmod 600` выполняется явно
  после каждого пересохранения `storage-state`.
- Схема имён спроектирована так, чтобы пережить переезд в менеджер секретов
  («этап 2» в `.secrets/README.md`) без переименования карточек сервисов —
  но сегодня этого менеджера, посредника или брокера выдачи не существует:
  исполнитель (`var/login-checks/lib.mjs`, функция `secret()`) читает `.secrets/env`
  напрямую `fs.readFileSync`-построчно, без какого-либо промежуточного слоя.

## Последствия

Положительные:
- Устранён конкретный подтверждённый класс уязвимости — инъекция кода через
  спецсимволы пароля при `source`; альтернативный путь чтения (построчный парсинг)
  безопасен для любого содержимого значения.
- Модель проста и не требует внешней инфраструктуры (секрет-менеджера, сетевого
  сервиса выдачи) для того, чтобы MITA сегодня вообще могла работать с сервисами.
- Схема имён `<client>/<service>/<field>` → `CLIENT__SERVICE__FIELD` уже
  спроектирована под будущий переезд custody к посреднику — перенос значений не
  потребует переименования карточек сервисов, которые ссылаются на имена секретов.
- Явное разделение трёх категорий (env-пары, TOTP-seed, storage-state) с разными
  правами и разными шаблонами формата снижает риск смешения — например, попытки
  положить TOTP-seed со спецсимволом (`#`) в общий `env`.

Отрицательные / что становится дороже:
- Секреты лежат в открытом виде на диске узла и напрямую доступны процессу-
  исполнителю без какого-либо посредника: `secret()` — это обычный `readFileSync`.
  Ничего не мешает самому исполнителю вынести значение секрета в отчёт, заметку или
  коммит в обход `.gitignore`, просто вписав его текстом в файл вне `.secrets/`.
  Единственная защита от этого — нормативная политика (`.agents/policy/common/04-secrets.md`)
  и дисциплина исполнителя, не техническое ограничение.
- Защита от утечки в git одноуровневая: `.gitignore` плюс единственный барьер —
  `.githooks/pre-commit` (`agents.mjs lint`), причём линт на литералы учётных данных
  прогоняется только по канону `.agents/`, а `clients/`/`projects/`/`internal/`
  осознанно исключены из машинной проверки. Права `600`/`700` защищают от других
  пользователей узла, но не от git и не от самого процесса, у которого и так есть
  чтение.
- `storage-state` шире по охвату, чем предполагает имя файла (слепок всего профиля
  браузера, а не одного сервиса) — задача фильтрации по домену признана нужной, но
  не реализована; выдача такого файла (в целевой архитектуре) фактически даёт
  доступ ко всем сервисам, бывшим в том же браузерном профиле.
- Ротация секретов сегодня — не авторизуемая операция, а прямая правка файла
  (`sed -i .secrets/env`, `printf > .secrets/totp/...`) тем же процессом, что ведёт
  диалог с пользователем; отдельного структурированного журнала доступа/ротации
  нет, только человекочитаемые записи в `llm/`.
- Дороже становится любой будущий перенос custody: пока схема имён спроектирована
  «на вырост», сама миграция файлов, замена `lib.mjs` на клиента к посреднику и
  отзыв прямого файлового доступа у узла MITA — не сделанный, а лишь предусмотренный
  шаг.

## Рассмотренные альтернативы

- **`source .secrets/env` в shell-скриптах** — исходно казался самым простым
  способом подставить секреты в переменные окружения. Отвергнут после разбора на
  реальном пароле (2026-08-08): падает на части спецсимволов и тихо теряет данные
  на других (`abc&touch PWNED` исполняется как команда).
- **`export $(cat env | xargs)`** — сработал на конкретном проверенном пароле, но
  `xargs` сам разбирает кавычки и обратный слэш, то есть на другом значении соврёт
  так же незаметно, как `source`. Признан ненадёжным тем же разбором и не принят
  как общий способ чтения.
- **Хранение TOTP-seed внутри `env` вместе с паролями** — отклонено: значения,
  начинающиеся с `#`, ломают часть парсеров как комментарий, и это было бы легко
  пропустить при последующем добавлении сервисов с 2FA. TOTP вынесен в отдельные
  файлы по фиксированному пути.
- **Внешний секрет-менеджер вместо плоских файлов** — рассмотрен как принципиально
  более безопасный вариант («этап 2»), но не реализован и не начат на момент
  принятия этого решения: не было ни второго участника, которому нужно было бы
  разграничивать доступ, ни готовности вкладываться в инфраструктуру ради одного
  оператора. Схема имён спроектирована заранее так, чтобы этот переезд не потребовал
  переписывать карточки сервисов.

## Условия пересмотра

В источниках явного условия пересмотра для модели хранения секретов в целом не
зафиксировано. Ближайшая по духу оговорка относится к соседнему решению —
единственному барьеру `.githooks/pre-commit` (`.agents/ARCHITECTURE.md` §8.1):
«появление второго человека с правом коммита или PR-флоу» требует внешнего gate —
и по той же логике снижает достаточность модели «секрет доступен исполнителю
напрямую, без посредника», разделяемой этим ADR. Отдельно в исследовании
зафиксирован явный кандидат на пересмотр всей модели целиком — перенос custody
секретов под PACT при разделении контуров (см. «Источник»): выдача значений по
авторизованному запросу конкретной задачи вместо прямого `readFileSync`, выдача
TOTP-кода вместо seed, зашифрованное хранение и TTL для `storage-state`, а также
структурированный аудит-лог ротации. Пока PACT не существует как работающая
система, этот перенос остаётся нереализованным планом, а не фактом.
