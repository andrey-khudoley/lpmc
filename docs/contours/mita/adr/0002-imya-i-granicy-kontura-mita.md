# Имя контура MITA и критерий отнесения задачи к нему

- **Статус:** Принято
- **Дата:** 2026-08-09 (имена контуров LINA/PACT/MITA/CITA зафиксированы этим числом —
  `second-system/DECISIONS.md` D-002, «Хронология»; имя MITA как переименование
  агентской учётной записи ESTA→MITA во внешних сервисах самого репозитория
  `cloud-tech-tasks` тем же числом — research/allocation.md)
- **Контур:** mita

## Контекст

MITA расшифровывается как Manual Interaction Task Agent (`second-system/DECISIONS.md`
D-002). Имя выбрано не произвольно: три агентные структуры (LINA, MITA, CITA) названы
однотипно, PACT — не агент и назван иначе по форме, а не только по раскрытию, чтобы
асимметрия была видна до чтения расшифровки (D-002, «Основание»; CONTOURS.md §2.1).
Общий суффикс `-TA` обозначает уровень исполнителя; первые буквы несут модальность
взаимодействия с внешним миром (CONTOURS.md §2.1).

Ключевой вопрос, который обязан закрыть этот ADR: по какому признаку задача относится
к MITA, а не к CITA (соседнему исполнителю того же уровня) или к PACT/LINA (другой
уровень). Источники дают на это два независимых, но согласованных ответа:

1. **Разрез по модальности, а не по предметной области** (CONTOURS.md §7.1): «граница
   проходит по наличию пригодного API у целевой системы, а не по предметной области».
   Один и тот же вендор (например, GetCourse) может частично лежать в MITA (браузерная
   карточка `services/gc-chatium-gateway/`) и одновременно быть «ближайшим реальным
   кандидатом в CITA», потому что у него есть подготовленный gateway на его же API
   (research/allocation.md §2.6). Это не два разных вендора — это один и тот же
   предмет, распределённый по модальности исполнения.
2. **Capability не содержит указания на модальность** (D-007, инвариант 9): задача
   именуется `invoice.submit`, а не `invoice.submit.via-web`, и адресуется не
   заказчиком напрямую исполнителю, а диспетчером PACT. Основание D-007 дословно:
   «Граница MITA/CITA подвижна: при появлении API у внешнего сервиса возможность
   переезжает между контурами. Указание модальности в имени потребовало бы
   переписывания политик вместо изменения маршрута».

Оба ответа сходятся в одном: **MITA — это не набор задач про конкретных вендоров,
а модальность исполнения** — интерфейсы, спроектированные для человека (браузер,
веб-панели), применяемая тогда и только тогда, когда для цели нет пригодного
опубликованного контракта (research/allocation.md §1, принцип 2: MITA/CITA отвечают
на вопрос «как именно это делается», а не «что делается» и не «можно ли»).

Настоящий ADR — дубликат D-002 в воркспейсе MITA: та же фиксация имени и критерия
границы, но с явными последствиями для этого конкретного участка, которых не может
быть в общесистемном документе (`second-system/` ни разу не упоминает
`cloud-tech-tasks` — research/allocation.md §0.5). Важная оговорка о фактическом
положении дел: в исходниках самой MITA (`.agents/`, карточки сервисов, журналы `llm/`)
слова `LINA`, `PACT`, `CITA` не встречаются ни разу; имя `MITA` в этих исходниках
появилось только 2026-08-09 как переименование агентской учётной записи `ESTA→MITA`
во внешних сервисах — не как переименование самой системы, которая внутри себя
по-прежнему называется `cloud-tech-tasks`, а действующее лицо в её документах —
«main agent». Всякое сопоставление «сущность MITA ↔ контур» ниже — инженерная
реконструкция, а не факт из исходников MITA.

## Решение

1. Контур называется **MITA — Manual Interaction Task Agent**, и это имя относится
   к модальности исполнения (браузер, веб-интерфейсы, интерфейсы, спроектированные
   для человека), а не к перечню обслуживаемых сервисов или предметных областей.
2. Задача относится к MITA тогда и только тогда, когда у целевой системы **нет
   пригодного опубликованного контракта** (API), и, соответственно, действие
   выполняется через интерфейс, спроектированный для человека. Критерий —
   отсутствие/непригодность API, а не тип вендора, не клиент/проект/internal и не
   исторический факт «раньше делали руками».
3. Граница MITA/CITA **подвижна**: появление у целевой системы пригодного API
   переносит задачу (и, в целевой архитектуре — capability) из MITA в CITA без
   изменения имени capability и без переписывания политик PACT (D-007). Обратного
   движения (из CITA в MITA) источники не описывают, но принцип симметричен:
   отзыв или непригодность API вернул бы задачу к исполнению через интерфейс для
   человека.
4. Кто именно исполняет конкретную задачу — MITA или CITA — по целевой архитектуре
   решает диспетчер PACT, а не заказчик задачи и не сама MITA (D-007, инвариант 9;
   research/allocation.md §3.3: «MITA про CITA и наоборот: граница между нами
   подвижна и проходит по наличию пригодного API у целевой системы, а не по
   предметной области; переезд возможности из одного контура в другой не меняет
   имя capability»).
5. Сегодня, до появления PACT и CITA как работающих систем, это решение о критерии
   не имеет механизма принуждения: MITA сама решает, что для неё браузерная задача,
   а что можно было бы отдать по API — см. «Последствия».

## Последствия

**Положительные.**
- Имя MITA фиксирует контур как *способ действия*, а не как *список ответственности
  за вендоров* — это снимает соблазн описывать MITA через перечень сервисов
  (`services/bizon365`, `services/chatium`, …) как её сущностную границу; перечень
  сервисов — временное состояние, а не определение контура.
- Явный критерий («нет пригодного API») даёт проверяемый вопрос для любой новой
  задачи и для любого существующего сервиса: если у цели появляется API — задача
  кандидат на переезд, а не повод переписывать правила заново.
- Конкретные примеры уже видны в собственном материале MITA и подтверждают критерий
  на практике, а не только в теории: `services/gc-chatium-gateway/` (собственный
  gateway на GetCourse API) и `services/chatium/` (внешние интеграции: GetCourse SDK,
  AmoCRM OAuth2, Notion, Toggl v9, Bizon365 API v2.0) — «ближайшие реальные
  кандидаты в CITA» и «материал для первых интеграций CITA» соответственно;
  наблюдение эндпоинта `app.kinescope.io/api/entities` изнутри браузера — «признак
  „сервис пригоден к переезду в CITA“» (research/allocation.md §2.6).

**Отрицательные и то, что становится дороже.**
- Сегодня диспетчера PACT не существует, поэтому пункт решения 4 не выполняется:
  MITA сама решает, что делать браузером, а не через найденный API — например,
  наблюдаемый `app.kinescope.io/api/entities` не используется как контракт, хотя
  зафиксирован как признак пригодности к переезду; решение эксплуатировать его
  как API вместо браузера сегодня некому принять, кроме самой MITA явочным
  порядком. Это разрыв с инвариантом 9, задокументированный как факт.
- Правило «capability не знает о модальности» сегодня неприменимо буквально: у MITA
  нет реестра capabilities и нет PACT, который бы его вёл; задачи в `tasks/` сегодня
  именуются и маршрутизируются исходя из владельца и сервиса, а не из абстрактного
  действия с явно скрытой модальностью. Введение такого реестра — будущая миграция
  с реальной стоимостью (переопределение схемы карточек задач), а не переименование.
- Появление PACT как арбитра границы означает, что часть сегодняшних браузерных
  задач может быть признана «на самом деле CITA» задним числом (переезд по критерию
  «есть пригодный API»); это создаёт риск разночтения при разборе накопленной
  истории задач и журналов `llm/`, где решение «делать руками» принималось без
  формального критерия.
- Дороже становится любое обсуждение объёма MITA: нельзя аргументировать «этот
  сервис наш, потому что мы всегда его вели» — единственный легитимный аргумент
  теперь «у цели нет пригодного контракта», и это нужно каждый раз явно
  проговаривать, а не предполагать по умолчанию.

## Рассмотренные альтернативы

- **Разрез по предметной области или по вендору** (например: «всё про GetCourse — в
  одном контуре») — отвергнут. Он ломается на первом же реальном примере: у одного
  вендора (GetCourse) одновременно есть материал под MITA (карточка
  `gc-chatium-gateway`) и под CITA (сам gateway построен на API того же вендора)
  (research/allocation.md §2.6). Разрез по предмету также требовал бы переписывания
  политик при каждом появлении API у очередного вендора (D-007, «Основание»).
- **Указание модальности в имени capability** (`invoice.submit.via-web` вместо
  `invoice.submit`) — отвергнуто явно в D-007: «Указание модальности в имени
  потребовало бы переписывания политик вместо изменения маршрута» при переезде
  задачи между MITA и CITA.
- **Различимые, а не похожие имена исполнителей** (например, из отклонённого списка
  D-002: VETA, CLARA, MIMA, ASTA, INTA, ARTA) — отвергнуты в пользу родственности
  имён MITA/CITA, несмотря на то что сходство создаёт риск опечатки в таблицах
  правил PACT; риск компенсируется проверкой идентификатора исполнителя по
  закрытому перечню (D-002, «Принятый компромисс»; инвариант 11).
- **Заказчик задачи сам выбирает исполнителя (MITA или CITA)** — отвергнуто:
  задача не адресуется исполнителю заказчиком, исполнителя выбирает диспетчер PACT
  (D-007, первый абзац решения).

## Условия пересмотра

- Появление работающего PACT и введение реестра capabilities — момент, когда
  критерий «нет пригодного API» из декларации становится проверяемым механически;
  до этого MITA обязана честно писать в docs, что применяет критерий сама, без
  арбитра.
- Любой сервис из текущих карточек MITA, у которого появляется задокументированный,
  пригодный для использования API (не наблюдение из браузера, а контракт, которым
  можно пользоваться напрямую), — кандидат на пересмотр принадлежности к MITA;
  ближайшие такие кандидаты уже названы в research/allocation.md §2.6
  (`gc-chatium-gateway`, `chatium`, `kinescope`).
- План MITA по подключению Telegram напрямую в `tasks/inbox/` (`ROADMAP.md` MITA,
  этап 2) не относится к границе MITA/CITA, но затрагивает соседнюю границу
  MITA/LINA и уже помечен в ADR 0001 как подлежащий пересмотру; настоящий ADR его
  не переоткрывает.
- Изменение самого D-007 или инварианта 9 CONTOURS.md §10 требует отдельного
  архитектурного решения, а не правки этого ADR.
