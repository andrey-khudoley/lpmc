# Семантика безопасности не может зависеть от метаданных, которые клиент игнорирует

- **Статус:** Принято
- **Дата:** 2026-08-03
- **Контур:** mita

## Контекст

Канонический формат роли в `.agents/agents/<name>.md` содержит поле frontmatter
`tools` — словарь инструментов, доступных роли. На Claude Code это поле реально
работает как ограничение: экспериментально проверено, что делегированная роль
получает ровно перечисленные инструменты (например, ровно 5, без `Bash`/`Agent`,
если они не перечислены).

На Codex CLI 0.146.0 такого механизма нет вовсе. Эксперимент (проведён дважды)
показал: Codex не фильтрует набор инструментов роли по полю `tools` — роль получает
доступ так, как определено на стороне клиента, а не так, как записано в каноне.
Поле `tools` для Codex — не более чем рекомендация, которую клиент технически
свободен игнорировать.

Это устроено ровно так же, как и `.codex/config.toml`: проектный MCP-конфиг Codex
не читает вообще (проверено дважды, включая `trust_level=trusted`) — MCP для Codex
настраивается оператором вручную в `~/.codex/config.toml`, то есть ещё одно место,
где вендор молча не применяет канонический артефакт.

Модель угроз промпт-инъекций (`notes/2026-08/2026-08-05-prompt-injection-threat-model.md`)
прямо опирается на разделение ролей по доверию как на одну из мер: «роль, читающая
недоверенные страницы, не получает `Bash`/`.secrets`; роль с секретами не ходит по
вебу». Эта мера технически осуществима только на Claude Code — под Codex `tools`
ничего не ограничивает, и такое разделение было бы фиктивным на этом клиенте, если
бы система на него полагалась. (Мера, впрочем, зафиксирована в заметке как «не
начато» ни на одном клиенте — этот ADR не о статусе внедрения меры, а о принципе,
которым она обязана руководствоваться, когда будет внедряться.)

Общая архитектурная модель `.agents/ARCHITECTURE.md` строится вокруг связки «один
канонический источник — N вендорных проекций»: адаптер клиента вправе менять
транспорт, синтаксис, имена инструментов и сопоставление профилей моделей, но не
вправе менять цель, политику, ограничения безопасности или критерии результата
сущности (несущий инвариант 6). Факт с полем `tools` — конкретный экспериментально
обнаруженный случай, когда один из клиентов (Codex) фактически ведёт себя так, будто
сам себе присвоил право менять ограничение безопасности — просто не применяя его.

## Решение

Зафиксирован несущий инвариант 7 архитектуры агентского тулинга (дословно,
`.agents/ARCHITECTURE.md`, §2): «Семантика безопасности не может зависеть от
метаданных, которые какой-либо клиент игнорирует. В частности, поле `tools` роли не
является защитой: Codex его не применяет».

Следствие для проектирования изоляции: любой механизм, задуманный как граница
доверия (какие инструменты доступны роли, какая роль видит секреты, какая роль
ходит по недоверенному вебу), обязан быть **enforcement**, а не полем описания,
которое лишь один из клиентов интерпретирует как ограничение. Поле `tools` в каноне
сохраняется — оно полезно там, где клиент его действительно применяет (Claude Code),
и как явная декларация намерения для читающего человека — но проектирование
изоляции не имеет права опираться на него как на единственный барьер, если система
должна работать одинаково безопасно на обоих подключённых клиентах.

Это частный, экспериментально подтверждённый случай общего требования: граница
доверия должна быть навязана средой исполнения (детерминированно, вне зависимости
от того, что и как «понял» конкретный клиент/агент), а не декларативным
метаданными, соблюдение которых не гарантировано.

## Последствия

Положительные:
- Явно названа причина, по которой в текущей MITA разделение ролей по доверию из
  модели угроз промпт-инъекций не может считаться закрытой мерой, даже если поле
  `tools` расставлено «правильно» — Codex сделает его декоративным.
- Инвариант даёт критерий отбраковки будущих решений об изоляции: если механизм
  работает только благодаря добровольному соблюдению клиентом декларативного поля —
  он не в счёт как защита.
- Формализует урок, который дальше используется системой шире собственных границ:
  это методологический предок общесистемного правила «enforcement не использует
  LLM» (D-003, `second-system/DECISIONS.md`) — там та же логика применена не к
  вендорному клиенту, а к самой LLM: выбор маршрута может делать LLM, но полномочия
  назначает только детерминированный слой, потому что LLM тоже не гарантированно
  «соблюдает» инструкцию, если ей передан недоверенный текст.

Отрицательные / что становится дороже:
- Реальную изоляцию по доверию между ролями (недоверенный веб vs секреты) в текущей
  архитектуре MITA нельзя построить средствами `.agents/agents/*.md` в одиночку,
  пока систему нужно подключать и к Claude Code, и к Codex CLI — нужен либо
  клиент-независимый enforcement (не найден и не спроектирован в текущем MITA),
  либо отказ от Codex CLI для ролей, где изоляция критична, либо явное признание
  риска как принятого (сегодня и происходит: мера 2 модели угроз висит «не начато»).
- Дороже становится ревизия любого будущего предложения «давайте ограничим роль
  через `tools`» — теперь оно обязано явно указать, на каком клиенте это реально
  проверено, а не только описано в каноне.

## Рассмотренные альтернативы

- Считать поле `tools` достаточной защитой на основании того, что оно работает на
  Claude Code — отвергнуто: у системы два подключённых и проверенных клиента
  (Claude Code, Codex CLI), и защита, работающая на одном из двух, не является
  защитой системы в целом.
- Отказаться от Codex CLI как клиента, чтобы полагаться на `tools` — не
  рассматривалось как решение в источниках; Codex остаётся вторым подключённым и
  проверенным клиентом наравне с Claude Code.
- Написать для Codex собственный enforcement-слой поверх `tools` — не
  рассматривалось и не спроектировано в текущем MITA; сам факт, что это не сделано,
  и есть причина, по которой мера 2 модели угроз числится «не начато».

## Условия пересмотра

В источниках условия пересмотра не зафиксированы явно. Инвариант закреплён в
`.agents/ARCHITECTURE.md` (статус `DECIDED`, версия 1.0, дата 2026-08-03) и ни разу
не подвергался пересмотру. Он перестанет быть актуальным для конкретного клиента
только если этот клиент начнёт технически применять `tools` как ограничение —
до тех пор изоляция по доверию, построенная на этом поле, остаётся фиктивной для
Codex CLI.
