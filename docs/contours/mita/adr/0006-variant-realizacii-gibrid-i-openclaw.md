# Гибрид на готовом шлюзе как вариант реализации; OpenClaw на контуре исполнения отложен

- **Статус:** Предложено
- **Дата:** 2026-08-09 (дата документа `second-system/DECISIONS.md`, Draft 0.1, в котором
  зафиксированы D-008 и D-009 со статусом «предложено»; отдельная дата принятия именно
  этих двух решений в источниках не выделена, «Хронология» DECISIONS.md §2 фиксирует
  только сам факт вынесения решений в документ этим числом, а не их подтверждение —
  дата первого черновика самого варианта `IMPLEMENTATION-OPTION-OPENCLAW.md` — 2026-08-06)
- **Контур:** mita

## Контекст

Базовая спецификация Second System (`second-system/SPECIFICATION.md`) допускает
несколько способов реализации. Один из них — `IMPLEMENTATION-OPTION-OPENCLAW.md`
(Draft 0.1, 2026-08-06, статус на титуле «вариант для обсуждения») — описывает
третий из трёх рассмотренных вариантов: не полностью самостоятельная реализация всех
канальных адаптеров и Workers, не единственный экземпляр OpenClaw без брокера, а
**гибрид**: OpenClaw на границах системы (Intake Gateway для приёма каналов и
Execution Gateway для запуска Codex/Claude Code) плюс собственное событийное ядро
(брокер, PACT, реестр задач) остаются самостоятельными.

Этот вариант отражён в `second-system/DECISIONS.md` двумя раздельными решениями:

- **D-008** «Вариант реализации: гибрид на готовом шлюзе» — использовать OpenClaw на
  границе внешних коммуникаций, сохранив брокер, событийные контракты, PACT и реестр
  задач самостоятельными. Основание: периферия каналов (webhook lifecycle,
  переподключения, rate limiting, медиа, разбиение сообщений, семантика тредов,
  подтверждения доставки, протокол веб-чата) не создаёт ценности и оценивается
  DECISIONS.md в 4–8 недель самостоятельной разработки, тогда как ценность системы
  сосредоточена в квалификации, политике и контрактах, которые в любом варианте
  остаются собственными.
- **D-009** «OpenClaw на контуре исполнения отложен» — на первом этапе исполнение
  реализуется собственным тонким runner-ом, а не через OpenClaw Execution Gateway;
  готовый runtime рассматривается позже. Основание DECISIONS.md: экономия на
  исполнении наименьшая (одноразовый запуск CLI в изолированной рабочей области —
  сотни строк собственного кода), при этом использование готового шлюза добавляет
  две системы состояния задачи и два уровня политики (business policy PACT и
  technical policy OpenClaw, `IMPLEMENTATION-OPTION-OPENCLAW.md` §8.7), а зависимость
  от стороннего компонента появляется именно в том контуре, где находятся
  персональные учётные данные исполнителя — то есть в MITA/CITA.

Оба решения имеют статус **«предложено»**, а не «принято» — как и связанное с ними
**D-011** «Этап 0: минимальный контур» (начать с одного экземпляра OpenClaw-шлюза,
настроенного конфигурацией, без брокера и собственного кода). При этом
`second-system/STAGE-0.md` (Draft 0.1, 2026-08-09), на который ссылается D-011,
содержит готовые к непосредственному исполнению команды: `curl -fsSL
https://openclaw.ai/install.sh | bash`, `openclaw onboard --install-daemon`, порт
шлюза по умолчанию 18789, конкретные значения конфигурации (`dmPolicy: "allowlist"`,
упоминание `sandbox.mode`). Это создаёт объективный риск: детализация исполнения
опережает статус решения, которое эту детализацию оправдывает, и нигде в источниках
это несоответствие не проговорено явно (research/allocation.md §4.8).

Дополнительно значимо для MITA: раздел 8 `IMPLEMENTATION-OPTION-OPENCLAW.md`
(OpenClaw Execution Gateway) — это и есть архитектурный кандидат на замену
исполнительной части MITA/CITA. Именно этот раздел (не Intake Gateway) отложен
решением D-009. Раздел 15 того же документа перечисляет условия нецелесообразности
варианта (нужен полный контроль над channel pipeline, запрещено загружать сторонний
agent gateway, требования сертификации не позволяют его security-модель), а раздел 17
— одиннадцать открытых вопросов, включая «какую точную версию OpenClaw закрепить» и
«где проходит approval внешней отправки результата»; ни один из них не закрыт.

Фактическое положение MITA не меняется этим ADR ни в одну сторону: MITA сегодня —
`/home/agent/workspaces/cloud-tech-tasks`, независимая система без PACT, без брокера,
без OpenClaw. Слово `OpenClaw` в исходниках MITA не встречается.

## Решение

1. Зафиксировать в воркспейсе MITA сам факт существования варианта реализации:
   систему предполагается собирать как **гибрид на готовом шлюзе** — OpenClaw на
   границах (приём каналов и, отдельным вопросом, исполнение), собственное ядро
   (брокер, PACT, реестр задач) — самостоятельно. Это D-008 second-system.
2. Отдельно и явно зафиксировать, что применение OpenClaw **именно на контуре
   исполнения** (Execution Gateway, `IMPLEMENTATION-OPTION-OPENCLAW.md` §8) —
   **отложено**. Первый этап исполнения — собственный тонкий runner, а не готовый
   шлюз. Это D-009 second-system, и это решение прямо касается MITA/CITA, поскольку
   именно там находятся персональные учётные данные исполнителя.
3. Сохранить статус обоих решений как **«предложено»**, не повышать его этим ADR.
   Наличие в `STAGE-0.md` готовых к исполнению команд (`openclaw onboard
   --install-daemon`, порт 18789 и т.д.) не является фактом принятия D-008/D-009/D-011
   и не должно интерпретироваться как таковой ни в одном документе `docs/` контура
   MITA.
4. Установить правило для всей документации `docs/` MITA (кроме `spec/` и `adr/`):
   **ни одна страница не имеет права описывать OpenClaw как часть текущего
   состояния**. OpenClaw не установлен, не запущен и не используется ни в одной
   части существующей MITA. Любое упоминание OpenClaw вне `docs/adr/` и
   `docs/spec/` — нарушение правил документооборота.

## Последствия

**Положительные.**
- Явно зафиксирована граница между «предложенным вариантом реализации» и «текущим
  состоянием MITA» — это снимает риск того, что кто-то из исполнителей примет
  готовые команды STAGE-0.md за инструкцию к действию.
- D-009 явно защищает наиболее чувствительную часть MITA (custody секретов,
  браузерные сессии, необратимые действия) от преждевременной зависимости от
  стороннего agent gateway с датовым версионированием и нестабильным plugin API
  (риск, зафиксированный в D-008: «удаление бандла `codex-cli` — уже произошедший
  пример подвижности интеграционной поверхности»).
- Разделение Intake Gateway и Execution Gateway на два решения (D-008 отдельно от
  D-009) позволяет в будущем принять одно без автоматического принятия другого —
  граница между «предложено на периферии» и «отложено на исполнении» проведена
  на уровне решений, а не только описания.

**Отрицательные и то, что становится дороже.**
- До момента, когда D-008/D-009/D-011 получат статус «принято», любое планирование
  MITA, опирающееся на OpenClaw Execution Gateway (в частности — как на будущую
  замену собственного тонкого runner-а исполнения задач MITA/CITA), остаётся
  предположением, а не основанием для работы. Это дороже в смысле неопределённости
  горизонта: непонятно, когда и произойдёт ли переход вообще, поскольку D-009
  прямо формулирует условие включения как открытый вопрос («потребность в
  интерактивных возобновляемых сессиях, фоновых задачах и готовой sandbox-модели»),
  а не срок.
- Несоответствие между статусом решений («предложено») и детализацией STAGE-0.md
  (готовые команды установки) само по себе является источником риска
  рассинхронизации документации — исполнителям других контуров (LINA, PACT, CITA)
  придётся повторно сверяться со статусом D-008/D-009/D-011 в `DECISIONS.md`
  при каждом обращении к STAGE-0.md, а не доверять детализации по умолчанию.
- Раздел 17 `IMPLEMENTATION-OPTION-OPENCLAW.md` («Открытые вопросы») и раздел 18
  («Критерий принятия решения») не закрыты; в частности не решено, какую версию
  OpenClaw закреплять и как синхронизировать его task ledger с внешним реестром
  задач PACT/MITA — при принятии D-008/D-009 в будущем эта работа не бесплатна.

## Рассмотренные альтернативы

Альтернативы перечислены в `IMPLEMENTATION-OPTION-OPENCLAW.md` §1 как три варианта
реализации Second System в целом (гибрид — рассматриваемый в этом ADR третий вариант):

1. **Полностью самостоятельная реализация** всех канальных адаптеров и Workers —
   не выбрана для периферии каналов (D-008): полный контроль над каждым байтом
   pipeline, но 4–8 недель на функциональность, не создающую собственной ценности
   системы (webhook lifecycle, rate limiting, медиа, треды, доставка).
2. **Один экземпляр OpenClaw без внешнего брокера** — не рассмотрен подробно в
   зафиксированных решениях; отвергнут неявно тем, что D-008 явно требует сохранения
   самостоятельного брокера и событийных контрактов.
3. **OpenClaw сразу и на приёме, и на исполнении** (без разделения D-008/D-009) —
   не выбран для исполнения: D-009 явно откладывает именно эту часть, аргументируя
   наименьшей экономией (сотни строк собственного runner-а против интеграции с
   датовым внешним API) при наибольшей чувствительности (учётные данные) этого
   контура.
4. Внутри самого варианта OpenClaw `IMPLEMENTATION-OPTION-OPENCLAW.md` §6.2
   рассматривает in-process plugin против external bridge worker для интеграции с
   брокером — оставлено открытым вопросом §17, решение не принято ни в одну сторону.

## Условия пересмотра

- Статус D-008 меняется на «принято» только вместе с явной фиксацией этого факта в
  `second-system/DECISIONS.md`; до этого момента текст настоящего ADR не подлежит
  повышению статуса без синхронного обновления источника.
- Условие включения OpenClaw на контуре исполнения (D-009) сформулировано в
  DECISIONS.md как «потребность в интерактивных возобновляемых сессиях, фоновых
  задачах и готовой sandbox-модели» — наступление этого условия является поводом
  пересмотреть D-009, но не автоматически повышает его статус.
- Критерий принятия варианта в целом сформулирован в
  `IMPLEMENTATION-OPTION-OPENCLAW.md` §18 как семь условий по итогам PoC (§16);
  первые пять из них — обязательные («если хотя бы один... не подтверждается,
  следует вернуться к самостоятельным адаптерам или использовать OpenClaw только
  как execution runtime» — что для MITA означает обратный по смыслу D-009 исход).
- Появление в `docs/` MITA (вне `adr/`, `spec/`) любого описания OpenClaw как уже
  используемого компонента — повод для немедленного исправления документации, а не
  для пересмотра этого ADR.
