# Владельцы физически разделены на clients / projects / internal

- **Статус:** Принято
- **Дата:** 2026-08-08
- **Контур:** mita

## Контекст

К 08.08.2026 в каталоге `clients/` вперемешку лежали 20 сущностей разной природы:
двое постоянных ретейнерных клиентов (NeSo Академия, ИП Ларина) и 18 разовых/
проектных отношений (активные пилоты, завершённые и остывшие проекты, backlog-лиды)
— всё это исторически осталось от миграции из Obsidian-vault (30.07.2026), где
такого различия не проводилось. Отдельно обнаружился собственный технический
контур пользователя (`akh-tech`), формально заведённый как ещё один «клиент».

08.08.2026 в 13:24, во время разбора доступов по общим сервисам (Bizon365,
Kinescope — см. ADR-0009), пользователь явно определил термин: «клиенты» — это
только NeSo и Ларина (постоянные ретейнерные отношения), всё остальное —
«проекты» (разовая или сорвавшаяся работа). Это разошлось с фактическим
устройством каталога `clients/`, где под одной крышей были и клиенты, и проекты,
и внутренний контур.

Смешение имело практическую цену, а не только терминологическую:
- команда «проверь у всех клиентов» при плоском `clients/` требовала либо ручного
  фильтра по 20 записям, либо ошибочно трактовалась как обход всех владельцев —
  зафиксировано как типовая ошибка агента;
- классификация владельца определяет, в чей headed-браузерный инстанс (ADR-0007,
  ADR-0008) попадает сессия при выполнении задачи — ошибка здесь не просто
  косметическая, а меняет фактический маршрут выполнения;
- поле-классификатор в frontmatter карточки owner решило бы это только на
  бумаге: ошибочное значение поля тихо искажает любой срез «по клиентам» без
  видимого сигнала — карточка выглядит валидной, но обход по каталогу и обход
  по полю дают разные множества, и расхождение обнаруживается не раньше, чем
  кто-то сверит их вручную.

Пользователю задан явный вопрос (AskUserQuestion): физическое разделение на три
корня сразу — или промежуточный шаг с полем `relationship` во frontmatter. Выбран
немедленный физический раздел.

## Решение

Владельцы (`owner`) физически разнесены по трём непересекающимся корням
одинаковой внутренней структуры: `clients/` (постоянное сотрудничество —
ретейнер; на сегодня ровно двое: `neso`, `larina`), `projects/` (разовая/
проектная работа — 18 каталогов), `internal/` (собственный технический контур
исполнителя — `akh-tech`). Перенос выполнен через `git mv`, чтобы не рвать
историю файлов: 18 каталогов → `projects/`, `akh-tech` → `internal/`, в
`clients/` остались только `neso` и `larina`.

Слаг владельца уникален глобально среди всех трёх корней (например, `neso` не
может повториться ни в `projects/`, ни в `internal/`) — поэтому идентификатор
задачи (`<slug>/YYYY-MM-DD-<slug задачи>`) не требует указания корня и не
меняется при переносе владельца между корнями.

У каждого корня — свой `INDEX.md` (`clients/INDEX.md`, `projects/INDEX.md`,
`internal/INDEX.md`).

Введено общее слово-зонтик «владелец» (owner) для всех трёх корней — для правил
вида «проверь у всех владельцев» (обход всех трёх корней) против «проверь у всех
клиентов» (теперь буквально `clients/neso` и `clients/larina`, не 20 каталогов).
Обход всех трёх корней делается только по явному «везде»/«по всей системе» или
для системных задач.

Скилл `add-client` переименован в `add-owner`; первым шагом добавлен явный выбор
корня по таблице признаков с инструкцией «корень не угадывать — спросить».

Осознанный технический долг: поле `client:` во frontmatter карточек owner НЕ
переименовано в `owner:` — переименование затронуло бы все карточки разом, а имя
`owner` уже занято в `templates/service.md` под «ответственного со стороны
клиента». Долг зафиксирован явно, не как недосмотр.

## Последствия

Положительные:
- Классификация владельца видна из пути файла, а не из значения поля — обход
  «только клиенты»/«только проекты»/«только internal» становится буквальным
  обходом каталога, без риска, что поле молча разошлось с фактическим местом
  файла.
- Ошибка классификации теперь обнаруживается структурно (не тот каталог) вместо
  того, чтобы тихо искажать срезы «по клиентам» без видимого сигнала.
- Команда «проверь у всех клиентов» перестала быть неоднозначной: это ровно два
  каталога, а не обход 20+ владельцев.
- Глобальная уникальность слага сохранила идентификаторы задач неизменными при
  переносе владельца между корнями (перенос `akh-tech` не потребовал смены id
  существующих задач).

Отрицательные / что становится дороже:
- Поле `client:` во frontmatter осталось несогласованным с фактическим корнем
  владельца (технический долг) — при чтении карточки в отрыве от пути её нельзя
  однозначно классифицировать по одному только frontmatter.
- Перенос владельца между корнями (смена статуса «проект» → «клиент» и обратно)
  теперь требует физического перемещения каталога (`git mv`) вместо правки одного
  поля — дороже разовая операция ради дешевизны постоянного чтения.
- Три корня со своими `INDEX.md` нужно поддерживать в актуальном состоянии
  раздельно; риск рассинхрона `INDEX.md` с фактическим списком каталогов
  добавился к системе (индексы не генерируются автоматически из каталога).

## Рассмотренные альтернативы

- Поле `relationship`/классификатор во frontmatter карточки owner при сохранении
  единого каталога `clients/` — рассматривалось явно как первый вариант вопроса
  пользователю. Отвергнуто: не устраняет главный риск (ошибочное значение поля
  тихо искажает срез, не давая структурного сигнала о расхождении), при этом не
  меняет маршрутизацию по браузерным инстансам, для которой требуется решить,
  куда физически положить сессию, а не как её пометить.
- Оставить единый `clients/` без разделения — отвергнуто пользователем как
  несоответствующее его фактическому словарю («клиенты» ≠ «проекты»); также не
  снимало типовую ошибку обхода «все клиенты» как «все владельцы».

## Условия пересмотра

В источниках условия пересмотра не зафиксированы явно. Отдельно зафиксирован как
факт (не как условие пересмотра) осознанный технический долг — несовпадение
поля `client:` во frontmatter с фактическим корнем владельца; устранение долга
(переименование поля в `owner:` во всех карточках, с учётом коллизии имени в
`templates/service.md`) в источниках не запланировано датой или триггером.
