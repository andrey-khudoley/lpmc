# Агентский тулинг: один канонический источник и N вендорных проекций

- **Статус:** Принято
- **Дата:** 2026-08-03 — приведение агентского тулинга к единому канону («canon
  migration», начато 2026-08-03 00:44); статус документа-источника `.agents/ARCHITECTURE.md`
  — `DECIDED`, версия 1.0, дата 2026-08-03
- **Контур:** mita

## Контекст

До канонизации агентская политика MITA (тогда — `cloud-tech-tasks`) существовала как
22 смысловых блока, продублированных рукописно в 2–14 копиях каждый (правило
журналирования было продублировано 14 раз). Копии расходились по смыслу: например,
описание процедуры `execute-task` теряло шаг архивирования в одних копиях и сохраняло
в других. Единый источник правды был нужен, чтобы добавление нового клиента, роли или
скилла не требовало ручной синхронизации множества файлов — и чтобы расхождение копий
не превращалось в невидимый отказ безопасности (забытый пункт политики в одной из
копий).

Система при этом обслуживает двух реально установленных и проверенных запуском
AI-клиентов с разной механикой — Claude Code и Codex CLI, — у которых разные пути
обнаружения сущностей, разный формат ролей (Markdown-frontmatter против TOML) и,
что критично, разное фактическое поведение: Claude Code применяет поле `tools` роли
как техническое ограничение набора инструментов, Codex CLI такого механизма не имеет
вовсе (проверено экспериментально дважды, включая `trust_level=trusted`). Это означает,
что семантика безопасности не может полагаться на метаданные, которые конкретный
клиент игнорирует — иначе изоляция «роль без Bash/секретов», работающая под Claude
Code, тихо перестаёт действовать под Codex CLI.

## Решение

Единственный физический источник истины — `.agents/`. Всё, что видят конкретные
AI-клиенты (`.claude/`, `.codex/`) и корневые файлы политики (`CLAUDE.md`, `AGENTS.md`,
`AGENTS.override.md`), — либо симлинки на канон, либо детерминированно генерируемые из
него артефакты; ручные правки в этих местах запрещены.

Три типа канонических сущностей, у каждой ровно один путь обнаружения на клиента:

- **Скиллы** (`.agents/skills/<name>/SKILL.md`) — процедура для случая «работаешь
  сам» (главный агент выполняет напрямую).
- **Роли** (`.agents/agents/<name>.md`) — сущность для случая «делегируешь»
  (субагент/спаун); frontmatter `name`, `description`, `tools`, `profile` (`fast |
  balanced | deep | session` — рекомендация оркестратору, не имя модели; поле `model`
  запрещено принципиально).
- **Команды** (`.agents/commands/<name>.md`) — явная пользовательская точка входа,
  обязателен `disable-model-invocation: true`, модель не может вызвать её сама.

Адаптер конкретного клиента вправе менять транспорт, синтаксис, имена инструментов и
сопоставление профилей моделей на конкретные модели — и не вправе менять цель,
политику, ограничения безопасности или критерии результата сущности. Общая политика
инжектируется в делегированную роль целиком (нативно у Claude Code, вклейкой в тело
роли при сборке у Codex CLI) — не по-пунктной подгонке под роль (per-role списки
политики намеренно не создаются: забытый пункт даёт невидимый отказ безопасности).

Generated-артефакты коммитятся в git (свежий clone работает сразу), несут шапку
`GENERATED / source-hash / DO NOT EDIT`; строгие форматы (JSON) регистрируются в
`scripts/generated.lock.json` — хеш всей политики плюс хеш каждого строгого
артефакта. Единый сборщик `node scripts/agents.mjs {build|check|lint}` — `build`
идемпотентно применяет план и сам включает `core.hooksPath`; `check` ничего не
пишет и сверяет план с диском побайтово, падает на отсутствующем/лишнем/устаревшем
артефакте и на выключенном git hook; `lint` валидирует frontmatter, ищет в каноне
литералы credentials/персональных данных, проверяет коллизии имён и единственность
discovery-path. Enforcement одноуровневый и сознательно так: единственный барьер —
`.githooks/pre-commit` (`lint && check`) при одном операторе без второго коммитера и
без PR-флоу; внешнего серверного CI/gate нет.

Подключение нового клиента формально требует только `policy/runtime/<runtime>.md` +
`runtimes/<runtime>.json` (плюс новый модуль доставки в `scripts/agents.mjs`, если
транспорт принципиально новый) — и не требует ни одной правки в `.agents/skills`,
`.agents/agents`, `.agents/commands`, `.agents/policy/common`. Это проверено
механически добавлением пробного `probe.json`/`probe.md`.

`core.symlinks=true` и реальная поддержка симлинков файловой системой — жёсткое
предусловие репозитория; `build`/`check` проверяют это первым действием.

## Последствия

Положительные:

- Устранён источник расхождений копий политики — правка одного места вместо 2–14.
- Добавление роли/скилла/команды или нового клиента не требует ручной синхронизации
  существующих канонических файлов; проверено механически.
- Забытый пункт политики в одной из копий больше не может создать невидимый отказ
  безопасности — политика инжектируется целиком, а не выборочными списками.
- Generated-артефакты с хешем в lock-файле дают механическую (не на honor system)
  проверку того, что вендорная проекция не разошлась с каноном.

Отрицательные / что становится дороже:

- Изоляция по `tools` роли фактически работает только под Claude Code: у Codex CLI
  нет технического ограничения набора инструментов роли (проверено экспериментально
  дважды), поле `tools` там — рекомендация, а не enforcement. Роль, спроектированная
  как «без Bash/без секретов», под Codex CLI такой защиты не имеет.
- Доставка MCP-конфигурации для Codex CLI не автоматизирована до конца:
  `.codex/config.toml` клиентом не читается, генерируемый `.codex/mcp-servers.toml` —
  честно задокументированный фрагмент для ручного переноса оператором в
  `~/.codex/config.toml`; фактической доставки нет.
- Единственный барьер enforcement (`pre-commit` + локальный `core.hooksPath`) сам по
  себе слабое звено: хук лежит в git, но активируется локальной настройкой, которой
  git не хранит — свежий clone приходит без хука, пока `build` не будет запущен явно.
- Любая правка агентской политики требует прогона сборщика (`agents.mjs build`)
  и понимания, какие файлы — источник, а какие — производные; прямая правка
  `.claude/`/`.codex/`/корневых файлов политики технически возможна (симлинк можно
  случайно заменить обычным файлом) и требует отдельной дисциплины, которую
  проверяет только `check`/`lint` на этапе коммита, а не в момент правки.
- Развитие модели на новых клиентов (Gemini CLI, Kimi Code и т. п.) сознательно не
  начато — карты рантаймов заводятся только для установленных и проверенных запуском
  клиентов, непроверяемое утверждение в канон не попадает.

## Рассмотренные альтернативы

Отдельного раздела альтернатив в источниках не зафиксировано — решение принято сразу
в форме «один канон + генерация», по образцу архитектуры, взятой из соседнего
воркспейса `cloud-chatium-coder`. Явно отвергнутые внутри самого решения элементы
(зафиксированы как «намеренно не созданы», а не как рассмотренные и отклонённые
внешние варианты):

- отдельные `entity.yaml`, граф воркфлоу, prompt-DSL — не заведены;
- per-role списки политики вместо общей инъекции целиком — не заведены (риск
  забытого пункта);
- вендорные вставки внутри канонических сущностей — не допускаются;
- отдельная таксономия capability — не заведена.

Отдельно был снят (2026-08-03, реконструировано постфактум) первоначально
двухуровневый enforcement: pre-commit hook + внешний GitHub Actions CI. GitHub
Actions отклонён как не соответствующий модели «один оператор, прямые коммиты в
`main`, без PR-флоу» — gate на push сообщает о расхождении постфактум, когда оно уже
в истории, и репозиторий содержит контактные данные живых людей, что делает checkout
на внешние раннеры необоснованной экспозицией.

## Условия пересмотра

Явно зафиксировано в `.agents/ARCHITECTURE.md` §8.1: появление второго коммитера или
переход на PR-флоу обязывает вернуть внешний серверный gate с branch protection —
локального `pre-commit` в этом случае недостаточно.

Отдельно как открытый (не решённый) вопрос архитектуры зафиксировано отсутствие
точечного отсечения опасных инструментов MCP (например, `browser_run_code_unsafe`)
внутри allowlist-шаблона `mcp__playwright__*` — это не условие пересмотра решения о
каноне как таковом, а известный пробел модели угроз в её нынешнем виде.

Различие в фактическом enforcement `tools` между Claude Code и Codex CLI (см.
«Последствия») — рассматривается как постоянное ограничение модели, а не как
временный дефект: пересмотр потребовался бы, если бы Codex CLI приобрёл собственный
механизм фильтрации инструментов ролей, либо если бы система перестала полагаться на
`tools` как единственный барьер изоляции для чувствительных ролей.
