# Общий секрет не означает общую сессию; слаг shared для общих учётных записей

- **Статус:** Принято
- **Дата:** 2026-08-08
- **Контур:** mita

## Контекст

08.08.2026 при разборе доступов для карточек сервисов вскрылось, что часть учётных
записей физически общая для нескольких владельцев, а не отдельная у каждого.

Первый случай — Bizon365: пользователь попросил записать доступы для трёх владельцев
(NeSo, Larina, internal), и логин, пароль и TOTP-секрет совпали посимвольно во всех
трёх «блоках» — различался только project ID в URL. Это одна учётная запись с доступом
к трём проектам, а не три отдельных доступа. Запись трижды означала бы три копии
одного пароля с риском тихого рассинхрона при следующей ротации (расхождение
вскрылось бы только отказом входа). Решение вынесено пользователю явным вопросом
(AskUserQuestion): общий слаг `shared` для позиции `<client>` в имени секрета
против дублирования записи по каждому владельцу — выбран `shared`.

Второй случай — Kinescope, 08.08.2026, тем же днём: тот же паттерн `shared`, но с
другой природой владения — аккаунт Kinescope принадлежит лично пользователю
(владелец `internal`), а клиенты живут как «проекты» внутри его личного аккаунта
(в отличие от Bizon365, где общая учётка — агентская, обслуживающая чужие проекты
клиентов). Разная природа владения не изменила механику: тот же слаг `shared`
используется одинаково в `env` (`SHARED__<SERVICE>__*`), `totp/shared/<service>` и
`storage-state/shared/<service>.json`.

К моменту введения `shared` уже существовала изоляция браузера по клиентам —
отдельные headed-инстансы (см. ADR-0007) с раздельными профилями/сессиями на
владельца, реализованная несколькими часами ранее в тот же день. Это сделало
возможным развести общий секрет по раздельным рантаймам, не разделяя при этом
пароль.

Явной формулировкой при записи в `services/bizon365/overview.md` зафиксировано:
«общий секрет ≠ общая сессия» — профили браузера у владельцев разные, несмотря на
общий пароль.

## Решение

Один физический аккаунт сервиса может легитимно обслуживать нескольких владельцев
(клиентов/проектов). Для такой учётной записи в позиции `<client>` канонического
имени секрета (`<client>/<service>/<field>`) введён специальный слаг `shared`:
`shared/bizon365`, `shared/kinescope`. Тот же слаг используется одинаково во всех
трёх местах хранения — `env` (`SHARED__<SERVICE>__*`), `totp/shared/<service>`,
`storage-state/shared/<service>.json` — и в общей карточке сервиса
(`services/<service>/overview.md`, `client: shared`), на которую ссылаются
клиентские карточки-потребители.

`shared` используют только когда учётная запись **физически одна** (совпадают
логин, пароль, TOTP-секрет — различается лишь то, к каким объектам она даёт
доступ, например project ID в URL). Если у владельцев разные учётные записи с
совпадающим паролем — это разные секреты и разные записи, `shared` здесь не
подходит.

Это разрешение делить секрет не распространяется на рантайм. Правило введено явно
и дважды (Bizon365, Kinescope): **делить учётные данные допустимо, делить сессию
(профиль браузера, процесс) — запрещено.** Каждый владелец, пользующийся общей
учётной записью, работает через свой headed-браузерный инстанс (ADR-0007) со
своим профилем/сессией. Общий пароль не означает общую cookie-сессию и не
означает, что действие одного владельца видно как действие другого внутри
сервиса.

## Последствия

Положительные:
- Ротация пароля/TOTP для общей учётной записи выполняется один раз в одном месте,
  без риска рассинхрона копий, который раньше вскрывался бы только отказом входа.
- Природа доступа («учётка одна на всех» против «у каждого своя») теперь видна
  прямо из имени секрета (`shared/...`), а не восстанавливается по совпадению
  паролей постфактум.
- Разделение секрета и сессии позволило использовать общий пароль без того, чтобы
  действия разных владельцев смешивались в одном браузерном профиле.

Отрицательные / что становится дороже:
- `shared`-учётки размывают границу «владелец = единица изоляции»: выдача доступа
  к задаче под одним владельцем (например, `neso`) физически означает выдачу
  секрета, действующего и на остальных потребителей той же общей учётки
  (`larina`, `internal` — для Bizon365). Технически ограничить действие секрета
  рамками одного владельца средствами самого секрета нельзя — MITA сегодня этого
  и не делает.
- Побочные эффекты общей учётки затрагивают всех владельцев разом, а не одного:
  зафиксирован реальный случай (Kinescope) — заморозка аккаунта за долг бьёт по
  всем клиентам-потребителям сразу, хотя внешне выглядит как проблема одного
  клиента.
- Дороже становится ревизия карточек при появлении общей учётки: две ранее верных
  формулировки в карточке NeSo/Kinescope (привязка workspaceId к NeSo,
  предполагаемая изоляция заморозки) стали неверными и потребовали исправления с
  явной пометкой, что раньше было записано иначе.

## Рассмотренные альтернативы

- Дублирование записи секрета по каждому владельцу (три копии пароля Bizon365 под
  NeSo/Larina/internal) — отвергнуто как источник тихого рассинхрона при ротации:
  расхождение копий вскрывалось бы только отказом входа, без явного сигнала на
  момент рассинхрона.
- Поле `relationship`/пометка в frontmatter вместо отдельного слага в позиции
  `<client>` — не рассматривалось как отдельный вариант в источниках для этого
  конкретного решения (в отличие от структурного разделения
  `clients/projects/internal` тем же днём, где такая альтернатива обсуждалась
  явно); слаг `shared` выбран сразу как естественное расширение уже существующей
  схемы имени `<client>/<service>/<field>`.

## Условия пересмотра

В источниках условия пересмотра не зафиксированы явно. Правило действует с
08.08.2026 и ни разу не подвергалось сомнению вплоть до 09.08.2026 (дата
журнала-источника). Отдельно отмечено (не как условие пересмотра, а как открытый
риск): при разделении контуров политику «секрет привязан к владельцу задачи» для
`shared`-учёток технически построить нельзя — авторизация на общий секрет
расширяет радиус поражения на всех его потребителей, и это придётся делать видимым
в вердикте о выдаче доступа, а не молчаливо принимать как факт.
