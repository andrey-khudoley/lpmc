# Capability не содержит указания на модальность исполнения

- **Статус:** Принято
- **Дата:** 2026-08-08 (CONTOURS.md §7.3 зафиксировал правило вместе с разрезом контуров
  по модальности исполнения; как отдельное решение D-007 закреплено в
  `second-system/DECISIONS.md`, документ датирован 2026-08-09; CONTOURS.md §10
  фиксирует его же как инвариант 9)
- **Контур:** mita

## Контекст

Граница между MITA и CITA проходит не по вендору и не по предметной области, а по
наличию у целевой системы пригодного опубликованного контракта (CONTOURS.md §7.1:
«граница проходит по наличию пригодного API у целевой системы, а не по предметной
области»). Эта граница по определению подвижна: у сервиса, сегодня доступного только
через веб-интерфейс, завтра может появиться API — и тогда работа с ним переезжает из
MITA в CITA без изменения сути задачи (CONTOURS.md §7.3).

Конкретный пример такой подвижности уже виден в самой MITA, а не только в архитектурной
прозе. `services/gc-chatium-gateway/` — карточка сервиса типа `web` (браузерная
модальность, обслуживается MITA), но `research/allocation.md` §2.6 называет его
«ближайшим реальным кандидатом в CITA»: у GetCourse есть собственный API (старый и
новый), и gateway на нём уже частично построен. Один и тот же предмет — интеграция с
GetCourse — распределён между двумя контурами по признаку модальности, и эта граница
способна сдвинуться в любую сторону без изменения того, что именно делается.

Если бы имя возможности несло способ исполнения (например, `invoice.submit.via-web`),
переезд возможности между контурами потребовал бы переименования capability и,
следовательно, переписывания всех политик, ссылающихся на старое имя, — то есть смена
инфраструктурного механизма (браузер → HTTP-клиент) превращалась бы в смену контракта
между PACT и заказчиком задачи. Задача не адресуется исполнителю заказчиком напрямую:
исполнителя для конкретного вызова выбирает диспетчер PACT (CONTOURS.md §7.3, D-007),
и это возможно только если имя capability не завязано на то, кто именно её выполнит.

Настоящий ADR — дубликат D-007 в воркспейсе MITA: переносит то же решение с тем же
статусом, но фиксирует, для чего именно это правило применимо здесь — правило переезда
возможностей MITA → CITA, а не абстрактная формулировка. Оговорка о фактическом
положении: в исходниках самой MITA (`.agents/`, карточки `services/*`) понятия
`capability` в смысле D-007 не существует вовсе — реестра capability, PACT и
диспетчеризации задач по контрактам в MITA сегодня нет. Задачи адресуются напрямую
человеком в сессии Claude Code / Codex CLI, а не выдаются диспетчером. Слово
`capability` в `.agents/ARCHITECTURE.md` (§4.4, §12) встречается в другом, не связанном
с D-007 смысле — как отклонённая идея таксономии способностей агентских сущностей
(skills/roles/commands) внутри канона `.agents/`, а не как единица политики PACT; эти
два употребления не следует смешивать.

## Решение

1. Имя capability описывает **действие**, а не способ его выполнения: глагол и объект
   действия (`invoice.submit`), без суффикса модальности (`.via-web`, `.via-api`,
   `.browser`).
2. Модальность исполнения — свойство исполнителя (MITA или CITA), которого выбирает
   диспетчер PACT под конкретный вызов, а не свойство, зашитое в идентификатор
   возможности или выбираемое заказчиком задачи.
3. Переезд возможности из браузерной модальности MITA в контрактную модальность CITA
   (появление у сервиса пригодного API) не меняет имя capability и не требует
   переоформления политики, ссылающейся на это имя, — меняется только маршрут
   диспетчеризации.
4. Для MITA это означает: карточка сервиса (`services/<name>/`) может фиксировать
   текущую модальность (поле `type: web` — фактическое положение сервиса сегодня), но
   эта модальность — свойство состояния интеграции с конкретным вендором на сегодня,
   а не часть контракта возможности, которую предстоит формализовать при появлении
   PACT.

## Последствия

**Положительные.**
- Появление API у сервиса, который MITA сегодня обслуживает через браузер (кандидат —
  `gc-chatium-gateway`, `research/allocation.md` §2.6), не потребует переписывания
  политик доступа, approval-правил или ссылок на возможность в других частях системы —
  потребуется только сменить исполнителя в маршруте PACT.
- Политика, написанная один раз в терминах действия, остаётся валидной независимо от
  того, кто её исполняет сегодня и кто будет исполнять завтра.
- Правило снимает соблазн зашивать в имя возможности сведения об инфраструктуре
  (браузер, CDP-порт, конкретный сервис) — эти сведения принадлежат карточке сервиса и
  исполнителю, а не идентификатору задачи.

**Отрицательные и что становится дороже.**
- Диагностика усложняется: по одному имени capability нельзя на глаз понять, каким
  именно способом задача будет исполнена — эта информация вынесена в отдельный
  маршрут диспетчеризации (в PACT) или, до появления PACT, — в карточку сервиса и
  ручное решение человека.
- Правило сегодня не на чем проверять на практике: в MITA нет ни реестра capability, ни
  диспетчера, который выбирал бы исполнителя, — задачи адресуются напрямую человеком,
  а не именем возможности. Решение зафиксировано заранее, до появления механизма,
  который его исполняет.
- При появлении реестра capability в MITA/PACT потребуется договориться об одном
  общем словаре имён действий отдельно от существующей структуры карточек сервисов
  (`services/<name>/`, поле `type`) — это дополнительная работа по согласованию,
  которой сегодня не существует.

## Рассмотренные альтернативы

Альтернативы разбирались на уровне системы в целом (CONTOURS.md §7.3, D-007,
«Основание»), а не отдельно для MITA, и воспроизводятся здесь по тем же источникам.

- **Кодировать модальность в имени возможности** (`invoice.submit.via-web` /
  `invoice.submit.via-api`) — отвергнуто: переезд возможности между контурами при
  появлении API у сервиса потребовал бы переименования capability и переписывания всех
  политик, ссылающихся на старое имя, вместо простого изменения маршрута
  диспетчеризации.
- **Адресовать задачу исполнителю напрямую заказчиком** (человек или вышестоящая
  система указывает «отправь через MITA» вместо «выполни `invoice.submit`») —
  отвергнуто как модель на уровне системы: выбор исполнителя — полномочие диспетчера
  PACT, а не заказчика задачи; иначе заказчик мог бы обходить арбитра выбором
  исполнителя. Сегодня в MITA это правило нарушается по факту, поскольку PACT не
  существует и задачу человек ставит напрямую MITA — этот разрыв уже зафиксирован
  ADR-0002 (§ «Контекст») и не переоткрывается здесь.
- **Хранить модальность как метаданные в самой возможности, но не в имени** (например,
  поле `preferred_modality` в описании capability) — не отвергнуто в общесистемных
  источниках прямо, но не выбрано как решение: раз модальность — атрибут исполнителя,
  выбираемый диспетчером под конкретный вызов, хранение её как атрибута самой
  возможности создавало бы второй источник истины о том же факте.

## Условия пересмотра

- Появление в MITA работающего реестра capability и диспетчера, соответствующего PACT,
  — момент, когда это правило впервые становится проверяемым на практике, а не только
  декларативным; раздел «Последствия» тогда обязан быть переписан из «не на чем
  проверять» в фактическое состояние.
- Реальный переезд `gc-chatium-gateway` (или любого другого сервиса из
  `services/`) из карточки типа `web` в интеграцию CITA — первый практический случай,
  на котором это правило проверяется; если переезд потребует переименования имён
  возможностей или политик, правило нарушено по факту и это должно быть зафиксировано
  честно, а не скрыто.
- Изменение самого D-007 или инварианта 9 CONTOURS.md §10 требует отдельного
  архитектурного решения, а не правки этого ADR.
