# Декомпозиция системы на четыре контура и место MITA в ней

- **Статус:** Принято
- **Дата:** 2026-08-08 (CONTOURS.md зафиксировал разрез на четыре контура); имена контуров (LINA/PACT/MITA/CITA) закреплены 2026-08-09 (DECISIONS.md D-002, «Хронология»)
- **Контур:** mita

## Контекст

Система, частью которой является MITA, проектируется как четыре контура с разными
причинами меняться: LINA (диалог с человеком), PACT (политика, авторизация,
реестр задач), MITA (исполнение через интерфейсы для человека — браузер, веб-панели)
и CITA (исполнение по опубликованным API-контрактам). Обоснование разреза —
«у каждого контура своя ось изменений, и эти оси не пересекаются» (CONTOURS.md §3.1),
и то, что контуров доверия только два — недоверенный и привилегированный, — а граница
между ними проходит по PACT, единственному арбитру (CONTOURS.md §3.2).

Это решение принято на уровне всей системы как D-001 в
`second-system/DECISIONS.md` («Декомпозиция на четыре контура», статус «принято») и
детально раскрыто в `second-system/CONTOURS.md` §1 (назначение документа), §9
(таблица владения состоянием) и §10 (11 зафиксированных инвариантов). Настоящий ADR —
дубликат D-001 в воркспейсе MITA: тот же факт декомпозиции, но с явной фиксацией
следствий для MITA, которых нет и не может быть в общесистемном документе, писавшемся
без знания о существующей MITA (`second-system/` ни разу не упоминает
`cloud-tech-tasks` — research/allocation.md §0.5).

Важная оговорка по фактическому положению дел (research/allocation.md §0): сегодня
реально существует и почти готова только MITA, репозиторий
`/home/agent/workspaces/cloud-tech-tasks`. LINA, PACT и CITA как работающие системы
не существуют, их рабочие каталоги пусты. Слова `LINA`, `PACT`, `CITA` не встречаются
в исходниках MITA ни разу; сопоставление «сущность MITA ↔ контур» — инженерная
реконструкция, а не факт из источника MITA.

## Решение

Система делится на четыре контура — LINA, PACT, MITA, CITA. Контуров доверия два:
недоверенный (LINA) и привилегированный (MITA, CITA); PACT — арбитр на границе между
ними, единственная точка, через которую проходит путь от внешнего сообщения к
исполнителю и обратно (CONTOURS.md §3.2, §3.3; инварианты 1–2 из CONTOURS.md §10).

Место MITA в этом разрезе: MITA — привилегированный, но недоверенный по итогу
исполнения контур. Она обладает доступом к внешним системам (браузерные сессии,
секреты — по целевой архитектуре custody у PACT) и не принимает решений о том, что и
когда выполнять (CONTOURS.md §2). Прямое следствие для MITA из инвариантов CONTOURS.md
§10, воспроизведённое дословно там, где это применимо к контуру:

- MITA не имеет пути к человеку в обход PACT: диалог, уточнения и доставка результата —
  зона LINA (инвариант 2; CONTOURS.md §5).
- MITA не публикует внешние сообщения и не решает, что из результата раскрыть —
  единственный продюсер внешних сообщений — egress-часть PACT (инвариант 6;
  D-004 «PACT является двусторонней точкой сужения»).
- MITA по целевой архитектуре не имеет прямого исходящего сетевого доступа; весь
  трафик — через egress proxy под управлением PACT (инвариант 7; D-005).
- Учётные данные внешних систем по целевой архитектуре не находятся в MITA;
  custody — у PACT (инвариант 8).
- Исполнителя (MITA либо CITA) на конкретную задачу выбирает PACT; capability не
  содержит указания на модальность — граница MITA/CITA подвижна и определяется
  наличием пригодного API у целевой системы, а не предметной областью
  (инвариант 9; D-007; CONTOURS.md §7.1, §7.3).
- В MITA необратимые действия по умолчанию требуют approval; отнесение действия к
  необратимым определяет таблица PACT, а не решение агента MITA (инвариант 10; D-006).

## Последствия

**Положительные.**
- Явная граница «можно ли» (PACT) / «как именно» (MITA) снимает с MITA обязанность
  решать о легитимности задачи и владельца, о полномочиях, о допустимости раскрытия
  результата — это чужая зона ответственности, и её не нужно проектировать внутри MITA.
- Подвижность границы MITA/CITA по наличию API (а не по предметной области) означает,
  что появление у вендора API не требует переписывания политик PACT — только смены
  исполнителя при том же имени capability (CONTOURS.md §7.3).
- Асимметрия риска MITA (недоверенный веб-контент, живые сессии, необратимые действия)
  получает системный, а не самодельный ответ: approval по умолчанию на необратимое,
  а не решение агента ad hoc.

**Отрицательные и то, что становится дороже.**
- Сегодня PACT физически не существует, поэтому все перечисленные следствия для MITA —
  целевое состояние, а не факт: MITA сама решает о легитимности и владельце задачи,
  сама читает секреты без посредника, сама решает, что отдать человеку в отчёте, ведёт
  диалог напрямую в сессии Claude Code / Codex CLI, имеет прямой исходящий доступ
  (нет egress-принуждения, цепочка OUTPUT в nftables — policy accept). Это явный
  разрыв с инвариантами 2, 6, 7, 8 CONTOURS.md §10, задокументированный как факт, а
  не как проект (research/allocation.md §0, §4.5).
- Перенос custody секретов, введение egress proxy и передача реестра задач в PACT —
  это будущие миграции с реальной стоимостью (переписывание `var/login-checks/*.mjs`,
  схемы карточек задач, схемы каталогов владельцев), а не бесплатное переименование.
- Ближайший практический конфликт с этим решением — план MITA по прямому подключению
  Telegram в `tasks/inbox/` (`ROADMAP.md` MITA, этап 2) противоречит тому, что каналы
  и диалог принадлежат LINA (CONTOURS.md §2, §5); подлежит пересмотру в пользу LINA
  (research/allocation.md §4.7).
- Дороже становится документирование: любое утверждение о MITA теперь обязано
  различать «как есть сегодня» (docs/) и «как должно быть по контуру» (spec.md), иначе
  документация начинает пересказывать спецификацию в будущем времени.

## Рассмотренные альтернативы

Альтернативы самой декомпозиции на четыре контура в источниках не описаны — D-001
зафиксирован без явного перечня отвергнутых вариантов; основание решения приведено
как согласованность оси изменений (CONTOURS.md §3.1) и необходимость арбитра между
двумя контурами доверия (CONTOURS.md §3.2). Альтернативы, зафиксированные для смежных
частей той же декомпозиции, релевантные для MITA:

- Разрез MITA/CITA по предметной области вместо модальности исполнения — отвергнут:
  привёл бы к переписыванию политик PACT при появлении API у вендора вместо простой
  смены исполнителя (CONTOURS.md §7.3, D-007).
- Совмещение диспетчерской классификации задачи (кто исполнитель, какие capabilities)
  с ролью `qualifier` внутри MITA — отвергнуто; граница проведена по вопросу «хватает
  ли информации, чтобы передать запрос дальше» (LINA) против «к какому классу
  относится задача и кто исполнитель» (диспетчер PACT); граница помечена как
  предложение с отсылкой к открытому вопросу CONTOURS.md §13 (research/allocation.md
  §4.2).

## Условия пересмотра

- Изменение любого из 11 инвариантов CONTOURS.md §10 требует отдельного архитектурного
  решения (правило зафиксировано там же).
- Открытый вопрос CONTOURS.md §13 «где проходит граница между подчинёнными агентами
  LINA и диспетчером PACT при классификации» не закрыт этим ADR и подлежит решению
  при проработке контуров.
- План MITA (`ROADMAP.md`, этап 2, подключение Telegram напрямую в `tasks/inbox/`)
  противоречит этому разрезу и должен быть пересмотрен в пользу передачи канала LINA
  до его реализации.
