# Механический контроль — локальный pre-commit, внешний CI снят

- **Статус:** Принято
- **Дата:** 2026-08-03 (снятие внешнего CI зафиксировано в 12:19 этого дня; запись
  журнала — реконструкция постфактум из git-диффа в 13:2x, помечена в источнике как
  утрата исходного журнала за эту сессию)
- **Контур:** mita

## Контекст

На момент канонизации агентского тулинга («canon migration», 2026-08-03 00:44)
enforcement механической проверки канона (`.agents/`) был двухуровневым: локальный
git-хук `pre-commit` плюс внешний GitHub Actions CI на `push`. Тем же днём, позже,
внешний CI был снят отдельным решением.

Обоснование снятия, зафиксированное в источнике: при одном операторе и прямых
коммитах в `main` (без PR-флоу) gate на `push` ничего не предотвращает — он сообщает
о расхождении постфактум, когда несоответствие канону уже попало в историю
репозитория. К этому добавлен второй довод: репозиторий содержит контактные данные
живых людей (клиентов, владельцев), и checkout этого репозитория на внешние раннеры
GitHub Actions — необоснованная экспозиция этих данных вовне узла.

Настоящей слабой точкой самого `pre-commit` оказался при этом не флаг `--no-verify`,
а способ включения хука: файл хука лежит в git, но применяется он только через
локальную настройку `core.hooksPath`, которую git не хранит как часть репозитория —
свежий clone приходит без действующего хука. Это закрыто отдельно, механически:
`agents.mjs build` сам выставляет `core.hooksPath`, а `agents.mjs check` требует,
чтобы хук был включён, и завершается с exit 2, если нет.

## Решение

Единственный барьер механической проверки канона — локальный
`.githooks/pre-commit`, запускающий `agents.mjs lint && agents.mjs check`. Внешнего
серверного CI/gate нет.

Тем же хуком, отдельным некритичным шагом после `lint`/`check`, выполняются ещё два
действия обслуживания индекса `knowledge-search` (`obsidian-hybrid-search`):

- починка симлинка `.obsidian-hybrid-search.db` → `var/knowledge-search/index.db`,
  если он был снесён предыдущим `reindex --force` (движок вычисляет путь к базе
  жёстко внутри `OBSIDIAN_VAULT_PATH` и при `wipeDatabaseFiles()` удаляет файл по
  этому пути, включая симлинк, без ошибки);
- переиндексация (`reindex`) — неудача этого шага коммит не останавливает, это
  удобство, а не барьер.

## Последствия

Положительные:

- Расхождение с каноном ловится до появления в истории `main`, а не постфактум на
  `push` — единственная точка, где вообще можно остановить коммит, это локальный
  хук перед его созданием.
- Контактные данные живых людей, хранящиеся в репозитории, не покидают узел через
  checkout на внешние раннеры CI.
- `knowledge-search` синхронизируется с тем же ритмом, что и коммиты, без отдельного
  файлового вотчера (которого у движка нет) и без второго источника правды для
  списка исключений индексации (хук читает `env` MCP-сервера прямо из
  `.agents/mcp/registry.json`).

Отрицательные / что становится дороже:

- Единственный барьер — локальный `pre-commit`, активируемый локальной настройкой
  `core.hooksPath`, которую git не версионирует: свежий clone уязвим до первого
  запуска `build`. Это компенсировано (см. «Контекст»), но остаётся структурным
  свойством модели «один барьер», а не устранено полностью — `--no-verify` по-прежнему
  обходит хук технически.
- Известное свойство переиндексации: она выполняется внутри `pre-commit` **до**
  создания коммита и индексирует **рабочее дерево**, а не staged-содержимое. Это
  значит, что в индекс может попасть незакоммиченное или впоследствии отменённое
  изменение, а частично застейдженные правки индексируются в неконсистентном виде
  относительно того, что реально фиксируется коммитом. Некритично для поиска по
  знаниям, но дороже, если на индекс начнут полагаться как на точный слепок истории.
- Модель явно держится на допущении «один оператор, прямые коммиты в `main`, без
  PR-флоу». Как только это условие перестаёт быть верным, единственный локальный
  барьер становится недостаточным — сообщить о нарушении канона до появления его в
  истории `main` при параллельных ветках и мёрджах он больше не сможет.
- Возврат внешнего gate (если условие пересмотра наступит) — не бесплатная операция:
  придётся заново решать вопрос экспозиции контактных данных на внешних раннерах,
  который и был одним из двух исходных доводов против CI.

## Рассмотренные альтернативы

Явного перечня отклонённых альтернатив (кроме исходного двухуровневого
enforcement, который и был заменён) в источниках не зафиксировано. Решение принято
как снятие одного из двух уже существовавших уровней, а не как выбор среди
нескольких новых вариантов.

## Условия пересмотра

Условие пересмотра зафиксировано явно и буквально в источнике (`.agents/ARCHITECTURE.md`
§8.1): появление второго коммитера или переход на работу через PR обязывает вернуть
внешний серверный gate вместе с branch protection — локального `pre-commit` в этом
случае недостаточно.

Отдельно зафиксировано как открытый вопрос, не закрытый в источниках: с 8 августа
2026 в системе реально появились параллельные/фоновые браузерные инстансы и
исполнители (реализация изоляции по клиентам), и формально это по-прежнему
«один оператор» в смысле условия пересмотра (один человек-пользователь, коммиты
по-прежнему делает он), но вопрос «достаточно ли этого узкого прочтения условия
теперь, когда параллельно с человеком коммитить в принципе может фоновый агент»
после появления такой параллельности повторно не поднимался. Это не факт о
пересмотре решения, а честно зафиксированный пробел: решение остаётся в силе как
есть, пока кто-то не поднимет вопрос явно.
