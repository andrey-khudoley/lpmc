# Плейбуки

> docs-as-state: этот документ описывает то, что есть сейчас, по исходникам репозитория
> `cloud-tech-tasks` (снимок каталога `playbooks/` и `templates/playbook.md` на
> 2026-08-08/2026-08-09, дата чтения — 2026-08-10). Целевое владение плейбуками и
> требования к их содержанию — `docs/spec/spec.md` §13.3 «Плейбуки»; здесь этот пункт
> упомянут один раз как указатель: по факту сегодняшняя форма плейбука уже совпадает с
> тем, что там описано (плейбук целиком принадлежит MITA, отвечает на вопрос «как
> именно»), пересказа желаемого состояния ниже нет.

## 1. Что такое плейбук

Плейбук — оформленная процедура для класса повторяющихся ручных сценариев: не под одну
конкретную задачу, а под класс задач с одинаковыми шагами и признаками применения. Один
плейбук = один файл `<playbook-slug>.md` по шаблону `templates/playbook.md` (§2 ниже).

Плейбуки живут на двух уровнях, физически разных каталогах:

- **Общие** — `playbooks/<playbook-slug>.md` в корне репозитория. Применимы к любому
  владельцу, для которого подходят признаки из раздела «Когда применять».
- **Клиентские (локальные)** — `<root>/<owner>/playbooks/<playbook-slug>.md`, где
  `<root>` — один из трёх корней владельцев (`clients/`, `projects/`, `internal/`).
  Описывают процедуру, специфичную для конкретного владельца (например,
  `clients/larina/playbooks/getcourse-lesson-replication.md` — тиражирование урока
  GetCourse между потоками одного курса, применимо только к сервису и структуре курсов
  этого клиента).

При заведении нового владельца каталог `<root>/<owner>/playbooks/` создаётся сразу
(скилл `add-owner`), пустым — с `.gitkeep`. На срез документа он заполнен только у
`clients/larina/`; у остальных 20 владельцев — пуст.

## 2. Шаблон `templates/playbook.md`

Полный текст шаблона:

```markdown
---
name: <playbook-slug>
client: shared          # или <client-slug>, если процедура клиентская
task-class: ""          # класс задач, к которому применим
updated: YYYY-MM-DD
---

# <Название процедуры>

## Когда применять

<Признаки задачи, для которой этот плейбук.>

## Предусловия

<Какие доступы/сервисы/данные нужны до начала.>

## Шаги

1. <...>

## Верификация

<Как убедиться, что результат достигнут.>

## Известные проблемы

<Что может пойти не так и что с этим делать.>
```

Frontmatter — четыре поля: `name` (совпадает со слагом файла), `client` (`shared` для
общих плейбуков или слаг конкретного владельца), `task-class` (свободный текст —
описание класса задач, к которому применим плейбук), `updated` (дата последней правки).
Тело — пять фиксированных секций: «Когда применять», «Предусловия», «Шаги» (нумерованный
список), «Верификация», «Известные проблемы». Порядок и состав секций в фактических
плейбуках не варьируется.

## 3. Приоритет клиентских плейбуков над общими

Правило зафиксировано в `.agents/policy/common/05-client-precedence.md`: поиск плейбука
(и сервиса) для задачи владельца идёт **сначала у владельца, потом в общих каталогах**.
То же самое, но операционно — в шаге подготовки контекста скилла `execute-task`
(`.agents/skills/execute-task/SKILL.md`, шаг 2): «релевантные плейбуки (сначала
`<root>/<owner>/playbooks/`, затем `playbooks/INDEX.md`)».

Смысл приоритета: всё специфичное для владельца обязано жить строго внутри его
каталога, чтобы при необходимости выделяться в отдельный репозиторий одним `mv` без
хирургии по остальному дереву. Общий плейбук остаётся действующим по умолчанию для всех,
у кого нет собственного варианта на тот же класс задач; локальный вариант, если он
заведён, не дополняет общий, а замещает его для этого владельца.

Других механизмов разрешения конфликта (слияние, наследование секций общего плейбука в
локальном и т. п.) в системе нет — правило ровно одно: «нашёл у владельца — общий не
смотришь».

## 4. `playbooks/INDEX.md`

Плоский список общих плейбуков с однострочным описанием и ссылкой; для каждого корня
владельцев — свой `playbooks/INDEX.md` внутри `<root>/<owner>/`. Правило, общее для всех
каталогов с `INDEX.md` в репозитории: после изменения состава каталога — обновить
`INDEX.md` (в частности, это явный шаг скилла `compact-notes`, который среди прочего
сверяет `INDEX.md` с фактическим содержимым каталога).

Текст `playbooks/INDEX.md` на срез документа — один пункт:

```
- [Капча на пути агента](captcha-escalation.md) — агент упёрся в проверку «вы человек»:
  что пробовать самому, когда звать человека и как передать ему управление браузером.
```

## 5. Единственный существующий общий плейбук: `captcha-escalation.md`

`playbooks/captcha-escalation.md` — единственный оформленный `.md`-плейбук в общем
каталоге на срез документа. Frontmatter: `name: captcha-escalation`, `client: shared`,
`task-class: браузерная работа с сервисами, защищёнными капчей`,
`updated: 2026-08-08`. Ниже — процедура по самому файлу, без пересказа журналов.

Вводная строка файла фиксирует контекст, из которого процедура выросла: рассчитана на
контур с инстансом браузера на владельца (роль `kiosk_browser`, применена на узле
2026-08-08), поэтому все команды в шагах — в форме с именем инстанса.

### Когда применять

Агент работает через Playwright и упирается в проверку «вы человек». Признаки, по
которым это опознаётся однозначно (файл прямо требует не гадать по косвенным):

- HTTP 403/503 при заголовке страницы `Just a moment...` или `Attention Required!`
  (Cloudflare);
- iframe с `challenges.cloudflare.com`, `google.com/recaptcha`, `hcaptcha.com`,
  `smartcaptcha.yandexcloud.net`;
- текст «Verify you are human», «Подтвердите, что вы не робот»;
- страница с картинкой-текстом и полем ввода — простая капча.

### Предусловия

- Агент работает в инстансе браузера своего клиента: у каждого инстанса свой экран,
  свой профиль и свой порт CDP `9222+index`. Порт сессии приходит переменной
  `KIOSK_CDP_PORT` при её старте (переменной нет — это инстанс `default`, порт `9222`).
  Переключить инстанс посреди сессии нельзя.
- Связка инстанса поднята; проверка — `infra/web-browser/view.sh status`. Руками
  поднимать штатно не нужно: клиентский порт CDP держит systemd-сокет и поднимает
  браузер по первому обращению.
- Человек и агент работают в одном браузере — в пределах инстанса. На этом держится вся
  схема: человек проходит проверку прямо в браузере застрявшего агента, ничего никуда не
  перенося.

### Шаги

1. **Классифицировать капчу.** Простую картинку с текстом — попробовать самому
   (`browser_take_screenshot`, прочитать, ввести), не больше двух попыток.
   Поведенческую/интерактивную (Cloudflare, reCAPTCHA, hCaptcha, SmartCaptcha,
   головоломки) — своими силами не проходить, сразу к шагу 2; подбор отпечатков,
   stealth-патчи и сервисы-решалки запрещены (нестабильно и против правил сервисов).
2. **Определить имя своего инстанса** через `infra/web-browser/view.sh status` — таблица
   по всем инстансам, источник правды, какой порт у какого клиента; найти строку со
   своим портом и взять имя. Агент знает только порт, человеку нужно имя.
3. **Зафиксировать состояние:** скриншот и URL — в `artifacts/` карточки задачи; в
   карточке — `status: blocked`, причина (капча), имя инстанса, что именно требуется от
   человека (какой сервис, какая страница, что нажать).
4. **Поднять аварийный выход:** `infra/web-browser/view.sh start <инстанс>` — именно на
   свой инстанс. Печатает одноразовую ссылку на экран этого инстанса; окно и ссылка
   живут не дольше 30 минут. Сеансы разных инстансов независимы и могут жить
   одновременно.
5. **Позвать человека.** Сообщение: клиент, задача, сервис, имя инстанса, что именно
   сделать, что окно живёт 30 минут. Ссылку передавать только тем каналом, которым
   просил пользователь, и не дублировать в журналы/заметки/карточки задач — владение
   ссылкой внутри окна равно полному доступу к браузеру со всеми сессиями этого клиента.
6. **Ждать, не трогая вкладку:** опрашивать раз в 5–10 секунд (заголовок, URL,
   исчезновение признаков из раздела «Когда применять»); не перезагружать, не
   навигировать, не переключать вкладки.
7. **Продолжить работу** в той же вкладке того же инстанса; перед первым действием —
   `browser_tabs select` на свою вкладку (человек мог оставить активной другую). Снять
   `blocked`.
8. **Погасить доступ:** `infra/web-browser/view.sh stop <инстанс>`, не дожидаясь
   таймера, и только свой инстанс — `stop --all` снесёт и чужие живые сеансы.
9. **Записать факт:** в карточку сервиса (`services/<slug>/overview.md` или
   `<root>/<owner>/services/...`) — тип защиты и дату; в журнал `llm/` — сколько прожил
   пропуск до следующей проверки (сырьё для решения о переводе сервиса на другую точку
   интеграции — API/экспорт).

### Верификация

- Целевая страница открыта, признаков проверки нет.
- Задача снята с `blocked`, работа продолжена в том же инстансе и в той же вкладке (не в
  новом контексте и не в другом браузере).
- `infra/web-browser/view.sh status` в строке своего инстанса показывает `inactive` в
  колонках `wayvnc` и `view-web` (браузер при этом остаётся `active` — гашение просмотра
  работу агента не прерывает); сеансы других инстансов, если они были, не затронуты.

### Известные проблемы

Дословно по разделу файла:

- **Челлендж зацикливается** — проверка проходится, страница перезагружается, проверка
  снова. Дело не в человеке, а в репутации IP дата-центра; аварийный выход не поможет,
  задачу оставить `blocked`, поднимать вопрос смены точки интеграции (API, экспорт) или
  резидентного IP.
- **Пропуск живёт недолго и не переносится.** `cf_clearance` у Cloudflare привязан к IP
  и user-agent — не переносится между машинами и между инстансами (у каждого свой
  профиль); звать человека нужно именно в тот инстанс, который встал.
- **Инстанс не тот.** `KIOSK_CDP_PORT` читается при старте сессии, до того как агент
  узнал задачу; если сессия по клиенту стартовала без переменной, агент сидит в
  `default`, а позванный в инстанс клиента человек откроет чужой экран. Лечится
  перезапуском сессии с правильной переменной, а не эскалацией. Соответствие
  «клиент → индекс» живёт вне репозитория, источник правды — `view.sh status`.
- **Нестандартный порт.** Доступ на `:22325`; сети, режущие всё кроме 80/443 (гостевой
  Wi-Fi, корпоративные), не пропустят — первое, что проверять на жалобу «страница не
  открывается»; с мобильного интернета работает.
- **Ссылок может быть несколько.** Одновременно живут сеансы разных инстансов,
  различаются только одноразовым путём — в сообщении всегда указывать инстанс, ссылку
  выдавать ровно одну, свежую.
- **Профиль — на клиента, но внутри инстанса общий.** Владение ссылкой в пределах окна
  равно полному доступу ко всем сервисам этого клиента (но не других клиентов); это
  граница против враждебной страницы и против получателя ссылки, но не против кода,
  выполнившегося в самом браузере — все инстансы работают под одним пользователем
  `kiosk-browser` (uid 988).
- **Инстанс новый — значит, разлогинен.** Прежние сессии из профиля `default` не
  переезжают в новый инстанс; форма входа вместо рабочей страницы здесь норма, лечится
  обычным входом по секретам из `.secrets/env` со снятием storage-state, а не
  эскалацией.
- **Фоновая вкладка ломает клики.** Правило «первым действием после `browser_navigate` —
  `browser_tabs select`» инстансами не отменяется; симптом — `TimeoutError` и `waiting
  for element to be visible, enabled and stable` при исправном элементе, диагностика —
  `document.visibilityState` (подробности — `notes/2026-08/2026-08-07-playwright-
  background-tab-clicks.md`).
- **Капча появляется регулярно** — сигнал, что сервису нужна не браузерная
  автоматизация, а отдельная задача на API/экспорт, а не привычка дёргать человека.

## 6. Чего сегодня нет

Других плейбуков, кроме `captcha-escalation.md` в общем каталоге и
`getcourse-lesson-replication.md` у клиента Ларины, в репозитории не заведено. В
частности, нет оформленных `.md`-плейбуков на очевидные повторяющиеся классы задач —
«дать доступ к сервису», «снять storage-state», «работа с финансами клиента»: логика
снятия storage-state существует, но только как ad hoc код в `var/login-checks/*.mjs`,
без обёртки в плейбук.

Механизма, который следил бы за устареванием плейбука (например, автоматической
проверки, что `updated` не разошлось с фактическим поведением сервиса), нет — обновление
целиком на исполнителе (шаг «промоушен знаний» в `execute-task`, шаг 10).
