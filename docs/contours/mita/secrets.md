# Обращение с секретами как есть

Дата среза: 2026-08-09 (по состоянию `.secrets/` и журналов `llm/` в
`/home/agent/workspaces/cloud-tech-tasks`), дата чтения — 2026-08-10.

Это docs-as-state: ниже — как секреты хранятся и используются в MITA сегодня,
без пересказа желаемого устройства. Про перенос custody под PACT — только
указатель на `docs/spec/spec.md` §9 и на ADR-0011/ADR-0012 этого воркспейса, без
пересказа содержимого. **Ни одно значение секрета в этом файле не приводится** —
только пути, форматы, имена ключей и количества.

Прямым текстом, одной фразой: **секреты лежат в открытом виде на диске узла,
исполнитель читает их напрямую без какого-либо посредника, права доступа
выставляются вручную**. Ни PACT, ни какого-либо другого арбитра между MITA и
файлом секрета сегодня не существует.

---

## 1. Каталог `.secrets/` вне git

Единственное место хранения чувствительных данных — каталог `.secrets/` в корне
репозитория `cloud-tech-tasks`. В git из него коммитится только `README.md`; всё
остальное существует исключительно на диске узла-исполнителя.

```
.secrets/
├── README.md                              # единственное, что коммитится, chmod 644
├── env                                    # KEY=VALUE, один файл, chmod 600
├── storage-state/
│   ├── _TEMPLATE.json                     # образец формата, не рабочая сессия
│   └── <client>/<service>.json            # сессии Playwright, chmod 600, каталог chmod 700
└── totp/<client>/<service>                # TOTP-секрет (base32), chmod 600, каталог chmod 700
```

Сам каталог `.secrets/` — права `755` (не ограничен на уровень выше), но
чувствительные подкаталоги внутри — `700`, файл `env` — `600`. Разграничение
прав идёт по содержимому, не по родительскому каталогу.

Фактическое состояние на срез 2026-08-09 (только структура и метаданные, без
значений):

- `.secrets/env` — 1 файл, 1931 байт, 10 ключей.
- `.secrets/totp/` — 4 файла в четырёх каталогах-клиентах: `larina/getcourse`,
  `neso/getcourse`, `shared/bizon365`, `shared/kinescope`.
- `.secrets/storage-state/` — 4 файла: `larina/getcourse.json`,
  `larina/tilda.json`, `neso/getcourse.json`, `shared/kinescope.json`, плюс
  `_TEMPLATE.json` (не рабочая сессия, образец формата).

## 2. Три категории секретов

1. **Учётные пары `env` (`KEY=VALUE`).** Логины и пароли к сервисам. На срез —
   10 ключей: `LARINA__GETCOURSE__{USERNAME,PASSWORD}`,
   `LARINA__TILDA__{USERNAME,PASSWORD}`, `NESO__GETCOURSE__{USERNAME,PASSWORD}`,
   `SHARED__BIZON365__{USERNAME,PASSWORD}`, `SHARED__KINESCOPE__{USERNAME,PASSWORD}`.
   **Логин — тоже значение секрета**, а не безобидный адрес: политика
   `.agents/policy/common/04-secrets.md` явно запрещает выписывать логин/email
   входа открытым текстом в карточках сервисов и заметках. Секрет — вся пара
   логин+пароль, а не только пароль.
2. **TOTP-секреты (base32, RFC 6238), по одному файлу на сервис.** Хранятся
   отдельно от `env`, не строкой внутри него: `.secrets/README.md` прямо
   говорит, что значение, начинающееся с `#`, или иначе «неудобное» для
   построчного формата `env`, нужно выносить отдельным файлом по образцу TOTP.
3. **Playwright storage-state — сессионные слепки браузерного профиля.** По
   факту самый широкий по охвату вид секрета: файл `storageState` (`cookies[]`
   + `origins[].localStorage[]`) даёт доступ к аккаунту без пароля и в обход
   2FA. Задокументированный и подтверждённый на реальных сохранениях факт:
   файл называется по одному сервису, а несёт **весь профиль браузера** —
   cookies всех доменов, в которые заходили в этом браузерном инстансе.
   Реальные замеры (только количества, без значений): `larina/getcourse.json`
   — 47 cookies на 4+ доменах (сервис клиента + Tilda + Kinescope + счётчики);
   `shared/kinescope.json` вырос с 9 до 44 cookies за сутки — просто потому что
   в тот же профиль (`larina`) за это время заходили и на другие сервисы. То
   есть «сессия Tilda» на деле — сессия Tilda плюс Kinescope и всё остальное,
   что было в этом же профиле. Фильтрация по домену признана нужной, но не
   реализована — `.secrets/README.md` фиксирует это явно: «непроверенный
   запасной путь хуже отсутствующего». Разбор классификации этого класса
   секретов как секрета высшей категории — `docs/adr/0012-storage-state-sekret-vysshey-kategorii.md`
   (статус: Предложено).

## 3. Схема имён: `<client>/<service>/<field>` и слаг `shared`

Каноническое имя секрета — `<client>/<service>/<field>` (например,
`neso/getcourse/password`). В `env` оно кодируется как `CLIENT__SERVICE__FIELD`:
`/` → `__`, весь идентификатор — верхний регистр, `-` → `_`.

Это имя уже спроектировано так, чтобы пережить переезд в менеджер секретов —
`.secrets/README.md` прямо называет такой переезд «этапом 2» относительно
нынешнего плоского файлового хранения. Реализации этого этапа сегодня нет:
менеджера секретов, посредника или брокера выдачи не существует.

Позиция `<client>` допускает слаг **`shared`** — для одной учётной записи,
физически общей для нескольких клиентов. Реальный пример — агентский аккаунт
Bizon365 с доступом к проектам трёх владельцев (`neso`, `larina`, `internal`).
Мотив — ротация: если писать три копии одного пароля под каждым клиентом, они
молча расходятся при смене пароля, а расхождение вскрывается только отказом
входа. `shared` используется, когда учётка физически одна; если у клиентов
разные учётки с совпадающим паролем — это разные секреты и разные записи.
Тот же слаг применяется одинаково в `env` (`SHARED__<SERVICE>__...`), в
`totp/shared/<service>` и в `storage-state/shared/<service>.json`.

Явное следствие, зафиксированное отдельно: «общий секрет ≠ общая сессия» —
общая учётная запись сервиса не означает общий браузерный профиль или общую
сессию у разных владельцев (`docs/adr/0009-obshchiy-sekret-ne-obshchaya-sessiya.md`,
Принято).

## 4. Формат `env`: почему это не shell-файл

Значение хранится «как есть» — без кавычек и экранирования, от первого `=` до
конца строки. `.secrets/README.md` документирует реальный разбор на настоящем
пароле со спецсимволами (2026-08-08): `source .secrets/env` при пароле,
содержащем `)`, падает с синтаксической ошибкой — терпимый случай. Но при
пароле вида `abc&touch PWNED` `source` **не падает**: тихо исполняет хвост как
команду оболочки и кладёт в переменную только `abc`. Заранее не известно,
какие символы окажутся в очередном пароле (пароль задаёт внешний сервис или
пользователь), поэтому **`source .secrets/env` запрещён безусловно**.

Единственные безопасные способы прочитать значение:

- построчный парсинг по первому `=` — `sed -n 's/^KEY=//p'` в shell,
  `line.split('=', 1)[1]` / `indexOf('=')` в коде;
- поиск значения по содержимому — только `grep -F` (обычный `grep -E` на таких
  паролях падает так же, как `source`).

Именно построчный парсинг и реализован в `var/login-checks/lib.mjs`:
`secret()` ищет строку с точным префиксом ключа и возвращает хвост после `=`.

Отдельно: если значение начинается с `#`, оно ломает часть парсеров как
комментарий — тогда оно выносится в отдельный файл по образцу TOTP (см. §2).

Полный разбор инцидента и решения — `docs/adr/0011-model-hraneniya-sekretov-v-repozitorii.md`
(статус: Принято).

## 5. Как исполнитель читает значения напрямую

Практический слой — `var/login-checks/` (сам каталог `var/` целиком в
`.gitignore` как производное состояние инструментов, не версионируется):

- `lib.mjs` (33 строки) — три примитива:
  - `secret(key)` — построчно читает `.secrets/env` (`fs.readFileSync`),
    отдаёт значение по точному совпадению ключа с префиксом до `=`;
  - `totp(path, step=30, digits=6)` — читает base32-файл, декодирует без
    внешних библиотек (алфавит RFC 4648, побитовая упаковка), считает
    HOTP/TOTP по HMAC-SHA1 от `Date.now()/1000/step`;
  - `connect(port)` — подключается к уже запущенному браузерному инстансу по
    CDP-порту (`chromium.connectOverCDP`). Инстансы заданы вне этого
    репозитория, в `/var/lib/infra/src/config/ansible-vars.yml`, ключ
    `kiosk_browser_instances`: `default`=9222, `larina`=9223, `neso`=9224,
    `internal`=9225 (формула `9222+index`).
- Три сервисных скрипта-исполнителя логина: `larina-getcourse.mjs`,
  `neso-getcourse.mjs`, `shared-kinescope.mjs`. Общий паттерн: подключиться к
  профилю по CDP → очистить куки/`localStorage`/`sessionStorage` для целевого
  домена → заполнить форму логина значениями `secret('...USERNAME')` /
  `secret('...PASSWORD')` → при запросе 2FA сгенерировать код `totp(path)` и
  ввести → проверить успех запросом защищённой страницы, а не по URL (найдено:
  GetCourse после ввода кода иногда возвращает на страницу логина в варианте
  «вы уже вошли», что похоже на отказ, если судить по URL) → пересохранить
  `ctx.storageState({ path: OUT })` и сразу `chmod 600`. В консоль печатаются
  только метаданные (URL, title, количество cookies, список доменов) —
  значения секретов в лог/консоль не идут ни в одном из просмотренных
  скриптов.

Итог: исполнитель имеет **прямой файловый доступ** к `.secrets/env` и
`.secrets/totp/*` — обычный `readFileSync` в процессе, который сам же
управляет браузером и вводит текст в DOM недоверенной страницы. Секрет
проходит путь файл → память Node-процесса → поле ввода браузера, без
какого-либо брокера или прослойки, которая могла бы проверить или ограничить
это действие.

## 6. Что защищает от утечки в git

Три линии защиты, ни одна не является полной:

1. **`.gitignore`**: `.secrets/*` с исключением `!.secrets/README.md`, плюс
   общие `*.env`, `.env`. Отдельно игнорируются `deploy/` (staging для
   миграции легаси-данных) и `var/` (в котором лежат `login-checks`).
2. **`.githooks/pre-commit`** — единственный барьер уровня репозитория.
   `.agents/ARCHITECTURE.md` §8.1 явно называет его «единственным барьером» и
   объясняет отсутствие внешнего серверного gate: один оператор, прямые
   коммиты в `main`, внешний CI ничего не мог бы предотвратить постфактум, а
   checkout контактных данных на внешние раннеры — лишняя экспозиция. Хук на
   каждый коммит гоняет `node scripts/agents.mjs lint`, который среди прочего
   ищет литералы учётных данных, телефоны, адреса почты, персональные
   абсолютные пути — **но только в каноне `.agents/`**, не по всему
   репозиторию. `clients/`, `projects/`, `internal/` осознанно исключены из
   машинной проверки: там легитимно живут контактные данные, и запрет утечки
   именно *секретов* (паролей, токенов) в этих каталогах держится только
   нормативной политикой `04-secrets.md`, не машиной. Разбор решения об
   отказе от внешнего CI — `docs/adr/0015-lokalnyy-pre-commit-vmesto-vneshnego-ci.md`
   (Принято).
3. **Права доступа** (`600`/`700`) — защита от других *пользователей узла*, а
   не от git и не от самого процесса-исполнителя, у которого чтение и так
   есть.

**Важно: ничего не мешает самому процессу-исполнителю** вынести значение
секрета в отчёт, заметку, сообщение пользователю или коммит в обход
`.gitignore` — просто вписав его текстом в файл вне `.secrets/`. Единственная
защита от этого — нормативная политика (`04-secrets.md`: «значения секретов
никогда не попадают в карточки задач, заметки, отчёты, логи и коммиты») и
дисциплина исполнителя, плюс частичный lint, который не покрывает
`clients/`/`projects/`/`internal/`. Технического ограничения на этот путь
утечки не существует.

Отдельная слабость самого хука: хук лежит в git, но включается локальным
`core.hooksPath=.githooks`, которого в git нет — свежий клон приходит без
хука вообще. Закрывается тем, что `build` сам выставляет `core.hooksPath` и
громко об этом сообщает, а `check` падает, пока хук не включён.

## 7. Ротация — как устроена на практике

Ротации нет как процесса с расписанием — это полностью реактивный, ручной,
человеко-инициированный механизм. Никакой третьей стороны/арбитра в процессе
нет: пользователь инициирует и диктует новое значение, тот же
агент-исполнитель, что ведёт диалог, физически вносит правку и верифицирует.

Единственный полностью задокументированный цикл (`llm/2026-08/2026-08-09-1050-main-agent-account-rename.md`,
переименование агентской учётной записи ESTA→MITA, 2026-08-09):

1. Пользователь в диалоге продиктовал новый адрес почты логина для трёх ключей
   (`NESO__GETCOURSE__USERNAME`, `SHARED__BIZON365__USERNAME`,
   `SHARED__KINESCOPE__USERNAME`) и новый TOTP-секрет для одного сервиса;
   пароли остались прежними.
2. Агент сверил продиктованное с уже лежащим в `.secrets/env`, не печатая
   значение целиком (сравнение вида `[ "$v" = "..." ]` плюс маскирование при
   показе длины/формы несовпадения) — обнаружил расхождение (опечатку) и
   уточнил у пользователя до правки.
3. Правка выполнена напрямую — `sed -i` по `.secrets/env`,
   `printf > .secrets/totp/...` — тем же процессом/сессией, что вела диалог с
   пользователем. Никакого отдельного привилегированного шага или апрува нет.
4. Проверка: `grep -ci <старое> .secrets/env` → 0, количество ключей не
   изменилось, TOTP-файл сверен с продиктованным.
5. Фактическая верификация входом — прогон login-check скриптов по изменённым
   сервисам, перевыпуск `storage-state`.
6. Находки по ходу ротации фиксируются в карточках сервисов и в
   `llm/`-журнале (неструктурированный markdown, append-only) — это
   единственный «аудит-лог» изменений секретов, который есть в системе;
   отдельного структурированного журнала доступа/ротации не существует.

Второй подтверждённый пример того же паттерна (`shared/bizon365`, завод
секрета, 2026-08-08): пользователь один раз надиктовывает секрет в чат, агент
вписывает его в `.secrets/env` и `.secrets/totp/`, помечает как «обновлено
вслепую» до первой фактической проверки входа (в тот момент сеть блокировала
сервис). Отдельно зафиксировано правило для `shared`-аккаунтов: ротация
пароля/TOTP общей учётки задевает всех клиентов разом — ровно ради этого и
введён слаг `shared` (см. §3).

Второй канал появления секретов — миграция легаси-данных
(`.agents/skills/migrate-legacy/SKILL.md`, фаза 4): найденные в старых
источниках значения складываются в `deploy/SECRETS-INBOX.md` (не коммитится,
`deploy/` целиком в `.gitignore`), пользователь сам переносит их в
`.secrets/` и удаляет inbox-файл; в `AUDIT.md` попадают только *имена*
найденных секретов, с пометкой, если секрет «засветился» в источнике
(транскрипт, переписка, старый репозиторий) настолько, что его стоит
ротировать.

## 8. Задокументированные грабли

- **Инцидент с правами `644`.** Playwright сам права на `storage-state` не
  выставляет — задокументирован реальный случай, когда пересохранённый файл
  получил `644` из-за гонки `umask` между разными вызовами оболочки.
  Полагаться на `umask` нельзя: `chmod 600` выполняется явно, отдельным шагом,
  сразу после каждого сохранения `ctx.storageState()`.
- **Storage-state шире собственного имени.** Файл называется по одному
  сервису (`<client>/<service>.json`), но по факту несёт весь профиль браузера
  — см. §2. Задача фильтрации по домену признана нужной, но не сделана и не
  проверена на восстановление сессии; см. `docs/adr/0012-storage-state-sekret-vysshey-kategorii.md`.
- **`.secrets/env` нельзя `source`.** Разобрано на реальном пароле со
  спецсимволами — см. §4.
- **Верификация успешного логина — по факту, а не по URL.** Минимум один
  сервис (GetCourse) после ввода 2FA-кода возвращает на страницу логина в
  «варианте для вошедших», что похоже на отказ, если проверять только адрес
  страницы.

## 9. Чего сегодня не существует

- Менеджера секретов или брокера выдачи («этап 2» по `.secrets/README.md`) —
  нет ни реализации, ни выбора конкретного продукта.
- Custody секретов под PACT (файл, читаемый только по авторизованному запросу
  конкретной задачи, выдача TOTP-кода вместо seed, TTL и зашифрованное
  хранение `storage-state`) — PACT как работающая система не существует, весь
  этот перенос — план, а не факт. Указатель без пересказа —
  `docs/spec/spec.md` §9.
- Структурированного машиночитаемого аудит-лога доступа/ротации — есть только
  человекочитаемые записи в `llm/`.
- Расписания или триггеров плановой ротации — вся ротация реактивна (см. §7).
- Фильтрации `storage-state` по домену — признана нужной, не реализована
  (см. §2, §8).
