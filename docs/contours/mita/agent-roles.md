## 0. Скилл vs роль — единая процедура, два способа её запустить

В каноне `.agents/` есть ровно три типа сущностей, у каждой — ровно одна редактируемая
версия:

- **Скилл** (`.agents/skills/<name>/SKILL.md`, frontmatter `name`, `description`) —
  процедура для случая «работает сам главный агент» (в сессии Claude Code — как
  `/<имя>` или через инструмент `Skill`).
- **Роль** (`.agents/agents/<name>.md`, frontmatter `name`, `description`, `tools`,
  `profile`) — та же по смыслу процедура, но для случая «делегируешь субагенту».
  Поле `model` в роли запрещено канонически — модель не фиксируется, выбирается
  клиентом по `profile`.
- **Команда** (`.agents/commands/<name>.md`, frontmatter `description`,
  `argument-hint`, обязательный `disable-model-invocation: true`) — явная
  пользовательская точка входа; такую сущность не может вызвать сама модель, только
  человек.

Тело роли не пересказывает общую политику `.agents/policy/common/` — она
наследуется целиком (нативно у Claude Code, вклейкой при сборке у Codex CLI; детали
доставки — `docs/operating-model.md` не описывает, это уровень инфраструктуры
тулинга, а не операционной модели задач). Правило, общее для всех четырёх ролей:
**делегированная роль не обращается к пользователю напрямую** — всё неясное она
возвращает вопросами в своём ответе, а не задаёт их сама.

Существенная оговорка про поле `tools` роли — оно реально фильтрует набор
инструментов только под Claude Code; под Codex CLI это поле не применяется вовсе
(механизм фильтрации отсутствует технически). Подробности и последствия для модели
угроз — `docs/adr/0014-semantika-bezopasnosti-ne-zavisit-ot-ignoriruemyh-metadannyh.md`,
здесь не пересказываются.

Соответствие `profile` → модель у Claude Code: `fast` → haiku, `balanced` → sonnet,
`deep` → opus (`.agents/runtimes/claude.json`). У Codex CLI `profile` не сопоставляется
модели — там всегда действует модель текущей сессии CLI.

## 1. Четыре роли (`.agents/agents/*.md`)

| Роль | `tools` | `profile` | Назначение |
|---|---|---|---|
| `task-executor` | `Read, Write, Edit, Grep, Glob, Bash, ToolSearch, mcp__playwright__*` | `deep` | Исполнитель задач: доводит **одну** задачу из `<clients\|projects\|internal>/<owner>/tasks/active/` от плана до отчёта менеджеру и архивирования (по скиллу `execute-task`). Один вызов роли = одна задача, путь к карточке передаётся при запуске. |
| `qualifier` | `Read, Grep, Glob, Write, Edit, Bash` | `fast` | Квалификатор постановок: разбирает сырую постановку менеджера (текст или файл из `tasks/inbox/`) в карточку задачи (по скиллу `intake`), не выполняя её по существу и не занимая контекст главного агента. |
| `service-scout` | `Read, Grep, Glob, Write, Edit, Bash, WebFetch, WebSearch, ToolSearch, mcp__playwright__*` | `balanced` | Разведчик сервисов: когда у владельца появился незнакомый сервис — изучает его (grep по репозиторию → публичная документация → при настроенном Playwright — сам сервис) и заполняет карточку `<root>/<owner>/services/<slug>/overview.md`. Отдельного `SKILL.md` у неё нет — процедура описана прямо в теле роли. |
| `librarian` | `Read, Grep, Glob, Write, Edit, Bash` | `fast` | Библиотекарь системы: периодическая уборка — компакция заметок (по скиллу `compact-notes`), промоушен устойчивых знаний в базу, актуализация `INDEX.md`, поиск зависших задач. Запускается по расписанию или по просьбе «наведи порядок». |

Детали по каждой роли:

**`task-executor`** — единственная роль с одновременным доступом к `Bash` (а
значит технически и к `.secrets/`) и к полному Playwright. Формат ответа: статус
задачи, что сделано, верификация по каждому пункту DoD, готовый текст отчёта
менеджеру (или вопросы, если `status: blocked`). Инструменты `mcp__playwright__*`
не загружены по умолчанию — подгружаются через `ToolSearch` по требованию, но
заполненный `tools` роли под Claude Code всё равно ограничивает, какие
MCP-инструменты `ToolSearch` вообще способен выдать.

**`qualifier`** — без Playwright, не ходит в веб. Явно спроектирована как точка
приёма недоверенного/неструктурированного человеческого ввода — в её собственном
`description` прямо указано «на этапе 2 будет вызываться автоматически для
постановок из Telegram» (это формулировка `ROADMAP.md` MITA, не факт о работающей
интеграции; сам Telegram-канал не реализован — `docs/operating-model.md` §6).
Формат ответа: id созданной карточки и путь к ней (или причина отказа), клиент,
краткая постановка, DoD, открытые вопросы, сформулированные так, чтобы их можно
было переслать менеджеру как есть.

**`service-scout`** — текстовое, а не инструментальное ограничение: роль физически
имеет `Write/Edit/Bash`, в её теле явно написано «в сервисе — только чтение и
навигация, никаких изменяющих действий», но полагаться на это как на жёсткую
защиту нельзя — ограничение не закреплено набором `tools`. Формат ответа: путь к
карточке, что выяснено, TODO и вопросы.

**`librarian`** — принципы работы: ничего не удалять безвозвратно (устаревшее — в
`archive/`), переносимое в базу знание переписывать самодостаточно, при сомнении —
оставить заметкой. Формат ответа: что промоутнуто и куда, что заархивировано, какие
индексы поправлены, зависшие задачи, карточки сервисов с незакрытыми TODO.

## 2. Шесть скиллов (`.agents/skills/<name>/SKILL.md`)

| Скилл | Роль-обёртка | Назначение |
|---|---|---|
| `intake` | `qualifier` | Принять сырую постановку задачи (текст из чата или файл в `tasks/inbox/`) и превратить в нормализованную карточку задачи. |
| `execute-task` | `task-executor` | Выполнить задачу из `tasks/active/` по её карточке — от подготовки контекста до верификации DoD, отчёта менеджеру и архивирования. |
| `add-owner` | нет (нет обёртывающей роли) | Завести нового владельца задач (клиента, проект или внутренний контур): создать каталог `<root>/<slug>/` со всей структурой и зарегистрировать в `INDEX.md` корня; при необходимости — завести инстанс браузера через точечный прогон Ansible-роли `kiosk_browser`. |
| `compact-notes` | `librarian` | Компакция заметок в `notes/`, перенос устойчивых знаний в базу знаний, актуализация всех `INDEX.md`. Периодически (раз в две недели) или по просьбе пользователя. |
| `migrate-legacy` | нет (нет обёртывающей роли) | Разовый перенос прежних разнородных материалов в структуру репозитория, со сборкой в staging `deploy/` (вне git) и аудитом полноты в `deploy/AUDIT.md`; отдельная фаза поиска секретов складывает найденные значения в `deploy/SECRETS-INBOX.md` (не коммитится, удаляется пользователем по завершении). Аргумент — путь(и) к источникам. |
| `status` | нет (нет обёртывающей роли) | Сводка состояния системы: активные и заблокированные задачи по всем владельцам, необработанный inbox, зависшие задачи, незакрытые TODO. Только читает, ничего не меняет. |

Три скилла (`add-owner`, `migrate-legacy`, `status`) не имеют обёртывающей роли —
их выполняет только главный агент сам, делегировать их субагенту через `Agent`
сегодня некому: соответствующей роли в `.agents/agents/` не заведено.

Отдельно про `status`: это единственная процедура в системе, которая **не** пишет
журнал в `llm/` — логировать чтение признано шумом (`.agents/policy/common/08-llm-logs.md`
формулирует это как общее правило «только читающие процедуры журнал не пишут»,
применённое здесь).

## 4. Две команды (`.agents/commands/*.md`)

Обе с `disable-model-invocation: true` — модель не может вызвать их сама, только
пользователь явно. Под Claude Code это нативные repo-команды (`.claude/commands/*.md`
— симлинки на канон, `$ARGUMENTS` раскрывается автоматически); под Codex CLI
нативных slash-команд не существует вовсе, обе эмулируются router-секцией внутри
сгенерированного `AGENTS.override.md`.

### `/new-task`

`argument-hint: '<client>: текст постановки (или путь к файлу из tasks/inbox/)'`

Принимает постановку от менеджера, делегирует разбор роли `qualifier` (исходный
текст передаётся дословно, без пересказа и домысливания). Дальше по ответу роли:

- карточка создана → показать пользователю путь, клиента, DoD, открытые вопросы;
- клиент не определился → показать кандидатов и задать вопрос пользователю **сама
  команда** (в главном контексте) — делегированная роль так сделать не может;
- карточка создана со `status: blocked` → показать, чего не хватает, готовым к
  пересылке менеджеру текстом.

Команда только заводит карточку, ничего не выполняет по существу.

### `/task`

`argument-hint: '<client>/<YYYY-MM-DD-slug> [уточнения]'`

Находит карточку по глобальной ссылке (сначала `tasks/active/`, затем `archive/`
и `inbox/` того же владельца), делегирует выполнение роли `task-executor` (путь к
карточке и уточнения пользователя — дословно), показывает итоговый статус,
верификацию по каждому пункту DoD и готовый текст отчёта менеджеру (или вопросы,
если результат `blocked`). Явно помечена в собственном теле: «меняет содержимое
репозитория и коммитит — запускается только по явной просьбе пользователя».

## 5. `librarian`, `add-owner`, `migrate-legacy`, `status` — вне четырёхконтурной модели

Эти четыре сущности — **внутренняя служебная гигиена самой MITA**, а не про задачи
клиента, не про диалог с человеком и не про арбитраж полномочий:

- `librarian` / `compact-notes` — уборка заметок и знаний **самой системы**
  (компакция, актуализация индексов, поиск зависших задач);
- `add-owner` — административная операция заведения нового владельца (создание
  структуры каталогов, регистрация в `INDEX.md`, при необходимости — прогон
  Ansible-роли `kiosk_browser`), не выполнение клиентской задачи;
- `migrate-legacy` — разовая техническая ETL-процедура переноса данных из прежних
  систем, не про исполнение и не про диалог;
- `status` — read-only observability-утилита для оператора, не диалоговый
  интерфейс и не арбитраж.

Это явная позиция, а не пробел: ни одну из этих четырёх сущностей не следует
относить к LINA, PACT, MITA-как-исполнителю или CITA по содержанию функции —
только физическое расположение файлов (в каноне `.agents/` репозитория MITA)
привязывает их к этому воркспейсу. В `docs/spec/spec.md` контура PACT эти четыре
сущности не упоминаются вовсе, они не переезжают ни в один из трёх остальных
контуров.

## 6. Открытый вопрос, вынесенный в спецификацию

Соответствие роли `qualifier` и команд `/new-task`/`/task` функции LINA —
неоднозначный, намеренно не закрытый здесь вопрос: `qualifier` физически часть
MITA (тот же security-контекст, что и `task-executor`), но по функции ближе всего
к «собрать из диалога полный запрос, не владея задачей и полномочиями». Разбор и
рабочее (не окончательное) разведение границы —
`docs/adr/0016-priyom-postanovok-iz-telegram-peresmatrivaetsya.md`
и `docs/spec/spec.md`; здесь содержание не пересказывается.
