## 1. Принцип: один канонический источник — N вендорных проекций

`.agents/ARCHITECTURE.md` (статус `DECIDED`, версия 1.0, дата 2026-08-03)
формулирует главный критерий дословно:

> У каждой смысловой сущности существует ровно одна редактируемая каноническая
> версия. Всё, что нужно конкретному клиенту, либо ссылается на неё, либо
> детерминированно из неё строится и никогда не редактируется вручную.

Физический источник истины — только каталог `.agents/`. Всё остальное, что видят
конкретные AI-клиенты (`.claude/`, `.codex/`) и корневые файлы политики (`CLAUDE.md`,
`AGENTS.md`, `AGENTS.override.md`), — либо симлинк на канон, либо детерминированно
генерируемый артефакт. Ручные правки в этих местах запрещены; правка всегда идёт
через `.agents/`, затем `node scripts/agents.mjs build`.

Архитектура привязана к **клиенту (runtime)**, а не к компании или модели: один
клиент может работать с моделями разных поставщиков. Сегодня подключено и проверено
запуском ровно два клиента:

| Клиент | Бинарь | Версия | Статус |
|---|---|---|---|
| Claude Code | `/usr/bin/claude` | — | подключён, проверен запуском |
| Codex CLI | `/usr/local/bin/codex` (`@openai/codex`) | 0.146.0 | подключён, проверен запуском |

Gemini CLI и Kimi Code на узле не установлены — карты рантаймов для них
принципиально не заводятся: непроверяемое запуском утверждение в канон не попадает.

Что вправе делать адаптер конкретного клиента: менять транспорт, синтаксис
конфигурации, имена инструментов и сопоставление профилей моделей на конкретные
модели. Что он не вправе делать: менять цель, политику, ограничения безопасности
или критерии результата сущности. Один клиент получает ровно один путь обнаружения
каждой сущности — двух каталогов скиллов у одного клиента быть не может, даже если
клиент технически умеет читать оба (см. §6, случай `.codex/skills/`).

## 2. Три типа канонических сущностей

Все три — Markdown с плоским YAML-frontmatter, диалект, который клиенты читают
нативно. Собственные плейсхолдеры/prompt-DSL в теле сущности запрещены.

### 2.1. Скиллы — `.agents/skills/<name>/SKILL.md`

Процедура для случая «работаешь сам»: главный агент выполняет её напрямую, без
делегирования.

Обязательный frontmatter: `name` (совпадает с именем каталога), `description`.
Тело, `references/`, `scripts/`, `assets/` — часть того же канонического пакета.
Версии задачи или политики в метаданных пакета нет.

Сегодня в `.agents/skills/` шесть каталогов: `add-owner`, `compact-notes`,
`execute-task`, `intake`, `migrate-legacy`, `status`.

### 2.2. Роли — `.agents/agents/<name>.md`

Сущность для случая «делегируешь»: субагент/спаун. Обязательный frontmatter:

```yaml
---
name: task-executor
description: Назначение и условия выбора роли
tools: Read, Write, Edit, Grep, Glob, Bash, ToolSearch
profile: deep
---
```

- `name` — стабильный id и одновременно имя файла;
- `description` — назначение и условия выбора роли; это **единственное** место, где
  формально описано, когда роль выбирают, — перечень ролей в `README.md`/`CLAUDE.md`
  генерируется из него, рукописного дублирующего перечня нет и заводить его нельзя;
- `tools` — словарь инструментов из общего списка (`Read`, `Write`, `Edit`, `Grep`,
  `Glob`, `Bash`, `Agent`, `Skill`, `WebFetch`, `WebSearch`, `ToolSearch`,
  `NotebookEdit`, `TodoWrite`) плюс MCP-инструменты вида `mcp__<server>`,
  `mcp__<server>__*`, `mcp__<server>__<tool>`, где `<server>` обязан существовать в
  `.agents/mcp/registry.json` (иначе `lint` падает — опечатка в имени сервера иначе
  молча оставила бы роль без браузера);
- `profile` — `fast | balanced | deep | session`, логическая рекомендация
  оркестратору, не имя модели.

Поле `model` в роли **запрещено принципиально** — конкретную модель выбирает
клиент по `profile` и текущей доступности (для Claude Code: `fast→haiku`,
`balanced→sonnet`, `deep→opus`, `session→inherit`; для Codex CLI все три первых
профиля разрешаются в `session` — модель выбирается на уровне сессии, `profile`
роли для Codex не более чем совет).

Сегодня в `.agents/agents/` четыре роли: `task-executor`, `qualifier`,
`service-scout`, `librarian`.

### 2.3. Команды — `.agents/commands/<name>.md`

Явная пользовательская точка входа. Обязательный frontmatter:

```yaml
---
description: Краткое назначение команды
argument-hint: '<аргументы>'
disable-model-invocation: true
---
```

`disable-model-invocation: true` обязателен для каждой публикуемой команды —
модель не должна вызывать её сама, только пользователь явно. Для клиента, который
этот ключ не понимает (Codex CLI не имеет нативных слэш-команд репозитория вообще),
тот же запрет продублирован текстом в генерируемом router-разделе (§4) — семантика
безопасности не может зависеть от метаданных, которые клиент игнорирует.

Сегодня в `.agents/commands/` две команды: `/new-task`, `/task`.

Служебные файлы каталогов сущностей — `README.md`, `INDEX.md`, `.gitkeep` — не
являются сущностями и не публикуются как скиллы/роли/команды: индексный файл в
каталоге команд иначе превращался бы в команду `/README`.

### 2.4. Что намеренно не создаётся

Отдельные `entity.yaml` рядом с телом сущности, граф воркфлоу, условный
prompt-DSL, per-role списки политики (общая политика инжектируется в роль целиком —
и Claude Code нативно, и Codex CLI вклейкой при сборке; забытый пункт в
выборочном списке даёт невидимый отказ безопасности, тогда как избыточный контекст
видим и измерим), произвольные вендорные вставки внутри канонических сущностей,
отдельная таксономия capability. Frontmatter и есть описание сущности;
оркестрационная логика — проза в теле файла, не YAML.

## 3. Матрица доставки

| Сущность | Claude Code | Codex CLI |
|---|---|---|
| Скиллы | `.claude/skills/<name>` → симлинк на `.agents/skills/<name>` | прямое чтение `.agents/skills/` (native, без генерации) |
| Роли | `.claude/agents/<name>.md` → симлинк на `.agents/agents/<name>.md` | generated `.codex/agents/<name>.toml`: политика + тело роли вклеены |
| Команды | `.claude/commands/<name>.md` → симлинк, нативный `/<имя>`, `$ARGUMENTS` раскрывается | нет нативных slash-команд репозитория; generated router-раздел внутри `AGENTS.override.md`, эмулирующий конвенцию `/<имя> <аргументы>` |
| Корневая политика | generated `CLAUDE.md` = общая политика + overlay Claude | generated `AGENTS.override.md` = общая политика + overlay Codex + router команд |
| MCP | generated `.mcp.json` (реально читается клиентом) | generated `.codex/mcp-servers.toml` — фрагмент для **ручного** переноса оператором, сам файл клиентом не читается (см. §7) |

Дополнительно генерируется вендор-нейтральный `AGENTS.md` (общая политика +
перечень сущностей) — fallback для инструментов, ещё не описанных картой рантайма,
и резерв на случай, если overlay Codex когда-либо будет снят.

Проверено на этой машине экспериментально (не пересказ доков):

| Вопрос | Claude Code | Codex CLI 0.146.0 |
|---|---|---|
| Наследует ли делегированная роль корневую политику | Да, нативно (субагент без единого вызова инструментов дословно процитировал `CLAUDE.md`) | Наблюдение неотличимо от пересказа родителем → политика всё равно вклеивается сборщиком |
| Применяется ли `tools` роли фактически | Да — роль получила ровно перечисленные инструменты, без `Bash`/`Agent`, если их нет в списке | Нет такого механизма вообще |
| Откуда читаются скиллы | `.claude/skills/` (симлинки) | `.agents/skills/` — и технически ещё `.codex/skills/`, если бы он существовал; этот второй путь запрещён инвариантом «один путь обнаружения на клиента», каталог `.codex/skills/` в репозитории не создаётся, `lint` падает, если он появится |
| Корневая политика | `CLAUDE.md` | При наличии `AGENTS.override.md` — только он; `AGENTS.md`/`CLAUDE.md` в контекст не попадают. Без overlay читается `AGENTS.md` |
| Репозиторные slash-команды | Да | Нет вообще — эмулируются router-секцией overlay |
| Определения ролей | `.claude/agents/*.md` | `.codex/agents/*.toml`, вызов через `collaboration.spawn_agent(agent_type=<роль>)` |
| Проектный MCP-конфиг | `.mcp.json` читается | `.codex/config.toml` **не читается** (проверено дважды, включая `trust_level=trusted`) |
| Вложенное делегирование | Роль без `Agent` в `tools` спавнить не может; с `Agent` — может | Есть `collaboration.spawn_agent` |

## 4. Наследование общей политики

```
policy_inheritance:
  claude: native            # делегированная роль наследует CLAUDE.md сама
  codex:  inject-workspace  # общая политика вклеивается в тело роли при сборке
```

Overlay клиента содержит только механику клиента (как вызываются инструменты, где
искать сущности) и не вправе спорить с общей политикой или телом роли — это
проверяется на review, а не механически: линтер не разбирает семантику
произвольной прозы, только структуру.

## 5. Сборщик `scripts/agents.mjs`

Один инструмент, три подкоманды:

```
node scripts/agents.mjs build   # идемпотентно применяет план к диску
node scripts/agents.mjs check   # ничего не пишет, сверяет план с диском побайтово
node scripts/agents.mjs lint    # валидирует канон
```

**`build`** — идемпотентно применяет план доставки: создаёт/обновляет симлинки,
рендерит `file`/`json`/`region`-артефакты (в т.ч. region-блоки внутри рукописных
файлов между маркерами); сам включает git hook (`core.hooksPath=.githooks`), если
он ещё не включён; отказывается затирать обычный файл там, где по плану должен быть
симлинк; удаляет из каталогов доставки артефакты, которых больше нет в плане.

**`check`** — ничего не пишет; строит тот же план и сравнивает его с диском
побайтово; падает на отсутствующем, лишнем или устаревшем артефакте; падает, если
git hook не включён. Именно `check` — механическое доказательство того, что
вендорные проекции не разошлись с каноном, а не honor system.

**`lint`** — валидирует:
- frontmatter: совпадение `name` с именем файла/каталога, допустимые `profile`
  (`fast|balanced|deep|session`), словарь `tools` (общий список + `mcp__<server>...`
  с проверкой существования `<server>` в `.agents/mcp/registry.json`), запрет поля
  `model`, обязательность `disable-model-invocation: true` у команд;
- отсутствие в каноне (только `.agents/`, не во всём репозитории) литералов
  credentials/телефонов/email/персональных путей/версий моделей;
- коллизии имён (скилл/команда, скилл/роль);
- единственность discovery-path на клиента и полноту матрицы доставки;
- отсутствие вендорных путей внутри канона — список запрещённых каталогов
  выводится из карт рантаймов (`.agents/runtimes/*.json`), а не хардкодится в
  скрипте.

Пример реального вывода на момент чтения: `lint: канон чист — 6 скилл(ов),
4 рол(и), 2 команд(ы), 2 клиент(а)`; `check: 22 артефакт(ов) совпадают с каноном`.

### 5.1. Enforcement — одноуровневый и сознательно так

Единственный барьер — `.githooks/pre-commit`, который прогоняет `lint && check`
перед каждым коммитом; активируется локальным `core.hooksPath`, включённым
`build`. Внешнего серверного CI/gate нет: один оператор, прямые коммиты в `main`,
PR-флоу отсутствует — внешний gate на push в этой модели ничего не предотвращает,
только сообщает постфактум. Условие пересмотра прямо зафиксировано в
`.agents/ARCHITECTURE.md` §8.1: появление второго коммитера или переход на PR-флоу
обязывает вернуть внешний серверный gate с branch protection.

Тот же `pre-commit` попутно переиндексирует `knowledge-search`
(obsidian-hybrid-search): переиндексация выполняется **в конце того же хука, до
создания коммита**, и индексирует **рабочее дерево**, а не staged-содержимое
(частичный `git add -p` временно уводит индекс вперёд истории — следующий коммит
выправляет). Неудача переиндексации коммит не останавливает — это не барьер, а
удобство. Хук дополнительно восстанавливает симлинк
`.obsidian-hybrid-search.db` → `var/knowledge-search/index.db`, если `reindex
--force` заменил его настоящим файлом.

## 6. `generated.lock.json`

`scripts/generated.lock.json` — реестр строгих (не текстовых с шапкой-комментарием,
а строго форматных, например JSON) generated-артефактов и хеша всей политики:

```json
{
  "generator": "scripts/agents.mjs",
  "policyHash": "<sha256 всей общей политики>",
  "toolingDirs": [".agents", ".claude", ".codex"],
  "artifacts": {
    ".mcp.json": "<sha256 файла>"
  }
}
```

Каждый текстовый generated-артефакт (Markdown/TOML с комментариями) несёт
собственную шапку `GENERATED — не редактировать вручную` + перечень
файлов-источников + `source-hash`. Один `source-hash` сам по себе не доказывает
актуальность артефакта — инвариант обеспечивается пересборкой плана и побайтовым
сравнением командой `check`, а не чтением хеша глазами.

## 7. Требование `core.symlinks`

`core.symlinks=true` и фактическая поддержка симлинков файловой системой — жёсткое
предусловие репозитория, а не свойство конкретной машины: вся доставка Claude Code
(скиллы, роли, команды — все три строки левой колонки §3) опирается на симлинки.
Без этого условия `checkout` молча создаёт обычные файлы вместо симлинков — то есть
ровно то состояние («рукописная копия канонического текста»), которое архитектура
запрещает. `build` и `check` проверяют оба условия (`core.symlinks=true` и реальную
поддержку симлинков ФС) первым действием и падают с внятным сообщением, если
условие не выполнено.

## 8. Фактические ограничения — то, что нельзя спроектировать вокруг словом

Три пункта, подтверждённые экспериментом на этой машине, а не документацией
поставщика клиента:

1. **Codex CLI не применяет поле `tools` роли.** Под Claude Code роль реально
   получает ровно перечисленный набор инструментов (проверено: роль с
   `tools: Read, Grep, Glob, Write, Edit` получила ровно эти пять, без `Bash` и
   без `Agent`). Под Codex CLI такого механизма нет вовсе — `tools` для Codex
   является только рекомендацией в тексте, а не enforcement. Любая изоляция по
   доверию (например, «роль без `Bash`/секретов»), спроектированная как граница на
   поле `tools`, реально работает только под Claude Code и фиктивна под Codex CLI.
   Разбор этого факта как архитектурного инварианта —
   `docs/adr/0014-semantika-bezopasnosti-ne-zavisit-ot-ignoriruemyh-metadannyh.md`.
2. **`.codex/config.toml` проектным клиентом не читается** — проверено дважды,
   включая `trust_level=trusted`, на версии 0.146.0. Артефакт `.codex/mcp-servers.toml`
   в репозитории — генерируемый, синтаксически валидный фрагмент, но **фактической
   доставки MCP для Codex CLI нет**: перенос содержимого в `~/.codex/config.toml`
   выполняет оператор вручную. На момент чтения этого документа Codex CLI работает
   без настроенных MCP-серверов, пока оператор не перенёс фрагмент сам.
3. **Command-router Codex — это конвенция, а не платформенный механизм.** Нет
   нативных слэш-команд репозитория для Codex CLI; они эмулируются генерируемой
   секцией внутри `AGENTS.override.md` по конвенции `/<имя> <аргументы>`, причём
   router срабатывает **только если команду произнёс пользователь**, а не сам
   агент (иначе `disable-model-invocation: true` для этого клиента ничего бы не
   значило).

Практическое следствие для любого, кто планирует новую роль или команду: считать,
что она одинаково защищена на обоих клиентах, нельзя. Формулировка защиты обязана
явно называть клиент, на котором она проверена.

## 9. Подключение нового клиента

Формально требуется только `.agents/policy/runtime/<runtime>.md` +
`.agents/runtimes/<runtime>.json` (+ новый модуль доставки в `scripts/agents.mjs`,
только если транспорт принципиально новый) — и **не требуется** ни одной правки в
`.agents/skills`, `.agents/agents`, `.agents/commands`, `.agents/policy/common`. Это
проверено механически: добавление пробного `probe.json`/`probe.md` прошло
`lint`/`build`/`check` без изменения ни одного существующего канонического файла.

## 10. Что не реализовано и не описано здесь

Механизм точечного отсечения опасных MCP-инструментов внутри allowlist-шаблона
`mcp__playwright__*` (например, отдельного запрета `browser_run_code_unsafe` при
разрешённом `mcp__playwright__*`) в каноне не существует — это открытый пробел
модели угроз, а не спроектированная и не реализованная возможность сборщика.
Формальный enforcement выдачи полномочий (какая роль вправе быть вызвана на какую
задачу, кем и с каким лизингом) канон `.agents/` не реализует вообще — сегодня это
решает сам исполнитель по тексту роли; перенос этой функции к PACT — вопрос
`docs/spec/spec.md`, не факт этого репозитория.
