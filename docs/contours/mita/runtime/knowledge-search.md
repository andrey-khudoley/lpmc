# Поиск по базе знаний

> docs-as-state: этот документ описывает то, что есть сейчас, по исходникам репозитория
> `cloud-tech-tasks` (`infra/knowledge-search/README.md`, `.agents/mcp/registry.json`,
> `.githooks/pre-commit`); снимок на 2026-08-05/09, дата чтения — 2026-08-10. Почему
> механический контроль репозитория (и заодно обслуживание этого индекса) висит
> исключительно на локальном `pre-commit`, а не на внешнем CI — `docs/adr/0015-lokalnyy-
> pre-commit-vmesto-vneshnego-ci.md`; здесь только факт устройства и правила
> эксплуатации, без пересказа истории решения.

## 1. Назначение

Поиск по содержимому самого репозитория `cloud-tech-tasks` — клиенты, сервисы,
плейбуки, заметки, задачи. Это не поиск по внешнему Obsidian-vault: движок использован
для индексации самого рабочего дерева репозитория, vault для него — корень репозитория
(`OBSIDIAN_VAULT_PATH=.`).

## 2. Движок и модель

Движок — `obsidian-hybrid-search`, гибридный поиск: BM25 (лексический) + семантический
поиск по эмбеддингам, объединение результатов через RRF (Reciprocal Rank Fusion).
Установленная версия — 0.13.13 (по данным `status`; актуальная на момент подключения
была 0.13.25 — обновление не делалось). Обновление — только через Ansible-роль в
`/var/lib/infra/src`, не ручным `npm install -g`.

Эмбеддинги считаются локальной моделью (`local:Xenova/multilingual-e5-small`), без
обращения к внешним API — в репозитории живут контактные данные реальных людей
(клиентов, владельцев), и эта отправка наружу была явно исключена как решение при
подключении сервиса.

## 3. Подключение как MCP-сервер

Единственный источник правды о конфигурации — `.agents/mcp/registry.json` (запись
`knowledge-search`), из которого генерируется `.mcp.json`; руками `.mcp.json` не
правят. Запись канона:

```json
"knowledge-search": {
  "transport": "stdio",
  "command": "obsidian-hybrid-search-mcp",
  "args": [],
  "env": {
    "OBSIDIAN_VAULT_PATH": ".",
    "OBSIDIAN_IGNORE_PATTERNS": ".secrets/**,deploy/**,var/**,.obsidian/**,templates/**,node_modules/**,*.canvas"
  }
}
```

MCP-сервер не привязан ни к одной роли во frontmatter `.agents/agents/*.md` — он
доступен в главном контексте сразу через `.mcp.json` (для Claude Code, реально
читается) и через сгенерированный `.codex/mcp-servers.toml` (для Codex CLI — это лишь
фрагмент для ручного переноса оператором в `~/.codex/config.toml`; фактической доставки
MCP для Codex сегодня нет — подробности переноса и доставки MCP по двум клиентам см.
`docs/agent-toolkit.md`).

### Переменные окружения

- `OBSIDIAN_VAULT_PATH=.` — vault движка совпадает с корнем репозитория.
- `OBSIDIAN_IGNORE_PATTERNS=.secrets/**,deploy/**,var/**,.obsidian/**,templates/**,node_modules/**,*.canvas`
  — по умолчанию движок индексирует всё дерево, включая `.secrets/` и `deploy/`; это
  было явно закрытой дырой при подключении сервиса (первый прогон индексации затянул
  бы секреты и служебный staging-каталог в базу).
  `var/**` исключён отдельно — это оперативный, не version-controlled по смыслу
  каталог (сам индекс `var/knowledge-search/` в git не попадает, но как обычные файлы
  дерева не индексируется).

Хук `.githooks/pre-commit` не хранит копию этого списка — при переиндексации он читает
`env` сервера прямо из `.agents/mcp/registry.json` через `node -e`, чтобы CLI и MCP-сервер
не разъехались на два источника правды (если бы CLI индексировал по своим умолчаниям,
`.secrets/` снова попал бы в базу).

## 4. CLI-команды

Помимо MCP-инструментов, движок доступен из шелла напрямую:

```bash
OBSIDIAN_VAULT_PATH=. obsidian-hybrid-search status        # состояние индекса
OBSIDIAN_VAULT_PATH=. obsidian-hybrid-search reindex        # досборка после правок
OBSIDIAN_VAULT_PATH=. obsidian-hybrid-search search "..."   # поиск из шелла
```

## 5. Хранение индекса и симлинк в корне

Сам индекс — SQLite-база `var/knowledge-search/index.db` (+ `index.db-wal`,
`index.db-shm`; на момент наблюдения ~7.3 МБ `index.db` + ~9.4 МБ WAL). Индекс — чистая
производная от содержимого репозитория: в git не попадает никогда, при утрате
пересобирается с нуля командой `reindex`.

Движок вычисляет путь к своей базе жёстко: `OBSIDIAN_VAULT_PATH` + `/.obsidian-hybrid-
search.db` (внутри его собственного `config.js`). Переменной окружения, которая
переопределяла бы этот путь, нет; флаг `--db` не помогает — он только открывает
указанную базу, читает из её таблицы `settings` путь к vault и подставляет его в
окружение, но писать движок всё равно будет по вычисленному пути. Поскольку vault —
корень репозитория, база обязана быть доступна по имени `.obsidian-hybrid-search.db`
именно в корне.

Чтобы не держать бинарные файлы вне `var/` (правило репозитория «бинарники — только в
`var/`», `.agents/policy/common/01-repository-layout.md`), в корне репозитория лежит
симлинк:

```
.obsidian-hybrid-search.db → var/knowledge-search/index.db
```

SQLite резолвит симлинк при открытии, и WAL-спутники создаются рядом с реальным файлом
в `var/`, а не в корне. Симлинк сознательно не отслеживается в git (`.gitignore`
исключает `.obsidian-hybrid-search.db*`) — так бинарник не может попасть в историю
репозитория даже при `git commit --no-verify`. Обратная сторона размена: свежий clone
получает базу прямо в корне (обычным файлом), пока её туда не положит первый `reindex`
без вмешательства хука, — она уезжает в `var/` только после первого прогона
`pre-commit`.

### Хрупкость: `reindex --force` сносит симлинк

`obsidian-hybrid-search reindex --force`, а также восстановление после повреждения
базы, вызывают внутри движка `wipeDatabaseFiles()` — эта функция удаляет файлы по
вычисленному пути, то есть физически стирает сам симлинк, и новая база при следующей
записи ложится в корень обычным файлом. Ошибки при этом нет — просто бинарник тихо
возвращается в корень.

Обычный `reindex` (без `--force`), которым и работает `pre-commit`, симлинк не трогает.

Починка вручную, если симлинк всё же снесён:

```bash
mv .obsidian-hybrid-search.db var/knowledge-search/index.db
ln -s var/knowledge-search/index.db .obsidian-hybrid-search.db
```

## 6. Нет файлового вотчера: `pending: 0` вводит в заблуждение

У сервера (ни у MCP-инстанса, ни у CLI) нет файлового вотчера. Это значит: запись новой
заметки или правка существующей никак не регистрируется движком сама по себе — файл
для поиска не виден, пока явно не выполнен `reindex`. Ловушка в том, что в этот момент
`status` показывает `pending: 0` — не потому что индекс актуален, а потому что движок
о новом/изменённом файле попросту не знает вовсе. По одному `status` нельзя отличить
«индекс свежий» от «движок не видел изменений» — нужно вызывать `reindex` и проверять
результат, а не полагаться на счётчик `pending`.

Никакого штатного демона-наблюдателя за файловой системой в системе нет и не
планировалось отдельно — вопрос закрыт не вотчером, а перепривязкой момента
переиндексации (см. §7).

## 7. Переиндексация повешена на `pre-commit`

Раз вотчера нет, переиндексация вызывается механически в конце `.githooks/pre-commit`,
после шагов `lint`/`check` канона `.agents/`, отдельным некритичным шагом: сбой
переиндексации не блокирует коммит (индекс — производная, а не источник истины, поэтому
неудача его пересборки не повод останавливать работу). Логика хука:

1. Если `.obsidian-hybrid-search.db` в корне существует и не является симлинком —
   значит его снёс предыдущий `reindex --force`; хук переносит файл(ы) обратно в
   `var/knowledge-search/` и восстанавливает симлинк (см. §5).
2. Переменные окружения для запуска CLI хук не хардкодит, а читает из
   `.agents/mcp/registry.json` (запись `knowledge-search` → `env`), чтобы не завести
   второй источник правды на список исключений.
3. Выполняется `obsidian-hybrid-search reindex` с этими переменными. Успех —
   `pre-commit: индекс knowledge-search обновлён`; неудача печатает предупреждение в
   `stderr` с командой для ручной пересборки, но коммит не останавливает.

Индексируется **рабочее дерево**, а не staged-содержимое git. Для репозитория, где
обычно коммитят файлы целиком, разница непринципиальна; при частичном `git add -p`
индекс на короткое время может оказаться «впереди» истории (видит несохранённые в
коммит правки) — это выправляет следующий коммит.

Побочное следствие: если `.githooks/pre-commit` не подключён как активный git-хук
(`core.hooksPath` не выставлен — см. `docs/adr/0015-lokalnyy-pre-commit-vmesto-vneshnego-
ci.md` про то, как это подхватывается `agents.mjs build`/`check`), переиндексация не
происходит вовсе, и индекс отстаёт от репозитория на неопределённый срок без явного
предупреждения — кроме несоответствия результатов поиска содержимому файлов, сигнала
об этом никакого нет.

## 8. Открытые вопросы

  результатов поиска с содержимым репозитория.
