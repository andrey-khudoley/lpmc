# Локальное состояние: var/ и вспомогательные скрипты

> docs-as-state: этот документ описывает то, что есть сейчас в репозитории
> `cloud-tech-tasks`, по прямому чтению `var/`, `.gitignore` и
> `var/login-checks/lib.mjs`; вспомогательные конспекты вне репозиториев (не
> первоисточник, могут исчезнуть) — `research/mita-machinery.md` §§4.1, 4.3, 6
> и `research/secrets-model.md` §7. Снимок структуры на 2026-08-09, дата
> чтения — 2026-08-10. Про целевое
> разнесение этой машинерии между будущими MITA/PACT (например, расщепление
> `var/login-checks/*.mjs` на «логика входа» и «доступ к значению секрета») —
> `docs/spec/spec.md`, здесь только указатель, без пересказа.

## 1. `var/` целиком — производное состояние, не version-controlled

`var/` исключён из git одной строкой в `.gitignore` (с комментарием «производное
состояние инструментов… всё содержимое пересоздаётся инструментами — терять там
нечего») и отдельно — из индексации `knowledge-search`
(`OBSIDIAN_IGNORE_PATTERNS` содержит `var/**`). Ничего из содержимого `var/` не
несёт информации, которую нельзя было бы восстановить: индекс поиска
пересобирается из файлов репозитория, вывод Playwright MCP — расходный лог
инструмента, ad hoc скрипты по клиенту-сервису переживают только до следующей
правки. Единственное, что физически теряется при `rm -rf var/` без резервной
копии, — это history скриптов `var/kinescope/*.mjs` (см. §4), потому что их
исходный код нигде больше не хранится; их *данные* (доступ к сервисам,
storage-state) не теряются — они лежат отдельно, в `.secrets/`.

Структура на срез 2026-08-09:

```
var/
├── kinescope/            ← 27 скриптов .mjs + скриншоты .png (см. §4)
├── knowledge-search/
│   └── index.db, index.db-shm, index.db-wal    ← SQLite-индекс гибридного поиска
├── login-checks/         ← lib.mjs + 3 скрипта проверки логина/пересъёма storage-state (см. §3)
└── playwright-mcp/       ← вывод MCP playwright: console-*.log, page-*.yml, *.png (см. §2)
```

## 2. `var/playwright-mcp/` — вывод MCP Playwright

Каталог задан флагом `--output-dir var/playwright-mcp` в конфигурации MCP-сервера
`playwright` (канон — `.agents/mcp/registry.json`, подробности запуска и
подключения — `docs/runtime/browser.md` §7). Сюда автоматически уходят все файлы,
которые инструменты Playwright создают без явного имени: скриншоты,
accessibility-снапшоты страницы (`page-*.yml`), консольные логи (`console-*.log`).
Действует LRU-вытеснение по лимиту `--output-max-size 52428800` (50 МБ) — старые
файлы сами уступают место новым, специального обслуживания не требуется.

Если инструменту передать явный `filename`, файл ляжет по нему относительно
корня репозитория, мимо `var/playwright-mcp/` — на практике этого избегают, а
если явное имя нужно, пишут его целиком как `var/playwright-mcp/<имя>.png`.
Результаты, доказывающие выполнение задачи (для DoD), в этот каталог **не
кладут** — их место в `<root>/<owner>/tasks/<id>/artifacts/`, которое переживает
вытеснение и идёт в git.

## 3. `var/login-checks/*.mjs` — проверка входа и пересъём storage-state

Не тестовый фреймворк и не оформленный плейбук, а набор рабочих ad hoc скриптов,
запускаемых вручную оператором/агентом, когда нужно подтвердить, что вход в
сервис всё ещё работает, или переснять `storage-state` после смены учётных
данных. Структура на срез — 4 файла:

- `lib.mjs` — общие помощники, переиспользуемые остальными скриптами;
- `larina-getcourse.mjs`, `neso-getcourse.mjs`, `shared-kinescope.mjs` — по
  одному файлу на пару клиент/сервис (нейминг `<владелец>-<сервис>.mjs`).

### Помощники в `lib.mjs`

- **`secret(key)`** — читает значение секрета из `.secrets/env` построчным
  разбором: поиск первого `=` через `indexOf` и `slice` (`line.slice(0, i) === key`
  → `line.slice(i + 1)`), точное совпадение префикса строки до `=` с именем ключа,
  без `source`. Это принципиально: `env` —
  не shell-файл, и на некоторых паролях `source` либо падает, либо (хуже) молча
  выполняет часть значения как shell-команду. Формат ключа — `CLIENT__SERVICE__FIELD`
  (модель нейминга и правила chmod разобраны в `docs/data-model.md`).
- **`totp(path)`** — генерирует одноразовый TOTP-код локальной реализацией
  HMAC-SHA1 по base32-секрету, прочитанному из `.secrets/totp/<client>/<service>`;
  внешнего сервиса или библиотеки-посредника нет.
- **`connect(port)`** — подключается к уже работающему браузерному инстансу по
  CDP напрямую (`chromium.connectOverCDP` из пакета Playwright, установленного
  через npx в `~/.npm/_npx/...`), в обход MCP Playwright. Приём применяется
  умышленно: в текущей сессии агента MCP-сервер мог быть привязан не к тому
  порту (`KIOSK_CDP_PORT` читается один раз при старте сессии — см.
  `docs/runtime/browser.md` §4), а прямое CDP-подключение позволяет обратиться к
  конкретному инстансу владельца безусловно.

### Порядок работы скрипта

1. `secret()` читает логин/пароль, `totp()` — код второго фактора (если у
   сервиса включена 2FA).
2. `connect(port)` подключается к CDP нужного инстанса — **инстанса конкретного
   владельца, а не `default`**: например, `larina-getcourse.mjs` подключается к
   порту 9223 (инстанс `larina`), `shared-kinescope.mjs` — тоже к 9223, а
   `neso-getcourse.mjs` — к 9224 (инстанс `neso`). Список инстансов и портов —
   `docs/runtime/browser.md` §3.
3. Вход в сервис выполняется через обычные UI-локаторы (клики, заполнение форм) —
   то же, чем пользуется обычная задача агента, без специальной обвязки.
4. По завершении входа снимается сессия — `ctx.storageState({ path: OUT })`, куда
   `OUT` указывает в `.secrets/storage-state/<client>/<service>.json`, — и на файл
   сразу выставляется `chmod 600`.

Оформленного универсального плейбука «переснять storage-state по секретам, с
ротацией» нет — логика входа пишется отдельным скриптом под конкретный сервис
по мере надобности; факт зафиксирован и в `docs/playbooks.md` §6 («Чего сегодня
нет»). Задокументированное применение — минимум дважды, 2026-08-08 и 2026-08-09,
для реальной проверки входов после смены учётных данных (переименование
агентской учётки ESTA → MITA и смежная ротация, разобраны в `docs/overview.md` и
`llm/2026-08/2026-08-09-1050-main-agent-account-rename.md` репозитория
`cloud-tech-tasks`).

## 4. `var/kinescope/*.mjs` — браузерная CDP-автоматизация по одному сервису

27 файлов `.mjs` (плюс скриншоты `.png` рядом) — рабочие ad hoc скрипты для задач
по Kinescope: например `bill.mjs`, `login.mjs`, `otp.mjs`, `project.mjs`,
`folders.mjs`, `check.mjs`, `net.mjs`, `probe.mjs`, `save.mjs`, `tilda.mjs` и
несколько пронумерованных вариаций (`gc-neso2.mjs` … `gc-neso6.mjs`). Не
оформлены как плейбук и не сведены в общую библиотеку — каждый скрипт написан
под конкретный шаг конкретной задачи (снять биллинг, залогиниться, получить
проект/папку, показать состояние) по мере необходимости, часть — черновики или
повторные попытки одной и той же операции (`bill.mjs`/`bill2.mjs`,
`gcl.mjs`/`gcl2.mjs`, `tilda.mjs`/`tilda2.mjs`).

По устройству это тот же класс машинерии, что и `var/login-checks/*.mjs`: прямое
CDP-подключение к браузерному инстансу (не HTTP-клиент к API Kinescope) —
**браузерная автоматизация**, использующая UI-поверхность сервиса, а не
опубликованный контракт. Это осознанная граница: у Kinescope есть API
(`app.kinescope.io/api/entities` упоминается в `docs/services.md`), но текущие
скрипты работают через UI, потому что задачи возникали ad hoc и по частям, а не
как единая интеграция.

Скриншоты `.png` в том же каталоге (`01-state.png`, `05-larina-project.png`,
`n5-gc.png` и т. п.) — побочные артефакты отладки при написании скриптов, не
результаты задач: доказательства выполнения задач по-прежнему кладутся в
`<root>/<owner>/tasks/<id>/artifacts/`, а не сюда (то же правило, что и для
`var/playwright-mcp/`, см. §2).

## 5. `var/knowledge-search/index.db` и симлинк в корне

```
.obsidian-hybrid-search.db  → var/knowledge-search/index.db   (симлинк в корне репозитория)
```

Симлинк существует потому, что движок `obsidian-hybrid-search` вычисляет путь к
своей базе жёстко как `OBSIDIAN_VAULT_PATH + '/.obsidian-hybrid-search.db'` — без
переменной окружения для переопределения места записи (флаг `--db` только
задаёт путь к vault, не к базе), а vault здесь — корень репозитория. Симлинк
уводит бинарник базы в `var/`; файлы WAL-режима SQLite (`-wal`, `-shm`)
создаются рядом с реальным файлом, то есть тоже в `var/knowledge-search/`, а не
в корне.

В `.gitignore` игнорируется маска `.obsidian-hybrid-search.db*`, а не точное имя
— это защищает сразу от двух вещей: спутников WAL, которые иначе всплывали бы в
`git status` как неотслеживаемые, и от `obsidian-hybrid-search reindex --force`,
который вызывает `wipeDatabaseFiles()` и удаляет файл по вычисленному пути —
**сносит симлинк**, после чего новая база тихо ложится в корень обычным файлом,
без ошибки. Обычный `reindex` (без `--force`) симлинк не трогает.

Восстановление после такого сноса — вручную или автоматически внутри
`.githooks/pre-commit` (хук чинит симлинк тем же способом при каждом коммите):

```bash
mv .obsidian-hybrid-search.db var/knowledge-search/index.db
ln -s var/knowledge-search/index.db .obsidian-hybrid-search.db
```

Индекс — производная от файлов репозитория, обновляется командой
`obsidian-hybrid-search reindex`, повешенной на `.githooks/pre-commit`
(коммит — точка синхронизации; свежий файл не виден поиску, пока не
выполнен `reindex`). При утрате пересобирается с нуля, ничего не хранит,
чего нет в самом репозитории. Устройство MCP-сервера `knowledge-search` и
формат конфигурации — `docs/agent-toolkit.md`.

## 6. Что попадает в `.gitignore` и почему

Из `.gitignore` репозитория `cloud-tech-tasks` (фрагмент, относящийся к
локальному состоянию):

```gitignore
# Артефакты инструментов
node_modules/
__pycache__/
*.log

# Производное состояние инструментов: индекс knowledge-search, вывод Playwright MCP.
# Собрано в один каталог, чтобы бинарники не расползались по корню репозитория.
# Всё содержимое пересоздаётся инструментами — терять там нечего.
var/

# Индекс knowledge-search физически лежит в var/knowledge-search/, но обязан быть
# доступен по этому имени в корне...
.obsidian-hybrid-search.db*
```

Отдельной строкой (не относится к `var/`, но к тому же классу «не в git»):
`.secrets/*` с исключением `!.secrets/README.md`, и `deploy/` целиком —
устройство этих каталогов описано в `docs/data-model.md` и не дублируется
здесь. Важное разграничение: `var/` — **производное состояние инструментов**
(пересоздаётся из репозитория и из `.secrets/`), тогда как `.secrets/` —
**источник чувствительных данных** (не пересоздаётся ничем, теряется
безвозвратно при утрате без резервной копии). Скрипты в `var/login-checks/` и
`var/kinescope/` читают из `.secrets/` и пишут снятые сессии обратно в
`.secrets/storage-state/` — то есть `var/` в этой связке только код и
временный вывод, а результат работы (сессия) оседает вне `var/`.

## 7. `infra/webapp` — не реализован

В `cloud-tech-tasks` каталог `infra/webapp/` содержит только документацию о
том, каким веб-интерфейс должен быть, — рабочего кода, сервера, HTTP API или
БД в репозитории нет. Заявлен как «этап 3» в `ROADMAP.md` MITA (после этапа
переезда под текущую структуру владельцев/задач). Идея по README — тонкий
слой над файлами репозитория, а не отдельная система со своим хранилищем:
источником истины останутся `clients/`, `projects/`, `internal/`, `notes/`, а
сервис их читал бы и писал в тех же форматах. Планируемые (не реализованные)
функции: рендер очереди задач/карточек, HTTP API приёма постановок в
`<root>/<owner>/tasks/inbox/`, синхронизация с брокером событий, дашборд по
клиентам/сервисам. Раскрытие целевого устройства — вне этого документа, см.
`docs/spec/spec.md`.

### Порт 8080 узла — зарезервирован, без привязки в файлах

В таблице веб-контура узла (`docs/runtime/human-view.md` §4) порт `8080`
значится как «зарезервирован под будущее приложение» — предположительно под
этот `webapp`, по логике совпадения с идеей HTTP-интерфейса из §6/§7. Явной
привязки этого порта к `infra/webapp/` в файлах репозитория не найдено: ни в
`ROADMAP.md`, ни в `infra/webapp/`, ни в конфигурации nginx на узле порт 8080
не упоминается. Резервирование сегодня — устная договорённость/соглашение о
топологии портов, а не зафиксированный факт.
