> docs-as-state: этот документ описывает то, что есть сейчас, по исходникам репозитория
> `cloud-tech-tasks` (`infra/playwright/`, `infra/web-browser/`) и по конфигурации узла
> вне этого репозитория (`/var/lib/infra/src`, роль `kiosk_browser`); снимок на

## 1. Принцип: общий браузер для агента и человека

MCP-сервер `playwright` **не запускает браузер сам** — он подключается по CDP к уже
живущему постоянному Chrome на узле. Смысл именно в постоянстве: браузер общий для
агента и человека — когда агент упирается в капчу, человек проходит её с телефона в той
же вкладке, и агент продолжает (см. также `docs/playbooks.md` про `captcha-escalation`).

Побочный эффект — браузер **headed**, а не headless: обычный user-agent, постоянный
профиль, нет типичных маркеров автоматизации (`navigator.webdriver === false`, UA
`Chrome/151.0.0.0` без `Headless`, окно 1280×720). Headless для этой задачи отвергнут
отдельным решением (ADR-0007) — он ломает прохождение антибот-защиты Cloudflare.

## 2. Устройство стека одного инстанса (сверху вниз)

```
телефон → https://vds.khudoley.pro:22325/<одноразовый путь>/   (nginx: TLS)
              ↓ 127.0.0.1:(6080+i)
          websockify + noVNC        ← поднимается на сеанс просмотра, гаснет через 30 минут
              ↓ 127.0.0.1:(5900+i)
          wayvnc (без аутентификации, только петля 127.0.0.1)
                                    ← поднимается вместе с сеансом просмотра, постоянно не висит
              ↓ /run/kiosk-browser/<имя>/wayland-0
          cage — headless-композитор на wlroots, свой процесс на инстанс (~19 МБ)
            └── Chrome headed, профиль /home/kiosk-browser/profiles/<имя>
                  ↑ CDP 127.0.0.1:(9600+i)   ← слушает сам браузер (без аутентификации)
                systemd-socket-proxyd
                  ↑ CDP 127.0.0.1:(9222+i)   ← этот порт знают агенты (KIOSK_CDP_PORT)
                MCP Playwright ← сюда подключается агент
```

Верхняя часть стека (nginx → websockify → wayvnc, аварийный просмотр сеанса человеком)
здесь описана только как контекст; она поднимается лишь на время сеанса просмотра и не
нужна для обычной работы агента. Нижняя часть (cage → Chrome → CDP) живёт постоянно,
пока с ней кто-то работает.

Юниты systemd (шаблонные, `<имя>` = имя инстанса):

| Юнит | Что делает | Состояние по умолчанию |
|---|---|---|
| `kiosk-browser-session@<имя>.service` | `cage` с Chrome внутри | `disabled` |
| `kiosk-browser-cdp@<имя>.socket` | держит клиентский порт CDP (`9222+i`), socket-activation | `indirect` |
| `kiosk-browser-vnc@<имя>.service` | `wayvnc` на время сеанса просмотра | `static` |
| `kiosk-browser-view@<имя>.service` | `websockify` + noVNC, жёсткий предел через `timeout(1)` в `ExecStart` (`kiosk_browser_view_max_seconds`, сегодня 30 минут; код 124 — успех) | `static` |
| `kiosk-browser-idle.timer` | двухуровневая выгрузка простаивающих браузеров (закрыть вкладки → остановить браузер) | `enabled` |

Порт CDP держит **не браузер, а systemd**: сокет `kiosk-browser-cdp@<имя>.socket`
слушает клиентский порт (`9222+i`) постоянно и поднимает связку `cage`+Chrome по первому
обращению через `systemd-socket-proxyd`. Автозапуска всех инстансов сразу нет намеренно —
узел не тянет их по CPU одновременно (см. §6). На прогретом узле ответ приходит быстрее
секунды — замер холодного старта до готовности CDP: 487 мс.

`wayvnc` не висит постоянно — только пока идёт сеанс просмотра человеком; после `stop`
уходит в `inactive`, порты `5900+i`/`6080+i` освобождаются, сам браузер и работа агента
при этом не прерываются.

## 3. Четыре инстанса и порты

Браузер разделён на **инстансы по владельцам**: у каждого владельца свой экран
(cage-композитор), свой профиль Chrome и свой порт CDP. Имя инстанса = слаг владельца
(`larina`, `neso`), либо `default` для системной работы без привязки к владельцу.

Индекс инстанса **явный** (не подразумевается порядком списка) и задаётся в
`config/ansible-vars.yml` роли `kiosk_browser` в отдельном репозитории
(`/var/lib/infra/src`, вне git `cloud-tech-tasks` и под root). Порт при индексе `i`:

| Что | Порт | Кто знает |
|---|---|---|
| CDP для агентов (клиентский, через `systemd-socket-proxyd`) | `9222+i` | агенты (`KIOSK_CDP_PORT`), MCP Playwright |
| CDP бэкенда (сам Chrome, без аутентификации) | `9600+i` | только роль |
| VNC (`wayvnc`) | `5900+i` | только роль |
| Просмотр (websockify+noVNC) | `6080+i` | nginx |

На сегодня (2026-08-09) заведено **четыре** инстанса:

| Имя | Index | CDP-порт |
|---|---|---|
| `default` | 0 | 9222 |
| `larina` | 1 | 9223 |
| `neso` | 2 | 9224 |
| `akh-tech` | 3 | 9225 |

Проекты пока изоляции не имеют — все делят инстанс `default`; это нужно держать в уме
при работе с проектными задачами в вебе. Обязательное правило — свой инстанс у каждого
владельца в `clients/` и `internal/`; для `projects/` — по мере надобности, но до первой
реальной работы в вебе.

**Список инстансов сознательно не хранится в этом репозитории** — «копия разошлась бы с
узлом молча». Источник правды — `/var/lib/infra/src/config/ansible-vars.yml` (ключ
`kiosk_browser_instances`) и команда `infra/web-browser/view.sh status` на узле (см. §9).
При заведении нового владельца скиллом `add-owner` требуется добавить ему инстанс с явным
свободным `index` в этом файле и прогнать роль (см. §5) — иначе владелец попадёт в общий
`default` и его страница будет видеть сессии остальных.

## 4. Привязка владелец → инстанс и правило «одна сессия — один владелец»

Переключение инстанса — переменной окружения **при старте сессии**:

```bash
KIOSK_CDP_PORT=9223 claude      # инстанс larina (index 1)
```

Переменная читается один раз при старте MCP-сервера `playwright`; посреди сессии
переключить инстанс нельзя (агент ещё не знает задачу в момент, когда переменная уже
подставлена). Отсюда правило: **одна сессия — один владелец**. Субагенты наследуют
подключение родителя и попадают в тот же инстанс — это и есть корректная изоляция по
владельцу, а не недостаток.

Без явного `KIOSK_CDP_PORT` сессия попадает в инстанс `default` (порт 9222) — так же, как
и любой соседний воркспейс на этом узле, если переменную не выставить.

## 5. `kiosk-browser` — общий системный пользователь как граница изоляции

Все инстансы работают под одним непривилегированным системным пользователем
`kiosk-browser` (uid 988, без sudo и без shell, без доступа к репозиторию `cloud-tech-tasks`
и к `.secrets/`). Это определяет, что именно закрыто изоляцией по инстансам, а что нет:

- **Закрыто от враждебной веб-страницы.** Страница в инстансе одного владельца не видит
  профиль/куки/экран другого — это разные процессы Chrome с разными каталогами профиля
  (`/home/kiosk-browser/profiles/<имя>`) и разными wayland-сокетами
  (`/run/kiosk-browser/<имя>/wayland-0`); проверено сопоставлением сокетов по inode.
- **Не закрыто от скомпрометированного процесса браузера.** Аутентификации на
  CDP-бэкенде (`9600+i`) нет. Код, выполнившийся от имени `kiosk-browser`, получает разом
  профили, экраны и CDP-бэкенды всех владельцев сразу — общая граница отказа для всего
  браузерного контура. Разнесение инстансов по разным системным пользователям — открытая
  незакрытая работа, а не скрытый факт (зафиксировано как таковое в ADR-0008).

Прежний общий профиль `/home/kiosk-browser/chrome-profile` (со всеми накопленными куки
всех владельцев) переехал в `profiles/default`; каталога `chrome-profile` больше нет.
**Новый инстанс = пустой профиль.** Владелец, ранее работавший в общем браузере, не
наследует сессии — вход и снятие storage-state придётся повторять заново в новом
инстансе; автоматического переноса куки между инстансами нет и не планируется.

## 6. Стоимость инстанса (замер 2026-08-08)

- Браузер с живой страницей — ~380 МБ PSS; первый инстанс дорогой, каждый следующий
  маржинально ~250 МБ (бинарь/библиотеки общие).
- `cage` — ~19 МБ, плюс GPU-процесс, ~100–150 МБ PSS сверх headless-замера.
- Холодный старт до готовности CDP — 487 мс.
- Профиль на диске — 14 МБ после живой страницы; `profiles/default` накопил 100 МБ
  (наследие общего профиля).
- **Узкое место — CPU, не память.** На узле 4 ядра: пять одновременных инстансов
  проходят по памяти, но не по CPU; восемь одновременных дали loadavg 24.7 и своп.
  Механического лимита одновременности в роли `kiosk_browser` нет — это открытый риск
  деградации узла при неконтролируемом росте числа владельцев/инстансов, а не
  гипотетический.

## 7. Подключение MCP Playwright и переменная `KIOSK_CDP_PORT`

Конфигурация MCP-сервера `playwright` — каноническая, в `.agents/mcp/registry.json`,
из которой `node scripts/agents.mjs build` собирает рабочий `.mcp.json` (руками
`.mcp.json` не редактируют, см. `docs/agent-toolkit.md`). Актуальный `.mcp.json` в корне
репозитория `cloud-tech-tasks`:

```json
"playwright": {
  "type": "stdio",
  "command": "npx",
  "args": ["-y", "@playwright/mcp@latest",
           "--cdp-endpoint", "http://127.0.0.1:${KIOSK_CDP_PORT:-9222}",
           "--output-dir", "var/playwright-mcp", "--output-max-size", "52428800"]
}
```

Такой же сервер прописан у пользователя (`~/.claude.json`) без `--output-dir` и с портом,
зашитым числом `9222`; проектный конфиг побеждает (`claude mcp get playwright` →
`Scope: Project config`), поэтому соседние воркспейсы на этом узле всегда попадают в
инстанс `default`, если явно не выставить `KIOSK_CDP_PORT`.

Подтверждено фактически (не по выводу `claude mcp get`, который печатает `${...}` сырьём,
а подменой сервера скриптом, фиксирующим реально полученные аргументы): подстановка
`${VAR:-default}` работает и в `args`, и в `env`, дефолт через `:-` обязателен — без него
незаданная переменная подставляется буквальным текстом `${KIOSK_CDP_PORT}`, и падение
выглядит как невнятная ошибка подключения, а не как понятная причина.

`--output-dir var/playwright-mcp` уводит автоматически именованные рабочие файлы
(скриншоты, DOM-снимки, консоль) из корня в `var/playwright-mcp/`; `--output-max-size`
50 МБ — LRU-вытеснение при переполнении. Если инструменту передать явный `filename`, файл
ляжет по нему **относительно корня репозитория**, мимо `var/` — поэтому явный `filename`
избегают, а если он нужен — пишут `var/playwright-mcp/<имя>.png` целиком. Результаты,
доказывающие выполнение задачи, в `var/playwright-mcp/` не кладут — их место в
`<root>/<owner>/tasks/<id>/artifacts/` (переживает вытеснение, идёт в git).

Инструменты у агента — `mcp__playwright__browser_*` (navigate, click, snapshot,
take_screenshot, fill_form, run_code_unsafe и др.), схемы подгружаются по запросу через
`ToolSearch`. Для разовых проверок вне MCP есть локальный CLI `npx playwright --version`
(на момент снимка — 1.62.1, `/usr/bin/npx`).

## 8. Ловушка: фоновая вкладка ломает клики

У неактивной вкладки Chrome останавливает `requestAnimationFrame`
(`document.visibilityState === "hidden"`), actionability-проверка Playwright ждёт
совпадения bounding box в двух подряд кадрах rAF и не завершается никогда → внешне это
выглядит как `TimeoutError` / «waiting for element to be visible, enabled and stable» на
полностью исправном элементе.

**Правило: первым действием после `browser_navigate` — `browser_tabs select` на свою
вкладку.** Диагностика — выполнить в странице `() => ({v: document.visibilityState})` и
проверить, что значение `visible`.

Инстанс на владельца убирает главный источник этой ловушки (человек с телефона
переключил вкладку в общем браузере), но не сам класс отказа — если агент сам открыл в
своём инстансе вторую вкладку, эффект тот же. Разобрано в
`notes/2026-08/2026-08-07-playwright-background-tab-clicks.md` репозитория
`cloud-tech-tasks`.

## 9. Источник правды: конфигурация узла и `view.sh status`

`infra/web-browser/README.md` в `cloud-tech-tasks` **устарел** — на момент своего
последнего обновления (2026-08-08) он называет **два** инстанса (`default`, `larina`),
тогда как фактически их **четыре** (`default`=0, `larina`=1, `neso`=2, `akh-tech`=3, CDP
9222–9225). Расхождение появилось уже на следующий день после того, как README был
написан, и с тех пор README не источник правды по составу инстансов.

Это не случайность, а сознательное решение: список инстансов **не дублируется в git**,
чтобы копия не расходилась с узлом молча. Источник правды — два места, оба вне
`cloud-tech-tasks`:

1. `/var/lib/infra/src/config/ansible-vars.yml`, ключ `kiosk_browser_instances` — полный
   список имён, индексов и (выводимых из индекса) портов.
2. `infra/web-browser/view.sh status` на узле (обёртка над
   `/usr/local/sbin/kiosk-browser-session`, разворачивается той же ролью) — что сейчас
   реально поднято и работает, по всем инстансам.

Перед первым обращением к браузеру в новой задаче стоит свериться с одним из этих двух
источников, а не доверять числу инстансов в README или в этом документе буквально —
оба могут отстать от узла.

## 10. Управление ролью узла

Устройство браузерного стека (юниты, порты, профили) целиком настраивается идемпотентной
ролью Ansible `kiosk_browser` из отдельного репозитория `/var/lib/infra/src`. В
`cloud-tech-tasks` живёт только документация и обёртка `view.sh` — `/etc/nginx`,
`/etc/systemd/system` и профили браузеров руками не правят: ближайший прогон роли
незаметно перезапишет правку.

Прогон роли — строго точечный:

```bash
cd /var/lib/infra/src && sudo .venv/bin/ansible-playbook playbooks/optional.yml \
  -e '{"optional_roles_enabled":["kiosk_browser"]}' -e infra_single_role=true
```

`infra_single_role=true` обязателен: без него предполёт `role-list.yml` требует
присутствия зависимостей роли (`claude`, `nginx`) в списке и падает без изменений.
Эквивалент — `make role ROLE=kiosk_browser`. **`make optional` и `make site` прогонять
запрещено** — оба рестартуют `claude-remote-control` и рвут живые сессии агентов, включая
ту, из которой запущен прогон.

## Открытые вопросы

- Разнесение инстансов по разным системным пользователям (закрытие границы
  «скомпрометированный процесс браузера») не реализовано — см. §5 и ADR-0008.
- Механического лимита числа одновременных инстансов в роли `kiosk_browser` нет — см. §6.
- Владение этим контуром между будущими MITA и PACT — за пределами того, что сегодня
  реализовано; см. `docs/spec/spec.md`.
