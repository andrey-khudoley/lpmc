# Реестр сервисов и карточка сервиса

> docs-as-state: этот документ описывает то, что есть сейчас, по исходникам
> репозитория `cloud-tech-tasks` (снимок каталога `services/` на 2026-08-09,
> дата чтения — 2026-08-10). Про целевое разнесение содержимого карточки между
> контурами — `docs/spec/spec.md` (§13.1 «Карточка сервиса») и `docs/adr/`; здесь
> только факт сегодняшнего устройства и один указатель, без пересказа желаемого
> состояния.

## 1. Два уровня, где живут карточки сервисов

Сервис — внешняя система (веб-платформа/API/сервер), через которую выполняются задачи
владельца. Карточка сервиса заводится на одном из двух уровней:

1. **Клиентский сервис** — `<root>/<owner>/services/<service-slug>/overview.md`.
   Описывает конкретный проект/аккаунт данного владельца внутри сервиса (например, у
   NeSo и у Ларины — разные проекты Bizon365 внутри одного общего аккаунта).
2. **Общий (shared) сервис** — корневой `services/<service-slug>/overview.md`. Для
   сервисов, доступ к которым даётся не по клиенту, а по аккаунту исполнителя, один на
   несколько владельцев сразу.

Этот документ — про корневой каталог `services/` (общие сервисы). На сегодня в нём
ровно четыре карточки и `INDEX.md`:

```
services/
├── INDEX.md
├── bizon365/overview.md
├── chatium/overview.md
├── gc-chatium-gateway/overview.md
└── kinescope/overview.md
```

Клиентские карточки (`clients/<owner>/services/bizon365/overview.md` и т. п.) существуют
отдельно и ссылаются на общую карточку за деталями доступа; общая карточка ссылается на
клиентские за деталями операций конкретного проекта. Ссылки — двусторонние,
относительными путями. Их содержимое в этот документ не переносится — здесь только
реестр четырёх общих карточек.

## 2. `services/INDEX.md`

Плоский список карточек с однострочным описанием и ссылкой. Правило (общее для всех
каталогов с `INDEX.md` в репозитории): после изменения состава каталога — обновить
`INDEX.md`. Текст на 2026-08-09:

| Сервис | Однострочное описание в `INDEX.md` | Секреты |
|---|---|---|
| [`bizon365`](../../cloud-tech-tasks/services/bizon365/overview.md) | общий агентский аккаунт: одна учётка на проекты нескольких клиентов (`199542` neso, `129807` larina, `177956` akh-tech) | `shared/bizon365/*` |
| [`chatium`](../../cloud-tech-tasks/services/chatium/overview.md) | low-code облачная платформа (веб-сервисы, боты, лендинги, ЛК); основной рабочий инструмент как аккредитованного интегратора | не перенесены (см. §5) |
| [`gc-chatium-gateway`](../../cloud-tech-tasks/services/gc-chatium-gateway/overview.md) | собственный gateway-продукт Chatium ↔ GetCourse на воркспейсе `s.chtm.khudoley.pro`; обслуживает нескольких клиентов клуба Chatium | не перенесены (см. §5) |
| [`kinescope`](../../cloud-tech-tasks/services/kinescope/overview.md) | аккаунт исполнителя (AKH Tech) в Kinescope: одно рабочее пространство, внутри — проекты всех клиентов, пользующихся трансляциями | `shared/kinescope/*` |

Примечание про происхождение: `chatium` и `gc-chatium-gateway` перенесены из
Obsidian-vault `second_brain` 2026-07-30, при переносе раздел «Доступ» намеренно не
заполнялся (решение зафиксировано в
`llm/2026-07/2026-07-30-1430-legacy-migration-audit.md`). Карточки `bizon365` и
`kinescope` заведены позже, 2026-08-08, сразу с записанными доступами.

## 3. Шаблон `templates/service.md`

Карточка заводится по шаблону `templates/service.md`, путь фиксированный:
`services/<service-slug>/overview.md` (+ дополнительные файлы при необходимости).
Полный текст шаблона:

```markdown
---
name: <service-slug>
client: <client-slug>   # или shared для общих сервисов
type: web               # web | api | db | server | other
url: ""
owner: ""               # ответственный на стороне клиента, если известен
updated: YYYY-MM-DD
---

# <Название сервиса>

## Что это и зачем

<Назначение сервиса, роль в инфраструктуре клиента.>

## Доступ

- URL входа: <...>
- Учётные данные: секреты `<client>/<service>/username`, `<client>/<service>/password`
- 2FA: нет | TOTP (секрет `<client>/<service>/totp`)
- Playwright storage-state: `.secrets/storage-state/<client>/<service>.json`

## Возможности и типовые операции

<Что через этот сервис делается; ссылки на плейбуки, если есть.>

## Грабли и особенности

<Неочевидное поведение, ограничения, известные проблемы.>
```

Фактические карточки расширяют этот минимум: у `bizon365` и `kinescope` добавлена
секция «Проекты по клиентам» / «Рабочее пространство и проекты» (таблица
`id`/`parentId`/`folderId` по владельцам), у импортированных `chatium` и
`gc-chatium-gateway` в frontmatter есть дополнительные поля происхождения — `source`,
`imported`, `completeness: partial` (конвенция для файлов, перенесённых из старого
Obsidian-vault, см. `.agents/policy/common/09-imported-files.md`).

## 4. Четыре карточки: факты по разделам

### 4.1. `bizon365` — общий агентский аккаунт (вебинарная платформа)

- **Доступ.** URL `https://start.bizon365.ru`. Секреты `shared/bizon365/username`,
  `shared/bizon365/password`, TOTP `shared/bizon365/totp`
  (→ `.secrets/totp/shared/bizon365`). Storage-state
  `.secrets/storage-state/shared/bizon365.json` — **ещё не снят**. Сервис **недоступен с
  узла с 2026-08-08**: TLS до `start.bizon365.ru` рвётся после ClientHello — фильтрация
  по SNI на стороне сети узла (тот же эффект на посторонних доменах, `bizon365.ru` без
  SNI открывается нормально); диагностика — `notes/2026-08/2026-08-08-bizon365-sni-blocked.md`.
  Вход **проверить нельзя**. Учётка переименована 2026-08-09 (адрес почты сменился,
  пароль и TOTP-секрет прежние, отображаемое имя ESTA→MITA — на этом сервисе **не
  подтверждено**, потому что войти нельзя; секрет обновлён вслепую).
- **Возможности и типовые операции.** Платформенная механика (создание вебинарной
  комнаты, настройка перед эфиром, CSRF-механика, ограничения на `id` комнаты) записана
  не здесь, а в клиентской карточке `clients/neso/services/bizon365/overview.md` — с
  подставленным проектом `199542`, хотя сама механика от проекта не зависит. Карточка
  прямо помечает это как TODO: знание платформенное и по-хорошему принадлежит общей
  карточке, перенос не сделан (это отдельная операция, скилл `compact-notes`).
- **Грабли.** Аккаунт общий — действие уровня учётки (смена пароля, 2FA, профиль)
  задевает разом три проекта (`199542` neso, `129807` larina, `177956` akh-tech), в
  пределах одного проекта операции безопасны. Общий секрет ≠ общая сессия — у каждого
  владельца свой инстанс `kiosk_browser`, вход и storage-state снимаются в каждом
  профиле отдельно. Финальный запуск реального эфира — только по явной команде
  пользователя, агенту можно создавать и настраивать комнату, но не нажимать старт.

### 4.2. `kinescope` — аккаунт исполнителя (видеохостинг и трансляции)

- **Доступ.** URL `https://app.kinescope.io/live`. Секреты `shared/kinescope/username`,
  `shared/kinescope/password`, TOTP `shared/kinescope/totp`
  (→ `.secrets/totp/shared/kinescope`). Storage-state
  `.secrets/storage-state/shared/kinescope.json` — переснят 2026-08-09 в инстансе
  `larina` (44 cookies). Вход **фактически перепроверен 2026-08-09** в инстансе `larina`
  (CDP 9223): логин/пароль/TOTP приняты, капчи нет, видны все три проекта, роль
  «Администратор». Учётка переименована 2026-08-09 (адрес почты сменился, пароль и TOTP
  прежние, отображаемое имя стало MITA, было ESTA).
- **Возможности и типовые операции.** Механика создания трансляции (GraphQL
  `createEvent` → обязательный `updateEvent`, получение ссылок через `event`, обход
  недоступного UI) разобрана не здесь, а в `clients/neso/services/kinescope/overview.md`
  — тот же TODO-перенос, что у Bizon365, не сделан. `workspaceId`
  `167d1247-1fdd-48b9-a487-d0b460981b29` — свойство аккаунта, не клиента; в интерфейсе
  разделов два («Трансляции» и «Каталог»/записи), у каждого владельца свой проект в
  каждом разделе с разными `id` (таблица `parentId`/`folderId` по neso/larina/akh-tech и
  историческому проекту «Дмитрий Гончаров» — в карточке).
- **Грабли.** Два формально независимых бага формы TOTP: поле кода сабмитится само при
  заполнении (кнопка «Подтвердить» к этому моменту уже пропадает из DOM — клик по ней
  падает, но вход уже прошёл), и у поля кода нет HTML-атрибута `type` (`input[type=text]`
  не находит его, брать по `input:visible`). Пароль содержит `) & | } ]` — читать только
  через `sed -n 's/^KEY=//p'` или `split('=', 1)`, `source .secrets/env` на нём падает
  (подробности — `.secrets/README.md`). Биллинг общий на всех клиентов и на 2026-08-08 —
  в минусе (задолженность 795.27 ₽, к оплате 700 ₽); тот же механизм в июле 2026 уже
  замораживал эфиры обоим клиентам сразу (~3055.66 ₽, разблокировано к 2026-07-29) — при
  недоступности студии сначала проверять биллинг. `parentId`/`folderId` не копировать
  между клиентами вслепую, `workspaceId` — общий на аккаунт. Интроспекция GraphQL-схемы в
  этом окружении отключена.

### 4.3. `chatium` — low-code платформа (основной рабочий инструмент)

- **Доступ.** Раздел **не заполнен**: `TODO: доступы намеренно не перенесены в этом
  проходе — решение по способу их хранения принимается отдельно`
  (`llm/2026-07/2026-07-30-1430-legacy-migration-audit.md`). Единственный URL в карточке
  — публичная документация платформы (`https://chatium.ai/docs`), не рабочий аккаунт.
- **Возможности и типовые операции.** Платформа для веб-сервисов/ботов/лендингов/ЛК:
  роутинг file-based, БД Heap, джобы, платежи (подписки, автосписание), аналитика через
  ClickHouse, и — важно для §5 ниже — встроенные **внешние интеграции**: GetCourse SDK,
  AmoCRM (OAuth2), Notion, Toggl Track v9, Bizon365 API v2.0. Источник — 62-файловый свод
  автодоков платформы (`05_Knowledge/06_services/chatium/autodocs/`, входная точка
  `000-summ.md`), в карточку перенесён не построчно, а сводкой ключевых модулей.
- **Грабли.** Сервером управляет платформа — нельзя администрировать как обычный VPS,
  ограниченный стек. Секреты, токены и приватные ключи нельзя хранить в обычных markdown
  или публичном коде (правило автора, распространяется и на эту базу знаний). File-based
  routing — не хардкодить URL, использовать `route.url()`.

### 4.4. `gc-chatium-gateway` — собственный gateway Chatium↔GetCourse

- **Доступ.** Раздел **не заполнен**, тот же TODO и та же причина, что у `chatium`.
  Единственный URL в карточке — воркспейс продукта `https://s.chtm.khudoley.pro`.
- **Возможности и типовые операции.** Интеграция Chatium ↔ GetCourse через старый и
  новый API GetCourse; SDK-методы под конкретные клиентские сценарии (например
  UTM-методы для одного из клиентов клуба). Возник после отключения GC IDE-плагинов
  GetCourse (декабрь 2025). Полная архитектурная документация (4 ADR, реестр операций,
  клиентские сценарии) осталась в источнике (`03_Projects/active/gc-chatium-integration-5d9a2f/`)
  и не транскрибирована — при операционной работе читать актуальную версию там, не в
  этой карточке.
- **Грабли.** Мульти-клиентский продукт — изменение gateway влияет на всех подключённых
  клиентов клуба Chatium одновременно, не только на того, для кого делается конкретная
  фича.

## 5. Факт, который нужно проговорить прямо: карточка смешивает три разные природы

Сегодня одна и та же карточка сервиса совмещает сведения трёх разных природ, и всё это
целиком лежит в MITA, без разделения:

1. **Доступ** — имена секретов (`<owner-или-shared>/<service>/<field>`), наличие
   второго фактора, путь к storage-state. По сути custody-данные.
2. **Возможности и типовые операции через веб** — что и как делается руками через
   браузер (Playwright), включая известные механики интерфейса (например, `createEvent`
   у Kinescope, CSRF у Bizon365).
3. **Наблюдения об API** — не отдельная секция, а факты, всплывающие внутри «Возможностей»
   там, где сервис на самом деле имеет опубликованный контракт: у `chatium` это перечень
   встроенных интеграций (GetCourse SDK, AmoCRM OAuth2, Notion, Toggl v9, Bizon365 API
   v2.0), у `gc-chatium-gateway` — работа со старым/новым API GetCourse, у `kinescope` —
   упомянутый в тексте эндпоинт `app.kinescope.io/api/entities`, замеченный из браузера
   (перехват сетевых запросов), а не из документации API.

Наименование секретов, на которые ссылается раздел «Доступ», единообразно во всех
четырёх карточках: каноническое имя `<owner-или-shared>/<service>/<field>`, на диске в
`.secrets/env` — `SHARED__BIZON365__PASSWORD` и т. п. (слэши → `__`, верхний регистр,
дефисы → `_`); слаг `shared` — когда один физический аккаунт обслуживает нескольких
владельцев, чтобы секрет не дублировался и не расходился молча при ротации; TOTP —
`.secrets/totp/<owner>/<service>`, снимки Playwright-сессии —
`.secrets/storage-state/<owner>/<service>.json`. Сама карточка хранит только эти имена и
пути, значения — нет (см. `.secrets/README.md`, версионируется только он).

Сегодня в MITA нет механизма, который разносил бы эти три природы по разным контурам —
нет ни PACT (владел бы разделом «Доступ» и правилами выдачи), ни CITA (владел бы
операциями через опубликованные контракты, вместо того чтобы они оставались наблюдением
внутри браузерной карточки). Как это должно быть устроено по целевой архитектуре — не
пересказывается здесь; указатель — `docs/spec/spec.md`, §13.1 «Карточка сервиса»
(таблица владения разделами карточки по контурам).
