## 1. Назначение контура и границы ответственности

### 1.1. Назначение

MITA — контур исполнения задач через интерфейсы, спроектированные для человека: браузер, веб-панели,
ручные сценарии. MITA отвечает на вопрос **«как именно это делается»**.

Дословно (CONTOURS.md §2): MITA отвечает за «выполнение задач через веб-интерфейсы там, где API отсутствует»
и не отвечает за «выбор того, что и когда выполнять».

Предмет ведения MITA:

1. Сценарии веб-исполнения: селекторы, порядок шагов, ожидания, обработка отказов конкретного веб-интерфейса
   (владение состоянием — CONTOURS.md §9, строка «Сценарии веб-исполнения → MITA»).
2. Фактическая верификация результата в целевой системе (§15).
3. Рабочие материалы исполнителя: план выполнения, журнал хода работы, артефакты (§12).
4. Плейбуки — процедуры для повторяющихся классов ручных сценариев (§13).
5. Знание о сервисах в браузерной модальности: что и где делается, известные грабли интерфейса (§13).
6. Браузерная инфраструктура и изоляция по владельцам: инстансы, профили, привязка «владелец → инстанс» (§10).
7. Аварийный вывод сессии человеку при капче и ручном входе (§11).
8. Отчёт для человека — как текст, готовый к пересылке без редактирования (§16), передаваемый на egress-проверку PACT.

### 1.2. Зачем MITA существует отдельно от соседей

Критерий корректности разреза (CONTOURS.md §3.1): у каждого контура своя причина меняться, и причины не пересекаются.
Для MITA дословно: меняется, когда «целевой веб-интерфейс переделали, добавили новый сайт»; не меняется, когда
«у вендора появилось API» (в этом случае возможность переезжает в CITA, §18).

Второе основание — асимметрия риска (CONTOURS.md §7.2): MITA читает недоверенные веб-страницы и действует
по прочитанному, работает в живых сессиях внешних систем, её действия часто необратимы и неидемпотентны.
Отсюда особый режим: approval на необратимое (§7) и модель угроз недоверенного контента (§20).

### 1.3. Чего этот контур НЕ делает

Перечень исчерпывающий для границ с соседями. Каждый пункт — запрет, а не «пока не реализовано».

1. **Не ведёт диалог с человеком.** MITA не принимает постановку задачи из чата, не задаёт уточняющих вопросов
   человеку, не доставляет ему результат. Это LINA (CONTOURS.md §2, §5).
2. **Не решает, легитимна ли задача.** Классификация, выбор исполнителя, выдача полномочий, отказ — PACT
   (CONTOURS.md §6.1, §6.2).
3. **Не владеет реестром задач, состояниями и лизингами.** Хранение состояния задачи — PACT
   (CONTOURS.md §9). MITA ведёт только рабочие материалы запуска (§12).
4. **Не классифицирует действие как необратимое.** Отнесение действия к необратимым определяется таблицей PACT
   по хосту и типу операции, а не решением агента (CONTOURS.md §7.2, D-006).
5. **Не хранит учётные данные внешних систем и не владеет их custody.** Инвариант 8 (CONTOURS.md §10).
6. **Не имеет прямого исходящего сетевого доступа и не решает, куда можно ходить.** Инвариант 7 (CONTOURS.md §10);
   allowlist доменов — политика PACT, принуждение — egress proxy (§8).
7. **Не публикует внешние сообщения.** Единственный продюсер внешних сообщений — egress-часть PACT
   (SPECIFICATION.md §23, инвариант 12; REVIEW-FINDINGS.md §3.1, статус «закрыто»). MITA формирует
   предложение ответа, а не ответ.
8. **Не решает, что из результата допустимо раскрыть.** Egress-проверка результата — enforcement-часть PACT
   (CONTOURS.md §6.4, D-004).
9. **Не выбирает себя исполнителем.** Исполнителя выбирает PACT (инвариант 9, CONTOURS.md §10; D-007).
10. **Не исполняет задачи по опубликованным контрактам и API.** Это CITA (CONTOURS.md §7.1). Граница —
    в §18.
11. **Не пишет в хранилища соседних контуров** и не читает их напрямую: «ни один контур не изменяет хранилище
    другого» (CONTOURS.md §9). Обмен — только событиями и непрозрачными идентификаторами.
12. **Не владеет каналами доставки** (Telegram, Max, веб-чат) и не имеет с ними интеграции.
13. **Не определяет и не изменяет маршрут ответа.** `reply_route` создаётся доверенным компонентом
    (SPECIFICATION.md §23, инвариант 8; §11 п.1). MITA оперирует непрозрачным `reply_route_id`.

## 2. Место в четырёхконтурной схеме и словарь

### 2.1. Имя и расшифровка

**MITA — Manual Interaction Task Agent** (CONTOURS.md §2; имена зафиксированы решением D-002, статус «принято»).

Разбор имени (CONTOURS.md §2.1, дословно): «Общий суффикс `-TA` обозначает уровень исполнителя. MITA и CITA —
родственники: один уровень, разные способы взаимодействия с внешним миром. Первые буквы несут модальность,
`-TA` несёт принадлежность к исполнителям.»

Плата за родственность (CONTOURS.md §2.1, дословно): MITA и CITA различаются одним символом; «опечатка переносит
разрешение с исполнителя, работающего по контракту, на исполнителя, управляющего чужим веб-интерфейсом, то есть
в сторону большего риска». Компенсация — закрытый перечень идентификаторов исполнителя (§19).

Имя `MITA` в отношении агентской учётной записи во внешних сервисах и имя контура `MITA` — разные вещи.
Совпадение имён не создаёт связи: контур не определяется учётной записью.

### 2.2. Соседи и направление потоков

Контуров четыре, контуров доверия два, граница проходит по PACT (CONTOURS.md §10, инвариант 1; §3.2):

```
недоверенный          арбитр            привилегированные
    LINA        →      PACT        →      MITA / CITA
    LINA        ←      PACT        ←      MITA / CITA
```

MITA расположена в привилегированном контуре: обладает доступом к внешним системам и не принимает решений
(CONTOURS.md §3.2).

Прямых связей MITA ↔ LINA не существует (инвариант 2, CONTOURS.md §10: «не существует пути от внешнего сообщения
к исполнителю и обратно, минующего PACT»). Прямых связей MITA ↔ CITA не существует: оба исполнителя получают
задачи от PACT независимо.

**Контур-контрагент у MITA ровно один — PACT.** Число событийных обменов с ним больше двух; ниже приведён
их исчерпывающий перечень. Отсутствие в этой таблице означает отсутствие связи: обмен, не перечисленный здесь,
не существует и не вводится реализацией.

| № | Направление | Что передаётся | Раздел |
|---|---|---|---|
| С-1 | PACT → MITA | «авторизованная задача» | §4 |
| С-2 | MITA → PACT | внутренний результат запуска | §5.2 |
| С-3 | MITA → PACT | предложение ответа | §5.4 |
| С-4 | MITA → PACT | запрос approval на необратимое действие | §7.2 |
| С-5 | PACT → MITA | решение approval | §7.5 |
| С-6 | MITA → PACT | запрос секрета, одноразового кода или снимка сессии на `run_id` | §9.2 |
| С-7 | PACT → MITA | выдача запрошенного значения с TTL; возврат обновлённого состояния сессии — тем же обменом в обратную сторону | §9.2, §9.4 |
| С-8 | PACT → MITA | обновление проекции реестра владельцев | §14.2 |
| С-9 | PACT → MITA | отмена запроса и отзыв лизинга | §5.6 |
| С-10 | MITA → PACT | сигналы: расхождения проверок, признаки переезда в CITA, обнаруженные инъекции | §17.2, §17.3 |
| С-11 | MITA → PACT | одноразовая ссылка аварийного вывода сессии в ответ на решение PACT | §11.3 |

Плюс одна связь с механизмом под управлением PACT:

| Направление | Что передаётся | Раздел |
|---|---|---|
| MITA → egress proxy → внешний сервис | HTTP-запрос, проверяемый на авторизацию, домен и метод | §8 |

И одно **документированное исключение**, не являющееся связью между контурами и не проходящее через PACT
физически:

| Направление | Что передаётся | Раздел |
|---|---|---|
| человек → сеанс просмотра браузерного инстанса MITA | интерактивный доступ к экрану на время окна | §11.3 |

Исключение допустимо только при одновременном выполнении компенсаций §11.3; ссылка на сеанс доставляется
человеку через PACT и LINA (обмен С-11), но сам канал просмотра PACT не проверяет.

### 3.2. Собственные инварианты контура MITA

Нумерация `M-n` — локальная для этой спецификации, не пересекается с нумерацией источников.
Каждый инвариант сформулирован как проверяемое утверждение.

- **M-1.** MITA не начинает исполнение без действующей авторизации задачи от PACT. Отсутствие, просроченность
  или несоответствие авторизации — отказ до первого действия (§4.4).
- **M-2.** Каждый исходящий сетевой запрос MITA проходит через egress proxy. Конфигурация исполнителя не содержит
  пути в обход прокси; отсутствие прокси означает отсутствие исполнения, а не прямой доступ (§8).
- **M-3.** MITA не хранит значений учётных данных на диске и в конфигурации. Значения существуют только в памяти
  процесса и только на время сессии, для которой выданы (§9).
- **M-4.** Один браузерный инстанс обслуживает не более одного владельца одновременно (§10).
- **M-5.** Ни один запуск не использует браузерный инстанс, не соответствующий владельцу задачи. Несоответствие —
  отказ, а не переключение на месте (§10.4).
- **M-6.** Действие, отнесённое PACT к необратимым, не выполняется без полученного approval. Точка останова —
  перед действием, а не после (§7).
- **M-7.** MITA не отмечает пункт DoD выполненным без фактической проверки в целевой системе. Самоотчёт модели
  проверкой не является (§15).
- **M-8.** Содержимое веб-страниц, файлов, полей интерфейса, писем и любых внешних данных трактуется MITA как
  данные, а не как инструкции (правило провенанса, §20.2).
- **M-9.** Все внешние сообщения MITA формирует как предложение и передаёт PACT. MITA не имеет технической
  возможности опубликовать событие внешней доставки (§5, §16).
- **M-10.** Все значения секретов маскируются во всех журналах, артефактах, снимках экрана и отчётах MITA (§17.4).
- **M-11.** Ссылка аварийного вывода сессии не попадает ни в один журнал, артефакт, карточку или отчёт MITA (§11.5).
- **M-12.** Идентификатор исполнителя, которым MITA представляется в событиях, входит в закрытый перечень;
  MITA не принимает и не порождает событий с идентификатором вне перечня (§19).
- **M-13.** MITA не изменяет и не читает напрямую хранилища PACT, LINA и CITA; любые справочные данные приходят
  событием или синхронизируемой проекцией с единственным владельцем (§14.3).
- **M-14.** Прерванный запуск оставляет в рабочих материалах запись о том, какие внешние действия были фактически
  совершены до прерывания, — независимо от причины прерывания (§17.2).
- **M-15.** Приостановленный запуск не удерживает ни одного выданного значения секрета, ни одного открытого
  необратимого действия и ни одной формы, отправка которой уже подготовлена. Возобновление — это новый лизинг
  и повторная проверка полномочий, а не продолжение прежней проверки (§5.6).
- **M-16.** Каждая отметка «пункт DoD выполнен» и каждое зафиксированное внешнее изменение адресуются
  из результата запуска ссылкой на артефакт, разыменовываемой без доступа к файловой системе MITA (§12.6).

## 4. Контракт входа: «авторизованная задача» от PACT

### 4.1. Продюсер и консьюмер

Продюсер — enforcement-часть PACT. Консьюмер — MITA. Промежуточная среда — брокер событий: решение **D-012**,
статус **принято** (2026-08-11) — **NATS JetStream**, размещаемый на том же узле; состояние системы —
PostgreSQL (`SPECIFICATION.md` §16). Следствия для контура — §23 и `docs/adr/0017`.

### 4.2. Конвенция имён (принята 2026-08-11, D-015)

Имена топиков (SPECIFICATION.md §8) и имена `event_type` (SPECIFICATION.md §10) в источниках расходились;
конвенция принята решением **D-015**: subject — адрес доставки (домен во множественном числе, версия
в конце), `event_type` — тип содержимого (объект в единственном числе, действие в прошедшем времени,
без версии), версия payload — поле `schema_version`. Для MITA действуют имена: `tasks.authorized.v1` /
`task.authorized` (вход), `runs.requested.<исполнитель>.v1` / `run.requested`, `runs.started.v1` /
`run.started`, `runs.blocked.v1` / `run.blocked`, `runs.completed.v1` / `run.completed`,
`runs.failed.v1` / `run.failed`, `replies.proposed.v1` / `reply.proposed`, `requests.cancelled.v1` /
`request.cancelled`. Нормативная таблица — `DECISIONS.md`, D-015. Таблица ниже сохранена как история
расхождения источников:

| Смысл | Вариант из §8 (топология) | Вариант из §10 (контракты) |
|---|---|---|
| Адресованная задача | `tasks.accepted.v1` | `task.requested.v1` |
| Запрос запуска | `runs.requested.claude.v1` / `runs.requested.codex.v1` | не описан |
| Внутренний результат запуска | `runs.completed.v1` | `agent.run.completed.v1` |
| Отказ запуска | `runs.failed.v1` | не описан |
| Предложение ответа | `reply.proposed.v1` | не описан |
| Отмена запроса | `requests.cancelled.v1` | не описан |

Требование держать соответствие имён **конфигурацией, а не константами в коде**, сохраняется и после
принятия конвенции: оно защищает от следующего изменения номенклатуры, а не только от её отсутствия.
Запрет считать одно из имён каноническим снят — каноническими являются имена D-015.

Отмена запроса — единственная строка таблицы, для которой поведение MITA описано отдельно и не зависит
от выбора конвенции: см. §5.6.4. Промежуточные события ожидания (запрос approval, запрос вмешательства человека)
и событие возобновления в обеих номенклатурах источников отсутствуют; их имена задаются той же конфигурацией
и подпадают под то же ограничение.

### 4.3. Состав авторизованной задачи

MITA принимает событие, содержащее как минимум:

| Поле | Обязательность | Назначение |
|---|---|---|
| `task_id` | обязательно | Непрозрачный идентификатор задачи в реестре PACT. Единственная связь MITA с реестром |
| `run_id` | обязательно | Идентификатор конкретного запуска; ключ дедупликации исполнения |
| `executor` | обязательно | Идентификатор исполнителя из закрытого перечня (§19). Имя поля — по PACT §17.4; асимметрия с полем `worker` во внутреннем результате запуска зафиксирована в §19.1 |
| `owner` | обязательно | Владелец задачи (слаг из реестра владельцев PACT, §14). Определяет браузерный инстанс (§10) |
| `granted_capabilities` | обязательно | Перечень **фактически разрешённых** возможностей без указания модальности (§6), выданный enforcement-частью PACT отдельно от `requested_capabilities`, предложенных диспетчером PACT (PACT §17.4, SPEC §14). Поле `requested_capabilities` MITA не получает и не использует: оно остаётся внутри PACT как вход диспетчера, а не как часть авторизованной задачи |
| `lease` | обязательно | Лизинг: идентификатор, поколение, момент истечения. Ограничивает срок исполнения (§4.5) |
| `reply_route_id` | обязательно | Непрозрачная ссылка на маршрут ответа. MITA его не разыменовывает и не изменяет |
| `objective` | обязательно | Формулировка цели задачи |
| `dod` | обязательно | Критерии завершения, зафиксированные в реестре PACT (§15.1) |
| `context_refs` | опционально | Ссылки на материалы (вложения, выгрузки), а не сами материалы |
| `approval` | опционально | Блок `{required, decision_id}` по PACT §17.4: признак того, что для задачи требуется approval, и идентификатор решения, если оно уже вынесено (§7) |
| `deadline`, `priority` | опционально | Ограничения планирования |
| `idempotency_key` | обязательно | Ключ дедупликации на стороне исполнителя |
| `correlation_id`, `causation_id`, `trace_id` | обязательно | Поля конверта события (SPECIFICATION.md §9) |

Поля `task`, `recipient`, `reply_route_id`, `idempotency_key` соответствуют контракту «адресованной задачи»
SPECIFICATION.md §10.3. Поля `lease`, `dod`, `approval`, `executor`, `owner` в §10.3 отсутствуют:
лизинг присутствует в модели состояний (`LEASED`, SPECIFICATION.md §13) и в правилах дедупликации
(«запуски — по `run_id` и lease generation», §15.2), но в описанный контракт события не внесён.
Это расхождение вынесено в §25, вопрос O-2.

**Запрещено в составе входа.** Значения секретов и учётных данных (SPECIFICATION.md §9, §18.3); текст
пользователя в роли инструкции для исполнителя без пометки провенанса (§20.2); указание модальности внутри
имени capability (инвариант 9, CONTOURS.md §10).

### 4.4. Отказ при отсутствующей или недействительной авторизации

MITA отказывает в исполнении **до первого внешнего действия** при любом из условий:

1. Событие не содержит хотя бы одного поля, помеченного в §4.3 как обязательное. Перечень исчерпывающий
   и повторяется здесь целиком, чтобы список условий отказа не расходился с таблицей состава:
   `task_id`, `run_id`, `executor`, `owner`, `granted_capabilities`, `lease`, `reply_route_id`, `objective`,
   `dod`, `idempotency_key`, а также поля конверта `correlation_id`, `causation_id`, `trace_id`.
   Пустое значение обязательного поля приравнивается к его отсутствию; пустой `granted_capabilities`
   и пустой `dod` — тоже отказ (§15.1, п. 3).
2. `executor` не входит в закрытый перечень (§19) либо не равен идентификатору принимающего исполнителя.
3. `lease` истёк на момент приёма события либо его поколение ниже уже наблюдавшегося для этого `task_id`.
4. Требуемое действие не покрывается ни одной выданной capability (§6.3).
5. `owner` отсутствует в проекции реестра владельцев MITA (§14.2) — исполнение невозможно, так как не определяется
   браузерный инстанс.
6. Событие не проходит проверку схемы или версии.

Форма отказа: событие «запуск не выполнен» с типизированной причиной, без попытки самостоятельно
доработать недостающие данные и без обращения к человеку. Отказ не является провалом задачи — задача остаётся
в ведении PACT.

**Запрещённое поведение при отказе:** запрос недостающих полномочий у человека; исполнение «частично, в пределах
имеющегося»; повторная отправка того же события с исправленными полями; ожидание продления лизинга.

### 4.5. Лизинг и его истечение

1. Лизинг ограничивает не сессию, а каждый отдельный внешний запрос: по истечении лизинга следующий запрос
   отклоняется egress proxy в середине выполнения (CONTOURS.md §8.2).
2. MITA обязана проверять остаток лизинга самостоятельно **до** начала необратимого действия и не начинать его,
   если остатка заведомо недостаточно (§7.3).
3. Истечение лизинга в середине запуска — не ошибка исполнения, а нормальный терминальный исход. MITA обязана
   зафиксировать фактически совершённые внешние действия (инвариант M-14) и вернуть результат со статусом
   «прервано по лизингу».
4. Продление лизинга запрашивается у PACT отдельным событием и до получения ответа не предполагается.

### 4.6. Дедупликация входа

Модель доставки — at-least-once, консьюмер обязан быть идемпотентным (SPECIFICATION.md §15.1).
MITA дедуплицирует запуски по паре `run_id` + поколение лизинга (SPECIFICATION.md §15.2).
Повторно полученное событие уже завершённого запуска не приводит к повторному внешнему действию, а приводит
к повторной публикации сохранённого результата.

Возобновляющий запуск (§5.6.3) дедупликацией не отсекается и отсекаться не должен: у него другой `run_id`.
Защитой от повторного применения уже совершённого изменения служит не дедупликация, а обязательная проверка
фактического состояния внешней системы в начале возобновляющего запуска (§5.6.3, п. 4).

## 5. Контракт выхода: внутренний результат запуска

### 5.1. Два разных объекта

Инвариант (SPECIFICATION.md §23, инв. 6): «Внутренний результат запуска и внешний ответ являются разными событиями.»

| | Внутренний результат запуска | Отчёт для человека |
|---|---|---|
| Назначение | машинная запись исхода для PACT и аудита | текст, который человек прочитает |
| Адресат | enforcement-часть PACT (реестр, egress-проверка) | LINA — после одобрения PACT |
| Содержание | статусы, ссылки на артефакты, перечень изменений, метрики, диагностика | результат, ограничения, следующий шаг |
| Раскрытие | **не предназначено для прямой отправки во внешний чат** (SPECIFICATION.md §10.4) | предназначено, но только после egress-проверки |
| Раздел | §5.2–§5.4 | §16 |

MITA публикует оба, но **ни один из них не является внешним сообщением**: право публикации событий внешней
доставки принадлежит исключительно egress-части PACT (SPECIFICATION.md §17, §23 инв. 12; инвариант M-9).

### 5.2. Состав внутреннего результата запуска

| Поле | Назначение |
|---|---|
| `task_id`, `run_id` | связь с реестром PACT |
| `worker` | идентификатор исполнителя из закрытого перечня |
| `status` | исход запуска (§5.3) |
| `reason` | типизированная причина из закрытого перечня (§5.7); обязательна для любого статуса, кроме `completed` |
| `suspension` | только для приостанавливающих исходов: `{condition, awaited_decision_id, external_state}` — чего именно ждёт задача, идентификатор ожидаемого решения (если применимо) и в каком состоянии оставлена внешняя система (§5.6.2) |
| `result.summary` | краткое машинное описание исхода, без форматирования под человека |
| `result.artifact_refs` | **ссылки** на артефакты, а не их содержимое (SPECIFICATION.md §9: крупные данные передаются ссылками) |
| `result.changes` | перечень фактически совершённых изменений во внешних системах: система, объект, тип операции, обратимость |
| `result.dod` | по каждому пункту DoD: выполнен / не выполнен / не проверялся + ссылка на подтверждающий артефакт (§15) |
| `external_calls` | сводка внешних вызовов: домен, метод, исход, счётчик; без тел запросов |
| `capabilities_used` | какие из выданных возможностей были фактически задействованы |
| `approvals` | перечень запрошенных и полученных подтверждений с идентификаторами |
| `metrics.duration_ms` | длительность запуска |
| `diagnostics` | типизированная причина отказа/прерывания; внутренние трассировки допустимы (это внутреннее событие) |
| `provenance_flags` | признак того, что в ходе запуска был обнаружен недоверенный контент, похожий на инструкцию (§20.3) |

### 5.3. Статусы запуска

Закрытый перечень. Неизвестное значение принимающей стороной трактуется как ошибка контракта, а не как успех.

Колонка «Класс» различает два вида исходов и устраняет неоднозначность первой редакции: **терминальный** исход
закрывает `run_id` окончательно, **приостанавливающий** — закрывает текущий запуск, но допускает возобновление
работы по той же задаче новым `run_id` (§5.6). Приостанавливающий исход не является ни успехом, ни провалом задачи.

| Статус | Класс | Значение |
|---|---|---|
| `completed` | терминальный | все пункты DoD проверены фактически и выполнены |
| `partially_completed` | терминальный | часть пунктов DoD выполнена и проверена, часть — нет; перечень обязателен |
| `blocked_awaiting_approval` | приостанавливающий | достигнута точка останова перед необратимым действием, подтверждения нет (§7.4) |
| `blocked_awaiting_human` | приостанавливающий | требуется физическое участие человека в интерфейсе (капча, вход, MFA) — §11 |
| `lease_expired` | приостанавливающий | запуск прерван истечением лизинга (§4.5) |
| `cancelled` | терминальный | запуск прекращён по отмене от PACT (§5.6.4); фактически совершённые действия зафиксированы |
| `denied_by_egress` | терминальный | запрос отклонён egress proxy (домен, метод, авторизация) — §8.5 |
| `failed` | терминальный | отказ исполнения по причине, не относящейся к политике: интерфейс изменился, сервис недоступен, сценарий не сходится |
| `rejected` | терминальный | вход не прошёл проверку (§4.4); внешних действий не совершалось |

Для всех статусов, кроме `rejected`, поле `result.changes` обязательно и может быть пустым списком только
если внешних изменений действительно не было.

Каждый статус, кроме `completed`, сопровождается обязательной типизированной причиной из закрытого перечня §5.7.
Решение о том, будет ли задача продолжена после приостанавливающего исхода, принимает PACT: MITA сообщает исход
и условие возобновления, но не планирует его сама (§5.6.3).

### 5.4. Предложение ответа

Отдельным событием MITA публикует предложение ответа (`reply.proposed.v1` — имя встречается в §8 и в
сценарии §12 SPECIFICATION.md; отдельного контракта события для него в §10 нет, что усиливает открытый
вопрос O-1), содержащее: `task_id`, `run_id`, `reply_route_id` исходной задачи и текст отчёта
для человека по требованиям §16.

Ограничение (SPECIFICATION.md §11, инв. 3): маршрут ответа — только маршрут исходной задачи либо маршрут,
отдельно разрешённый политикой. MITA не конструирует маршрут и не выбирает канал.

### 5.5. Что MITA не отправляет наружу никогда

1. Значения секретов и любых учётных данных, включая логины (§9.6).
2. Ссылку аварийного вывода сессии (инвариант M-11).
3. Внутренние трассировки, стеки, сырые дампы страниц — в предложении ответа; их место во внутреннем результате
   и в артефактах по ссылке.
4. Данные владельца, отличного от владельца задачи.

### 5.6. Жизненный цикл запуска: ожидание, приостановка, возобновление, отмена

#### 5.6.1. Два разных объекта: ожидание внутри запуска и приостанавливающий исход

Первая редакция не различала их, из-за чего §7.4 и §11.3 читались как противоречащие §5.3. Различие вводится явно:

| | **Ожидание внутри запуска** | **Приостанавливающий исход** |
|---|---|---|
| Что публикуется | промежуточное событие «требуется решение/вмешательство» | внутренний результат запуска (§5.2) со статусом класса «приостанавливающий» |
| Судьба `run_id` | остаётся открытым, работа продолжается после получения ожидаемого | закрывается; продолжение — только новым `run_id` (§5.6.3) |
| Браузерный инстанс и вкладка | удерживаются | освобождаются (исключение — §5.6.2, п. 4) |
| Выданные секреты | не удерживаются: значение, нужное после ожидания, запрашивается заново перед вводом (§9.5, п. 2; M-15) | возвращаются в custody PACT до публикации исхода |
| Кто решает, что дальше | ожидание разрешается само по приходу события | PACT: возобновлять задачу или закрывать |

Выбор между ними **детерминирован**, а не оставлен на усмотрение исполнителя. Ожидание внутри запуска допустимо
тогда и только тогда, когда одновременно выполнены все условия:

1. остатка лизинга заведомо хватает на само ожидание **и** на завершение действия после него (§4.5, п. 2);
2. удержание внешней системы в промежуточном состоянии безопасно: состояние не протухает, форма не удерживается
   в отправляемом виде, сессия не истекает раньше конца ожидания (§7.3, п. 1);
3. ожидание укладывается в предел удержания (§5.6.5);
4. ни одно значение секрета не требуется удерживать на время ожидания.

Невыполнение любого условия означает приостанавливающий исход. Умолчание — в сторону исхода, а не удержания.

#### 5.6.2. Что MITA обязана сделать перед публикацией приостанавливающего исхода

1. Прекратить подготовку необратимого действия; подготовленная, но не отправленная форма не удерживается (M-15).
2. Вернуть в custody PACT обновлённое состояние сессии (§9.4, п. 4) и считать все выданные значения отозванными;
   значения стираются из памяти процесса. Если возврат технически невозможен — например, лизинг уже истёк и
   выданное считается отозванным (§9.2, п. 1), — значения всё равно стираются, а факт невозврата фиксируется
   в машиночитаемом аудите (§17.2): несохранённое обновление сессии означает, что при возобновлении вход
   выполняется штатной процедурой заново (§10.2).
3. Заполнить блок `suspension` (§5.2):
   - `condition` — чего именно ждёт задача, из закрытого перечня причин §5.7;
   - `awaited_decision_id` — идентификатор ожидаемого решения, если PACT его уже присвоил;
   - `external_state` — состояние, в котором оставлена внешняя система, из закрытого перечня:
     `no_change` (внешних изменений не было), `prepared_reversible` (совершены только обратимые шаги),
     `partially_applied` (часть изменений применена; перечень — в `result.changes`),
     `unknown` (состояние достоверно не установлено; требует проверки при возобновлении).
4. Освободить браузерный инстанс. **Единственное исключение** — статус `blocked_awaiting_human`: вкладка и
   инстанс удерживаются нетронутыми (§11.2, п. 4) до конца окна вмешательства (§5.6.5). По истечении окна
   инстанс освобождается, а `external_state` понижается до `unknown`, если состояние не подтверждено проверкой.
5. Отметить непроверенные пункты DoD исходом `not_checked` (§15.4). Приостанавливающий исход никогда не даёт
   `completed`.

#### 5.6.3. Возобновление

1. Возобновление — **новый запуск**: тот же `task_id`, новый `run_id`, новый лизинг, новая авторизованная задача
   от PACT (§4). MITA не возобновляет задачу по собственной инициативе и не хранит очередь отложенного.
2. Все проверки §6.2 выполняются заново и в полном объёме. Ничто из проверенного в прежнем запуске не переносится.
3. Approval, выданный по прежнему `run_id`, для нового запуска **недействителен** (§7.4). PACT обязан выдать
   решение на новый `run_id` — требование П-13 (§21.1).
4. Новый запуск обязан начинаться с проверки фактического состояния внешней системы, если прежний исход
   имел `external_state` равным `partially_applied` или `unknown`. Повторение уже применённого изменения без
   такой проверки — нарушение M-7 и потенциальное второе выполнение необратимого действия (§18.2).
5. Рабочие материалы прежнего запуска (§12) сохраняются и адресуются по прежнему `run_id`; новый запуск ведёт
   собственную рабочую тетрадь и ссылается на артефакты прежнего по §12.6, а не переписывает их.
6. Число возобновлений спецификацией не ограничивается: политика повторов — предмет PACT, а не исполнителя.

#### 5.6.4. Отмена

Отмена приходит событием от PACT (обмен С-9, §2.2; имя события — `requests.cancelled.v1` по §4.2, до принятия
конвенции O-1 поддерживается конфигурацией).

1. Отмена **не является ошибкой** и обрабатывается как штатный терминальный исход `cancelled`.
2. С момента приёма отмены MITA не начинает ни одного нового внешнего действия — ни обратимого, ни необратимого.
3. Внешнее действие, уже отправленное во внешнюю систему, **не отзывается**: технической возможности отозвать
   отправленный запрос не существует. MITA дожидается его наблюдаемого исхода, если ожидание укладывается
   в остаток лизинга, и фиксирует результат в `result.changes`; иначе фиксирует `external_state: unknown`.
4. MITA **не выполняет компенсирующих действий** по собственной инициативе: откат — это новое действие во внешней
   системе, требующее собственной capability и, как правило, approval. Компенсация назначается PACT отдельной
   задачей (§25, O-10 в части, относящейся к системе).
5. Отмена, полученная после публикации терминального исхода, игнорируется идемпотентно: повторная публикация
   сохранённого результата по §4.6, новых событий не порождается.
6. Отзыв лизинга без события отмены обрабатывается тождественно отмене со статусом `cancelled` и причиной
   `cancelled.lease_revoked` (§5.7); отличие от `lease_expired` в том, что лизинг прекращён решением PACT,
   а не истёк по времени, — это разные входы для разных действий PACT.
7. Приостановленный (уже закрытый приостанавливающим исходом) запуск отменять нечего: отмена относится к задаче
   и обрабатывается PACT, а не MITA.

Значения ниже действуют **до принятия системного решения** по нефункциональным требованиям (§25, O-6, O-7)
и заданы здесь потому, что без них §5.6.1 неисполним. Значения — конфигурация узла, а не константы в коде.

#### 5.6.6. Недоступность зависимостей

Поведение при недоступности брокера, egress proxy и сервиса выдачи секретов на уровне системы не определено
(§25, O-16). Для MITA как исполнителя оно определяется здесь и не откладывается:

1. **Недоступен egress proxy.** Исполнение не начинается или прекращается: отсутствие прокси означает отсутствие
   исполнения, а не прямой доступ (M-2). Статус `failed`, причина `dependency.egress_proxy_unavailable`.
2. **Недоступен сервис выдачи секретов.** Действие, требующее значения, не выполняется; уже начатая часть
   завершается или фиксируется. Статус `failed`, причина `dependency.secret_service_unavailable`.
3. **Недоступен брокер.** MITA не публикует событий, но и не теряет их: результат запуска и рабочие материалы
   сохраняются локально и публикуются при восстановлении связи с сохранением полей конверта, включая
   `occurred_at` и `deduplication_key`. Буферизация касается только исходящих событий и не даёт права
   продолжать внешние действия без подтверждённой авторизации.
4. Ни в одном из трёх случаев MITA не переходит на обходной путь, не откладывает проверку и не выполняет
   действие «в кредит».

## 6. Модель capabilities глазами исполнителя

### 6.1. Что означает выданное полномочие

Capability — имя разрешённой возможности, выданное PACT на конкретный запуск. Для MITA это **разрешение,
а не задание**: наличие capability не обязывает её использовать и не расширяет цель задачи.

Ключевое свойство (инвариант 9, CONTOURS.md §10; D-007, статус **принято**): **capability не содержит указания
на модальность**. Имя — `invoice.submit`, не `invoice.submit.via-web` (CONTOURS.md §7.3). Причина: граница
MITA/CITA подвижна, появление API у сервиса переносит возможность в другой контур; имя с модальностью потребовало бы
переписывания политик вместо изменения маршрута.

Следствия для MITA:

1. MITA не может вывести из имени capability, что задача адресована именно ей. Адресацию несёт поле `worker` (§19).
2. MITA не имеет права предлагать PACT имена capability, содержащие способ исполнения, селектор, домен или
   название интерфейса.
3. Перенос возможности в CITA не меняет имени capability (§18.3).

### 6.2. Что MITA проверяет сама

Перед каждым действием, имеющим внешний эффект:

1. **Покрытие.** Действие покрыто хотя бы одной выданной capability. Не покрыто — действие не выполняется.
2. **Владелец.** Действие выполняется в контексте владельца задачи и в его браузерном инстансе (§10.4).
3. **Лизинг.** Остаток лизинга существует на момент начала действия (§4.5).
4. **Необратимость.** Если PACT пометил класс действия как необратимый — наличие approval (§7).
5. **Провенанс.** Действие вытекает из `objective`/`dod` задачи, а не из текста, прочитанного на странице (§20.2).

Эти проверки — **вторая линия**, а не замена enforcement. Первая линия — детерминированная проверка PACT и
egress proxy. Совпадение результата проверок обязательно; расхождение (MITA считает действие разрешённым,
прокси отклонил) фиксируется как дефект и попадает в результат запуска со статусом `denied_by_egress` (§5.3).

### 6.3. Чего MITA не имеет права додумывать

1. **Расширять capability по смыслу.** `invoice.read` не даёт права нажать «Отправить», даже если это очевидный
   следующий шаг.
2. **Считать смежное действие включённым.** Отсутствие явного запрета не является разрешением.
3. **Выводить полномочия из интерфейса.** Доступность кнопки в веб-панели не означает наличия capability.
4. **Выводить полномочия из наличия сессии.** Живая авторизованная сессия в профиле браузера — не полномочие
   (§9.4).
5. **Переносить полномочия между задачами, владельцами и запусками.** Capability действует в пределах `run_id`
   и лизинга.
6. **Заменять недостающую capability обходным путём** (другой раздел интерфейса, экспорт вместо чтения,
   поддержка сервиса вместо кнопки).

Недостаток полномочий — это результат запуска со статусом `blocked_awaiting_approval` или `rejected`
и типизированной причиной, а не повод для творчества.

### 6.4. Гранулярность

Механизм egress proxy не закрывает класс «легитимное действие, выполненное не по назначению» (CONTOURS.md §8.4):
если разрешена операция создания записи, а создана не та запись — прокси пропустит запрос, потому что домен,
метод и авторизация корректны. Средства снижения по источнику — сужение capability до конкретной операции
и approval на необратимое.

Требование MITA к PACT, вытекающее отсюда: capability должна именовать **операцию**, а не раздел интерфейса
и не сервис целиком. Начальный набор capabilities и профилей approval не определён (CONTOURS.md §13,
SPECIFICATION.md §22) — см. §25, вопрос O-3.

## 7. Необратимые действия и approval

### 7.1. Кто классифицирует

Дословно (CONTOURS.md §7.2): «в MITA необратимые действия по умолчанию требуют approval, обратимые — нет.
Отнесение действия к необратимым определяется таблицей PACT по хосту и типу операции, а не решением агента.»
Решение **D-006**, статус **принято**. Инвариант 10 (CONTOURS.md §10).

Основание особого режима именно для MITA (CONTOURS.md §7.2): при доставке at-least-once «повторная отправка формы —
это второе выполнение действия, а не повторное чтение».

Следствия:

1. MITA **не ведёт** собственной таблицы необратимости и не имеет права смягчать классификацию.
2. MITA **обязана** уметь сопоставить готовящееся действие с записью таблицы: до действия ей известны целевой хост
   и тип операции.
3. Если сопоставление невозможно (тип операции не определяется однозначно) — действие трактуется как необратимое.
   Умолчание — в сторону остановки.

### 7.2. Точка останова

Точка останова — **непосредственно перед выполнением действия во внешней системе**, после того как все
подготовительные шаги выполнены и состояние интерфейса зафиксировано.

Требования к точке останова:

1. До неё выполняются только обратимые действия: навигация, чтение, заполнение полей формы.
2. В момент останова MITA фиксирует артефакт состояния (снимок экрана и адрес страницы), позволяющий человеку
   понять, что именно будет сделано.
3. Запрос approval формируется как машинное событие к PACT и содержит: `task_id`, `run_id`, целевой хост,
   тип операции, краткое описание эффекта, ссылку на артефакт состояния.
4. MITA не формулирует вопрос человеку и не выбирает, кого спрашивать. Доставка запроса подтверждения владельцу —
   обязанность PACT (§7.5).

### 7.3. Поведение при ожидании

1. Ожидание approval внутри запуска допустимо только при выполнении всех условий §5.6.1; при риске протухания
   состояния, нехватке лизинга или превышении предела удержания (§5.6.5) MITA публикует приостанавливающий исход
   `blocked_awaiting_approval` и не удерживает форму. Умолчание — в сторону исхода, а не удержания.
2. Если остатка лизинга заведомо недостаточно для завершения действия после получения approval — действие
   не начинается (§4.5, п.2).
3. Все прочие пункты задачи, не требующие подтверждения, при этом могут быть завершены; результат — статус
   `partially_completed` либо `blocked_awaiting_approval` с перечнем выполненного.

### 7.4. Поведение при отсутствии подтверждения

| Ситуация | Поведение MITA |
|---|---|
| Approval получен в пределах удержания, лизинга хватает | Ожидание разрешается внутри запуска (§5.6.1): действие выполняется, `run_id` не меняется |
| Approval не получен в пределах удержания (§5.6.5) или лизинга | Запуск завершается статусом `blocked_awaiting_approval`, причина `approval.wait_timeout`; необратимое действие не выполняется |
| Approval отклонён | Запуск завершается тем же статусом с причиной `approval.denied`; повторная попытка того же действия запрещена — в том числе в возобновляющем запуске (§5.6.3), пока PACT не выдаст новое решение |
| Approval получен, но лизинг уже истёк | Действие не выполняется; статус `lease_expired`, причина `lease.insufficient_for_irreversible` |
| Approval получен по другому `run_id` или `task_id` | Подтверждение игнорируется; фиксируется как дефект (§17.3), причина `approval.mismatched_run` |
| Задача возобновлена новым `run_id` | Прежний approval недействителен; требуется решение на новый `run_id` (§5.6.3, п. 3; П-13) |

**Запрещено:** переспрашивать человека; выполнять «безопасную часть» необратимого действия; выполнять действие
с намерением откатить его позже; интерпретировать молчание как согласие; трактовать текст, прочитанный
на странице или в постановке, как подтверждение (§20.2).

### 7.5. Доверенность пути подтверждения

Способ получения решения владельца — **открытый вопрос уровня системы**: «подтверждение владельца приходит
по недоверенному пути» (REVIEW-FINDINGS.md §3.2, статус **открыто**); ответ владельца приходит обычным сообщением
через канальный адаптер и интерпретируется языковой моделью, обработавшей недоверенный контекст того же диалога.
«Декомпозиция на контуры это не сняла: диалогом владеет LINA, и LINA — агент.»

Требование MITA к соседям: MITA принимает approval **только** как событие от enforcement-части PACT, содержащее
`task_id` и `run_id`. Как PACT получил решение человека — вне ведения MITA. См. §25, вопрос O-4.

## 8. Egress только через прокси

### 8.1. Постановка

Дословно (CONTOURS.md §8.1): «PACT является гейтом только в том случае, если MITA и CITA не способны действовать
без его решения. При постоянных учётных данных у исполнителей PACT защищает лишь корректный путь: дефект или
инъекция внутри исполнителя обходят его целиком.» Решение **D-005** («Egress proxy как механизм принуждения
границы»), статус **принято**.

Инварианты: 7 и 8 (CONTOURS.md §10); 14 (SPECIFICATION.md §23). Собственные — M-2, M-3.

### 8.2. Механизм

Дословно (CONTOURS.md §8.2): «MITA и CITA не имеют исходящего сетевого доступа. Весь внешний трафик проходит через
egress proxy, который хранит учётные данные и подставляет их сам.» На каждый запрос проверяются:
наличие действующей авторизации PACT для этой задачи, допустимость домена, допустимость метода.

Получаемые свойства (CONTOURS.md §8.2, дословно):

- учётные данные не находятся в памяти исполнителя, поэтому не могут быть из него извлечены;
- контроль применяется к каждому запросу, а не к сессии: по истечении лизинга следующий запрос отклоняется
  в середине выполнения;
- allowlist доменов исполняется на транспортном уровне, поэтому указание обратиться к постороннему хосту не проходит;
- журнал всех внешних вызовов ведётся в одном месте.

### 8.3. Браузерная модальность: MITM с собственным CA

Реализация для MITA (CONTOURS.md §8.2, дословно): «браузер запускается через proxy, работающий как MITM
с собственным CA, и подставляет `Cookie` в запросы к разрешённым доменам» — «браузер сессию не видит».

Требования к браузерному контуру, вытекающие из этого:

1. Браузерный инстанс сконфигурирован так, что весь его трафик идёт через прокси; конфигурация задаётся снаружи
   процесса-исполнителя и не изменяема им.
2. Корневой сертификат прокси установлен в профиль инстанса; профиль не редактируется исполнителем.
3. Подстановка учётных данных выполняется **вне исполнителя**: значение `Cookie`, заголовка авторизации, а также
   ввод логина и пароля в форму — предмет §9.
4. Отсутствие сетевого доступа у исполнителя вне прокси — свойство сетевой конфигурации узла, а не соглашение
   в коде. Исполнитель, обошедший прокси, обязан получить сетевой отказ.

### 8.4. Где физически размещено принуждение

Разделение владения (собственное решение спецификации, согласованное с CONTOURS.md §8 и §9):

| Что | Владелец | Комментарий |
|---|---|---|
| Политика egress: allowlist доменов, допустимые методы, требование авторизации | **PACT** | Часть таблиц правил |
| Хранение учётных данных и подстановка их в трафик | **egress proxy под управлением PACT** | CONTOURS.md §9 относит учётные данные к «egress proxy и хранилищу секретов»; custody и политика выдачи — PACT, механизм подстановки — прокси |
| Отсутствие прямого исходящего доступа у процессов исполнителя | **инфраструктура узла** | Механизм под управлением PACT, физически размещённый на узле; не является частью контура MITA |
| Соответствие браузерного инстанса требованиям §8.3 | **MITA** | Конфигурация браузерного контура — предмет ведения MITA (§10) |

Инвариант M-2 формулирует это со стороны MITA: отсутствие прокси означает отсутствие исполнения.

### 8.5. Поведение MITA при отказе прокси

1. Отказ прокси — нормальный, ожидаемый исход, а не сбой. Обработка — статус `denied_by_egress` (§5.3).
2. MITA не повторяет отклонённый запрос, не пробует другой домен, не меняет метод, не ищет зеркало сервиса.
3. Отказ по домену фиксируется отдельно от отказа по авторизации и от отказа по методу: это разные причины,
   ведущие к разным действиям PACT.
4. Отказ по авторизации в середине запуска трактуется как истечение лизинга (§4.5, п.3).

### 8.6. Порядок внедрения

Дословная таблица CONTOURS.md §8.3. «Шаги полезны по отдельности и внедряются последовательно. Шаг 0 наиболее
дёшев и снимает наиболее вероятное.»

| Шаг | Содержание | Что закрывает |
|---|---|---|
| 0 | нет прямого egress у исполнителей, proxy с allowlist доменов, учётные данные пока на месте | эксфильтрацию данных |
| 1 | учётные данные переносятся в proxy | извлечение секрета из исполнителя |
| 2 | proxy проверяет подпись PACT на каждом запросе | действие без авторизации |
| 3 | эфемерное окружение на задачу, отзыв лизинга по завершении | переиспользование доступа между задачами |

Формат подписи авторизации PACT, проверяемой egress proxy, — **открытый вопрос** (CONTOURS.md §13). См. §25, O-5.

### 8.7. Границы механизма

Механизм не закрывает два класса ситуаций (CONTOURS.md §8.4):

1. **Легитимное действие, выполненное не по назначению** — см. §6.4.
2. **Системы, работающие только с человеческой сессией** — MFA, капча, привязка к устройству. Дословно:
   «Техническая изоляция достигает потолка; остаётся подтверждение каждого необратимого действия.»
   Для MITA это не исключение, а норма работы: см. §11.

## 9. Секреты после переноса custody в PACT

### 9.1. Разделение владения

Единая формулировка, обязательная для всех четырёх контуров: **custody и политика выдачи — PACT, механизм
подстановки в трафик — egress proxy под управлением PACT.** Основание: CONTOURS.md §9 относит учётные данные
к «egress proxy и хранилищу секретов»; владельцем политики выступает PACT (CONTOURS.md §6.3).

Для MITA действует инвариант 8 (CONTOURS.md §10) и собственный M-3: значений на диске исполнителя нет.

### 9.2. Модель выдачи

| Класс секрета | Что получает MITA | Ограничение |
|---|---|---|
| Пароль / логин | ничего, если вход выполняет прокси или отдельный компонент; значение на одно использование — только если природа входа требует ввода в DOM (§9.5) | TTL сессии, одно использование |
| Второй фактор (TOTP) | **одноразовый шестизначный код** на конкретный запрос | seed не выдаётся никогда |
| Сессия браузера (storage-state) | набор cookie/origins, **отфильтрованный по домену целевого сервиса**, на время сессии | TTL сессии; фильтрация — обязательное условие выдачи (§9.4) |
| Ключ API | не выдаётся; подставляется прокси | — |

Общие правила выдачи:

1. Выдача привязана к паре `task_id` + `run_id` и к действующему лизингу; по истечении лизинга выданное считается
   отозванным.
2. Выдача имеет TTL, не превышающий срок лизинга.
3. Значение существует в памяти процесса-исполнителя и не записывается на диск, в переменные окружения,
   в конфигурацию, в журналы и в артефакты.
4. Каждая выдача фиксируется PACT в машиночитаемом аудите: какая задача, когда, какое имя секрета, для чего.
   MITA обязана указывать назначение в запросе.
5. MITA не кеширует выданное между запусками.

### 9.3. Одноразовый код вместо seed

Требование: MITA получает результат вычисления второго фактора, а не материал для его вычисления.
Обоснование: TOTP-seed даёт бессрочный обход второго фактора при компрометации, то есть по риску ближе
к сессионному токену, чем к паролю. Интерфейс минимален: запрос «код для `<owner>/<service>` в рамках `run_id`» →
ответ «код и срок его действия».

Следствие для MITA: логика входа (какое поле, в каком порядке, как распознать успех) остаётся у MITA;
владение материалом второго фактора — у PACT (§13.1).

### 9.4. Storage-state как секрет высшей категории

1. **Классификация.** Снимок состояния браузера эквивалентен обходу пароля и второго фактора одновременно
   и по охвату шире собственного имени: выгрузка состояния контекста возвращает весь профиль браузера,
   а не данные одного сайта.
2. **Обязательная фильтрация по домену.** Выдача снимка без фильтрации по домену целевого сервиса запрещена.
   Фильтрация — **условие переноса custody**, а не улучшение: непрофильтрованная выдача «сессии сервиса A»
   фактически выдаёт доступ к сервисам B, C, D, оказавшимся в том же профиле.
3. **Выдача на сессию.** Снимок выдаётся на время работы с конкретным сервисом в конкретном браузерном инстансе
   и отзывается по завершении запуска.
4. **Возврат.** Обновлённое состояние сессии возвращается в custody PACT тем же фильтрованным по домену составом.
   MITA не хранит его копию.
5. **Сессия — не полномочие.** Наличие живой сессии в профиле не даёт права на действие (§6.3, п.4).
   Проверка полномочий не зависит от состояния аутентификации.

### 9.5. Неустранимая экспозиция

Ограничение, которое спецификация фиксирует явно, а не обходит: природа контура MITA требует, чтобы значение
физически достигало браузера — вход через веб-интерфейс выполняется вводом в DOM потенциально недоверенной
страницы. Custody у PACT сужает окно экспозиции (одно использование, TTL, отсутствие значения на диске),
но не убирает его.

Требования, снижающие остаточный риск:

1. Где технически возможно, подстановка выполняется прокси (§8.3), а не вводом в DOM.
2. Где ввод в DOM неизбежен, значение запрашивается непосредственно перед вводом и не удерживается после него.
3. Роль, читающая недоверенные страницы, и роль, оперирующая значением секрета, разделяются (§20.4).
4. Снимок экрана, сделанный в момент, когда значение видно в интерфейсе, не сохраняется в артефакты (§17.4).

### 9.6. Логин — тоже значение секрета

Правило переносится из существующей практики без изменений: секрет — вся пара, а не только её вторая половина.
Логин и адрес почты учётной записи не выписываются открытым текстом в карточках, заметках, журналах, артефактах
и отчётах.

### 9.7. Схема имён и слаг `shared`

1. Каноническая схема имени секрета — `<client>/<service>/<field>`. **Реестр имён принадлежит PACT**;
   MITA потребляет имена и не заводит новых самостоятельно.
2. Схема сохраняется при переносе custody: имя не меняется, меняется владелец и способ доступа.
3. Слаг `shared` в позиции `<client>` обозначает **физически одну** учётную запись, обслуживающую нескольких
   владельцев. Если у владельцев разные учётки с совпадающим паролем — это разные секреты, а не `shared`.
4. Следствие, которое обязано быть видно в вердикте PACT, а не выясняться постфактум: авторизация на общий секрет
   расширяет радиус поражения на всех его потребителей.
5. Правило **«общий секрет ≠ общая сессия»** переносится дословно и действует в MITA: общий секрет не даёт права
   вести работу нескольких владельцев в одном браузерном инстансе (§10.3).
6. Противоречие «`shared` против принципа «клиент = единица изоляции»» не разрешено — см. §25, вопрос O-9.

## 10. Браузерный контур в целевом состоянии

### 10.1. Принадлежность

Браузерная инфраструктура, изоляция по владельцам и привязка «владелец → инстанс» — предмет ведения MITA
(CONTOURS.md §9, «Сценарии веб-исполнения → MITA»). Конфигурация узла (пакеты, юниты, сетевые ограничения)
принадлежит инфраструктуре узла и настраивается идемпотентными playbook-ами, а не ручными правками —
это внешнее по отношению к контуру ограничение, которое MITA обязана соблюдать.

### 10.2. Инстанс на владельца

- **M-4.** Один браузерный инстанс обслуживает не более одного владельца одновременно.
- Инстанс — отдельный процесс браузера, отдельный каталог профиля, отдельная точка подключения исполнителя,
  отдельный экран.
- Имя инстанса совпадает со слагом владельца; отдельный инстанс отведён под системную работу без владельца.
- Новый инстанс начинает с пустого профиля. Перенос сессий между инстансами не выполняется: сессия
  восстанавливается штатным входом (§9.2). Автоматический перенос cookie между инстансами запрещён.

### 10.3. Требования к изоляции

1. Страница, открытая в инстансе одного владельца, не имеет доступа к профилю, сессиям и экрану другого владельца.
2. Подключение исполнителя к инстансу определяется на старте запуска и не меняется в его середине.
3. Подчинённые исполнители (субагенты) наследуют инстанс родителя и его изоляцию; собственного подключения
   не устанавливают.
4. Общий секрет (`shared`) не отменяет п.1: работа под общей учётной записью ведётся в инстансе того владельца,
   которому адресована задача.
5. Точка подключения инстанса недоступна извне узла и не имеет пути в обход §8.

### 10.4. Справочник привязки «владелец → инстанс»

1. Справочник имеет **единственного владельца** и одну точку правки. Целевое состояние: перечень владельцев —
   производная проекция реестра PACT (§14.2), а параметры инстанса (индекс, порт, каталог профиля) —
   конфигурация узла.
2. Дублирование справочника в нескольких носителях запрещено: расходящиеся копии расходятся молча.
3. Источником правды о фактическом составе инстансов является состояние узла, а не файл в репозитории.
4. Несоответствие «владелец задачи ↔ инстанс подключения» — отказ исполнения (**M-5**), а не переключение на месте.

### 10.5. Честные границы изоляции

Спецификация фиксирует, что именно изоляцией **не** закрывается:

1. **Общий системный пользователь.** Если все инстансы работают под одним непривилегированным системным
   пользователем, код, выполнившийся от его имени, получает сразу все профили и все точки подключения.
   Целевое требование — разнесение инстансов по разным системным пользователям; до его выполнения изоляция
   защищает от враждебной веб-страницы, но не от скомпрометированного процесса браузера.
2. **Владение доступом к экрану.** Внутри окна аварийного вывода владение ссылкой равно полному доступу
   к браузеру этого инстанса (§11.4). Инстансы сужают радиус до одного владельца, но не убирают риск.
3. **Общий профиль внутри владельца.** Инстанс содержит сессии всех сервисов владельца; доступ к инстансу —
   доступ ко всем его сервисам. Отсюда требование §9.4 о фильтрации по домену при выдаче сессий и правило
   не помещать в один профиль сервисы с несопоставимым уровнем чувствительности.
4. **Ограничение по ресурсам.** Число одновременно живых инстансов ограничено ресурсами узла; ограничение
   одновременности — требование к планированию запусков, а не следствие изоляции. Численные пределы
   не определены (§25, O-6).

### 10.6. Headed-режим как несущее требование

Браузер работает в headed-режиме с постоянным профилем. Это **требование**, а не текущее удобство. Основания:

1. **Аварийное вмешательство человека** (§11) возможно только в видимой сессии: человек проходит проверку
   в той же вкладке, в которой работает исполнитель, после чего исполнитель продолжает.
2. **Работоспособность на защищённых сервисах.** Целевые системы MITA рассчитаны на человеческую сессию;
   headless-режим и типичные маркеры автоматизации ведут к отказам, которые нельзя обойти в рамках правил сервисов.
3. Обход средств защиты запрещён (§11.2, п.1), поэтому headed-режим — не оптимизация, а условие выполнимости задач.

Побочные требования, вытекающие из headed-режима:

- перед первым действием после навигации исполнитель обязан убедиться, что работает в активной вкладке:
  в фоновой вкладке проверки готовности элементов не завершаются, и исправный элемент выглядит как отказ
  по таймауту;
- исполнитель не открывает лишних вкладок и возвращает фокус на свою вкладку после любого переключения.

## 11. Аварийное вмешательство человека

### 11.1. Когда применяется

Класс ситуаций, зафиксированный CONTOURS.md §8.4 как принципиально не закрываемый техникой: системы, работающие
только с человеческой сессией — капча, MFA, привязка к устройству, подтверждение по SMS.

Признаки, по которым ситуация опознаётся однозначно (а не по догадке): ответ сервиса со страницей проверки;
встроенный фрейм известного поставщика проверок; явный текст с требованием подтвердить, что пользователь —
человек; форма ввода второго фактора, не покрываемая §9.3.

### 11.2. Что MITA обязана и чего не имеет права делать

1. **Запрещено** обходить средства защиты: подбор отпечатков, патчи маскировки автоматизации, сторонние сервисы
   распознавания. Причина — нестабильность и нарушение правил целевых сервисов.
2. Простая графическая проверка может быть предпринята исполнителем самостоятельно, с жёстким потолком попыток;
   поведенческие и интерактивные проверки не предпринимаются вовсе — сразу эскалация.
3. Перед эскалацией MITA фиксирует состояние: снимок экрана и адрес страницы в артефактах запуска, а также
   имя инстанса и точную формулировку того, что требуется от человека.
4. Во время ожидания MITA не трогает вкладку: не перезагружает, не навигирует, не переключает вкладки.
5. После вмешательства работа продолжается **в той же вкладке того же инстанса**.

### 11.3. Кто инициирует и кто выдаёт ссылку

| Шаг | Кто | Содержание |
|---|---|---|
| 1 | MITA | Определяет, что требуется физическое участие человека; фиксирует состояние; публикует **промежуточное событие «требуется вмешательство»** (ожидание внутри запуска, §5.6.1), указывая владельца, сервис, инстанс, требуемое действие и срок. Если условия удержания §5.6.1 не выполняются — вместо промежуточного события публикуется приостанавливающий исход `blocked_awaiting_human`, и дальнейшие шаги выполняются уже в возобновляющем запуске (§5.6.3) |
| 2 | PACT | Решает, допустимо ли открывать доступ к экрану, и кому. Это решение о полномочиях, а не о технике |
| 3 | MITA | По решению PACT поднимает сеанс просмотра и возвращает PACT одноразовую ссылку с указанием срока жизни |
| 4 | PACT | Проводит ссылку через egress-проверку как часть исходящего сообщения |
| 5 | LINA | Доставляет ссылку человеку в диалог |
| 6 | человек | Выполняет действие в браузере |
| 7 | MITA | Обнаруживает снятие блокировки, гасит сеанс просмотра **немедленно**, не дожидаясь таймаута, и продолжает работу в том же `run_id` |
| 7′ | MITA | Если вмешательства не произошло в пределах окна (§5.6.5), сеанс гасится по TTL, инстанс освобождается, запуск завершается исходом `blocked_awaiting_human` с причиной `human.window_expired` и `external_state` по §5.6.2, п. 3 |

Согласование с правилом «LINA — единственный, кто говорит с человеком»: MITA **не отправляет** ссылку человеку
и не выбирает канал. Ссылка — часть исходящего сообщения, а исходящие сообщения публикует только egress-часть PACT
(SPECIFICATION.md §23, инв. 12).

**Отношение к инварианту 2 — явное исключение, а не соблюдение.** Шаги 1, 2, 4, 5 (доставка и подтверждение ссылки)
проходят через PACT и инвариант 2 (CONTOURS.md §10) не нарушают. Но шаг 6 — прямое сетевое соединение человека
с сеансом просмотра, поднятым MITA, — обходит PACT физически: между человеком и браузерным инстансом исполнителя
на время сеанса существует канал, не проверяемый ни enforcement-частью PACT, ни egress-проверкой результата.
Формулировка «инвариант 2 не нарушается» относится только к доставке ссылки, а не к самому каналу просмотра,
и не может использоваться как утверждение о канале в целом. Путь признаётся **явным, документированным
исключением** из инварианта 2, допустимым только при одновременном выполнении следующих компенсаций:

1. ровно один браузерный инстанс на сеанс, привязанный к владельцу задачи (§10.2, M-4);
2. ровно один действующий сеанс просмотра и ровно одна действующая ссылка на инстанс (§11.4, п. 3);
3. жёсткий TTL сеанса (§11.4, п. 2) и его немедленное гашение по завершении, а не по таймауту (§11.3, шаг 7);
4. запись факта открытия и закрытия сеанса в машиночитаемом аудите (§17), при этом сама ссылка в аудит не
   попадает (M-11, §11.5);
5. решение об открытии канала принимается PACT по доверенному пути подтверждения, а не диспетчером или MITA
   (§11.3, шаг 2; PACT §17.10, где механика шагов 1–5 уже описана как частный случай запроса вмешательства
   человека).

Компенсации п. 1–5 закрывают риск только при условии, что модель полномочий PACT знает про этот канал явно,
а не молчаливо пропускает его через общий путь исходящего сообщения. Требование к PACT сформулировано как П-12
в §21.1: отдельная capability класса «доступ к экрану инстанса», обязательный approval по доверенному пути
(уже используемый веткой `APPROVAL_PENDING`, PACT §17.10 п. 2) и классификация одноразовой ссылки как секрета
высшей категории, наравне со storage-state (PACT §10.2), с TTL и запретом раскрытия во всех каналах, кроме
маршрута исходной задачи. Требование к LINA: доставлять ссылку как непрозрачное значение и не сохранять её
в истории диалога — сформулировано как Л-6 в §21.2.

### 11.4. Требования к механизму вывода сессии

1. **Одноразовость пути.** Доступ выдаётся по непредсказуемому одноразовому пути; аутентификации по паролю нет,
   защита строится на неугадываемости и краткости жизни.
2. **Ограниченный срок.** Сеанс имеет жёсткий предел жизни (целевое значение — 30 минут) и гасится по истечении
   автоматически, а также по явной команде и при падении сеанса.
3. **Ровно один сеанс на инстанс** и ровно одна действующая ссылка. Ссылка перестаёт работать сразу после
   гашения сеанса.
4. **Гашение точечное.** Гасится сеанс своего инстанса; массовое гашение всех сеансов запрещено — оно затрагивает
   чужие запуски.
5. **Внутренние точки доступа недоступны извне** и достижимы только через единственную внешнюю точку входа.
6. **Путь не попадает в журналы** веб-сервера и не логируется вместе со строкой запроса.
7. **Остаточный риск фиксируется явно:** внутри окна владение ссылкой равно полному доступу к браузеру инстанса;
   второго рубежа нет. Инстансы сужают радиус до одного владельца.

### 11.5. Обращение со ссылкой

- **M-11.** Ссылка не попадает ни в один журнал, артефакт, карточку задачи, заметку или отчёт MITA.
- Ссылка передаётся **только** тем маршрутом, который вернул PACT; дублирование в другие каналы запрещено.
- Повторная выдача ссылки требует нового решения PACT; продление существующего сеанса не предусмотрено.
- Факт эскалации фиксируется в рабочих материалах (§12) и в машиночитаемом аудите (§17) — но без самой ссылки.

### 11.6. Регулярная эскалация как сигнал

Повторяющаяся необходимость вмешательства человека на одном и том же сервисе — сигнал о непригодности браузерной
модальности для этого сервиса и основание рассмотреть его переезд в CITA (§18.4) либо смену точки интеграции.
MITA обязана отдавать этот сигнал в машиночитаемом виде (§17.2), а не хранить его как наблюдение в тексте.

## 12. Рабочие материалы исполнителя

### 12.1. Состав и принадлежность

Рабочие материалы принадлежат MITA и не являются реестром PACT. Это следствие CONTOURS.md §9: задачи, их состояния
и лизинги — у PACT; сценарии веб-исполнения — у MITA; «ни один контур не изменяет хранилище другого».

| Материал | Что это | Владелец | Виден PACT |
|---|---|---|---|
| **План выполнения** | последовательность шагов, выведенная исполнителем из цели и DoD | MITA | нет; сводка — в результате запуска |
| **Журнал хода работы** | пошаговая запись фактических действий и наблюдений в рамках запуска | MITA | нет; ссылки и сводка — в результате |
| **Артефакты** | файлы-доказательства: снимки экрана, выгрузки, дампы | MITA (хранение), PACT (ссылки в реестре) | только через интерфейс разыменования ссылки, не файлом (§12.6) |
| **Журналы сессий исполнителя** | сырой append-only лог работы агента и подчинённых ролей | MITA | нет |
| **Заметки и знания** | наблюдения об интерфейсах, устойчивое знание о сервисах | MITA | нет |

### 12.2. Разграничение «запись реестра» и «рабочая тетрадь»

Одна задача порождает **два разных объекта у двух разных владельцев**:

1. **Запись реестра** (PACT): идентификатор, владелец, состояние, лизинги, capabilities, решения approval,
   DoD как зафиксированный критерий, журнал вердиктов.
2. **Рабочая тетрадь запуска** (MITA): план, журнал хода, артефакты, наблюдения, черновики.

Связь между ними — **только** непрозрачный `task_id` (CONTOURS.md §9). Требования:

- MITA не хранит собственного состояния задачи и не считает своё представление источником истины о состоянии;
- расхождение между рабочей тетрадью и реестром разрешается в пользу реестра;
- удаление или архивирование рабочей тетради не влияет на состояние задачи;
- MITA не воспроизводит в рабочих материалах поля, за которые отвечает PACT (состояние, лизинг, вердикты),
  иначе появляется вторая, расходящаяся копия реестра.

### 12.3. Требования к журналу хода работы

1. Append-only: записи не переписываются задним числом.
2. Одна запись — один запуск; запись обязательна для любого запуска, изменившего что-либо во внешней системе
   или в рабочих материалах.
3. Значения секретов маскируются (**M-10**); ссылка аварийного доступа не записывается (**M-11**).
4. Фиксируются фактические наблюдения, а не намерения: что было сделано, что было получено в ответ.
5. Журнал — операционный лог исполнителя, а не аудит системы. Аудит — §17.

### 12.4. Требования к артефактам

1. Артефакт привязан к `task_id` и `run_id`.
2. Артефакт, доказывающий выполнение пункта DoD, обязателен для отметки пункта выполненным (§15.3).
3. Крупные данные передаются PACT **ссылками**, а не содержимым (SPECIFICATION.md §9); требования к самой
   ссылке и к её разыменованию — §12.6.
4. Рабочие технические файлы инструментов (промежуточные снимки, дампы, вытесняемые кеши) не являются артефактами
   и не могут быть единственным доказательством: доказательства обязаны переживать очистку рабочих каталогов.
5. Артефакт проходит маскирование секретов до сохранения (§17.4).

### 12.5. Что рабочие материалы не заменяют

- не заменяют реестр задач PACT;
- не заменяют машиночитаемый аудит (§17);
- не заменяют отчёт для человека (§16);
- не являются каналом связи с человеком: запись в журнале не считается сообщённой человеку.

### 12.6. Хранилище артефактов и разыменование ссылок

Первая редакция объявляла артефакты видимыми PACT «по ссылке», не определяя ни ссылку, ни способ её
разыменования, из-за чего §12.1 читался как противоречие правилу §14.3, п. 1 («не существует решения вида
„PACT читает файл в рабочих материалах MITA“»). Противоречие снимается разделением двух вещей.

#### 12.6.1. Хранилище артефактов — публикуемая поверхность, а не рабочая тетрадь

1. Артефакты хранятся отдельно от рабочей тетради запуска (плана, журнала хода, черновиков, сырых дампов).
   Рабочая тетрадь недоступна никому, кроме MITA; хранилище артефактов — единственная поверхность рабочих
   материалов, к которой существует внешний интерфейс.
2. Файловая раскладка хранилища — внутреннее устройство MITA. Ни PACT, ни любой другой контур не обращается
   к файлу, пути, каталогу или файловой системе узла. Правило §14.3, п. 1 сохраняется в силе: чтение
   **хранилища** запрещено, разрешено обращение к **интерфейсу**, который MITA предоставляет и контролирует.
3. Помещение файла в хранилище — сознательная публикация. То, что не должно покидать MITA, в хранилище
   не помещается (§17.1).
4. Конкретная раскладка каталогов и файлов контура — предмет отдельного документа `docs/spec/layout.md`.
   Он выведен из этой спецификации, но контрактом не является и может меняться, пока интерфейсы §5, §12.6
   и §17 остаются прежними.

#### 12.6.2. Ссылка на артефакт

| Свойство | Требование |
|---|---|
| Форма | непрозрачный идентификатор `artifact_ref`; из него не выводятся путь, имя файла, каталог, владелец и внутреннее устройство MITA |
| Адресация | ссылка привязана к `task_id` и `run_id`, в рамках которых артефакт создан (§12.4, п. 1) |
| Содержимое ответа | байты артефакта и метаданные: тип, размер, момент создания, `run_id`, отметка о пройденном маскировании (§17.4) |
| Аутентификация | разыменование доступно только PACT как авторизованному потребителю; неаутентифицированный доступ отсутствует |
| Одноразовость | не требуется: артефакт — доказательство, к нему обращаются многократно |
| Срок жизни | ссылка действительна, пока действителен артефакт (§12.6.3) |
| Изменяемость | артефакт неизменяем: обновление создаёт новый артефакт и новую ссылку, прежняя не переписывается |

Ссылка на артефакт **не является** ссылкой аварийного вывода сессии и не подчиняется M-11: артефакт — данные,
сеанс — доступ. Смешение этих двух объектов запрещено.

Требование **M-16** формулирует обязательную сторону этого контракта: доказательство существует не тогда, когда
файл лежит у MITA, а тогда, когда на него есть ссылка в результате запуска и её можно разыменовать, не зная
устройства хранилища.

#### 12.6.3. Срок хранения и исчезновение артефакта

1. Срок хранения по умолчанию — **90 суток** с момента создания, до принятия системного решения по срокам
   хранения (§25, O-7). Значение — конфигурация узла.
2. Артефакт, подтверждающий пункт DoD (§15.3, п. 3) или зафиксированное необратимое изменение (§5.2,
   `result.changes`), хранится не меньше, чем запись реестра задачи у PACT. Более короткий срок делает
   доказательство бессмысленным.
3. Разыменование ссылки на истёкший или отсутствующий артефакт возвращает типизированный отказ «артефакт
   недоступен», а не пустой ответ и не подстановку другого артефакта.
4. Исчезновение артефакта не изменяет ранее опубликованный результат запуска: результат остаётся тем, что был
   опубликован, а отсутствие доказательства фиксируется на стороне PACT как факт, а не как переоценка исхода.
5. Рабочие технические файлы инструментов артефактами не являются и в хранилище не попадают (§12.4, п. 4).

## 13. Расщепление знаний

Один документ сегодня может обслуживать несколько контуров. Целевое состояние — расщепление по владельцу
с явным правилом для каждого раздела. Основание — CONTOURS.md §9 и принцип «можно ли» / «как именно».

### 13.1. Карточка сервиса

| Раздел карточки | Владелец | Что содержит | Что запрещено |
|---|---|---|---|
| «Доступ»: имена секретов, наличие второго фактора, кто имеет доступ, срок и условия выдачи | **PACT** | имена вида `<client>/<service>/<field>` и правила выдачи | значения; логин открытым текстом (§9.6) |
| «Возможности и типовые операции» **через веб-интерфейс** | **MITA** | что и где делается, порядок шагов, ссылки на плейбуки, признаки успеха | имена секретов; политика допустимости операции |
| «Возможности и типовые операции» **через опубликованный контракт/API** | **CITA** | эндпоинты, схемы, коды ошибок, идемпотентность | то же |
| «Грабли и особенности» | **по модальности**: особенности веб-интерфейса → MITA; особенности контракта → CITA | неочевидное поведение, ограничения | смешение модальностей в одном разделе |
| Классификация операций по необратимости | **PACT** | таблица «хост + тип операции → обратимо/необратимо» | самостоятельная классификация исполнителем (§7.1) |
| Наблюдение «у сервиса обнаружен пригодный контракт» | **MITA фиксирует, CITA принимает решение** | признак пригодности к переезду (§18.4) | молчаливый переезд без изменения маршрута PACT |

Правило разрешения спора: раздел принадлежит тому контуру, чьё изменение заставляет его переписать
(CONTOURS.md §3.1). Переверстали интерфейс — MITA. Сменилась версия API — CITA. Изменились правила доступа — PACT.

### 13.2. Инструкции владельца

Документ «правила работы с владельцем» расщепляется на три части:

| Содержание | Владелец | Пример класса содержимого |
|---|---|---|
| Запреты и лимиты | **PACT** | что нельзя делать в системах владельца, пороги сумм, требование подтверждения на класс операций |
| Стиль коммуникации, тон, формат общения, предпочитаемый канал | **LINA** | как обращаться, что уточнять, как формулировать |
| Операционные особенности исполнения | **MITA** | нюансы интерфейсов владельца, порядок работы с его сервисами, устойчивые особенности его окружения |

Требования:

1. Запрет, сформулированный в части LINA или MITA, **не является** enforcement и не может служить основанием
   допустить действие. Единственный источник запретов — правила PACT.
2. MITA не читает часть PACT и часть LINA напрямую; необходимое приходит в авторизованной задаче
   (`granted_capabilities`, `approval`) — **M-13**.
3. Приоритет «локальное правило владельца важнее общего» сохраняется внутри каждой части, но не переносится
   между контурами: правило владельца в части MITA не может ослабить политику PACT.

### 13.3. Плейбуки

Плейбуки принадлежат **MITA** целиком: это описание того, «как именно» выполняется класс ручных сценариев.

Требования к плейбуку:

1. Раздел «Когда применять» формулируется через **однозначные признаки**, а не через догадку.
2. Раздел «Предусловия» перечисляет проверяемые условия (владелец, инстанс, состояние сессии).
3. Раздел «Шаги» нумерован и не содержит решений о допустимости — только исполнение.
4. Раздел «Верификация» обязателен и формулируется как фактическая проверка (§15).
5. Раздел «Известные проблемы» описывает наблюдаемые отказы и их отличие от дефекта исполнения.
6. Плейбук не содержит значений секретов, ссылок аварийного доступа и решений о полномочиях.
7. Локальный плейбук владельца приоритетнее общего.

Плейбук, требующий необратимого действия, обязан явно указывать точку останова (§7.2) — он не подменяет approval.

### 13.4. Заметки и знания

Заметка — наблюдение; знание — устойчивое утверждение, перенесённое в карточку сервиса, плейбук или документ
владельца. Обе категории принадлежат MITA. Модель угроз и правила безопасности — не знание MITA, а вход для PACT:
MITA фиксирует наблюдение, требование формулирует PACT (§21).

## 14. Реестр владельцев

### 14.1. Канонический владелец

Канонический реестр владельцев (клиент / проект / внутренний контур) принадлежит **PACT**. Основание: без него
нельзя ответить, кому адресована задача и какие правила применяются; слаг владельца определяет скоуп политик,
имена секретов и адресацию задач. Ошибочная классификация владельца — это ошибка в скоупе полномочий,
а не в раскладке файлов.

Требования к каноническому реестру (со стороны MITA как потребителя):

1. Слаг владельца **глобально уникален** независимо от категории (клиент / проект / внутренний контур).
2. Категория владельца является атрибутом записи, а не частью идентификатора.
3. Смена категории не меняет слаг.
4. Реестр отдаётся MITA как проекция (§14.2), а не читается напрямую.

### 14.2. Производная проекция у MITA

MITA держит проекцию реестра, необходимую и достаточную для двух вещей:

1. раскладка рабочих материалов по владельцам (§12);
2. привязка «владелец → браузерный инстанс» (§10.4).

Требования к проекции:

- проекция **только для чтения**; MITA не заводит, не переименовывает и не удаляет владельцев;
- проекция содержит минимум полей: слаг, категорию, признак наличия браузерного инстанса;
- проекция обновляется событием от PACT; расхождение разрешается в пользу канонического реестра;
- владелец, отсутствующий в проекции, приводит к отказу исполнения (§4.4, п.5), а не к созданию записи на месте;
- заведение нового владельца — операция PACT; MITA может отдать сигнал «такого владельца нет», но не решение.

### 14.3. Правило «ни один контур не пишет в хранилище другого»

Прямая цитата CONTOURS.md §9: «Ни один контур не изменяет хранилище другого. Связи между контурами передаются
непрозрачными идентификаторами в событиях.»

Следствия, обязательные для MITA (**M-13**):

1. Не существует проектного решения вида «PACT читает файл в рабочих материалах MITA». Разыменование ссылки
   на артефакт (§12.6) исключением из этого правила **не является**: PACT обращается к интерфейсу, который MITA
   предоставляет и контролирует, и получает байты по непрозрачному идентификатору, а не доступ к файловой
   системе, пути или каталогу. Признак различия проверяем: если потребителю нужно знать раскладку хранилища,
   правило нарушено.
2. Не существует решения вида «MITA пишет состояние задачи в реестр PACT».
3. Данные, нужные обоим, оформляются либо как контракт события, либо как справочник с единственным владельцем
   и односторонней проекцией.
4. Обмен ведётся идентификаторами (`task_id`, `run_id`, `reply_route_id`, слаг владельца, имя секрета,
   имя capability), а не содержимым.

## 15. Верификация результата и DoD

### 15.1. Три разных места

Definition of Done проходит через три контура, и каждый отвечает за своё:

| Что | Где | Контур |
|---|---|---|
| **Формулируется** — при сборе полноты запроса, вместе с человеком | диалог | **LINA** |
| **Фиксируется** — как критерий, привязанный к задаче, неизменяемый исполнителем | реестр задач | **PACT** |
| **Проверяется фактически** — в целевой системе | исполнение | **MITA / CITA** |

Требования:

1. MITA получает DoD в составе авторизованной задачи (§4.3) и **не изменяет** его.
2. MITA не дополняет DoD собственными пунктами. Обнаруженная неполнота — сигнал PACT, а не правка на месте.
3. Задача без DoD не исполняется: это неполный вход (§4.4, п.1).

### 15.2. Требование к формулировкам

Пункт DoD обязан быть **фактически проверяемым**: он описывает наблюдаемое состояние целевой системы
(«в системе X на странице Y отображается Z»), а не намерение («настроить интеграцию»).

MITA обязана отклонить как непроверяемый пункт, который:

- описывает намерение или процесс, а не состояние;
- не указывает, где именно наблюдается результат;
- проверяется только утверждением исполнителя.

Отклонение — типизированная причина в результате запуска, а не самостоятельная переформулировка.

### 15.3. Принцип «проверять фактически, а не верить самоотчётам»

- **M-7.** Пункт DoD не отмечается выполненным без фактической проверки в целевой системе.

Правила проверки:

1. Проверка выполняется **после** действия и **независимо** от него: наблюдается результирующее состояние,
   а не факт нажатия кнопки.
2. Проверка выполняется **запросом защищённого состояния**, а не по косвенным признакам. Косвенные признаки
   (адрес страницы, редирект, отсутствие ошибки) недостаточны: интерфейсы возвращают ложноотрицательные и
   ложноположительные признаки.
3. Каждый проверенный пункт сопровождается артефактом-доказательством (§12.4), адресуемым из результата запуска
   ссылкой по §12.6 (**M-16**).
4. «Должно работать», «действие выполнено успешно», «ошибок не было» результатом не считаются.
5. Отсутствие возможности проверить — это статус «не проверялся», а не «выполнен». Итог запуска в этом случае —
   не `completed`.
6. Самоотчёт подчинённой роли не является проверкой: результат делегированной работы проверяется тем же способом,
   что и внешний.

### 15.4. Верификация в терминах результата

Поле `result.dod` (§5.2) содержит по каждому пункту: исход (`verified` / `failed` / `not_checked`), способ проверки,
ссылку на артефакт. Статус запуска `completed` допустим **только** если все пункты имеют исход `verified`.

## 16. Отчёт для человека

### 16.1. Разделение ролей

| Шаг | Контур | Действие |
|---|---|---|
| 1 | **MITA** | формирует текст отчёта и публикует его как предложение ответа (§5.4) |
| 2 | **PACT** | проводит egress-проверку и, при одобрении, публикует событие внешней доставки |
| 3 | **LINA** | доставляет текст человеку в исходный диалог и оформляет под канал |

Основание: CONTOURS.md §6.4 (проверка результата перед раскрытием — обязанность enforcement-части PACT),
D-004 (двусторонняя точка сужения, статус **принято**), SPECIFICATION.md §23 инв. 12.

MITA не знает, в какой канал уйдёт текст, и не оформляет его под конкретный мессенджер: оформление под канал —
обязанность LINA. MITA отвечает за содержание.

### 16.2. Требования к тексту

Отчёт готов к пересылке человеку **без редактирования**. Это означает:

1. **Самодостаточность.** Текст понятен без чтения карточки задачи, журналов и артефактов.
2. **Результат первым.** Первая фраза отвечает на вопрос, сделано или нет.
3. **Фактичность.** Только проверенное (§15.3). Непроверенное называется непроверенным.
4. **Ограничения названы явно.** Что не сделано и почему — обязательный элемент при любом статусе, кроме
   полного выполнения.
5. **Следующий шаг.** Если требуется действие человека — оно сформулировано как конкретное действие, а не
   как описание проблемы.
6. **Без внутренней кухни.** Нет имён внутренних компонентов, путей файлов, идентификаторов запусков, названий
   инструментов, стектрейсов, селекторов.
7. **Без секретов.** Значений, логинов, кодов, ссылок аварийного доступа в тексте нет (**M-10**, **M-11**).
8. **Язык.** Содержимое — русский; технические идентификаторы внешних систем приводятся как есть.
9. **Без обещаний.** Текст не содержит обязательств о будущих действиях, которые MITA не уполномочена принимать.

### 16.3. Что отчёт не содержит

- оценку допустимости раскрытия (это решение PACT);
- маршрут доставки и имя канала (это `reply_route_id`, непрозрачный для MITA);
- обращение к человеку с вопросом: вопросы задаёт LINA, а необходимость уточнения MITA выражает статусом
  и типизированной причиной, а не текстом «уточните, пожалуйста».

### 16.4. Отчёт при неуспехе

Отчёт формируется при любом исходе запуска — как терминальном (`rejected`, `cancelled`, `denied_by_egress`,
`failed`), так и приостанавливающем (`blocked_awaiting_approval`, `blocked_awaiting_human`, `lease_expired`).
Приостанавливающий исход описывается человеку как незавершённость с названным условием продолжения, а не как
провал и не как обещание вернуться: решение о возобновлении принимает PACT (§5.6.3), и MITA не сообщает его
человеку как состоявшееся. Содержание для человека при отказе по политике определяется PACT: MITA формирует нейтральное
описание фактического исхода без внутренних деталей, а решение о том, что именно из этого раскрывается,
принимает egress-проверка (SPECIFICATION.md §12.3).

## 17. Наблюдаемость и аудит

### 17.1. Разделение «машиночитаемое» и «внутреннее»

| Категория | Кому | Форма |
|---|---|---|
| События запуска и их поля конверта | PACT, аудит системы | машиночитаемые события |
| Сводка внешних вызовов, изменений, approvals, использованных capabilities | PACT | поля результата запуска (§5.2) |
| Артефакты-доказательства | PACT по ссылке, человек — опосредованно | файлы с адресацией по `task_id`/`run_id` |
| Журнал хода работы, заметки, черновики | только MITA | внутренний лог (§12.3) |
| Сырые дампы страниц, снимки инструментов, промежуточные файлы | только MITA | внутренние, вытесняемые |

### 17.2. Что MITA обязана отдавать в машиночитаемом виде

1. Поля конверта каждого события (SPECIFICATION.md §9): `event_id`, `event_type`, `schema_version`, `occurred_at`,
   `published_at`, `producer`, `correlation_id`, `causation_id`, `trace_id`, `deduplication_key`.
2. Начало и завершение запуска, включая прерывания; статус из закрытого перечня (§5.3).
3. Перечень фактически совершённых внешних изменений с признаком обратимости (`result.changes`) — обязателен
   в том числе при прерывании (**M-14**).
4. Результаты проверки DoD по пунктам (§15.4).
5. Сводку внешних вызовов: домен, метод, исход, счётчик. Без тел запросов и ответов.
6. Факты запроса и получения approval с идентификаторами.
7. Факты запроса секретов у PACT: имя секрета, назначение, `run_id`. Значения — никогда.
8. Факты эскалации к человеку (§11) — без ссылки.
9. Признаки обнаружения недоверенного контента, похожего на инструкцию (§20.3).
10. Сигнал о пригодности сервиса к переезду в CITA (§18.4).
11. Типизированную причину исхода из закрытого перечня (§5.7) и — для приостанавливающих исходов — блок
    `suspension` с условием продолжения и состоянием внешней системы (§5.6.2, п. 3).
12. Промежуточные события ожидания внутри запуска: запрос approval (§7.2) и запрос вмешательства человека
    (§11.3, шаг 1) с моментом начала ожидания и его пределом (§5.6.5).
13. Факт приёма события отмены и момент прекращения внешних действий (§5.6.4).
14. Связь возобновляющего запуска с прежним: `task_id`, прежний `run_id`, новый `run_id` (§5.6.3).

### 17.3. Фиксация расхождений

MITA обязана отдельно и машиночитаемо фиксировать случаи, в которых её собственная проверка (§6.2) разошлась
с решением enforcement: действие считалось разрешённым, но отклонено прокси; approval получен не по своему
`run_id`; событие пришло с неизвестным `worker`. Такие записи — вход для пересмотра правил PACT, а не
предмет обработки на месте.

### 17.4. Маскирование секретов

- **M-10.** Все значения секретов маскируются во всех выходах MITA: события, журналы, артефакты, снимки экрана,
  отчёты.

Требования:

1. Маскирование выполняется **до** записи, а не при чтении.
2. Маскируется вся пара «логин + пароль», а не только пароль (§9.6).
3. Снимок экрана, на котором значение видно в интерфейсе, не сохраняется; вместо него сохраняется снимок
   состояния после ввода.
4. В журнал попадают метаданные (адрес, заголовок страницы, количество и домены cookie), но не значения.
5. Маскирование в MITA не заменяет egress-проверку PACT: это две независимые линии, обе обязательны
   (SPECIFICATION.md §18.9).

### 17.5. Прослеживаемость

Весь путь от авторизованной задачи до предложения ответа прослеживается по `correlation_id`; связь причин —
по `causation_id`; связь с реестром — по `task_id` и `run_id`. Нефункциональные требования (задержки, сроки
хранения, предельные размеры) на уровне системы не определены (REVIEW-FINDINGS.md §5.1, статус **открыто**) —
см. §25, вопрос O-7.

## 18. Граница MITA / CITA

### 18.1. Где проходит граница

Дословно (CONTOURS.md §7.1): «Граница проходит по наличию пригодного API у целевой системы, а не по предметной
области.»

Следствия:

1. Один и тот же владелец, один и тот же сервис и одна и та же предметная задача могут исполняться разными
   контурами в зависимости от того, есть ли пригодный опубликованный контракт.
2. Разрез «финансы — MITA, аналитика — CITA» и любые другие разрезы по предметной области **неверны**.
3. Граница подвижна и меняется без изменения задачи: у вендора появилось API — возможность переезжает.

Сравнение контуров (CONTOURS.md §7.1, дословная таблица):

| | MITA | CITA |
|---|---|---|
| Способ | веб-интерфейс, браузер | подготовленная API-интеграция |
| Стоимость | сценарий под каждую цель | интеграция один раз, переиспользуется |
| Хрупкость | ломается при редизайне | ломается при смене версии API |
| Ошибки | неструктурированные | коды и схемы |
| Идемпотентность | как правило отсутствует | как правило достижима |

### 18.2. Асимметрия риска

Дословно (CONTOURS.md §7.2): «Контуры соседние по положению и несопоставимые по риску. MITA читает недоверенные
веб-страницы и действует по прочитанному, работает в живых сессиях внешних систем, а его действия часто
необратимы. При модели доставки at-least-once повторная отправка формы — это второе выполнение действия,
а не повторное чтение.»

Отсюда режимные отличия MITA, не распространяющиеся на CITA: approval на необратимое по умолчанию (§7),
MITM-подстановка сессии (§8.3), браузерная изоляция по владельцам (§10), аварийный вывод сессии человеку (§11).

### 18.3. Переезд не меняет имя capability

Инвариант 9 (CONTOURS.md §10), D-007 (статус **принято**): capability не содержит указания на модальность.

Требования при переезде возможности из MITA в CITA:

1. Имя capability **не меняется**. Меняется маршрут: PACT назначает другого исполнителя.
2. Правила и профили approval не переписываются: они привязаны к имени возможности, а не к способу.
3. Классификация необратимости может измениться (у контракта появляется идемпотентность), но это решение PACT,
   а не следствие переезда.
4. MITA не выполняет переезд самостоятельно и не отказывается от возможности в одностороннем порядке:
   она отдаёт сигнал (§18.4), решение принимает PACT.
5. Обратный переезд (CITA → MITA) при отзыве или деградации API возможен по тем же правилам.

### 18.4. Признаки пригодности сервиса к переезду

MITA фиксирует и отдаёт в машиночитаемом виде (§17.2, п.10) следующие наблюдения:

1. Обнаружен опубликованный и документированный контракт целевой системы, покрывающий выполняемую операцию.
2. Наблюдаемый в браузере внутренний интерфейс, стабильно возвращающий структурированные данные, — **слабый**
   признак: неопубликованный контракт пригодным не считается, поскольку не даёт обязательств по совместимости.
3. Сервис регулярно требует аварийного вмешательства человека (§11.6) — модальность браузера для него дорога.
4. Сценарий регулярно ломается при редизайне интерфейса.
5. Требуется идемпотентность, недостижимая через форму.
6. Требуется объём или частота операций, несовместимые с ручной модальностью.

Признак «сервис пригоден» — это вход для решения, а не решение. Перечень исходных интеграций CITA и целевых
систем MITA на уровне системы не определён (CONTOURS.md §13) — см. §25, вопрос O-8.

### 18.5. Что MITA не делает на границе

- не вызывает опубликованные API вместо браузера «потому что так быстрее»: смена модальности — смена исполнителя;
- не поддерживает собственных интеграций по контракту;
- не передаёт задачу CITA напрямую (инвариант 2, CONTOURS.md §10);
- не именует свои возможности с указанием способа.

## 19. Идентификация исполнителя

### 19.1. Закрытый перечень

Инвариант 11 (CONTOURS.md §10), инвариант 16 (SPECIFICATION.md §23): «Идентификатор исполнителя в правилах
и событиях проверяется по закрытому перечню; неизвестное значение приводит к отказу.»

Основание (CONTOURS.md §2.1): MITA и CITA различаются одним символом; опечатка переносит разрешение
с контрактного исполнителя на исполнителя, управляющего чужим веб-интерфейсом, то есть в сторону большего риска.

Требования:

1. Перечень идентификаторов исполнителей — закрытый, ведётся PACT, проверяется детерминированно. **Значения утверждены 2026-08-11 (D-018): `mita` и `cita`**, нижний регистр, без разделителей; изменение перечня требует отдельного решения.
2. **M-12.** MITA представляется в событиях идентификатором из перечня и не принимает событий с идентификатором
   вне перечня.
3. Неизвестное или неожиданное значение приводит к **отказу**, а не к выбору по умолчанию. Умолчания
   не существует.
4. Сравнение идентификаторов точное, без нормализации регистра, без исправления опечаток, без сопоставления
   по префиксу или расстоянию.
5. Идентификатор исполнителя не выводится из содержимого задачи, имени capability или домена целевой системы.
6. **Имя поля асимметрично между входом и выходом, и это зафиксировано намеренно, а не является расхождением.**
   В авторизованной задаче (§4.3) идентификатор приходит в поле `executor` — по PACT §17.4. Во внутреннем
   результате запуска (§5.2) и во всех прочих событиях исполнитель → PACT тот же идентификатор передаётся
   в поле `worker` — по PACT §17.5. Значение идентификатора в обоих полях — одно и то же, из одного закрытого
   перечня; различается только имя поля в зависимости от направления события. Точное посимвольное сравнение
   по п. 4 применяется к значению поля, а не к его имени: сверка имени поля выполняется проверкой схемы события
   (§4.4, п. 6), а не логикой закрытого перечня.

### 19.2. Множественность одновременных исполнителей

1. Одновременно могут работать несколько экземпляров MITA. Каждый экземпляр различается **инстансом**
   (`producer.instance` в конверте события, SPECIFICATION.md §9), но не идентификатором исполнителя.
2. Идентификатор исполнителя обозначает **модальность**, а не процесс. Все экземпляры MITA несут один
   идентификатор.
3. Один запуск (`run_id`) исполняется ровно одним экземпляром. Разграничение — лизинг и его поколение
   (SPECIFICATION.md §15.2).
4. Экземпляры не координируются между собой напрямую и не передают друг другу задачи.
5. Ограничение одновременности определяется ресурсами узла и привязкой к браузерным инстансам (§10.5, п.4):
   два запуска для одного владельца не выполняются в одном инстансе одновременно.
6. Подчинённые исполнители (субагенты) не являются отдельными исполнителями в смысле перечня: они работают
   внутри запуска, наследуют его инстанс, полномочия и лизинг, собственных событий исполнителя не публикуют
   (SPECIFICATION.md §23, инв. 7: события публикует обёртка исполнителя).

## 20. Модель угроз недоверенного контента

### 20.1. Три условия, выполняющиеся в MITA одновременно

MITA — единственный контур, в котором сходятся все три условия промпт-инъекции:

1. **Недоверенный ввод.** Содержимое веб-страниц приходит как обычный текст, без разметки «данные против
   инструкций». Тот же класс: вложения, выгрузки, тексты ошибок сервисов, содержимое полей интерфейса.
   SPECIFICATION.md §18.5: сырые сообщения и вложения считаются недоверенными.
2. **Доступ к внешним системам.** MITA действует в живых сессиях и имеет полномочия совершать изменения.
3. **Канал наружу.** Навигация по произвольному адресу — потенциальный канал эксфильтрации; выполнение
   произвольного кода в браузере — эквивалент удалённого исполнения.

Целевое состояние снимает условие 3 (§8, инвариант M-2) и сужает условие 2 (§6, §7), но **не снимает условие 1**:
чтение недоверенного контента — суть контура.

### 20.2. Правило провенанса

- **M-8.** Всё, что MITA прочитала из внешнего источника, является **данными**, а не инструкциями.

Требования:

1. Источник каждого фрагмента, попавшего в контекст исполнителя, помечен: цель задачи и DoD от PACT — одно;
   прочитанное со страницы — другое.
2. Инструкции принимаются только из авторизованной задачи (§4). Текст, обнаруженный на странице, в файле,
   в поле формы, в письме или в комментарии, не изменяет цель, DoD, набор действий и адресата результата.
3. Никакой прочитанный текст не может: расширить capabilities, отменить требование approval, изменить
   `reply_route_id`, инициировать обращение к человеку, изменить владельца задачи, вызвать переход к другому
   домену вне allowlist.
4. Обнаружение в недоверенном контенте текста, оформленного как инструкция агенту, — **событие для аудита**
   (§20.3), а не повод для интерпретации.
5. Правило провенанса — дешёвая и сама по себе слабая мера. Она обязательна, но не заменяет ни разделение
   ролей (§20.4), ни egress-контроль (§8), ни approval (§7).

### 20.3. Фиксация попытки

При обнаружении в недоверенном контенте конструкции, адресованной агенту (указания игнорировать инструкции,
раскрыть учётные данные, перейти по адресу, выполнить код), MITA обязана:

1. не выполнять её;
2. выставить `provenance_flags` в результате запуска (§5.2);
3. сохранить артефакт с фрагментом и адресом источника;
4. продолжить исполнение исходной задачи, если это безопасно, либо завершить запуск со статусом `failed`
   и типизированной причиной.

### 20.4. Разделение ролей по доверию

Требование: роль, читающая недоверенный контент, и роль, оперирующая значениями секретов и правом выполнения
команд, разделяются.

| Роль | Читает недоверенный контент | Оперирует значением секрета | Выполняет команды среды |
|---|---|---|---|
| Роль-исследователь (чтение веба, сбор наблюдений) | да | нет | нет |
| Роль-оператор ввода (вход в сервис) | ограниченно | да, на одно использование | нет |
| Роль-исполнитель среды | нет | нет | да |

1. Совмещение всех трёх столбцов в одной роли запрещено.
2. Разделение действует и для подчинённых ролей: субагент наследует ограничения, а не ослабляет их.
3. Разделение ролей — мера снижения, а не гарантия: она не устраняет неустранимую экспозицию §9.5.

### 20.5. Ограничение: декларация инструментов не является enforcement

Фиксируемое ограничение, имеющее прямое архитектурное следствие:

1. Ограничение набора инструментов роли **фильтруется** одним клиентом исполнения (Claude Code) и **не
   применяется** другим (Codex CLI), где то же поле является рекомендацией.
2. Следовательно, разделение ролей по доверию (§20.4) — **не** механизм принуждения, если исполнение может идти
   под клиентом, игнорирующим декларацию.
3. Принуждение обязано находиться там, где оно не зависит от клиента: egress proxy (§8), выдача секретов
   с TTL (§9), approval (§7), сетевая конфигурация узла.
4. Общий принцип, из которого это следует: **семантика безопасности не может зависеть от метаданных, которые
   клиент игнорирует.** [реконструкция: принцип сформулирован во внутренней архитектуре существующей системы
   и здесь распространён на контурную модель; он же — методологический предок правила «enforcement не использует
   LLM», D-003.]

MITA не взаимодействует с LINA напрямую (инвариант 2). Требования формулируются как требования к содержанию

| № | Требование |
|---|---|

| Л-2 | Различие «клиент / проект / внутренний контур» соблюдено. Иначе формулировка «проверь у всех клиентов» будет понята как обход всех владельцев вместо клиентов |

| Л-5 | Маршрут ответа создан доверенным компонентом и не выводится из текста пользователя (SPECIFICATION.md §11, п.1) |
| Л-6 | Ссылка аварийного вывода сессии (§11) доставляется человеку как непрозрачное значение и не сохраняется в истории диалога. **Принято LINA:** инвариант L-13, правила доставки LINA §15.5, запрет хранения LINA §11.2 п. 5 |

### 21.3. Что MITA перестаёт делать после подключения соседей

[реконструкция: перечень описывает отчуждение обязанностей, исполняемых сегодня за отсутствующие контуры.]

| После подключения | MITA перестаёт |
|---|---|
| **PACT (custody секретов)** | читать значения секретов с диска; хранить TOTP-семена; хранить снимки сессий; выполнять ротацию |
| **PACT (реестр задач)** | вести состояние задачи и её переходы; решать, какая задача берётся в работу; хранить признак владельца как источник истины |
| **PACT (политика)** | решать, легитимна ли задача; классифицировать необратимость; решать, требуется ли подтверждение |
| **PACT (egress)** | иметь прямой сетевой доступ; решать, какой домен допустим; решать, что из результата раскрывается человеку |
| **LINA** | вести диалог с человеком; принимать сырые постановки; задавать уточняющие вопросы; доставлять отчёт |
| **CITA** | автоматизировать через браузер то, для чего есть пригодный контракт |

Отчуждение считается выполненным только тогда, когда прежний путь **закрыт технически**, а не заменён
соглашением. Оставленный прямой доступ превращает соседний контур в декоративный слой, обходимый обращением
к старому пути.

## 22. Целевые свойства контура (идентификаторы `Ц-n`)

### 22.1. Что такое `Ц-n` и чем они не являются

**`Ц-n` — стабильные идентификаторы целевых свойств контура. Порядкового смысла они не несут.**
Читать `Ц-0` как «первый шаг», а `Ц-7` как «последний» — ошибка; между идентификаторами не существует
отношения предшествования, существуют только зависимости, перечисленные в §22.3.

**О букве и о нумерации.** До 2026-08-11 те же позиции обозначались `Э-n` — от слова «этап»; после
решения D-013 буква перестала соответствовать содержанию и заменена на `Ц` («целевое свойство»).
**Нумерация сохранена неизменной**: на неё опираются §24.4 (соответствие «свойство → негативный
критерий»), `docs/spec/layout.md` §8–§9 и `docs/adr/0018`, и её сдвиг порвал бы эти ссылки. При чтении
старых редакций документов `Э-n` и `Ц-n` — одно и то же с точностью до буквы.

**Пространство имён.** В этой спецификации заняты: `M-n` — инварианты контура, `A-n` и `Н-n` — позитивные
и негативные критерии приёмки (§24), `С-n` — **обмены на границах контура** (§2.2), `O-n` — открытые
вопросы (§25), `Ц-n` — целевые свойства (этот раздел). Буква `С` под свойства не годится именно потому,
что уже обозначает обмены; смешение `С-2` («внутренний результат запуска») и свойства «реестр задач
и авторизация» было бы неразличимо по написанию. Отдельно: `Ц-n`, `Н-n` и `С-n` — **кириллические**,
а `C-n` контура CITA — латинское; при ссылках между контурами идентификатор пишется с указанием контура
(`CITA C-96`, `MITA Ц-4`).

Исходно раздел назывался «Этапность перехода» и описывал порядок, в котором обязанности отчуждались бы
у **уже работающей** автоматизации при её постепенном укреплении. Решение D-013 (2026-08-11, перенос
в контур — `docs/adr/0018`) сняло это прочтение: при сборке контура с нуля укреплять нечего, а путь через
восемь последовательных этапов провёл бы контур через шесть нецелевых состояний — исполнитель с прямым
egress, затем с секретами на диске, затем выполняющий необратимое без approval, затем публикующий ответ
напрямую, затем с собственным каналом постановок, — каждое из которых подлежало бы демонтажу.

Действующее прочтение: **Ц-0…Ц-6 — условия запуска контура**, выполняемые одновременно, до первой
выполненной задачи. Единственное свойство, которое допустимо отложить, — **Ц-7** (эфемерное окружение):
оно добавляет жизненный цикл рабочей области к уже существующим компонентам и ничего не заменяет.
План работ — `ROADMAP.md` в корне воркспейса; в его нумерации Ц-0…Ц-6 приходятся на W1 (для браузерной
модальности — на W2, когда разворачивается контур), Ц-7 — на W5.

### 22.2. Перечень свойств

Колонка «Признак наличия» формулирует наблюдаемую проверку: свойство считается имеющимся только тогда,
когда описанный отказ даёт механизм (§24.1).

| Идентификатор | Содержание | Признак наличия | Что становится невозможным |
|---|---|---|---|
| **Ц-0. Отсутствие прямого egress** | У исполнителя нет прямого исходящего доступа; весь трафик — через прокси с allowlist доменов | Запрос к домену вне allowlist получает сетевой отказ | Эксфильтрация на произвольный хост |
| **Ц-1. Custody секретов у PACT** | Значения, TOTP-семена и снимки сессий хранятся под PACT; исполнитель получает их по запросу на `run_id` с TTL; storage-state выдаётся отфильтрованным по домену | На узле исполнителя нет файлов со значениями; вход выполняется через выдачу | Извлечение секрета из исполнителя; бессрочный обход второго фактора |
| **Ц-2. Реестр задач и авторизация** | Реестр задач PACT, авторизованная задача как событие, лизинги, capabilities; MITA не решает, что брать в работу | Ни один запуск не стартует без события с действующим лизингом | Исполнение без авторизации |
| **Ц-3. Approval на необратимое** | Таблица необратимости и событийный approval; точки останова в сценариях | Необратимое действие без approval не выполняется ни в одном сценарии | Тихое необратимое действие |
| **Ц-4. Подпись авторизации на каждом запросе** | Прокси проверяет подпись PACT на каждом запросе | Запрос с истёкшим лизингом отклоняется в середине запуска | Действие после истечения лизинга |
| **Ц-5. Egress-проверка результата** | Отчёт уходит человеку только через egress-проверку PACT; MITA публикует предложение ответа | MITA не имеет права публикации внешних сообщений | Раскрытие непроверенного результата |
| **Ц-6. Канал общения принадлежит LINA** | Постановки и ответы идут через LINA; точек входа в MITA не существует | Ни одна постановка не приходит в MITA напрямую | Прямое общение исполнителя с человеком |
| **Ц-7. Эфемерное окружение** | Окружение на задачу, отзыв лизинга и сессии по завершении | Между задачами не переиспользуется ни сессия, ни выданный секрет | Переиспользование доступа между задачами |

### 22.3. Зависимости между свойствами

Отношения ниже — **зависимости по смыслу, а не порядок работ**. Они действуют и тогда, когда все свойства
вводятся одновременно: зависимость означает, что свойство не может быть проверено (а иногда и
сформулировано) в отсутствие другого.

1. **Ц-3 не имеет смысла без Ц-2.** Approval — это решение о конкретной задаче: подтверждать нечего,
   пока нет ни идентификатора задачи, ни адресата решения.
2. **Ц-3 опирается на таблицу необратимости**, а она — часть Ц-3. Отсюда правило, действующее и при
   одновременном вводе: пока строка для операции не заведена, операция классифицируется как необратимая
   и не выполняется. Отсутствие approval выражается **запретом класса операций**, а не его ослаблением.
3. **Ц-4 не проверяем без Ц-2**: проверять на каждом запросе нечего, пока нет лизинга.
4. **Ц-1 и Ц-5 связаны в обе стороны.** Проверка результата на секреты выполняется по набору хешей
   действующих выдач (PACT §16.2), а выдачи существуют только при Ц-1; без него остаётся эвристика
   формата, которая запрещена.
5. **Ц-0 — предусловие для Ц-1 и Ц-4** в том смысле, что подстановка учётных данных и проверка подписи
   выполняются механизмом, через который проходит весь трафик; при наличии обходного маршрута оба
   свойства перестают быть свойствами.
6. **Ц-6 не имеет зависимостей и не является «последним».** В прежней редакции он выполнялся последним,
   потому что до него прямой канал к исполнителю оставался единственным способом вмешаться при отказе.
   В целевой сборке прямого канала не существует изначально, а роль способа вмешательства выполняет
   процедура §11 — она и является настоящей зависимостью Ц-6.
7. **Ц-7 — единственное свойство, отсутствие которого не отменяет остальных.** Оно добавляет жизненный
   цикл рабочей области, поэтому допустимо отложить его, не создавая промежуточной формы.

## 23. Вариант реализации

### 23.1. Статус

Вариант реализации системы — **гибрид на готовом шлюзе**: готовый продукт на границе внешних коммуникаций,
а брокер, контракты событий, PACT и реестр задач — собственная разработка. Решение **D-008**, статус
**предложено** (не подтверждено).

Смежные решения:

| Решение | Тема | Статус |
|---|---|---|
| **D-008** | Вариант реализации: гибрид на готовом шлюзе (OpenClaw) | **предложено** |
| **D-009** | OpenClaw на контуре исполнения отложен | **предложено** |
| **D-011** | Этап 0: минимальный контур | **отклонено** (2026-08-11) |
| **D-013** | Волна ограничивает объём, а не устройство | **принято** (2026-08-11) |
| **D-012** | Брокер событий: NATS JetStream как транспорт, PostgreSQL как состояние | **принято** (2026-08-11) |

### 23.2. Что это означает для MITA

1. **D-009 напрямую касается MITA.** Готовый шлюз на контуре исполнения **отложен**: экономия на исполнении
   наименьшая, а зависимость появилась бы там, где персональные учётные данные — две системы состояния задачи
   и два уровня политики. Условие пересмотра: интерактивные возобновляемые сессии, фоновые задачи, готовая
   sandbox-модель.
2. Следовательно, в предложенном варианте исполнительный контур MITA остаётся собственным, а готовый продукт
   рассматривается для границы каналов (контур LINA) — то есть там, где MITA не участвует.
3. Отдельно зафиксировано: в описании варианта не проговорено, как внутри исполнительного слоя различаются
   браузерная и контрактная модальности; браузерный инструмент на стороне исполнения не описан
   [реконструкция: вывод сделан при анализе источника, а не заявлен в нём].

### 23.3. Запреты

1. **Запрещено описывать OpenClaw как часть текущего состояния.** Он не установлен и не используется.
   Ни одна страница `docs/` не имеет права упоминать его иначе как предложенный, не подтверждённый вариант.
2. Запрещено считать команды и параметры конфигурации из `STAGE-0.md` действующей конфигурацией: практическая
   инструкция там опережает формальный статус решений D-008 и D-011 (оба «предложено»), и это несоответствие

3. Запрещено закладывать в спецификацию MITA зависимость от конкретного продукта: требования §4–§20
   сформулированы через контракты и инварианты и обязаны выполняться при любом варианте реализации.

| Контур | Чем представлен на этапе 0 |
|---|---|
| LINA | канальный слой шлюза: Telegram, при необходимости веб-чат |

## 24. Критерии приёмки контура, включая негативные

### 24.1. Правило формулировки

Критерий приёмки — **наблюдаемая проверка**, а не намерение. Формулировка обязана указывать, что подаётся на вход
и что наблюдается на выходе. Позитивный критерий (`A-n`) проверяет, что разрешённое работает; негативный (`Н-n`) —
что запрещённое **получает отказ механизмом**, а не отсутствует по договорённости. Негативный критерий считается
пройденным только тогда, когда отказ даёт механизм, продолжающий работать при неисправном или скомпрометированном
исполнителе (§20.5, п. 3).

Критерий, проверяемый только чтением кода или самоотчётом агента, приёмкой не является — это то же правило,
что M-7 для DoD.

### 24.2. Позитивные критерии

| № | Проверка | Наблюдаемый результат | Раздел |
|---|---|---|---|
| A-1 | Подана полная авторизованная задача с действующим лизингом | Запуск стартует, публикуется событие начала с полями конверта | §4.3, §17.2 |
| A-2 | Запуск завершён успешно | `status: completed`, все пункты `result.dod` — `verified`, у каждого ссылка на артефакт | §15.4 |
| A-3 | Каждый пункт DoD проверен запросом состояния целевой системы после действия | В журнале — отдельное наблюдение результата, не совпадающее с фактом нажатия | §15.3 |
| A-4 | Необратимое действие с полученным approval | Действие выполняется; в результате — `approvals` с идентификатором решения | §7, §5.2 |
| A-5 | Ожидание approval, разрешённое в пределах удержания | `run_id` не меняется, действие выполняется, промежуточное событие ожидания опубликовано | §5.6.1, §17.2 п. 12 |
| A-6 | Вмешательство человека выполнено в пределах окна | Сеанс просмотра гасится немедленно, работа продолжается в той же вкладке того же инстанса | §11.3, шаги 6–7 |
| A-7 | Задача возобновлена после приостанавливающего исхода | Новый `run_id`, новый лизинг, новое решение approval; связь с прежним запуском видна в аудите | §5.6.3, §17.2 п. 14 |
| A-8 | Отмена принята во время исполнения | Новые внешние действия прекращаются, публикуется `cancelled` с фактическим `result.changes` | §5.6.4 |
| A-9 | Разыменование ссылки на артефакт авторизованным потребителем | Возвращаются байты и метаданные; путь и раскладка хранилища из ответа не выводятся | §12.6.2 |
| A-10 | Повторная доставка события уже завершённого запуска | Внешнее действие не повторяется, публикуется сохранённый результат | §4.6 |
| A-11 | Отчёт для человека при любом исходе | Текст самодостаточен, начинается с ответа «сделано или нет», содержит ограничения | §16.2, §16.4 |
| A-12 | Работа под общим секретом (`shared`) | Исполнение ведётся в инстансе владельца задачи, а не в общем | §9.7, п. 5; §10.3, п. 4 |

### 24.3. Негативные критерии

| № | Что подаётся или предпринимается | Требуемый отказ | Чем обеспечивается | Раздел |
|---|---|---|---|---|
| Н-1 | Задача без `dod` / без `lease` / без `reply_route_id` / с пустым `granted_capabilities` | `rejected` до первого внешнего действия, причина `input.missing_field` | проверка входа | §4.4, п. 1 |
| Н-2 | Событие с `executor` вне закрытого перечня или с чужим идентификатором | `rejected`, причина `input.unknown_executor` / `input.executor_mismatch`; без нормализации регистра и исправления опечаток | детерминированная проверка перечня | §19.1 |
| Н-3 | Задача с `owner`, отсутствующим в проекции реестра | `rejected`, причина `input.unknown_owner`; владелец на месте не заводится | проекция только для чтения | §14.2 |
| Н-4 | Попытка выполнить действие, не покрытое ни одной выданной capability | Действие не выполняется; `capability.not_granted` | проверка §6.2 + правила PACT | §6.3 |
| Н-5 | Попытка необратимого действия без approval | Действие не выполняется; точка останова **перед** действием | таблица необратимости PACT + approval | §7.1, §7.2 |
| Н-6 | Тип операции не сопоставляется с таблицей необратимости однозначно | Действие трактуется как необратимое и останавливается | умолчание в сторону остановки | §7.1, п. 3 |
| Н-7 | HTTP-запрос в обход egress proxy | Сетевой отказ на уровне узла, а не предупреждение в коде | сетевая конфигурация узла | §8.3, п. 4; M-2 |
| Н-8 | Запрос к домену вне allowlist | `denied_by_egress`, причина `egress.domain_not_allowed`; повтор, смена домена и поиск зеркала не предпринимаются | egress proxy | §8.5 |
| Н-9 | Запрос после истечения лизинга | Отказ прокси в середине запуска; `lease_expired` | проверка авторизации на каждом запросе | §4.5, §8.2 |
| Н-10 | Попытка прочитать значение секрета с диска исполнителя | Значения на диске отсутствуют; получить их нечем | custody PACT | §9.1, M-3 |
| Н-11 | Запрос TOTP-seed вместо одноразового кода | Отказ выдачи: seed не выдаётся никогда | интерфейс выдачи PACT | §9.3 |
| Н-12 | Запрос снимка сессии без фильтрации по домену | Отказ выдачи: нефильтрованная выдача запрещена | условие переноса custody | §9.4, п. 2 |
| Н-13 | Запуск задачи владельца A в инстансе владельца B | Отказ исполнения, причина `input.instance_mismatch`; переключения на месте не происходит | привязка «владелец → инстанс» | §10.4, п. 4; M-5 |
| Н-14 | Страница в инстансе одного владельца обращается к профилю или экрану другого | Доступа нет | изоляция инстансов | §10.3, п. 1 |

### 24.4. Связь со свойствами §22

1. Наличие свойства §22 доказывается конкретным негативным критерием, дающим отказ **механизмом**.
   Соответствие: Ц-0 → Н-7, Н-8; Ц-1 → Н-10, Н-11, Н-12; Ц-2 → Н-1, Н-2, Н-3; Ц-3 → Н-5, Н-6;
   Ц-4 → Н-9; Ц-5 → Н-16, Н-17; Ц-6 → отсутствие прямого канала постановок; Ц-7 → отсутствие переиспользования
   сессии и выданного секрета между запусками.
2. Свойство, для которого соответствующий негативный критерий проходит только «по договорённости»,
   отсутствует. Промежуточных состояний вида «свойство есть частично» не бывает: либо механизм даёт отказ,
   либо нет.
3. Позитивные критерии A-1…A-12 проверяются заново на каждой волне сборки (`ROADMAP.md`): волна не имеет
   права ломать работоспособность предыдущей.
4. Из §22.1 следует практическое правило приёмки контура: **Ц-0…Ц-6 проверяются вместе, как условия
   запуска**, а не по одному в разное время. Единственная допустимая частичная приёмка — без Ц-7.

### 25.1. Расхождения источников, зафиксированные, но не разрешаемые здесь

1. **Владелец учётных данных.** CONTOURS.md §9 относит учётные данные к «egress proxy и хранилищу секретов»,
   а не к PACT. Постановка задачи называет владельцем PACT. Единая формулировка, используемая во всех четырёх
   воркспейсах: **custody и политика выдачи — PACT, механизм подстановки в трафик — egress proxy под управлением
   PACT** (§9.1). Это соглашение о формулировке, а не разрешение расхождения в источнике.
2. **Две нумерации инвариантов** — см. O-13.
3. **Нумерации этапов.** Действующая планировочная нумерация одна — волны `W1…W5` (`ROADMAP.md`).
   Идентификаторы `Ц-n` этой спецификации порядкового смысла не несут и обозначают свойства (§22.1);
   шаги 0–3 `CONTOURS.md` §8.3 сохраняют собственную нумерацию, но при сборке шаги 0–2 выполняются
   одновременно; этап 0 по `STAGE-0.md` не применяется (D-011 отклонён); этапы существующей автоматизации
   к целевой системе не относятся. При любой ссылке источник нумерации указывается явно.
4. **`STAGE-0.md` опережает статус решений** D-008 и D-011 — см. §23.3, п.2.
5. **Разделение исполнителей по модальности** не следует читать как «Codex = MITA, Claude = CITA»:
   такого сопоставления в источниках нет, разделение проводится по модальности исполнения, а не по клиенту.
