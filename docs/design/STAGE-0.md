## 1. Что делает этап 0

Сообщение в Telegram → агент выполняет → ответ в тот же чат.

Ни брокера, ни квалификатора, ни реестра задач, ни собственного кода. Один экземпляр шлюза, настроенный конфигурацией. Ориентировочно 2–4 часа вместе с созданием бота и первым запуском.

Цель этапа — не построить систему, а получить фактические данные: какие задачи ставятся на практике, где ломаются сессии, нужен ли квалификатор вообще.

## 2. Отображение на контуры

| Контур | Чем представлен на этапе 0 |
|---|---|
| LINA | канальный слой шлюза: Telegram, при необходимости веб-чат |
| PACT | allowlist отправителей, профиль sandbox, политика инструментов |
| MITA | отсутствует |
| CITA | встроенные инструменты runtime |

Границы существуют в конфигурации, но не в развёртывании.

## 3. Установка

Требования: Node.js 22.22.3+, 24.15+ или 25.9+; рекомендуется 26.

```bash
curl -fsSL https://openclaw.ai/install.sh | bash
openclaw onboard --install-daemon
```

Мастер устанавливает демон и запрашивает провайдера модели и ключ. Шлюз по умолчанию слушает порт 18789. Проверка: `openclaw gateway status`.

Бот создаётся через `@BotFather` командой `/newbot`.

## 4. Конфигурация

### 4.1. Доступ к каналу

```json5
{
  channels: {
    telegram: {
      enabled: true,
      botToken: "…",
      dmPolicy: "allowlist",
      allowFrom: ["<numeric user id>"],
    },
  },
}
```

`dmPolicy: "allowlist"` вместо `pairing`. Telegram-бот доступен любому, кто узнал его имя; без ограничения посторонний получает доступ к агенту с вашими правами.

Числовой идентификатор определяется так: написать боту и посмотреть `from.id` в `openclaw logs --follow`. Альтернатива — режим `pairing` с последующим `openclaw pairing approve telegram <CODE>`; коды действительны один час.

Для групп существуют отдельные `groupPolicy` и `groupAllowFrom`. На этапе 0 группы не используются.

### 4.2. Изоляция исполнения

```json5
{
  agents: {
    defaults: {
      sandbox: {
        mode: "non-main",
        scope: "session",
        workspaceAccess: "rw",
      },
    },
  },
}
```

**`sandbox.mode` по умолчанию равен `off`.** Это главная ловушка этапа: агент подключается к внешнему каналу без изоляции, если режим не задан явно.

`workspaceAccess` принимает значения `none`, `ro` и `rw`. Рекомендация документации для агентов, доступных из мессенджера, — `none`, но тогда агент не сможет выполнять содержательную работу. Компромисс этапа 0: `rw` на **один выделенный проектный каталог**, а не на домашний каталог пользователя. Дополнительные каталоги подключаются точечно с явным указанием режима доступа.

Политика инструментов является отдельным и первичным гейтом: запрещённый глобально инструмент не возвращается через настройки sandbox.

### 4.3. Изоляция на уровне хоста

- отдельный системный пользователь, не владелец инфраструктуры;
- отдельные каталоги состояния и конфигурации (`OPENCLAW_HOME`, `OPENCLAW_STATE_DIR`, `OPENCLAW_CONFIG_PATH`);
- шлюз слушает только loopback, наружу выставляется через доверенный обратный прокси или не выставляется вовсе;
- в рабочей области нет SSH-ключей к боевым хостам, токенов внутренних систем, учётных данных облака.

> Точные имена ключей конфигурации для рабочего каталога и политики инструментов не проверялись и подлежат сверке с документацией закреплённой версии перед применением.

## 5. Принимаемые риски

Этап 0 сознательно не реализует часть требований базовой спецификации. Список существует для того, чтобы это было решением, а не умолчанием.

| Риск | Что именно принимается |
|---|---|
| Недоверенный контент | Allowlist защищает канал, но не содержимое. Агент читает логи, страницы и файлы, в которых могут находиться инструкции, и действует по ним. Отправитель доверенный — прочитанное нет. |
| Отсутствие разделения контуров | Приём и исполнение находятся в одном процессе. Компрометация канального слоя означает компрометацию исполнения. |
| Отсутствие контроля исходящего | Результат уходит в чат без проверки на секреты и внутренние данные. |
| Отсутствие egress-контроля | Исполнитель имеет прямой сетевой доступ; эксфильтрация не ограничена. |
| Отсутствие approval | Необратимые действия не требуют подтверждения. |
| Отсутствие аудита и повторной обработки | Нет событийного журнала, нет корреляции, нет разбора сбоев постфактум. |
| Отсутствие квот | Нет ограничения числа обращений к модели и стоимости. |
| Единственный фактор доступа | Компрометация учётной записи Telegram даёт доступ к агенту. |

Радиус поражения приемлем ровно до тех пор, пока рабочая область является песочницей и не содержит доступов к системам, потерю которых владелец заметит.

## 6. Критерий выхода к этапу 1

**Как только исполнителю потребуется доступ к системе, потерю которой владелец заметит.**

Критерий намеренно субъективен: объективного порога не существует, а ложная точность здесь хуже честной неопределённости.

Этап 1 — разделение на два контура доверия: приём без инструментов и исполнение без каналов. Ориентировочно неделя.

## 7. Что переносится дальше

Настройка канала, allowlist, выбор модели, профиль sandbox и рабочая область переходят на последующие этапы без изменений. Меняется топология, а не конфигурация: добавляется второй экземпляр и мост к брокеру.
